## 核心内容

### 概念与原理

一条指令的完整执行由多个阶段构成，经典五级流水（见[[01-10 流水线基础与时序]]）是一次指令执行的最小切分：
1. **IF 取指**：以 PC 为地址从 I-Cache/存储取指令，PC+4（或跳转目标）。
2. **ID 译码**：拆字段、读寄存器堆、生成控制信号。
3. **EX 执行**：ALU 运算、地址计算、分支判断。
4. **MEM 访存**：仅 load/store 访问 D-Cache/数据存储器，读回写回或写入。
5. **WB 写回**：把结果（ALU 或内存数据）写回寄存器文件。

顺序执行时，这条链在每个时钟沿推进，是的这两点：任何 SSI 依赖都由结构保证正确（先写后读）。

### 技术细节

#### PC 更新与分支
- 顺序指令：`PC <- PC + 4`。
- 分支/跳转：`PC <- 目标地址`（beq 目标 = PC+imm，jal 用绝对或 PC 相对）。
- 分支延迟槽（早期 RISC）现多废除，RISC-V 无分支延迟槽。

#### 时序与冒险
- 结构冒险：多条指令同时需要同一部件。
- 数据冒险：后续指令依赖前条的结果。
- 控制冒险：分支结果未知，取指方向不确定。
三者叠加是流水线必须解决的完整问题，见[[01-11]]与[[01-12]]。

#### 状态更新的原子性
顺序执行下，每条指令在 WB 后对架构状态（PC、寄存器、内存）一次性生效；这是后续乱序（见[[01-14]]）可观测性差异的前提（Meltdown 即利用这种“可观测副作用”）。

### 代码/命令示例

用 gdb 单步观察指令执行与寄存器变化（Linux）：

```bash
gcc -O0 -g t.c -o t
gdb -batch -ex 'break *main' -ex run -ex 'si' -ex 'info registers rax' -ex 'si' ./t
```

Python 模拟简单执行器（仅 2 条指令）：

```python
class TinyCPU:
    def __init__(self):
        self.pc = 0
        self.regs = [0]*4
    def run(self, code):
        while self.pc < len(code):
            op, a, b = code[self.pc]
            if op == "add":
                self.regs[a] += self.regs[b]
            elif op == "ldi":
                self.regs[a] = b
            print(f"PC={self.pc} regs={self.regs}")
            self.pc += 1
TinyCPU().run([("ldi",0,5),("add",0,0)])
```

## 实战案例（不少于全文30%篇幅）

### 案例1：gdb 单步观察三条指令的完整执行
- 场景描述：以汇编代码逐条单步，记录 PC、寄存器、内存变化，验证取指-执行闭环。
- 环境准备：Linux + gcc + gdb
- 操作步骤：
  1. 写 `int main(){int a=5; int b=a+1; return b-a;}` 编译 O0。
  2. `break main` 后 `si` 逐步执行，`info registers rip rax` 与 `x/i $pc` 对照。
  3. 记录每条指令前后状态。
- 预期结果：看到 mov/imul/add 等指令依次推进，寄存器按语义更新。
- 关键分析：把抽象的五阶段映射到真实寄存器/内存转移，是理解“指令究竟在干什么”的最小演练。

### 案例2：objdump 反汇编 C 的复合表达式
- 场景描述：观察编译优化下去除冗余后的指令序列，理解后端如何用指令集表达编程语言。
- 环境准备：Linux + gcc + objdump
- 操作步骤：
  1. `int f(int a,int b,int c){ return (a+b)*c; }`
  2. `-O0` 与 `-O2` 两版反汇编，比较指令数与临时寄存器用。
- 预期结果：O0 多用栈传值，O2 用寄存器直接计算（如 `lea`+`imul`）。
- 关键分析：同一 ISA 下不同编译策略产生不同指令流，直接影响逆向（模块12）与性能分析。

## 常见误区与陷阱
1. 认为指令一定按源代码顺序执行：编译器可能重排（O2 下）。
2. 把 PC+4 当作唯一更新方式：分支/跳转地址计算不同。
3. 忽略 load/store 在 MEM 阶段的延迟对整体执行的影响。
4. 以为 WB 一定是写寄存器：Store 不回写寄存器堆。
