## 核心内容

### 概念与原理

**字节序（endianness）**描述多字节数值在内存中的排列方向。小端：低有效字节在低地址（x86 为主）；大端：高有效字节在低地址（早期网络栈与部分 RISC）。`0x12345678` 在 32 位小端内存为 `78 56 34 12`，大端为 `12 34 56 78`。

**网络字节序（network byte order）**即大端，IP 头、TCP/UDP 头均按大端传输（RFC 791 规定）。主机字节序与网络字节序可能不同，因此所有网络编程必须显式转换（`htonl`/`ntohl` 等）。

### 技术细节

#### 检查主机字节序
C：

```c
int x = 1;
if (*(char*)&x == 1) puts("little-endian");
```

#### 转换函数
- POSIX：`htons`、`htonl`、`ntohs`、`ntohl`（见 man 7）。
- Python：`struct.pack('>I', val)`（大端）、`'<I'`（小端）。

#### 安全影响
- 恶意输入中长度/偏移字段按对端字节序解读：解析器必须一致，否则越界读取。
- 二进制逆向（模块12）与协议 fuzz (模块08) 常把字节序当边界查找的抓手。
- 大小端混用是取证与内存扫描时误判磁信息的常见来源。

### 代码/命令示例

Python 演示字节序转换：

```python
import struct
v = 0x12345678
print(struct.pack('>I', v).hex())   # 12345678  大端
print(struct.pack('<I', v).hex())   # 78563412  小端
# 解析 IP 头中的长度字段应使用 '>H'
```

## 实战案例（不少于全文30%篇幅）

### 案例1：解析一个伪造的 TCP 头
- 场景描述：用 Python 按网络字节序手工解包一个 TCP 头，与 Wireshark 结果对照。
- 环境准备：Python 3.11+、Wireshark
- 操作步骤：
  1. 抓一个 TCP 包（或使用样例 pcap）。
  2. 取第 20 字节开始的 TCP 头，手工拆出 src port/dst port/seq。
  3. 用 `struct.unpack('>HH', ...)` 解析与 Wireshark 显示对比。
- 预期结果：端口号与 Wireshark 一致，证明需要按大端读取。
- 关键分析：凡是协议头固定字段，解析器统一大端是规范要求；自己实现解析器时最容易踩字节序 bug。

### 案例2：内存中验证本机字节序
- 场景描述：用 C 与 gdb 观察一个 int 在内存的字节布局，确认主机序。
- 环境准备：Linux + gcc + gdb
- 操作步骤：
  1. `int v = 0x12345678;` 断点后 `x/4bx &v`。
  2. 对比期望的 78 56 34 12（小端）或 12 34 56 78（大端）。
- 预期结果：x86/x86-64 显示小端。
- 关键分析：观察内存原始字节是逆向/取证（模块12、蓝图取证）的基本功。

## 常见误区与陷阱
1. 误以为所有平台字节序都相同：拿本机小端假设解析他人大端。
2. 把“网络序”当作“约定顺序”：它是大端但含义是跨平台交换。
3. 忽略 `struct`/二进制文件处理时要选定字节序参数。
4. 把字符串的字符序与整数字节序混淆。
