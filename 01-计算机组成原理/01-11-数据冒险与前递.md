## 核心内容

### 概念与原理

流水线中后续指令可能依赖尚未执行完的前续指令结果，这就是**数据冒险（data hazard）**。经典顺序流水最主要的是 **RAW（Read After Write）**：后条指令读到的寄存器尚未由前条写回。顺序执行（in-order）满足顺序语义，RAW 必须解决，否则读到旧值。

**WAR（Write After Read）** 与 **WAW（Write After Write）**在乱序执行中才可能产生（因为会具体重排写顺序）。本专题聚焦 RAW 的转发。

**前递（Forwarding，亦称旁路 bypassing）**：把仍在流水中的结果（EX/MEM 或 MEM/WB 阶段）直接送到后续指令的 ALU 输入，避免等 WB。

### 技术细节

#### 前递与原旁路
典型五级流水支持两级转发：
- 从 EX/MEM 寄存器（ALU 结果）转发到「ID/EX 的输入 A 或 B」（若存在 EX 级依赖）。
- 从 MEM/WB（内存读回或写回值）转发到 ALU 输入。

控制逻辑校验：`(EX/MEM.Rd == ID/EX.rs1) && (EX/MEM.RegWrite)` 等条件，多路选择 MUX 优先级决定。

#### Load-use 冒险
前递无法消除 load 带来的 RAW：指令在 ID 需要数据，而 load 的读数据要到 MEM 之后（MEM/WB）才有。此时必须**停顿 1 ~ 2 个周期**（气泡）。编译器可重排指令减少 load-use 缝隙（调度）。

#### 与乱序的关系
乱序执行用**寄存器重命名 + Tomasulo 保留站**（见[[01-14]]），把数据相关从架构寄存器解耦，同时在硬件层面做更广的转发网络。前递是其中思想的最小实现。

### 代码/命令示例

Python 模拟前递决策（判断 EX/MEM 转发路径）：

```python
def need_fwd(ex_mem_rd, id_ex_rs, ex_mem_we):
    return ex_mem_we and ex_mem_rd != 0 and ex_mem_rd == id_ex_rs

print(need_fwd(3, 3, 1))   # True → 转发
print(need_fwd(0, 3, 1))   # False → 寄存器堆最新? 需看静态值，这里示例
```

## 实战案例（不少于全文30%篇幅）

### 案例1：在 Logisim 全流水上观察前递路径
- 场景描述：对支持两条顺序 add 的最小流水 CPU 添加前递 MUX，观察无停顿的依赖执行。
- 环境准备：Logisim-evolution 2.7.x
- 操作步骤：
  1. 搭建最小 3 级简化流水（IF/ID/EX/WB 合并）。
  2. 放置两条 `add x1,x2,x3` 与 `sub x2,x1,x4` 紧邻指令。
  3. 无转发运行，记录结果错误；添加前递 MUX 后重跑。
- 预期结果：转发开启后第二条指令正确取到上条结果，无需气泡。
- 关键分析：认清前递的硬件代价（MUX + 控制信号）与收益（IPC +），为流水性能优化提供依据。

### 案例2：GCC 反汇编观察编译器调度
- 场景描述：看编译器如何重排指令以减少 load-use 停顿。
- 环境准备：Linux + gcc + objdump
- 操作步骤：
  1. 写 `int f(int *a){ int x=a[0]; int y=a[1]; return x+y; }`。
  2. `gcc -O2 -S` 查看是否连续两条 lw（分别加载）再相加，或交错其他计算。
  3. 对比 `-O0` 版本（可能每步立即使用）。
- 预期结果：O2 版本倾向把独立 lw 尽量隔开，为调度器产生缝隙。
- 关键分析：编译器静态调度与硬件转发互补，是优化与逆向（模块12）都绕不开的窗口。

## 实验指南
1. 按案例1 在 Logisim 实现最小前递网络。
2. 用 `-O0/-O2` 对比观察汇编中的 lw/add 顺序（案例2）。
3. 选做：计算两条 back-to-back lw 的流水停顿周期。

## 常见误区与陷阱
1. 混淆 RAW 与 WAW/WAR：顺序流水主要 RAW，WAR/WAW 需乱序。
2. 认为前递对 load 也总有效：load-use 仍可能停顿。
3. 忽略 Rd==0（x0）被架构写死为 0 的特例：不该转发。
4. 把编译器重排视为并行：它仍受限于 ISA 语义（无副作用的尾依赖）。
