# 05-001 安全开发生命周期与 SSDF 框架

## 基础信息
- 难度：中级
- 前置知识：[[06-001-Web安全概览与OWASP-Top10]]
- 对应语言等级：按语言分级（精通/熟悉/入门）

## 核心原理

安全开发生命周期（Secure SDLC）把安全活动从「上线前的漏洞扫描」前置为贯穿需求、设计、编码、测试、部署、运维、退役全流程的常态化能力。核心思想是**风险前置**：修复一个设计缺陷的成本约是在需求阶段发现时的数十倍，因此整个流程以「在哪里、什么时间、用什么方法控制风险」来安排安全任务。微软在 2004 年提出的 SDL（Security Development Lifecycle，见《The Security Development Lifecycle》一书）是这一思路的奠基参照之一。

现代供应链安全背景下，NIST 在 2022 年发布 **SSDF（Secure Software Development Framework，SP 800-218）**，定义了四条实践族：**准备组织（Prepare）**、**保护软件（Protect）**、**生产安全软件（Produce）**、**响应漏洞（Respond）**，共 19 项实践，给出每项推荐的工具与证据。SSDF 本身不规定具体工具，而是为先进实践提供可执行清单，被美国联邦采购与多级合规（如 EO 14028）直接引用。

## 技术要点

- **需求与设计**：威胁建模（Threat Modeling）——用 STRIDE（Spoofing 仿冒/Tampering 篡改/Repudiation 抵赖/Information Disclosure 信息泄露/DoS 拒绝服务/Elevation of Privilege 提权）逐项枚举威胁，产出缓解措施；安全需求必须写成验收标准。
- **编码**：安全编码规范（按语言分级）、依赖锁定与漏洞扫描（SBOM 清单化）、禁止硬编码凭据、输入校验与输出编码（OWASP ASVS 提供可复用检查点）。
- **测试**：SAST（静态分析，如 CodeQL、Semgrep）、DAST（动态测试）、IAST（插桩）、模糊测试、依赖审计（`npm audit`/`pip-audit`）、渗透测试与红队。
- **部署与运维**：镜像签名、配置即代码的密钥管理（Vault 类）、权限最小化运行、补丁与应急响应预案。
- **SSDF 四族**：
  - Prepare（PW.1-PW.9）：定义安全要求、威胁模型、安全指南、审计规则；
  - Protect（PS.1-PS.3）：系统与依赖组件安全、持续保护、可溯源性；
  - Produce（PO.1-PO.6）：包含代码审查、漏洞扫描、SBOM 与审计记录；
  - Respond（RV.1-RV.4）：漏洞披露、评估、修补与缓解、数据分析。
- **SBOM**：软件材料清单（SPDX/CycloneDX 格式），记录每一个组件的版本与来源，是「依赖没了文档」的根治手段。

## 实践示例

环境：GitHub Actions + Semgrep CLI 1.9x（开源版）、Trivy 0.5x。

最小化 SSDF-Produce 自动化（以 Python 后端为例），在 CI 中串行执行左移检查：

```yaml
# .github/workflows/secure-ci.yml（节选）
jobs:
  secure-checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: SAST (Semgrep)
        run: |
          pip install semgrep
          semgrep scan --config p/security-audit .
      - name: Dependency audit
        run: |
          pip install pip-audit
          pip-audit
          jq -r '.packages[] | {{name}}:{{version}}' \
            <(pip freeze) > sbom-cicd.txt 2>/dev/null || true
      - name: DevOps secret scan (gitleaks)
        run: |
          wget -qO gitleaks.gz \
            https://github.com/gitleaks/gitleaks/releases/download/v8.18.0/gitleaks_8.18.0_linux_x64.tar.gz
          tar -xzf gitleaks.gz && ./gitleaks detect --source . -v
```

本地同样可直接运行：

```bash
semgrep --config p/security-audit ./src
pip-audit
gitleaks detect --source . -v
```

三项对应 SSDF 的 PO.5（代码审查）、PS.2（依赖跟踪）、PO.4（凭据与敏感数据保护），输出即审计证据。

## 常见问题与误区

- 误区一：把扫描工具当 SDLC。SAST/DAST 只是证据链的一环，威胁建模、安全需求与应急响应才是 SSDF 的主干；缺少前三者，扫描只能发现「已知的已知」。
- 误区二：只查 GitHub Dependabot 而忽视 SBOM 与私有组件。依赖树超出公开仓库范围（内部包、私有 registry）时，SBOM 才能完整刻画。
- 误区三：上线后才做安全。修复成本按阶段指数上升，安全活动必须在需求与设计阶段就介入，否则 SSDF 的 Prepare/Protect 全部失效。
