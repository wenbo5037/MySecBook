# 01-006 x86-64 调用约定与系统调用机制

## 基础信息
- 难度：高级
- 前置知识：[[01-002-x86-64汇编与栈帧基础]]
- 对应语言等级：精通级

## 核心原理

调用约定（Calling Convention）解决三件事：参数如何传递、返回值如何传递、谁负责清理栈。x86-64 时代分离成了两大体系：Unix/Linux 采用 **System V AMD64 ABI**（x86-64 的非 Windows 默认标准），Windows 采用 **Microsoft x64 调用约定**。二者的差异不仅影响日常逆向，也直接决定伪代码重构时的寄存器含义、调试堆栈的布局以及 shellcode/ROP 编写时的参数放置。System V ABI 的权威定义在 [System V Application Binary Interface, AMD64](https://gitlab.com/x86-psABIs/x86-64-ABI)（x86-64 psABI，由 psABI 维护组持续修订）。

系统调用（system call）则是用户态代码进入内核的唯一通道。x86-64 Linux 上通过 `syscall` 指令完成，Windows 通过 ntdll 中的系统服务存根（syscall stub）进入内核。理解用户态调用约定与内核态调用约定的差异（参数寄存器几乎相同，但第 5 个参数寄存器不同），是编写汇编级利用、Inline Hook、以及分析 EDR/钩挂绕过的必备知识。

## 技术要点

### System V AMD64（Linux/macOS 等）

- 整数/指针参数：前 6 个依次 `RDI, RSI, RDX, RCX, R8, R9`；第 7 个起从右往左压栈。
- 浮点参数：前 8 个用 `XMM0–XMM7`，与整数参数槽位并行使用。
- 返回值：整数在 `RAX`，128 位返回类型使用 `RDX:RAX` 对；浮点返回在 `XMM0`。
- 寄存器保存规则：`RBX, RBP, R12–R15` 为被调用者保存（callee-saved）；其余通用寄存器均为调用者保存（caller-saved）。所有 XMM 寄存器为调用者保存。
- 栈对齐：在 `call` 指令处栈顶必须 16 字节对齐；由于 `call` 压入 8 字节返回地址，函数入口处满足 `RSP % 16 == 8`。
- 红色区域（Red Zone）：`[RSP-128, RSP)` 的 128 字节在叶函数（不调用其他函数的函数）中可被直接使用，无需扩充栈帧——编译器常把无调用的局部变量放进 Red Zone，实用气库对其有依赖。
- 栈帧：链式栈帧用 `push rbp; mov rbp, rsp` 建立（`-fno-omit-frame-pointer`），省略帧指针时（`-fomit-frame-pointer`，默认优化）需依赖 `.eh_frame`/调试信息才能恢复栈回溯。

### Microsoft x64 调用约定（Windows）

- 参数：前 4 个依次 `RCX, RDX, R8, R9`；浮点用 `XMM0–XMM3`，与整数槽位并行。
- 影子空间（Shadow Space）：调用者在 `call` 前必须在栈上预留 32 字节（4×8），供被调用者保存前 4 个寄存器参数，即使参数少于 4 个也必须预留。
- 返回值：`RAX`（浮点为 `XMM0`）；`RAX, RCX, RDX, R8–R11` 为易失寄存器，`RBX, RBP, RDI, RSI, R12–R15` 为非易失（被调用者保存）。
- 栈对齐：`call` 时栈顶 16 字节对齐；入口处 `RSP % 16 == 8`。
- 展开数据：x64 默认省略帧指针，用 `.pdata`/`.xdata`（`IMAGE_DEBUG_TYPE_EXCEPTION`）中的 UNWIND_INFO 描述栈帧，逆向时 `RtlVirtualUnwind` 与调试器依赖它做栈回溯。稍有偏差即报 "Bad unwind"。

### Linux x86-64 系统调用

系统调用号放 `RAX`，参数依次 `RDI, RSI, RDX, R10, R8, R9`——注意第 4 个参数用的是 `R10` 而非 `RCX`，因为 `syscall` 指令本身会破坏 `RCX`（保存返回地址）与 `R11`（保存 RFLAGS）。返回时 `RAX` 为返回值，负数（-errno）表示错误。常用调用号：`read=0`、`write=1`、`open=2`、`close=3`、`mmap=9`、`mprotect=10`、`munmap=11`、`execve=59`、`exit=60`（x86_64 架构，见 Linux 源码 `arch/x86/entry/syscalls/syscall_64.tbl`）。

快速路径（快速系统调用）受 vDSO 加速：`clock_gettime`、`gettimeofday`、`getcpu` 等热点调用由内核映射的无特权 ELF（linux-vdso.so.1）在用户态完成，不发 `syscall` 指令。

### Windows 系统调用

用户态最终调用位于 ntdll 中的存根（如 `NtCreateFile`），其内部将服务索引放入 `RAX`，并把 4 个寄存器参数复制到 `RCX/RDX/R8/R9`（第 5 个起转到 `R10` 与栈）后执行 `syscall`。**服务索引随 Windows 版本与 Build 变化**，不具备跨版本稳定性；绕过用户态钩子（直接 `syscall`，又称 direct syscall）的攻击代码正是绕过这一层被加固的 EDR 钩挂，但 Usermode 下仅执行 `syscall` 无法绕过内核态检查（如 PatchGuard 不直接相关，但 ETW 与内核回调仍可观测）。

## 实践示例

环境：Ubuntu 22.04 LTS x86_64、NASM 2.15.05、GNU ld 2.38。

用纯汇编实现 write+exit，绕过 libc 直接做系统调用：

```asm
; syscall_write_exit.asm
section .data
msg db "syscall ok", 10, 0
len equ $ - msg

section .text
global _start
_start:
    mov rax, 1          ; __NR_write
    mov rdi, 1          ; fd = stdout
    lea rsi, [msg]
    mov rdx, len
    syscall
    mov rax, 60         ; __NR_exit
    xor rdi, rdi        ; exit(0)
    syscall
```

```bash
nasm -f elf64 syscall_write_exit.asm
ld -o syscall_demo syscall_write_exit.o
./syscall_demo          # 输出 "syscall ok"
```

在 GDB 里验证调用约定与寄存器变化：

```bash
gdb -q ./syscall_demo
(gdb) break *0x401000   # 视链接结果
(gdb) run
(gdb) info registers rax rdi rsi rdx r10 r11
```

`syscall` 执行前后对比 `RCX/R11`：RCX 变为返回地址、R11 变为 RFLAGS 快照，这正是内核调用约定把第 4 参用 R10 的原因。

## 常见问题与误区

- 误区一：把 Linux 用户态参数寄存器（RCX 第 4 参）套用到内核系统调用。内核侧第 4 参数必须放 R10，误用 RCX 会导致参数错位（且 RCX 会被 syscall 破坏）。
- 误区二：以为 System V 的压栈参数序和寄存器参数序一致。溢出第 6 个参数后，第 7 个是压栈区的第一个——利用编写中算偏移时常在这步出错。
- 误区三：忽略 Windows 的影子空间。跨平台移植汇编函数时，忘记预留 32 字节影子空间会破坏调用者栈，在 `RtlVirtualUnwind` 回溯时报错或静默覆盖数据。
