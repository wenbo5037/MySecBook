# 01-009 栈缓冲区溢出原理与偏移计算

## 基础信息
- 难度：中级
- 前置知识：[[01-007-利用保护机制NX-ASLR-PIE-Canary与RELRO]]、[[01-002-x86-64汇编与栈帧基础]]
- 对应语言等级：精通级

## 核心原理

栈缓冲区溢出（Stack Buffer Overflow, CWE-121）源于 C/C++ 不自动做越界检查：`memcpy`、`strcpy`、`gets` 等按调用者给出的长度或「直到 `\0`」写入，而不校验目标缓冲区容量。当写入量超过局部缓冲区后，多出的字节会顺栈地址向下（向更高地址）依次覆盖同帧的栈金丝雀（存在的话）、保存的 `rbp`、**返回地址**，进而落入调用者的帧。由于函数返回时 CPU 用 `ret`（pop rip）取出返回地址，只要溢出能精确覆盖到它，攻击者就把程序控制流改写为任意地址——这被称为经典控制流劫持（classic stack smash）。

x86-64 System V ABI 下典型帧布局（低地址在上）为：`局部变量区 → [canary] → saved rbp → return address → 调用者参数区`。溢出写入方向始终是从低地址向高地址；`strcpy` 类按字节写到命中 `\0` 为止（含写入那个 `\0`），`gets` 则一直读到换行。因此溢出「写到哪」取决于攻击者提供的数据长度与其中是否含 `\0`（截断点）。

要既能写入又保证可控，C 函数的内存复制与指针计算需要你精确知道「缓冲区地址 → 返回地址」的字节距离（offset）。这个偏移通过 GDB 的 `cyclic`/`cyclic -l`（De Bruijn 序列）或调试器手工计算得到。得到偏移后，溢出载荷布局为：`填充(offset字节) + 目标地址`。目标地址放到小端序，字节序与架构相关（x86/ARM 小端）。

栈溢出能否变成代码执行受 [[01-007-利用保护机制NX-ASLR-PIE-Canary与RELRO]] 约束：可执行栈（`-z execstack`）→ 直接返回栈内 shellcode；NX 开启 → ret2libc / ret2syscall / ROP。本主题先讲清「溢出 + 偏移」本身，下一主题再展开 ret2* 利用。

## 技术要点

### 触发源（无界/易用错函数）
- `gets`：无边界读入直到换行——最直接；glibc 仍提供，但 GCC 对 `gets` 编译报 warning 并建议替换为 `fgets`。
- `strcpy/strcat/strncat`（misuse）、`sprintf/vsprintf`、`scanf("%s")`、`perror`? 无关。读取网络流常用 `recv` + 错误长度判断。
- 手动数组越界：`for(i=0;i<N;i++) a[i]=data[i]` 写超、下标可被攻击者控制。
- 相关 CWE 组：CWE-120（缓冲区复制无边界检查）、CWE-787（内存越界写）。

### 偏移计算（关键技能）
1. 生成 De Bruijn 序列：pwndbg `cyclic 200`，或用 pwntools `cyclic(200)`。该序列保证任意 4/8 字节子串在该序列内唯一出现。
2. 以序列为输入运行直到崩溃；崩溃处 `RIP` 记录的正是「溢出覆盖返回地址」那一刻的内容（若崩溃在别处再灌序列判断）。
3. `cyclic -l <crash值>`（pwndbg）或 pwntools `cyclic_find` 返回偏移。
4. 交叉验证：改用 `padding + 0xdeadbeef` 复跑，确认 `RIP == 0xdeadbeef`（进程 die，正证明四个字节落在返回地址）。

### x86 vs x86-64 差异
- x86: 返回地址 4 字节；参数在栈上，返回地址下方就是调用者参数区，溢出易连带改写参数。
- x86-64: 返回地址 8 字节；参数走寄存器，栈上参数区仅在溢出参数>6 时才存在；canary（开启时）位于缓冲区和 saved rbp 之间，序列偏移会因 canary 插入而 +16（canary 8 + rbp 8）。若 canary 开启，**直接覆盖返回地址会触发 `__stack_chk_fail`，必须先泄露或绕过**（见 01-007 绕过条件）。

### 字节序与地址布局
- 小端：地址按「低字节在前」写，如 `0x00007fffffffde00` 写为 `\x00\xde\xff\xff\xff\x7f\x00\x00`。地址含 `\x00` 会截断 `strcpy`，需选用不含 `\x00` 的目标地址/负载结构，或改用 `recv` 类不截断的写入源。
- 64 位栈地址常形如 `0x7fff…`，其高 6 字节含 `0x7f` 且常有高位 `0x00`——直接链 `strcpy` 必须考虑截断，常用 `memcpy`、`read` 或部分覆盖规避。

### 堆栈金丝雀交互
- `-fno-stack-protector` 关闭。开启时偏移计算要把 canary 缝（通常 8 字节）算进去，但真正利用会先从 `__stack_chk_fail` 之前找到泄露口（如格式化字符串把 canary 打印出来）。
- 部分场景 canary 可爆破：fork 型服务、逐字节 256 次试探（配合每次不崩溃泄露二字节）整体难度偏高，教材里少直接使用。

## 实践示例

环境：Ubuntu 20.04 LTS x86_64、GCC 9.4.0、pwndbg 2023、Python 3.8。

```c
// stack.c
#include <stdio.h>
#include <string.h>
void vuln(char *input) {
    char buf[32];
    strcpy(buf, input);
    printf("buf = %s\n", buf);
}
int main(int argc, char **argv) {
    if (argc > 1) vuln(argv[1]);
    return 0;
}
```

```bash
gcc -no-pie -fno-stack-protector -o stack stack.c
```

步骤一：崩溃与确认控制 RIP。

```text
pwndbg> cyclic 128
# 以输出序列运行
pwndbg> run $(python3 -c 'from pwn import *; print(cyclic(128).decode())')
# RIP = 0x…（取自 cyclic 序列）
pwndbg> cyclic -l 0x…            # 输出偏移 offset
```

步骤二：按偏移构造、验证。

```bash
python3 -c 'from pwn import *; print(b"A"*<offset> + p64(0xdeadbeef).decode("latin1"))' > payload
```

```text
pwndbg> run < payload
# Program received signal SIGSEGV, RIP = 0x00000000deadbeef   ← 控制流已劫持
```

步骤三：确认该方法可用后，下一主题把 `deadbeef` 换成实际目标（ret2text/ret2libc/ROP）。也可以在 `gdb` 内用硬件 watchpoint 观察 `RSP` 回写时 RIP 被覆写的瞬间：在返回地址上 `watch *(void**)$rsp` 无法掌握精确时机，更常用的是崩溃后回溯。

## 常见问题与误区

- 误区一：偏移算对了地址却写不进。常因 64 位地址含 `\x00` 被 `strcpy` 截断；改用 `read`/`recv`/`memcpy` 型读入源，或牺牲精度做部分覆盖。
- 误区二：canary 开着还直接覆盖返回地址。`__stack_chk_fail` 在 `ret` 前触发，进程直接 abort；先 `checksec`，canary 存在时要把「泄露/绕过 canary」作为前置步骤，而不是死磕偏移。
- 误区三：混淆「缓冲区地址」和「返回地址位置」的方向。栈向低地址增长，函数内部缓冲区在高地址下方（低地址侧），溢出从缓冲区往**更高地址**方向写，越过 canary→rbp→返回地址。一次写多只须累计长度，方向千万别搞反。
- 合规提醒：仅限授权环境实验；真实软件发现此类 bug 应走厂商漏洞报告流程。
