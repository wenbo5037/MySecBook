## 1. 概述

### 1.1 虚拟内存的本质定义

虚拟内存（Virtual Memory）是现代操作系统与 CPU 硬件协同实现的核心内存管理机制。其本质是为每个进程提供一个独立的、连续的虚拟地址空间，通过页表（Page Table）这一软件数据结构，在内存管理单元（Memory Management Unit, MMU）的硬件支持下，将虚拟地址动态翻译为物理地址。

从安全视角看，虚拟内存机制实现了三重隔离：
- **进程间隔离**：每个进程拥有独立页表，彼此的虚拟地址空间完全独立
- **用户/内核隔离**：通过页表权限位（User/Supervisor）防止用户态访问内核内存
- **执行保护**：通过 NX（No-Execute）位防止数据区域被当作代码执行

### 1.2 知识体系定位

虚拟内存是操作系统内核最核心的基础设施之一，与多个安全研究领域深度关联：

- **逆向工程**：理解进程内存布局是分析恶意软件、漏洞利用的前提。`/proc/PID/maps` 揭示的段划分（`.text`、`.data`、`.bss`、`heap`、`stack`、`vdso`）直接影响逆向分析策略
- **漏洞利用**：堆喷射（Heap Spraying）、栈溢出（Stack Overflow）、格式化字符串攻击等经典漏洞利用技术，都依赖对虚拟内存布局和页表权限的精确操控
- **内核安全**：页表管理本身是内核攻击面的一部分，如页表 UAF、CR3 寄存器篡改等内核级漏洞直接影响系统安全根基
- **虚拟化安全**：VT-x/AMD-V 的 EPT（Extended Page Table）/RVI（Rapid Virtualization Indexing）是 Hypervisor 内存隔离的核心，也是 VM Escape 攻击的关键目标

### 1.3 核心应用场景

| 场景 | 技术细节 | 安全意义 |
|------|----------|----------|
| 进程隔离 | 每个进程的 CR3 指向独立页表树，虚拟地址 0x0 可映射到不同物理帧 | 防止跨进程内存读写 |
| 按需分页 | 页面首次访问触发缺页中断（Page Fault），OS 从磁盘加载到物理内存 | 支持大于物理内存的虚拟地址空间 |
| 写时复制（COW） | `fork()` 后父子进程共享物理页，仅在写入时复制 | fork 炸弹可耗尽物理内存 |
| 内存映射文件 | `mmap()` 将文件直接映射到虚拟地址空间 | 可用于无文件落地攻击（Fileless） |
| 共享库映射 | `.so` 文件通过 `mmap` 映射到多个进程的共享区域 | 减少内存占用，但引入 GOT/PLT 攻击面 |
| 大页/巨页 | 2MB（PSE）或 1GB（PML4）大页减少 TLB Miss | 大页区域更难被随机化，可能削弱 ASLR |

## 2. 核心原理

### 2.1 虚拟地址空间：进程视角的连续内存

在虚拟内存模型中，每个进程看到的是一个从 0 开始的连续地址空间。以 x86-64 Linux 为例，用户态虚拟地址范围为 `0x0000_0000_0000_0000` 至 `0x0000_7FFF_FFFF_FFFF`（共 128TB），内核态虚拟地址范围为 `0xFFFF_8000_0000_0000` 至 `0xFFFF_FFFF_FFFF_FFFF`（共 128TB）。

```
┌─────────────────────────────────────────────────────┐
│              x86-64 虚拟地址空间布局                 │
├─────────────────────────────────────────────────────┤
│  0xFFFF_FFFF_FFFF_FFFF  ┌─────────────────────────┐ │
│                         │   内核空间 (128TB)       │ │
│                         │  - 内核代码/数据         │ │
│                         │  - 内核模块 (.ko)        │ │
│                         │  - 内核栈                │ │
│  0xFFFF_8000_0000_0000  ├─────────────────────────┤ │
│         ...             │     非 Canonical 区域     │ │
│         ...             │   （硬件禁止访问）        │ │
│  0x0000_7FFF_FFFF_FFFF  ├─────────────────────────┤ │
│                         │   用户空间 (128TB)       │ │
│                         │  - 栈 (Stack)            │ │
│                         │  - mmap 区域             │ │
│                         │  - 堆 (Heap)             │
│                         │  - .bss / .data / .text  │ │
│  0x0000_0000_0000_0000  └─────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

**关键特性**：
- **Canonical Address 规范**：x86-64 要求虚拟地址的第 48~63 位必须是第 47 位的符号扩展，否则触发通用保护故障（#GP）。这防止了通过高位篡改绕过地址空间检查
- **KPTI 分离后**：用户态页表仅映射必要的内核入口点（syscall 入口、中断向量表），内核大部分代码在用户态页表中不可见

### 2.2 页表结构：从线性到多级

早期系统（如 Intel 80386）使用线性页表——一个巨大的数组，每个虚拟页对应一个页表项（Page Table Entry, PTE）。对于 32 位系统、4KB 页大小，线性页表需要 `2^20 × 4B = 4MB` 连续物理内存，且每个进程都要分配一份。

多级页表（Multi-Level Page Table）通过分层索引解决了这个问题：只有被实际使用的地址范围才会分配下一级页表，稀疏的虚拟地址空间只需极少的页表页。

```
┌──────────────────────────────────────────────────────────────┐
│              x86-64 四级页表结构概览                           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  CR3 寄存器 (页目录基址寄存器)                                │
│     │                                                        │
│     ▼                                                        │
│  ┌──────────────┐                                            │
│  │   PML4 表    │  512 个条目 (PGD)                           │
│  │  (Page Map   │  每条目指向下一级 PUD 表                     │
│  │   Level 4)   │  条目大小: 8 字节                           │
│  └──────┬───────┘                                            │
│         │ 索引: VA[47:39]                                    │
│         ▼                                                    │
│  ┌──────────────┐                                            │
│  │   PUD 表     │  512 个条目                                │
│  │ (Page Upper  │  每条目指向下一级 PMD 表                     │
│  │  Directory)  │                                            │
│  └──────┬───────┘                                            │
│         │ 索引: VA[38:30]                                    │
│         ▼                                                    │
│  ┌──────────────┐                                            │
│  │   PMD 表     │  512 个条目                                │
│  │ (Page Middle │  每条目指向下一级 PTE 表                     │
│  │  Directory)  │  支持 2MB 大页 (PSE)                       │
│  └──────┬───────┘                                            │
│         │ 索引: VA[29:21]                                    │
│         ▼                                                    │
│  ┌──────────────┐                                            │
│  │   PTE 表     │  512 个条目                                │
│  │ (Page Table  │  每条目指向最终物理帧                       │
│  │   Entry)     │  支持 4KB 普通页                           │
│  └──────┬───────┘                                            │
│         │ 索引: VA[20:12]                                    │
│         ▼                                                    │
│  ┌──────────────┐                                            │
│  │  物理帧      │  4KB 连续物理内存                           │
│  │  (Page Frame)│  页内偏移: VA[11:0]                        │
│  └──────────────┘                                            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**为什么是 512？** 每个页表页大小为 4KB，每个条目 8 字节，因此 `4096 / 8 = 512` 个条目。每个条目用 9 位索引（`log2(512) = 9`），四级索引共 `9 × 4 = 36` 位，加上 12 位页内偏移，恰好是 48 位虚拟地址。

### 2.3 地址翻译全过程

当 CPU 执行一条内存访问指令时，MMU 执行以下翻译过程：

```
┌─────────────────────────────────────────────────────────────────────┐
│                    地址翻译完整流程                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  1. CPU 发出虚拟地址 VA                                              │
│     │                                                               │
│     ▼                                                               │
│  2. 检查 TLB (Translation Lookaside Buffer) 缓存                    │
│     ├── 命中 → 直接得到物理地址 PA，跳到步骤 7                       │
│     └── 未命中 → 进入页表遍历 (Page Walk)                           │
│         │                                                           │
│         ▼                                                           │
│  3. 读取 CR3 → 获取 PML4 表基址                                     │
│         │                                                           │
│         ▼                                                           │
│  4. 用 VA[47:39] 索引 PML4 → 得到 PUD 表地址                       │
│     检查 Present 位: 0 → 触发 Page Fault (#PF)                     │
│                      1 → 继续                                      │
│         │                                                           │
│         ▼                                                           │
│  5. 用 VA[38:30] 索引 PUD → 得到 PMD 表地址                       │
│     检查 Present 位 + PS 位 (大页标志)                              │
│     ├── PS=1 → 2MB 大页，物理地址 = PUD.PFN << 21 + VA[20:0]       │
│     └── PS=0 → 继续查 PMD                                          │
│         │                                                           │
│         ▼                                                           │
│  6. 用 VA[29:21] 索引 PMD → 得到 PTE 表地址                       │
│     检查 Present 位 + PS 位                                         │
│     ├── PS=1 → 1GB 巨页（仅 PML4 直接映射时）                      │
│     └── PS=0 → 用 VA[20:12] 索引 PTE → 得到物理帧号 (PFN)          │
│         │                                                           │
│         ▼                                                           │
│  7. 物理地址 PA = PFN × PAGE_SIZE + VA[11:0] (页内偏移)             │
│         │                                                           │
│         ▼                                                           │
│  8. 检查 PTE 权限位 (RW/NX/User) 与当前 CPL (Ring 0/3)            │
│     ├── 权限不足 → 触发 Page Fault (#PF)                           │
│     └── 权限通过 → 完成翻译，访问物理内存                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**性能关键路径**：上述过程每次内存访问都需要 4 次额外的内存读取（每级页表一次），这将导致巨大的性能开销。TLB 缓存正是为了缓解这一问题——TLB 保存最近使用的 VA→PA 映射，命中时无需页表遍历。

### 2.4 页表项（PTE）结构

每个 64 位页表项不仅包含物理帧号，还包含多个控制标志位：

```
  63    62  61  58 57  52 51  12 11   9 8  7 6 5 4 3 2 1 0
┌──────┬─────┬────────┬─────────────┬──────┬─┬─┬─┬─┬─┬─┬─┬─┐
│  NX  │-Protection│  Available   │ PFN  │ G│ PAT│D│A│PCD│PWT│U/S│R/W│ P │
│ (XD) │  Keys     │   (OS use)  │(物理 │  │    │i│c│   │   │   │   │res│
│      │           │              │ 帧号)│  │    │r│e│   │   │   │   │ent│
└──────┴─────┴────────┴─────────────┴──────┴─┴─┴─┴─┴─┴─┴─┴─┴─┘
  Bit 63: NX (No Execute) - 1=不可执行, 0=可执行
  Bit 62-59: Protection Key (PKU, 第4代以后)
  Bit 51-12: 物理帧号 (PFN), 共40位
  Bit 9:    G (Global) - 1=TLB 在 CR3 切换时不刷新
  Bit 8:    PAT (Page Attribute Table) 索引
  Bit 7:    Dirty - 1=页面已被写入
  Bit 6:    Accessed - 1=页面已被访问过
  Bit 4:    PCD (Page Cache Disable)
  Bit 3:    PWT (Page Write-Through)
  Bit 2:    U/S (User/Supervisor) - 0=仅内核, 1=用户可访问
  Bit 1:    R/W (Read/Write) - 0=只读, 1=可读写
  Bit 0:    Present - 1=映射存在, 0=触发缺页
```

**安全关键标志位详解**：

| 标志位 | 安全影响 |
|--------|----------|
| **NX (Bit 63)** | 防止数据区域被作为代码执行（DEP/NX bit protection）。ROP 攻击正是为了绕过此限制——通过已有的可执行代码片段拼接攻击逻辑 |
| **U/S (Bit 2)** | 区分用户态和内核态访问权限。SMEP（Supervisor Mode Execution Prevention）强制内核不能执行用户态页面代码，SMAP（Supervisor Mode Access Prevention）强制内核不能访问用户态数据 |
| **R/W (Bit 1)** | 控制写权限。COW 机制在 `fork()` 后将父子进程的页标记为只写（R/W=0），写入时触发缺页进行页面复制 |
| **Dirty (Bit 7)** | 标记页面是否被修改。页面置换算法（如 LRU）依赖此位决定是否需要写回磁盘。在内存取证中，Dirty 位可用于识别近期活动页面 |
| **Accessed (Bit 6)** | 标记页面是否被访问。用于页面置换算法统计访问频率。侧信道攻击可利用 Accessed 位的时间差异推测内存访问模式 |

### 2.5 大页与巨页（Huge Page）

大页（Huge Page）通过在页表遍历的中间级别终止查表，提供比 4KB 更大的页面映射：

| 类型 | 大小 | 页表终止层级 | 索引位 | 典型应用 |
|------|------|-------------|--------|----------|
| 普通页 | 4KB | PTE | 12 位偏移 | 通用场景 |
| 大页 (PSE) | 2MB | PMD | 21 位偏移 | 数据库、JVM |
| 巨页 (PML5) | 1GB | PUD | 30 位偏移 | 大型数据库 |

**安全双刃剑**：
- **优势**：减少 TLB 条目占用，降低 TLB Miss 率，提升大内存应用性能
- **风险**：大页区域无法被细分随机化，ASLR 在大页映射区域的效果被削弱。攻击者可利用大页区域的确定性布局提高漏洞利用成功率

## 3. 详细知识点

### 3.1 线性页表的问题与多级页表的动机

线性页表（Linear Page Table）是虚拟内存最直观的实现方式：为每个虚拟页分配一个固定大小的页表项，所有条目连续存储在物理内存中。

**线性页表的三大问题**：

| 问题 | 详细说明 | 量化影响 |
|------|----------|----------|
| 空间浪费 | 进程地址空间通常是稀疏的（大量未映射区域），但线性页表仍需为每个虚拟页分配条目 | 32 位系统 4KB 页：4MB/进程；64 位系统：理论上可达 PB 级 |
| 缓存不友好 | 巨大的连续数组无法有效利用 CPU Cache，页表遍历的 Cache Miss 率高 | 每级页表遍历都是潜在的 Cache Miss |
| 物理内存分配困难 | 要求页表在物理内存中连续存放 | 碎片化严重的系统难以满足大块连续分配需求 |

**多级页表的解决方案**：

多级页表本质上是一棵**稀疏树**。只有被实际映射的虚拟地址范围才会分配下一级页表节点。对于一个典型的 64 位进程，虽然虚拟地址空间有 128TB，但实际使用的可能只有几百 MB，多级页表只需分配实际使用部分对应的页表节点，通常只需几 KB 到几十 KB 的页表内存。

**性能代价**：多级页表增加了地址翻译的内存访问次数（x86-64 四级页表需要 4 次额外内存访问），因此 TLB 的命中率对性能至关重要。这也是现代处理器 TLB 容量不断增大的原因（从早期的 32~64 条目增长到当代的 1536+ 条目）。

### 3.2 x86-64 四级页表详解

x86-64 的四级页表（Four-Level Page Table）是目前最广泛使用的页表实现，由 PML4（Page Map Level 4）、PUD（Page Upper Directory）、PMD（Page Middle Directory）和 PTE（Page Table Entry）四级组成。

**虚拟地址分解**：

```
┌───────────────────────────────────────────────────────────────────────┐
│             x86-64 虚拟地址分解 (48 位有效)                            │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  63      48 47      39 38      30 29      21 20      12 11       0   │
│ ┌──────────┬──────────┬──────────┬──────────┬──────────┬───────────┐  │
│ │  Sign    │ PML4 索引│ PUD 索引 │ PMD 索引 │ PTE 索引 │ 页内偏移   │  │
│ │ Extension│  (9 bit) │ (9 bit)  │ (9 bit)  │ (9 bit)  │ (12 bit)  │  │
│ │ (16 bit) │          │          │          │          │           │  │
│ └──────────┴──────────┴──────────┴──────────┴──────────┴───────────┘  │

│  总计: 16 + 9 + 9 + 9 + 9 + 12 = 64 位                               │

```

**各级页表的详细作用**：

```

    └──────────────┬──────────────────┘
```

|------|--------|-----------|-----------|
| PML4 索引 | [47:39] | 0x0FE | 254 |
| PUD 索引 | [38:30] | 0x089 | 137 |
| PMD 索引 | [29:21] | 0x123 | 291 |
| PTE 索引 | [20:12] | 0x456 | 1110 |
| 页内偏移 | [11:0] | 0x678 | 1656 |

### 3.3 ARM64 页表：TTBR0/TTBR1 与 48 位虚拟地址

ARM64（AArch64）架构的页表设计与 x86-64 有显著差异，核心特点是使用两个基址寄存器实现用户/内核地址空间的硬件级分离：

| 特性 | x86-64 | ARM64 |
|------|--------|-------|
| 页表基址寄存器 | CR3（单一） | TTBR0_EL1（用户）+ TTBR1_EL1（内核） |
| 用户地址范围 | `0x0` ~ `0x7FFF_FFFF_FFFF` | `0x0000_0000_0000_0000` ~ `0x0000_FFFF_FFFF_FFFF` (TTBR0) |
| 内核地址范围 | `0xFFFF_8000_0000_0000` ~ `0xFFFF_FFFF_FFFF_FFFF` | `0xFFFF_0000_0000_0000` ~ `0xFFFF_FFFF_FFFF_FFFF` (TTBR1) |
| 地址切换 | KPTI 需要切换整个 CR3（代价高） | 硬件自动选择 TTBR0/TTBR1，无需切换 |
| ASID | 依赖 PCID（12 位） | ASID（16 位），TLB 条目可标记进程 |
| 页表级别 | 4 级（可选 5 级） | 4 级（4KB 页）/ 3 级（16KB/64KB 页） |
| 大页支持 | 2MB / 1GB | 2MB / 1GB（与 x86-64 类似） |

**ARM64 地址选择硬件逻辑**：

```
  虚拟地址 VA
       │
       ├─── bit[63] = 0 → 使用 TTBR0 (用户空间页表)
       │
       └─── bit[63] = 1 → 使用 TTBR1 (内核空间页表)
```

ARM64 的 TTBR0/TTBR1 分离设计天然提供了用户/内核地址空间隔离，不需要像 x86-64 那样通过 KPTI 补丁来实现页表分离。但 ARM64 仍然需要 KPTI 来防御 Meltdown 类攻击（Cache-out 攻击）。

### 3.4 写时复制（COW）：fork() 的高效实现

`fork()` 系统调用创建子进程时，传统方式需要复制整个父进程的页表和物理内存，这在进程地址空间较大时（如几百 MB）会造成显著的延迟。写时复制（Copy-On-Write, COW）通过延迟复制解决了这个问题。

**COW 工作流程**：

```
┌──────────────────────────────────────────────────────────────┐
│                    COW 写时复制流程                            │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  步骤 1: fork() 调用                                         │
│  ┌─────────────────────┐    ┌─────────────────────┐         │
│  │     父进程           │    │     子进程           │         │
│  │  页表项: RW=1        │───→│  页表项: RW=0 (COW)  │         │
│  │  物理帧: Frame_A     │    │  物理帧: Frame_A     │         │
│  │  引用计数: 1         │    │  引用计数: 2         │         │
│  └─────────────────────┘    └─────────────────────┘         │
│                                                              │
│  步骤 2: 子进程尝试写入某个页面                               │
│  ├── CPU 检查 PTE: R/W=0 → 权限不足                         │
│  ├── 触发缺页中断 (#PF)                                      │
│  ├── 内核检查: 是 COW 页面? → 是                             │
│  ├── 分配新物理帧 Frame_B                                    │
│  ├── 复制 Frame_A → Frame_B (页面内容拷贝)                   │
│  ├── 更新子进程页表: 指向 Frame_B, R/W=1                     │
│  └── 更新 Frame_A 引用计数: 2→1                              │
│                                                              │
│  结果:                                                       │
│  ┌─────────────────────┐    ┌─────────────────────┐         │
│  │     父进程           │    │     子进程           │         │
│  │  页表项: RW=1        │    │  页表项: RW=1        │         │
│  │  物理帧: Frame_A     │    │  物理帧: Frame_B     │         │
│  │  引用计数: 1         │    │  引用计数: 1         │         │
│  └─────────────────────┘    └─────────────────────┘         │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**COW 安全风险——fork 炸弹（Fork Bomb）**：

COW 虽然高效，但也引入了新的安全风险。`fork()` 炸弹利用 COW 机制快速创建大量子进程，每个子进程在写入页面时都会触发 COW，导致物理内存被迅速耗尽。

```c

// 注意: 此代码仅供理解原理，禁止在生产环境执行
// :(){ :|:& };:
// 展开后: fork() { fork() | fork() & }; fork()
```

**防御机制**：
- `ulimit -u`：限制最大进程数
- `cgroup` 内存控制器：限制 cgroup 内的总内存使用
- `vm.overcommit_memory` 和 `vm.overcommit_ratio`：控制内核的内存过分配策略

### 3.5 内存映射（mmap）：文件映射与匿名映射

`mmap()` 系统调用将文件或匿名内存区域映射到进程的虚拟地址空间，是 Linux 最强大的内存管理接口之一。

**两种映射类型对比**：

| 特性 | 文件映射 (File-backed) | 匿名映射 (Anonymous) |
|------|----------------------|---------------------|
| 后备存储 | 磁盘文件 | 交换空间 (Swap) 或物理内存 |
| 创建方式 | `mmap(fd, ...)` | `mmap(MAP_ANONYMOUS, ...)` 或 `brk()/sbrk()` |
| 初始内容 | 文件内容 | 全零填充 |
| 典型用途 | 共享库、可执行文件、数据库文件 | 堆、栈、匿名 mmap 区域 |
| COW 行为 | 写入触发 COW，修改不回写文件（除非 MAP_SHARED） | 写入修改私有副本 |
| 安全影响 | 可用于无文件落地攻击 | 堆布局可被预测，影响利用难度 |

**mmap 在安全中的关键作用**：

- **无文件落地攻击（Fileless Malware）**：通过 `mmap(MAP_ANONYMOUS | MAP_PRIVATE)` 分配可读写内存，`mprotect()` 将其设置为可执行，然后将 shellcode 写入该区域。整个攻击过程不需要在磁盘上创建可执行文件
- **ROP/JOP gadget 搜索**：攻击者通过 `mmap` 映射大量文件（如 ELF 共享库），从中搜索可利用的代码片段
- **堆风水（Heap Feng Shui）**：通过精确控制 `mmap` 的大小和顺序，影响堆分配器的行为，提高漏洞利用的可靠性

### 3.6 安全视角：页表与地址空间布局

**ASLR（Address Space Layout Randomization）与页表的关系**：

ASLR 通过随机化进程的关键内存区域（栈、堆、共享库、mmap 区域）的基地址，使攻击者难以预测目标地址。页表本身不直接参与 ASLR 的随机化过程，但 ASLR 的效果依赖于页表提供的地址空间隔离。

```
┌──────────────────────────────────────────────────────────────┐
│              ASLR 随机化的内存区域                             │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  无 ASLR:                       有 ASLR:                    │
│  ┌──────────────┐ 0x7FFF...    ┌──────────────┐ 0x7FFF...   │
│  │     栈       │ 0x7FFF_FFF0  │     栈       │ 0x7FFC_A3.. │
│  ├──────────────┤              ├──────────────┤             │
│  │    (空洞)    │              │    (空洞)    │             │
│  ├──────────────┤              ├──────────────┤             │
│  │  mmap 区域   │ 0x7F7F...   │  mmap 区域   │ 0x7F2B_5C.. │
│  │  libc.so     │              │  libc.so     │             │
│  ├──────────────┤              ├──────────────┤             │
│  │     堆       │ 0x5555...   │     堆       │ 0x55C8_F1.. │
│  ├──────────────┤              ├──────────────┤             │
│  │    .bss      │              │    .bss      │             │
│  │    .data     │              │    .data     │             │
│  │    .text     │ 0x400000    │    .text     │ 0x400000    │
│  └──────────────┘              └──────────────┘             │
│                                                              │
│  注意: .text 段通常不随机化 (PIE 可执行文件除外)               │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**SMEP/SMAP 与页表权限位**：

SMEP（Supervisor Mode Execution Prevention）和 SMAP（Supervisor Mode Access Prevention）是 Intel 在 Ivy Bridge 以后引入的 CPU 安全特性，通过页表权限位强制执行用户/内核内存隔离：

| 特性 | 控制寄存器位 | 效果 | 防御的攻击 |
|------|-------------|------|-----------|
| SMEP | CR4.SMEP | 内核不能执行用户态页面的代码 | Ret2usr 攻击（在用户态 shellcode 上跳转） |
| SMAP | CR4.SMAP | 内核不能读写用户态页面的数据 | 用户态数据注入内核态 |

内核可以通过 `STAC`/`CLAC` 指令临时禁用 SMAP（在 PTE 的 Accessed 位设置时需要内核访问用户态页面），但每次禁用都会被记录在审计日志中。

### 4.3 地址翻译手动计算练习

**题目**：给定以下信息，手动计算虚拟地址 `0x0000_7FFF_1234_5678` 的物理地址。

已知条件：
- CR3 = `0x0000_0000_1A2B_3000`
- PML4[254] → PFN = `0x0000_0000_4567_8000`
- PUD[137] → PFN = `0x0000_0000_9ABC_1000`
- PMD[291] → PFN = `0x0000_0000_DEF0_2000`
- PTE[1110] → PFN = `0x0000_0000_1122_3000`, Present=1, RW=1, NX=0

**计算过程**：

| 步骤 | 操作 | 结果 |
|------|------|------|
| 1. VA 分解 | `0x7FFF12345678` | PML4=254, PUD=137, PMD=291, PTE=1110, Offset=0x678 |
| 2. 查 PML4 | CR3 + 254×8 = `0x1A2B_3000` + `0x7F0` = `0x1A2B_37F0` | 读取 PML4[254] = PFN `0x4567_8000` |
| 3. 查 PUD | `0x4567_8000` + 137×8 = `0x4567_8000` + `0x448` = `0x4567_8448` | 读取 PUD[137] = PFN `0x9ABC_1000` |
| 4. 查 PMD | `0x9ABC_1000` + 291×8 = `0x9ABC_1000` + `0x918` = `0x9ABC_1918` | 读取 PMD[291] = PFN `0xDEF0_2000` |
| 5. 查 PTE | `0xDEF0_2000` + 1110×8 = `0xDEF0_2000` + `0x2230` = `0xDEF0_4230` | 读取 PTE[1110] = PFN `0x1122_3000` |
| 6. 计算 PA | PFN×4096 + Offset = `0x1122_3000` + `0x678` | **PA = `0x0000_0000_1122_3678`** |

### 4.4 pagemap 接口读取物理帧信息

Linux 提供 `/proc/PID/pagemap` 接口，允许用户态程序查询虚拟页面到物理帧的映射关系：

```c
#include <stdio.h>
#include <stdint.h>
#include <fcntl.h>
#include <unistd.h>

// 每个虚拟页面对应一个 64 位 pagemap 条目
// Bit 63:    Page present (1=映射存在)
// Bit 62:    Page swapped (1=在交换区)
// Bit 55-0:  物理帧号 (PFN)
void check_page(uint64_t vaddr, int pid) {
    char path[64];
    snprintf(path, sizeof(path), "/proc/%d/pagemap", pid);
    int fd = open(path, O_RDONLY);
    
    // pagemap 条目在文件中的偏移 = (虚拟地址 / 页大小) × 8
    uint64_t index = vaddr / 4096;
    uint64_t offset = index * 8;
    
    lseek(fd, offset, SEEK_SET);
    
    uint64_t entry;
    read(fd, &entry, 8);
    
    if (entry & (1ULL << 63)) {
        uint64_t pfn = entry & 0x7FFFFFFFFFFFFF;
        printf("虚拟地址 0x%lx → 物理帧号 %lu (物理地址: 0x%lx)\n",
               vaddr, pfn, pfn * 4096);
    } else {
        printf("虚拟地址 0x%lx → 未映射\n", vaddr);
    }
    
    close(fd);
}

int main() {
    // 检查当前进程的栈基地址映射
    check_page(0x7FFF00000000UL, getpid());
    return 0;
}
```


## 5. 常见坑与避坑指南

### 5.1 虚拟地址空间的"连续"只是幻觉

**问题**：许多开发者误以为 `malloc()` 返回的内存是物理连续的。实际上，虚拟地址空间的连续性只是页表映射的抽象——底层物理内存可能是高度碎片化的。

```
  虚拟地址空间 (连续):        物理内存 (碎片化):
  ┌──────────────┐           ┌──────────────┐
  │ 0x600000     │ ────→     │ Frame 1024   │
  │ 0x601000     │ ────→     │ Frame 512    │  (不连续!)
  │ 0x602000     │ ────→     │ Frame 8192   │
  │ 0x603000     │ ────→     │ Frame 256    │
  └──────────────┘           └──────────────┘
```

**安全影响**：
- DMA 攻击需要物理连续内存时，虚拟连续不等于物理连续
- `virt_to_phys()` 在非线性映射区域的行为需要特别注意
- 内核 `vmalloc()` 分配虚拟连续但物理不连续的内存，与 `kmalloc()` 行为不同

### 5.2 PTE 的 NX 位与 ROP 利用的关系

NX（No-Execute）位是现代系统最重要的内存保护机制之一。当 PTE 的 NX 位被设置时，CPU 在该页面上执行指令会触发 #PF 异常。

**ROP（Return-Oriented Programming）攻击原理**：

ROP 攻击正是为了绕过 NX 保护。攻击者不注入新的可执行代码，而是利用程序已有的可执行代码片段（Gadgets），通过精心构造的栈布局（ROP Chain），让程序依次执行这些 Gadgets 来完成攻击目标。

```
  NX 保护生效时:
  ┌─────────────┐     ┌─────────────┐
  │ 数据区域     │     │ 代码区域     │
  │ NX=1 (禁止) │     │ NX=0 (允许) │
  │ 攻击者无法   │     │ ROP Gadgets │
  │ 直接执行     │     │ 可被利用     │
  └─────────────┘     └─────────────┘

  ROP Chain 示例:
  pop rdi; ret  →  设置第一个参数
  call system    →  调用 system()
  "/bin/sh"      →  攻击者需要将其放入可读区域
```

**绕过 NX 的其他技术**：
- **ROP/JOP**：利用已有代码片段
- ** ret2libc**：直接调用 libc 中的函数（如 `system()`）
- **mprotect/mmap**：如果能控制参数，可将数据页标记为可执行
- **PLT/GOT 劫持**：修改全局偏移表，重定向函数调用

### 5.3 页表缓存与 TLB Shootdown 的性能代价

TLB（Translation Lookaside Buffer）是 MMU 中用于缓存 VA→PA 映射的高速缓存。当页表被修改时，需要确保所有 CPU 核心的 TLB 中的旧映射被刷新，这个过程称为 TLB Shootdown。

**TLB Shootdown 的性能问题**：

| 场景 | 代价 | 说明 |
|------|------|------|
| 单核刷新 | 低 | INVLPG 指令直接刷新本地 TLB |
| 多核刷新 (IPI) | 高 | 通过处理器间中断（IPI）通知所有核心刷新 TLB |
| KPTI 切换 | 极高 | 切换 CR3 时整个 TLB 被刷新（PCID 可部分缓解） |
| 进程上下文切换 | 中等 | 切换 CR3（PCID 可避免全量刷新） |

**KPTI 的性能代价**：启用 KPTI 后，每次系统调用和中断都需要切换页表（用户态→内核态→用户态），每次切换导致 TLB 全量或部分刷新。根据内核文档和实际测试，KPTI 的性能开销在 5%~30% 之间，具体取决于工作负载的系统调用频率。

### 5.4 内核页表与用户页表的分离（KPTI）

KPTI（Kernel Page Table Isolation，内核页表隔离）是为应对 Meltdown 攻击而引入的安全机制。Meltdown 攻击利用推测执行，在用户态程序中非法读取内核内存——通过在用户态页表中保留的内核代码映射窗口执行推测指令。

**KPTI 防御原理**：

```
┌──────────────────────────────────────────────────────────────┐
│                    KPTI 页表分离架构                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  用户态页表 (CR3_User):                                      │
│  ┌──────────────┐  ┌──────────────┐                         │
│  │  用户空间     │  │ 内核: 仅映射  │                         │
│  │  完整映射     │  │ 最小入口点   │                         │
│  │              │  │ (syscall entry,│                        │
│  │              │  │  中断向量表)  │                         │
│  └──────────────┘  └──────────────┘                         │
│                                                              │
│  内核态页表 (CR3_Kernel):                                    │
│  ┌──────────────┐  ┌──────────────┐                         │
│  │  用户空间     │  │  内核空间     │                         │
│  │  完整映射     │  │  完整映射     │                         │
│  │  (用于返回    │  │  所有内核代码 │                         │
│  │   用户态时    │  │  和数据       │                         │
│  │   保持上下文) │  │              │                         │
│  └──────────────┘  └──────────────┘                         │
│                                                              │
│  进入内核态: 切换 CR3 → CR3_Kernel                           │
│  返回用户态: 切换 CR3 → CR3_User                             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**KPTI 对安全研究的影响**：
- Meltdown 攻击窗口被大幅缩小——用户态页表中几乎没有内核代码/数据的映射
- 但侧信道攻击（Spectre 变种）仍然可能绕过 KPTI，因为推测执行不受页表权限影响
- ARM64 的 TTBR0/TTBR1 硬件分离提供了更高效的 KPTI 实现
