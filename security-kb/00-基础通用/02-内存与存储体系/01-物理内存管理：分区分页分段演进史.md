## 1. 概述

### 1.1 技术定义与本质

物理内存管理（Physical Memory Management）是指操作系统内核对计算机真实安装的随机存取存储器（RAM，Random Access Memory）进行分配、组织、保护和回收的整套机制。其本质是一个**资源调度问题**：在有限的物理内存空间中，如何同时容纳多个进程（Process）的地址空间，并保证彼此隔离、互不干扰。

从安全视角看，物理内存管理机制直接决定了进程间的隔离边界是否牢固。每一次内存管理机制的演进，既是性能优化的产物，也是安全攻防博弈的推动力。分区分治（Partitioning）提供了最早的隔离模型，分段（Segmentation）引入了逻辑语义，分页（Paging）实现了离散化与虚拟内存，段页式（Segment-Paging）则融合了两者优势。

### 1.2 知识体系定位（与安全的关联）

物理内存管理在安全知识体系中处于**基础架构层**。理解它有助于理解以下安全机制的底层原理：

- **地址空间布局随机化**（ASLR，Address Space Layout Randomization）：依赖分页机制提供的页粒度映射能力，在进程加载时随机化代码段、数据段、堆栈的物理帧位置
- **非执行位保护**（NX/DEP，No-Execute / Data Execution Prevention）：通过页表项中的 NX 位标记数据页不可执行，阻止 shellcode 注入攻击
- **内核地址空间隔离**（KPTI，Kernel Page Table Isolation）：在 Meltdown 漏洞暴露后，通过维护两套页表实现用户态/内核态地址空间切换
- **DMA 攻击面**：外设通过 DMA（Direct Memory Access）直接访问物理内存，绕过 CPU 的 MMU（Memory Management Unit）保护

### 1.3 核心应用场景

| 场景 | 说明 |
|------|------|
| 多任务操作系统 | 多个进程共享物理内存，由内核调度器配合内存管理器进行分配 |
| 实时嵌入式系统 | 固定分区方案保障确定性响应时间，避免动态分配的不确定性 |
| 虚拟化环境 | Hypervisor 通过 EPT/NPT（Extended/Nested Page Table）对物理内存进行二次虚拟化 |

| 内核取证 | 通过内存转储（Memory Dump）分析进程内存布局，还原攻击痕迹 |

## 2. 核心原理

### 2.1 内存分区分治：固定分区与动态分区

**固定分区（Fixed Partitioning）** 是最早的内存管理方案。其核心思想是将物理内存预先划分为若干个固定大小的分区（Partition），每个分区在任意时刻最多容纳一个进程。

```
物理内存（假设总大小 64MB）
┌──────────────────────────────────────────────────┐
│  分区0:  0x00000000 - 0x00FFFFFF  (16MB)        │
│  [ 进程A: OS内核 ]                                │
├──────────────────────────────────────────────────┤
│  分区1:  0x01000000 - 0x01FFFFFF  (16MB)        │
│  [ 进程B: 用户程序 ]                              │
├──────────────────────────────────────────────────┤
│  分区2:  0x02000000 - 0x02FFFFFF  (16MB)        │
│  [ 进程C ]                                       │
├──────────────────────────────────────────────────┤
│  分区3:  0x03000000 - 0x03FFFFFF  (16MB)        │
│  [ 空闲 ]                                        │
└──────────────────────────────────────────────────┘
```

固定分区的核心优点是实现简单、调度开销低。其最大缺点是**内部碎片**（Internal Fragmentation）——当进程所需内存小于分区大小时，剩余空间无法被其他进程利用。例如一个 3MB 的进程被放入 16MB 分区，浪费 13MB。

**动态分区（Dynamic Partitioning）** 改进了固定分区的缺陷：不再预先划分，而是按进程需求动态分配连续内存块。分配时需要维护一个空闲块链表（Free Block List），常用的分配策略包括：

- **首次适应**（First Fit）：从头扫描找到第一个足够大的空闲块
- **最佳适应**（Best Fit）：找到最小的足够大空闲块，减少浪费但产生更多小碎片
- **最差适应**（Worst Fit）：找到最大的空闲块，保留较大碎片

动态分区解决了内部碎片问题，但引入了**外部碎片**（External Fragmentation）：随着进程的分配与释放，空闲内存被分割为许多不连续的小块，总空闲量足够但无单个连续块能满足新需求。

### 2.2 分段机制：逻辑视角的地址空间

分段（Segmentation）的核心思想是：从程序员的逻辑视角出发，将进程的地址空间划分为若干个**语义段**（Segment），每个段对应一个逻辑单元——代码段（Code Segment）、数据段（Data Segment）、堆栈段（Stack Segment）等。

在分段系统中，逻辑地址由两部分组成：

```
逻辑地址 = [ 段号(Segment Number) | 段内偏移(Offset) ]
```

操作系统维护一张**段表（Segment Table）**，每个段表项包含：

```
段表项结构:
┌─────────────┬──────────────┬──────────────┐
│  段基址     │  段限长       │  访问权限    │
│ (Base Addr) │ (Limit/Size) │ (R/W/X)     │
├─────────────┼──────────────┼──────────────┤
│ 4字节       │ 4字节        │ 属性位       │
└─────────────┴──────────────┴──────────────┘

地址翻译过程:
逻辑地址 [段号|偏移] → 查段表 → 检查偏移 < 段限长？
  → 是: 物理地址 = 段基址 + 偏移
  → 否: 触发段错误异常 (Segmentation Fault, SIGSEGV)
```

分段的显著优点是**天然支持权限保护**——不同段可设置不同的读/写/执行权限，这直接为安全机制提供了硬件基础。例如代码段可标记为"只读+可执行"（R-X），数据段标记为"可读写+不可执行"（RW-），后者正是 NX/DEP 防护的原型。

分段的致命缺陷是**外部碎片**：段的大小不固定，频繁的段分配与释放会导致内存空间碎片化。

### 2.3 分页机制：物理地址的离散化

分页（Paging）的核心创新是将物理内存等分为固定大小的**页帧**（Frame），进程的虚拟地址空间也等分为相同大小的**页**（Page），通过**页表（Page Table）** 建立虚拟页到物理帧的映射关系。

```
虚拟地址空间（进程视角）          物理内存（硬件视角）
┌──────────┐                    ┌──────────┐
│  页 0    │ ──────────────────→│  帧 12   │
├──────────┤                    ├──────────┤
│  页 1    │ ──────────────────→│  帧 5    │
├──────────┤                    ├──────────┤
│  页 2    │ ──────────────────→│  帧 87   │
├──────────┤                    ├──────────┤
│  页 3    │ ─ ─ ─ 未映射 ─ ─  │  帧 3    │
├──────────┤                    ├──────────┤
│  ...     │                    │  ...     │
├──────────┤                    ├──────────┤
│  页 N    │ ──────────────────→│  帧 201  │
└──────────┘                    └──────────┘

虚拟地址结构 (以 x86-64 48位虚拟地址, 4KB 页为例):
┌──────────────────┬────────────┐
│  页号 (VPN)      │  页内偏移  │
│  36 位           │  12 位     │
└──────────────────┴────────────┘
  36位VPN可寻址 2^36 = 68,719,476,736 个页
  每页 4KB, 总虚拟地址空间 = 256 TB
```

分页机制彻底消除了外部碎片——任何空闲页帧都可以分配给任何需要的虚拟页。但**内部碎片**依然存在：进程最后一个页通常不会被完全填满，平均浪费半页（约 2KB）。

分页的关键开销在于**页表本身占用内存**。以 32 位系统、4KB 页为例，每个进程的单级页表需要 2^20 = 1,048,576 个页表项，每项 4 字节，共 4MB——仅页表就占 4MB 内存，这在内存以 MB 计的年代是不可接受的。因此发展出了**多级页表**（Multi-Level Page Table）：

```
x86-64 四级页表结构:
┌─────────┬─────────┬─────────┬─────────┬──────────┐
│ PML4 (9)│ PDPT (9)│ PD (9)  │ PT (9)  │ Offset(12)│
│  级索引 │  级索引 │  级索引 │  级索引 │  页内偏移│
└─────────┴─────────┴─────────┴─────────┴──────────┘
        ↓         ↓         ↓         ↓
       PGD →     P4D →     PUD →     PMD → PTE → 物理帧

每级 9 位索引, 对应 512 个表项 (512 × 8字节 = 4KB, 正好一页)
```

### 2.4 段页式混合：两者的折中

段页式（Segment-Paging）结合了分段的逻辑语义优势和分页的离散化优势。其工作原理是：先将进程地址空间分为若干段，每个段内部再进行分页。

```
段页式地址结构:
┌──────────┬──────────┬──────────┐
│  段号    │  页号    │  页内偏移│
│  (S)     │  (P)     │  (D)     │
└──────────┴──────────┴──────────┘
     ↓          ↓
   段表      段内页表
     ↓          ↓
  基址+限长   页帧号 → 物理地址 = 帧号×页大小 + 偏移
```

x86 处理器在保护模式（Protected Mode）下正是采用段页式方案：逻辑地址先经过段选择子（Segment Selector）查段描述符表（GDT/LDT）得到线性地址（Linear Address），线性地址再经过分页机制翻译为物理地址。

但现代操作系统（Linux、Windows、macOS）在 x86-64 上将所有段的基址设为 0、限长设为最大值，使分段退化为"透明层"，实质上只使用分页机制。这种选择的原因是：纯分页方案更简单高效，且现代硬件的分页能力已足够满足安全需求。

## 3. 详细知识点

### 3.1 固定分区与动态分区

**固定分区**在早期批处理系统中广泛应用。IBM OS/360 的 MFT（Multiprogramming with Fixed Tasks）模式是经典实现。分区大小可以在系统生成时（System Generation）根据预期负载配置。

固定分区的关键数据结构是**分区表（Partition Table）**：

```
┌────────┬──────────┬──────────┬────────┬──────────┐
│ 分区号 │ 起始地址 │ 大小     │ 状态   │ 进程ID   │
├────────┼──────────┼──────────┼────────┼──────────┤
│   0    │ 0x0000   │ 64KB     │ 已分配 │ OS Kernel│
│   1    │ 0x10000  │ 128KB    │ 已分配 │ PID 101  │
│   2    │ 0x30000  │ 256KB    │ 空闲   │ -        │
│   3    │ 0x70000  │ 128KB    │ 已分配 │ PID 102  │
└────────┴──────────┴──────────┴────────┴──────────┘
```

**动态分区**的核心挑战是空闲内存管理。操作系统需要维护空闲区链表或位图，并在分配和回收时执行合并操作。回收相邻空闲块时需要进行**碎片合并**（Coalescing）：

```
回收前（进程B结束释放内存）:
[ 进程A ][ 空闲1 20KB ][ 进程C ][ 空闲2 30KB ][ 进程D ]

回收后（合并相邻空闲块）:
[ 进程A ][ 空闲 50KB(20+30)               ][ 进程D ]
```

动态分区在安全方面的局限性：由于分配的是连续物理内存，攻击者可以通过分析内核的内存分配行为（如 slab 分配器、buddy 分配器的工作模式）来预测对象位置，从而实施精确的堆溢出攻击。

### 3.2 分段机制深入

在 x86 架构的保护模式下，分段机制通过**段描述符（Segment Descriptor）** 实现，存放在全局描述符表（GDT，Global Descriptor Table）和局部描述符表（LDT，Local Descriptor Table）中：

```
x86 段描述符结构 (8字节):
┌──────────────────────────────────────────────────────────┐
│ 31          16│15       8│7        0                    │
├───────────────┼──────────┼──────────┤
│  基址 [31:16] │ 段限[19:16]+属性 │ 基址[15:0] │ ← 4字节  │
├───────────────┼──────────┼──────────┤
│  基址[31:24]  │  保留    │ 段限[15:0]│ ← 4字节           │
└───────────────┴──────────┴──────────┘

关键属性位:
- P (Present): 段是否存在内存中
- DPL (Descriptor Privilege Level): 特权级 (0=Ring0, 3=Ring3)
- S (System): 0=系统段, 1=代码/数据段
- Type: 段类型 (代码段/数据段/栈段等)
- G (Granularity): 段限长粒度 (0=字节, 1=4KB)
- R/W: 读写权限
- C/D: 代码/数据标志
```

段描述符中的 DPL 字段直接关联到 CPU 特权级模型（Ring 0–Ring 3）。这为操作系统提供了硬件级的内存保护：Ring 3 的用户态代码无法访问 Ring 0 内核态段，尝试越权访问会触发通用保护故障（General Protection Fault, #GP）。

分段机制的安全影响是双面的：段描述符本身提供了强大的隔离能力，但复杂的段管理逻辑也引入了攻击面。历史上，某些操作系统对段寄存器的不当管理导致了特权提升漏洞。

### 3.3 分页机制深入

现代操作系统的页表结构通常采用多级设计。以 Linux 在 x86-64 上的四级页表为例：

```
Linux 四级页表与虚拟地址映射:

虚拟地址: [PGD索引:9bit][P4D索引:9bit][PUD索引:9bit][PMD索引:9bit][PTE索引:9bit][偏移:12bit]
              │              │              │              │              │
              ↓              ↓              ↓              ↓              ↓
            PGD           P4D            PUD            PMD            PTE
        (页全局目录)   (页四级目录)   (页上级目录)   (页中间目录)   (页表项)
          [1项]          [512项]        [512项]        [512项]        [512项]
              │              │              │              │              │
              ↓              ↓              ↓              ↓              ↓
           cr3寄存器     每项指向下一级页表的物理帧号, 每级页表占一个 4KB 页
```

**页表项（PTE，Page Table Entry）** 的典型结构（x86-64）：

```
PTE 结构 (8字节/64位):
┌─┬─┬─┬─┬─┬──────────────────────┬─┬─┬─┬─┬─┬─┬─┬─┐
│N│G│M│D│A│  物理帧号 (PFN)      │C│W│U│P│W│V│R│X│
│X│ │ │ │T│  [51:12] 共40位      │D│T│/│ │ │ │ │ │
│ │ │ │ │ │                      │ │ │S│ │ │ │ │ │
└─┴─┴─┴─┴─┴──────────────────────┴─┴─┴─┴─┴─┴─┴─┴─┘

关键位说明:
- X/NX: No-Execute 位, =1 表示该页不可执行 (DEP/NX保护)
- P: Present 位, =1 表示该页在物理内存中
- R/W: 0=只读, 1=可写
- U/S: 0=超级用户(内核), 1=用户态可访问
- A: Accessed 位, 被访问时由硬件置1 (用于页面置换算法)
- D: Dirty 位, 被写入时由硬件置1 (决定页面置换时是否写回磁盘)
- G: Global 位, =1 表示TLB刷新时不刷新该条目
- CD: Cache Disable 位
- WT: Write-Through 位
```

**物理帧管理**：Linux 内核使用伙伴系统（Buddy System）管理物理内存帧。它将空闲帧组织为按 2 的幂次方大小的块链表：

```
Buddy System 结构:
Order 0: [帧1][帧5][帧23][帧47]...        (1页 = 4KB)
Order 1: [帧8-9][帧16-17][帧32-33]...     (2页 = 8KB)
Order 2: [帧64-67]...                      (4页 = 16KB)
Order 3: [帧128-135]...                    (8页 = 32KB)
...
Order 10: [帧0-1023]...                    (1024页 = 4MB)

分配时: 找到 >= 所需大小的最小阶, 必要时拆分
释放时: 检查伙伴(Buddy)是否空闲, 是则合并为更大块
```

**TLB（Translation Lookaside Buffer）** 是页表翻译的关键加速器。TLB 是一个高速缓存，存储最近使用的虚拟页号到物理帧号的映射。TLB 未命中（Miss）时需要遍历多级页表，耗时增加数十倍。

### 3.4 段页式混合与现代操作系统的选择

x86 架构在硬件层面提供段页式支持，但现代操作系统普遍选择"架空"分段层：

| 操作系统 | 分段处理方式 | 分页机制 |
|----------|-------------|----------|
| Linux (x86-64) | 所有段基址=0, 限长=最大 | 四级页表, 4KB/2MB/1GB 页 |
| Windows (x86-64) | 所有段基址=0 | 四级页表 |
| Linux (x86-32) | 基本段管理 | 二级页表 |
| macOS | 不使用分段 | 多级页表 |

Linux 在 x86-64 上定义了三个平坦段：

```
Linux x86-64 段选择子:
┌────────────┬──────────┬──────┐
│  请求特权级│  TI      │ 索引 │
│  (RPL)     │ (GDT/LDT)│(idx) │
└────────────┴──────────┴──────┘

__USER_CS (索引=5): 用户代码段, DPL=3, 基址=0, 限长=最大
__USER_DS (索引=6): 用户数据段, DPL=3, 基址=0, 限长=最大
__KERNEL_CS(索引=1): 内核代码段, DPL=0, 基址=0, 限长=最大
__KERNEL_DS(索引=2): 内核数据段, DPL=0, 基址=0, 限长=最大
```

选择纯分页而非段页式的理由包括：分页提供统一的管理粒度（4KB 页），便于实现按需分页（Demand Paging）和页面置换（Page Replacement）；分段的可变长度管理增加了算法复杂度；纯分页模型更易于在不同架构间移植。

### 3.5 安全视角：内存管理机制对安全的影响

内存管理机制对系统安全有深远影响：

**缓冲区溢出与内存保护**：在固定/动态分区时代，进程的栈和数据位于连续物理内存中，栈溢出可以覆盖相邻的代码段或返回地址。分页机制引入的页粒度权限控制使得可以将栈页标记为不可执行（NX 位），直接阻止了栈溢出中的代码注入攻击。

**NX/DEP 与 ROP 绕过**：NX（No-Execute）保护通过页表项的 NX 位实现。然而攻击者发展出了面向返回编程（ROP，Return-Oriented Programming），利用已有代码段中的指令片段（Gadgets）拼接执行恶意逻辑，绕过了 NX 保护。这推动了后续的 CFI（Control-Flow Integrity，控制流完整性）等防御技术。

**地址空间布局随机化（ASLR）**：ASLR 的实现完全依赖分页机制。操作系统在进程加载时随机化各段的虚拟页起始位置，由于页表映射的灵活性，相同的虚拟页可以映射到任意物理帧。但 32 位系统上 ASLR 的熵值有限（仅 8-16 位随机化），容易被暴力破解。

**Meltdown 与 KPTI**：2018 年披露的 Meltdown 漏洞利用了 CPU 推测执行（Speculative Execution）的缺陷，允许用户态进程通过侧信道读取内核内存。防御措施 KPTI（Kernel Page Table Isolation）维护两套页表——用户态页表不映射内核页，从而在推测执行路径上也无法访问内核数据。这是分页机制在安全领域的最新重大应用。

**DMA 攻击面**：IOMMU（I/O Memory Management Unit）通过为外设提供独立的地址翻译页表，防止恶意或有缺陷的 DMA 设备访问非授权物理内存区域。IOMMU 的引入本质上是将分页机制扩展到了 I/O 设备层面。

## 4. 实战与示例

### 环境说明

本文示例基于 Linux 系统（内核版本 5.x/6.x），需要 root 权限或 `CAP_SYS_RAWIO` 能力。部分命令（如 crash）需要安装对应工具。

### /proc/meminfo 解读

`/proc/meminfo` 是内核导出的内存状态虚拟文件：

```bash
$ cat /proc/meminfo
MemTotal:       16384000 kB    # 物理内存总量 (不含内核保留)
MemFree:         2048000 kB    # 完全空闲的物理内存
MemAvailable:    6144000 kB    # 可用内存 (含可回收缓存)
Buffers:          512000 kB    # 块设备缓冲区缓存
Cached:          4096000 kB    # 页缓存 (Page Cache)
SwapTotal:       8192000 kB    # 交换空间总量
SwapFree:        8000000 kB    # 交换空间空闲量
Slab:             512000 kB    # 内核 Slab 分配器占用
SReclaimable:     384000 kB    # 可回收的 Slab
SUnreclaim:       128000 kB    # 不可回收的 Slab
PageTables:        64000 kB    # 所有进程页表占用的内存
KernelStack:        16384 kB    # 内核栈空间
HugePages_Total:       0       # 大页总数
HugePages_Free:        0       # 大页空闲数
Hugepagesize:       2048 kB    # 大页大小
```

关键观察点：
- `PageTables` 字段直接反映所有进程页表占用的物理内存量
- `MemAvailable` 综合了 `MemFree`、可回收缓存和 Slab 可回收部分
- `Buffers` 与 `Cached` 的区别：前者是块设备的原始缓冲，后者是文件系统页缓存

### 查看页表信息的 crash 命令

`crash` 是 Linux 内核内存转储分析工具，可用于查看进程页表：

```bash
# 使用 crash 打开内核转储
$ crash vmlinux vmcore

# 查看指定进程的页表
crash> task -R mm_struct <PID>
crash> struct mm_struct <mm_struct地址>
crash> task -R pgd <PID>    # 查看 PGD (页全局目录) 地址

# 查看虚拟地址到物理地址的翻译
crash> vtop <虚拟地址>       # 虚拟地址到物理地址翻译

# 查看物理内存布局
crash> kmem -i               # 物理内存使用概览
crash> kmem <物理地址>       # 查看指定物理地址附近的内存信息
```

对于活跃系统，也可使用 `/proc/<pid>/pagemap` 查看进程页表：

```bash
# 查看进程虚拟页面到物理帧的映射
$ cat /proc/self/pagemap | xxd | head
# 每个虚拟页对应 8 字节的 pagemap 条目:
# Bit 63:  页面是否在物理内存中
# Bit 62:  页面是否为软脏页 (soft-dirty)
# Bit 55-0: 物理帧号 (PFN)
```

### 理解物理地址布局

Linux 内核在启动时通过 E820 或 EFI 内存映射获取物理内存布局：


## 5. 常见坑与避坑指南

### 5.1 别把"分段"和"分页"混淆

分段和分页是两个完全不同的概念，但初学者极易混淆：

| 维度 | 分段 (Segmentation) | 分页 (Paging) |
|------|---------------------|---------------|
| 粒度 | 可变长度（逻辑单元） | 固定长度（通常 4KB） |
| 碎片类型 | 外部碎片 | 内部碎片 |
| 地址结构 | [段号 + 偏移] | [页号 + 页内偏移] |
| 用户可见性 | 对程序员可见（逻辑段） | 对程序员透明（硬件管理） |
| 碎片产生原因 | 段大小不固定，分配释放导致空闲块碎片化 | 最后一页未填满 |

一句话总结：分段管理"逻辑意义"，分页管理"物理空间"。

### 5.2 虚拟地址 ≠ 物理地址

在启用分页的现代操作系统中，用户态程序看到的所有地址都是**虚拟地址（Virtual Address）**，而非物理地址。这是安全隔离的基石。

关键理解：
- 每个进程拥有独立的虚拟地址空间，进程 A 的虚拟地址 0x400000 和进程 B 的虚拟地址 0x400000 映射到不同的物理帧
- 虚拟地址空间大小由 CPU 架构决定（x86-64 为 256TB），与实际物理内存无关
- 虚拟地址到物理地址的翻译由 MMU 硬件完成，操作系统通过控制页表来实现隔离

```bash
# 查看进程的虚拟内存布局
$ cat /proc/self/maps
55a1b2c00000-55a1b2c80000 r-xp  # 代码段 (只读+可执行)
55a1b2e80000-55a1b2ea0000 r--p  # 只读数据段
55a1b2ea0000-55a1b2ec0000 rw-p  # 可读写数据段
7f8a1c000000-7f8a1c200000 r-xp  # 共享库映射
7ffc12340000-7ffc12360000 rw-p  # 栈
```

### 5.3 页表的层次与性能开销

多级页表虽然节省了内存（不需要为未使用的虚拟地址空间分配页表页），但增加了地址翻译的内存访问次数。x86-64 四级页表最坏情况下需要 5 次内存访问（1 次查 PGD + 4 次逐级查找），这对性能影响巨大。

缓解策略：
- **TLB 缓存**：存储最近使用的页表项，命中时一次翻译完成（典型命中率 >99%）
- **大页（Huge Page）**：2MB 或 1GB 的大页减少页表级数，TLB 覆盖范围更大
- **PCID（Process Context Identifier）**：为每个进程分配 TLB 标签，减少进程切换时的 TLB 刷新

```bash
# 查看系统大页配置
$ grep Huge /proc/meminfo
HugePages_Total:       0
HugePages_Free:        0
HugePages_Rsvd:        0
HugePages_Surp:        0
Hugepagesize:       2048 kB

# 查看 TLB 相关信息
$ dmesg | grep -i tlb
[    0.032000] Calibrating delay loop... 5988.46 BogoMIPS (lpj=11976928)
```

### 5.4 DMA 与物理地址的关系

DMA（Direct Memory Access）允许外设绕过 CPU 直接访问物理内存。这意味着 DMA 设备不受页表和 MMU 保护的约束——这是 IOMMU 出现的根本原因。

安全影响：
- **FireWire 攻击**：通过 FireWire 接口的 DMA 能力，攻击者可以在几秒内读取目标机器的全部物理内存，包括加密密钥和密码
- **Thunderbolt/DMA 攻击**：现代 Thunderbolt 接口同样支持 DMA，是物理安全审计的重点检查项
- **IOMMU 防护**：Intel VT-d 和 AMD-Vi 提供的 IOMMU 为每个 DMA 设备建立独立的地址映射表，限制设备只能访问授权的物理内存区域

```bash
# 检查 IOMMU 是否启用
$ dmesg | grep -i iommu
[    0.000000] AMD-Vi: IOMMU performance counters supported
[    0.000000] iommu: Default domain type: Translated

# 查看 IOMMU 组
$ ls /sys/kernel/iommu_groups/
```
