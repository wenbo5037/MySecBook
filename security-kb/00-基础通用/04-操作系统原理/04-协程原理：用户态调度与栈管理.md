## 1. 概述

现代高并发服务面临一个根本矛盾：**并发连接数远超 OS 线程可承受的规模**。一个线程栈虚拟地址空间约 8MB、切换需微秒级，难以承载百万级并发。协程(coroutine)提供了用户态解法：**协程是用户态自行调度、自主挂起恢复的执行单元**，切换开销约几十纳秒，内存占用从 KB 级起，可轻松创建数十万乃至百万个。

**协程 vs 线程的本质区别**：

| 维度 | 线程(Thread) | 协程(Coroutine) |
|------|--------------|----------------|
| 调度者 | 操作系统内核 | 用户态运行时/库 |
| 切换开销 | 微秒级（需陷入内核） | 纳秒~几十 ns（用户态） |
| 并发模型 | 抢占式(preemptive) | 协作式(cooperative，自主让出) |
| 栈 | 通常固定大栈（MB 级） | 小而可扩（KB 级） |
| 数量级 | 千~万 | 十万~百万 |
| 阻塞语义 | 阻塞仅影响本线程 | 阻塞调用可能导致整个调度器/事件循环卡住 |
| 并行性 | 内核可调度到多核并行 | 单调度器内串行，需多调度器/线程池才能并行 |

**协作式 vs 抢占式**：线程由内核抢占式调度，任何时刻可能被切走；协程由用户态调度器协作式调度，只有协程**主动让出(yield/suspend)** 或遇到 I/O 等待时才会切换。这让调度更可控（无并发竞争问题在同调度器内），但也意味着"恶意或幼稚的阻塞调用"会卡死整个调度域。

从安全视角看，协程的"非阻塞只在正确使用异步接口时成立"——若在协程内发起同步阻塞调用（如阻塞 sleep、阻塞 read），会冻结整个调度线程，形成自 DoS。理解协程的阻塞模型是编写健壮并发服务的核心。

**协程的两大分支**：

```ascii
协程(Coroutine)
├── 有栈协程(Stackful)          ← 独立用户栈，可任意嵌套/深度挂起
│     Boost.Coroutine, libco(微信), libgo, Go goroutine
│     通过切换用户栈保存/恢复执行上下文
└── 无栈协程(Stackless)         ← 无独立栈，编译器将其编译为状态机
      C++20 coroutine, Rust async/await, Kotlin suspend, Python async
      挂起点被编译为状态机的 case 跳转
```

## 2. 核心原理

### 2.1 协程如何工作：挂起与恢复

协程的核心操作只有两个：**挂起(suspend/yield)** 与 **恢复(resume)**。在挂起点，协程保存执行上下文（寄存器、指令指针、若是栈协程还要保存栈）；恢复时从挂起点继续。

```ascii
有栈协程上下文切换示意
       协程A                         协程B
执行:  [....挂起点....]--> save(A的栈+寄存器)
                              |  恢复B
                       恢复A <--|  执行B
                             ...       [B也挂起]
                             save(B) --> 恢复A
```

关键差异：**有栈协程**挂起时可保存整个调用栈（可深度递归、可嵌套挂起任意位置），通过切换真实用户栈实现；**无栈协程**挂起点被限制在函数边界，编译器把协程体编译为状态机，用"当前行号"记录位置，无独立栈（保存局部变量到协程帧）。

### 2.2 事件循环与协程的配合

协程调度器（尤其是异步 I/O 模型）通常与**事件循环(event loop)** 紧密结合：

```ascii
           +---------------------------+
           |       用户态调度器/事件循环    |
           |  +---------+  +---------+  |
           |  | 协程队列 |  | 事件表   |  |
           |  +----|----+  +----|----+  |
           |       |             |      |
           +-------|-------------|------+
                   |             |
        当协程执行到 await/suspend
                   | 注册I/O回调请求
                   v
           +-----------------+
           |  非阻塞I/O多路复用  |   (epoll/kqueue/io_uring)
           +-----------------+
                   |
        事件就绪 → 唤醒对应协程 → 入队 → 被调度继续执行
```

典型流程（以异步网络服务器为例）：
1. 连接到达 → 创建协程处理该连接。
2. 协程执行到 `read` → 立即挂起（不阻塞线程），注册到 epoll 等待数据。
3. 调度器运行其他就绪协程。
4. 数据可读 → epoll 返回 → 唤醒该协程，恢复执行。

这让 **一个 OS 线程可以同时驱动数十万协程**，正是高性能网络服务（如 nginx、redis 的协程化版本、网关）的核心。

### 2.3 协程调度策略

用户态调度器常见策略：

| 策略 | 说明 | 典型 |
|------|------|------|
| round-robin | 就绪队列轮转，简单公平 | 简单调度器、asyncio |
| work-stealing | 空闲 P 偷取其他 P 的任务，多核负载均衡 | Go GMP、Java ForkJoinPool |
| 优先级调度 | 按优先级挑选（可配 deadline） | 部分协程库 |
| LIFO/栈式 | 新任务优先（缓存局部性好） | Go 本地队列按 LIFO 取 |

Go runtime 的 GMP 即 work-stealing 的经典实现（见 [[03-线程模型：内核线程用户线程与混合模型]]）。

## 3. 详细知识点

### 3.1 有栈协程（Stackful）

#### 3.1.1 栈空间切换原理

有栈协程为每个协程分配独立用户栈，切换时保存/恢复栈指针(SP)和寄存器上下文，相当于在用户态模拟了线程切换。

```c
// 伪代码：协程切换
void coroutine_switch(ctx_from, ctx_to) {
    // 保存 from 的 SP、通用寄存器、连接变量
    // 加载 to 的 SP、寄存器
    asm("... save/restore callee-saved regs & sp ...");
}
```

**ucontext_t**（POSIX/glibc）提供用户态上下文切换原语：

```c
#include <ucontext.h>

ucontext_t main_ctx, co_ctx;
char co_stack[64 * 1024];   // 协程独立栈

// 初始化协程上下文
getcontext(&co_ctx);
co_ctx.uc_stack.ss_sp   = co_stack;
co_ctx.uc_stack.ss_size = sizeof(co_stack);
co_ctx.uc_link          = &main_ctx;   // 协程返回后回到哪
makecontext(&co_ctx, co_func, 0);

// 切换到协程
swapcontext(&main_ctx, &co_ctx);

// 协程内执行既然后又 swapcontext 切回 main_ctx
void co_func(void) {
    // 执行……
    swapcontext(&co_ctx, co_func_ctx_saved);   // 主动让出
}
```

`swapcontext` 保存当前上下文到第一个参数、加载第二个参数的上下文——这就是有栈协程切换的核心原语。

#### 3.1.2 setjmp / longjmp

C 语言的 `setjmp`/`longjmp` 是更轻量的非局部跳转原语，可做协程（但受限于 C 语义，不能用于 C++ 对象自动销毁）：

```c
#include <setjmp.h>
jmp_buf env_a, env_b;

void coB(void);
void coA(void) {
    if (setjmp(env_a) == 0)   // 第一次进入，保存 env_a
        coB();                // 转到 B
    else {                    // setjmp 第二次返回（从 B longjmp 回来）
        printf("A 继续\n");
        longjmp(env_b, 1);    // 切回 B
    }
}
```

setjmp/longjmp 和非局部 goto 常被用于简单协程、错误处理（Perl、早期 C 异常模拟），但不适合 C++ 下对象生命周期管理（跳过析构）。

#### 3.1.3 代表：Boost.Coroutine、libco

- **Boost.Coroutine2**：C++ 有栈协程库，基于 `fcontext`（汇编级上下文切换，比 ucontext 快数倍），支持对称/非对称协程。
- **libco**（腾讯微信开源的 C/C++ 协程库）：用于微信后台支撑数百万连接。核心是 `co_create/co_resume`，结合 epoll 实现协程化高效网络编程。其上下文切换用汇编实现，性能极高。

```cpp
#include <boost/coroutine2/all.hpp>
using coro_t = boost::coroutines2::coroutine<int>;

void producer(coro_t::push_type& sink) {
    for (int i = 0; i < 5; i++)
        sink(i);                 // yield，将 i 交给 main
}

int main() {
    coro_t::pull_type source(producer);
    for (int v : source)         // 每次迭代恢复协程取一个值
        std::cout << v << "\n";
}
```

Python 的 `yield` 生成器、`asyncio` 底层协程，本质上也是这条路径的用户态调度简化版。

### 3.2 无栈协程（Stackless）

无栈协程**不分配独立调用栈**，挂起点被编译器转换为**状态机（state machine）**，通过保存"下一条语句位置"来记录执行到哪，局部变量保存在协程帧(coroutine frame)中。

#### 3.2.1 C++20 协程

C++20 引入关键字 `co_await`、`co_yield`、`co_return`：

- `co_await expr`：挂起并等待异步结果。
- `co_yield v`：产出一个值后挂起。
- `co_return v`：结束并返回值。
- 编译器把协程体转为状态机，需要**协程 promise 类型**来管理生命周期。

```cpp
#include <coroutine>
#include <iostream>
#include <thread>

struct Task {
    struct promise_type {
        Task get_return_object() { return {}; }
        std::suspend_never initial_suspend() noexcept { return {}; }
        std::suspend_never final_suspend() noexcept { return {}; }
        void return_void() {}
        void unhandled_exception() { std::terminate(); }
    };
};

// 一个自定义 awaiter：模拟等待 100ms
struct TimerAwaiter {
    bool await_ready() const noexcept { return false; }
    void await_suspend(std::coroutine_handle<> h) const {
        std::thread([h]{ std::this_thread::sleep_for(std::chrono::milliseconds(100));
                         h.resume(); }).detach();
    }
    void await_resume() const noexcept {}
};

Task doWork() {
    std::cout << "协程开始\n";
    co_await TimerAwaiter{};     // 挂起 100ms 后恢复
    std::cout << "协程恢复\n";
}

int main() {
    doWork();                    // 触发协程执行
    std::this_thread::sleep_for(std::chrono::milliseconds(200));
}
```

C++20 协程是典型的**无栈**：`co_await` 挂起点只有一行语句，局部变量存在于协程帧，不占独立调用栈。

#### 3.2.2 Rust async/await

Rust 的异步使用 `async fn` + `.await`：

- `async` 函数返回 `Future`，`.await` 挂起。
- Future 被编译为状态机（无栈）。
- 需要执行器(executor)（如 tokio、async-std）驱动 Future 的 poll。
- `pin` 保证状态机自引用安全。

```rust
use tokio::time::{sleep, Duration};

async fn fetch() -> u32 {
    sleep(Duration::from_millis(100)).await;   // 挂起
    42
}

#[tokio::main]
async fn main() {
    let a = fetch();
    let b = fetch();
    let (x, y) = tokio::join!(a, b);           // 并发等待
    println!("{x} {y}");
}
```

无栈（无独立栈）使得 Future 极其轻量，适合大规模并发的 tokio 网络服务。

#### 3.2.3 Kotlin suspend 与 Python asyncio

- **Kotlin**：`suspend` 函数编译为状态机，由协程上下文(CoroutineDispatcher)调度；`withContext`、`launch`、`async` 提供结构化并发。
- **Python asyncio**：`async def` + `await` 无栈协程，配合 `event_loop`（第 4 节有手写示例）。

```kotlin
import kotlinx.coroutines.*

suspend fun download(name: String): String {
    delay(100)               // 挂起
    return "data:$name"
}

fun main() = runBlocking {
    coroutineScope {
        launch { println(download("a")) }
        launch { println(download("b")) }
    }
}
```

### 3.3 协程的栈管理

有栈协程必须管理好每个协程的栈，无栈协程则靠编译期帧管理，无需运行期栈管理。有栈协程的栈问题是工程重点：

#### 3.3.1 固定栈 vs 协程栈(segment stack)

| 方案 | 说明 | 问题 |
|------|------|------|
| 固定小栈（默认 64KB~512KB） | 每个协程分配固定小栈 | 深度递归/大局部变量栈不够→溢出 |
| 预留大栈 | 分配足量栈 | 内存浪费（百万协程 × 大栈 = 巨大内存） |
| 分段栈(segment stack) | 栈满时分配新段，由编译器在函数入口插入检查 | 早期 Go 方案，栈搬迁开销 |
| 栈复制(stack copying) | 栈满时整块搬迁到更大新栈（Go 1.3+） | 指针重定位需 GC 支持 |
| 栈溢出检测 | 栈底设 guard page | 溢出触发 SIGSEGV/异常可检测 |

**Go 的栈管理**：Go 用栈复制——goroutine 初始栈约 2KB，栈不足时分配更大栈并复制，通过 GC 机制更新所有栈内指针。这让 goroutine 内存开销极低且能安全深度增长。

**C 有栈协程（libco/libgo）**：一般固定栈（如 libco 默认 128KB），因此大递归或深调用可能溢出——这是 C 协程库的一个经典坑。

### 3.4 协程调度器设计要点

高性能协程调度器（如 libgo、coost、Go runtime）设计关注：

1. **执行上下文切换**：用汇编(fcontext/boost ctx)而非 setjmp/ucontext，速度可提升 3~10 倍。
2. **就绪队列**：多队列+work-stealing 保证多核均衡。
3. **I/O 集成**：调度器直接驱动 epoll/kqueue/io_uring，实现"协程内同步语义、底层异步"。
4. **定时器**：最小堆/时间轮管理协程的延迟唤醒。
5. **同步原语**：协程互斥锁、信号量的用户态实现（阻塞者让出 CPU 而非睡眠线程）。
6. **系统调用拦截**：拦截可能阻塞的 libc 调用（如 socket、sleep），改为异步版本——这是协程库替换网络栈的关键。

```ascii
协程网络栈替换示意
非协程:  thread 调用 read() → 阻塞线程(内核挂起)
协程:    goroutine 调 read() → 被 hook → 注册到 epoll → 协程挂起
        → 内核线程空闲 → 数据到达 → 恢复协程 → read 返回
```

### 3.5 高性能网络库中的协程

- **libgo**（腾讯）：C/C++ 有栈协程库，支持 hook 系统调用，天然支持网络协程化。
- **coost**：跨平台 C++ 协程网络库，beast/asio 兼容。
- **Go runtime**：最成功的 M:N 协程模型之一，前述 GMP。
- **Swoole**（PHP）、**OpenResty/lua-nginx-module**（Lua 同步协程化 nginx）：让脚本语言以同步写法拟合异步 I/O。

## 4. 实战与示例

### 4.1 C++20 co_await 实现一个简单的异步任务

```cpp
#include <coroutine>
#include <future>
#include <iostream>

// 完成 std::future 的 awaiter，让 co_await 一个 future
template<typename T>
struct future_awaiter {
    std::future<T> fut;
    bool await_ready() const noexcept { return fut.wait_for(std::chrono::seconds(0)) == std::future_status::ready; }
    void await_suspend(std::coroutine_handle<> h) {
        std::thread([this, h]{
            fut.wait();
            h.resume();
        }).detach();
    }
    T await_resume() { return fut.get(); }
};

template<typename T>
future_awaiter<T> operator co_await(std::future<T> f) { return {std::move(f)}; }

struct Task {
    struct promise_type {
        Task get_return_object(){ return {}; }
        std::suspend_never initial_suspend() noexcept { return {}; }
        std::suspend_never final_suspend() noexcept { return {}; }
        void return_void(){}
        void unhandled_exception(){ std::terminate(); }
    };
};

std::future<int> asyncCompute() {
    return std::async(std::launch::async, []{ return 7 * 6; });
}

Task run() {
    int r = co_await asyncCompute();   // 挂起等待异步结果
    std::cout << "结果: " << r << "\n";
}

int main() {
    run();
    std::this_thread::sleep_for(std::chrono::milliseconds(200));
}
```

编译：
```bash
g++ -std=c++20 -pthread -o co cpp20_co.cpp
./co
```

这个例子展示了 `co_await` 如何以一种"看起来同步"的方式等待异步 future，而无栈协程的挂起/恢复由编译器生成的状态机完成。

### 4.2 Python asyncio 手写协程处理并发

用 asyncio 展示无栈协程 + 事件循环的高并发模型：

```python
import asyncio
import time

async def fetch(url, delay):
    # 模拟网络请求：异步挂起
    await asyncio.sleep(delay)
    return f"<html>{url}: {delay}s</html>"

async def main():
    start = time.perf_counter()
    # 并发启动 10 个协程
    tasks = [asyncio.create_task(fetch(f"site{i}", i * 0.1)) for i in range(10)]
    # 等待全部完成
    results = await asyncio.gather(*tasks)
    for r in results:
        print(r)
    print(f"总耗时: {time.perf_counter()-start:.3f}s")  # 约 0.9s（并发）非 4.5s（串行）

asyncio.run(main())
```

关键点：
- `asyncio.sleep()` 是**非阻塞挂起**，不占线程。
- 单线程事件循环串行执行协程，但每个协程在 await 处让出，实现并发。
- `gather` 并发等待、`create_task` 创建协程任务。
- 总耗时≈最大 delay，而非累加——体现并发价值。

**性能对比**：用 10 万协程 vs 10 万线程：
```python
import asyncio, threading
import time

def thr_worker():
    time.sleep(0.001)

threads = []
start = time.perf_counter()
# 提示：10万线程大概率失败/极慢，勿在低配机试
for _ in range(1000):
    t = threading.Thread(target=thr_worker)
    t.start(); threads.append(t)
for t in threads:
    t.join()
print("1000线程:", time.perf_counter()-start)

async def co_worker():
    await asyncio.sleep(0.001)

async def run_co():
    tasks = [asyncio.create_task(co_worker()) for _ in range(100000)]
    await asyncio.gather(*tasks)

start = time.perf_counter()
asyncio.run(run_co())
print("10万协程:", time.perf_counter()-start)
```
协程方案在单线程内轻松处理 10 万并发，线程方案则受资源限制——直观展示差异。

### 4.3 Go goroutine vs 线程性能对比

```go
package main

import (
    "fmt"
    "sync"
    "time"
)

func spin(w *sync.WaitGroup) {
    defer w.Done()
    // 纯计算，模拟任务
    sum := 0
    for i := 0; i < 1000; i++ {
        sum += i
    }
}

func main() {
    const N = 100000

    // goroutine 版本
    var wg sync.WaitGroup
    start := time.Now()
    for i := 0; i < N; i++ {
        wg.Add(1)
        go spin(&wg)
    }
    wg.Wait()
    fmt.Printf("%d goroutines: %v\n", N, time.Since(start))

    // 改用 Native 线程（仅对比数量，非公平 CPU）
    start = time.Now()
    var wg2 sync.WaitGroup
    for i := 0; i < 1000; i++ {   // 只到 1000 避免资源耗尽
        wg2.Add(1)
        go func() {
            defer wg2.Done()
            spin(&wg2)
        }()
    }
    wg2.Wait()
    fmt.Println("1000 goroutines(同上):", time.Since(start))
}
```

要点：goroutine 创建（轻量栈 + 用户态调度）可在毫秒~几十 ms 内创建海量并发单元；OS 线程受栈大小与内核 limit 限制（`ulimit -u`、`vm.max_map_count`）。

### 4.4 用 Go 展示协程阻塞陷阱

```go
func badBlock(s string) {
    fmt.Println(s)
    time.Sleep(500 * time.Millisecond)   // 不能随便阻塞
}

func goodYield(s string) {
    fmt.Println(s)
    time.Sleep(1 * time.Millisecond)     // 真实 I/O 由 runtime 让出 P
}
```
在 GOMAXPROCS 很小场景下，若协程内做 CPU 紧密计算不主动让出（`runtime.Gosched()`），其他 goroutine 会被饿许久——协作式调度的写照。

## 5. 常见坑与避坑指南

### 5.1 协程内阻塞调用导致整个事件循环/调度器卡死

**现象**：高并发服务偶发整体停顿，连接全部超时。
**原因**：某协程内调用了阻塞的系统调用（如 `time.sleep(秒级)`、同步 `read()`、`DNS` 解析、同步日志刷盘），占住调度线程，后续协程全部排队。
**避坑**：
- 事件循环/单调度器环境：严禁同步阻塞调用，一律用异步版本（协程库大多 hook 了常见阻塞调用）。
- 必须做重 CPU 或真阻塞操作时，交给独立线程池/`run_in_executor`/`to_thread`，避免占用调度循环。
- Go 中阻塞系统调用会让 runtime 让出 P，通常安全；但纯 CPU 紧循环也要考虑 `runtime.Gosched`。
- 生产环境监控事件循环阻塞时长（如 asyncio 的 `loop.slow_callback_duration`）。

### 5.2 协程泄漏（文件描述符/句柄永久占用）

**现象**：服务长时间运行后 `fd` 数 / 内存持续攀升，最终资源耗尽。
**原因**：协程在等待某个永不返回的 I/O（如未关闭的连接、挂起的 future/fd），或忘记关闭持有的资源，导致协程永不完成，资源永不回收。
**避坑**：
- 使用**结构化并发**（Go 的 `context`、Kotlin 的 `coroutineScope`、Python 的 `async with`）确保协程有界、可取消。
- 协程内打开的资源务必用 `try/finally`、`defer`、`async with` 关闭。
- 设置超时(`asyncio.timeout`、`context.WithTimeout`)，防止无限等待。
- 监控协程/goroutine 数量与 fd 数（Go: `runtime.NumGoroutine()`）。

### 5.3 协程内异常/错误处理不当导致静默失败

**现象**：一个协程报错后，整个任务/应用行为异常，且错误信息丢失。
**原因**：协程的异常不会像同步调用那样沿调用栈抛出；若未捕获、未传播，导致协程静默消亡或波及调度器。
**避坑**：
- 每个协程入口捕获异常并记录 `task.exception()` / 结构化日志。
- 改用结构化并发 + 取消传播，让子协程的失败向上冒泡。
- Go: `panic` 在 goroutine 中需 `recover`；统一 error 返回而非 panic。
- C++20: `unhandled_exception()` 必须妥善处理（记录或传播），否则默认终止。

### 5.4 有栈协程栈溢出

**现象**：深递归/大栈局部变量导致段错误(SIGSEGV)，难以定位。
**原因**：有栈协程固定栈（如 128KB）比 OS 线程栈(8MB)小得多，深调用易溢出。
**避坑**：
- 明确协程栈大小上限，避免无限递归。
- 栈底设 guard page 以捕获溢出而非静默破坏。
- 深度递归/大局部变量改用堆或无栈协程。
- 使用库的栈检查/诊断能力（如 libco 栈轨迹）。

### 5.5 调试困难：协程栈信息与真实调用栈脱节

**现象**：协程崩溃/卡住时，传统调试器/gdb 只能看到当前调度线程的栈，看不到协程自身的完整调用链。
**原因**：大量协程复用少量线程，异常时线程栈回溯只反映"当前运行的协程"；挂起的协程栈不直接可见。
**避坑**：
- 使用协程感知的工具：Go pprof(`runtime/pprof`)、Kotlin `Thread`+coroutine stacks、`coost` 诊断、`libco` 抓栈。
- 为协程设可读的名字/标签，故障排查时定位协程功能。
- 开启协程库的栈/日志诊断开关。
- 使用结构化并发 + 请求 ID，把协程执行串到日志。

### 5.6 协程与线程池配合失当

**现象**：在协程内用阻塞线程池跑简单任务，结果并发数不升反降或资源浪费。
**原因**：协程内把每个小任务都 `run_in_executor`/派发线程，反而引入线程池排队与切换开销，丢失协程轻量优势。
**避坑**：
- 轻量/短任务优先在协程内直接执行（配合异步版本）。
- 仅将**真正阻塞/CPU 密集的**任务放入有界的线程池，池大小按核数与阻塞比例设定。
- Go 普通 goroutine 已可当作"线程池+调度器"合体，不必绕道。
- 监控线程池排队长度，避免池太小成为瓶颈。

### 5.7 协程数量"看起来无限"但内存/调度成本依旧

**现象**：轻易创建几十万协程，状态正常，但整体吞吐不升反降。
**原因**：协程虽轻，但每个协程仍有协程帧/栈(Go 2KB+，C 有栈 128KB+)、调度器维护、上下文切换开销。数量远超实际并发需求反而浪费。
**避坑**：
- 用信号量/限制器控制并发上限（`asyncio.Semaphore`、`errgroup.SetLimit`、Go `chan` 限额）。
- 根据实际 I/O 并行度设置并发数，而非盲目最大。
- 监控 `NumGoroutine`/协程数做容量规划。
