## 1. 概述

**死锁（Deadlock）** 是并发系统中最隐蔽、最致命的一类活性（liveness）故障。当两个或多个进程（或线程）各自持有某种资源，同时又等待获取对方持有的资源时，所有进程将永远阻塞——没有任何外部干预，系统无法自行从这种状态恢复。

在操作系统课程中，死锁问题通常从 Coffman 等人在 1971 年提出的**四个必要条件**切入理解。在生产环境中，死锁可能表现为：数据库连接池耗尽、多线程程序挂起（hang）、微服务间循环依赖导致的级联故障（cascading failure），甚至 Docker 容器内多进程死锁导致健康检查超时重启。

理解死锁需要区分三个层次：**死锁预防（Prevention）**——在设计阶段破坏四个必要条件中的至少一个；**死锁避免（Avoidance）**——运行时根据系统状态动态决策是否分配资源（如银行家算法）；**死锁检测与恢复（Detection and Recovery）**——允许死锁发生，但能检测并从死锁中恢复。三者各有适用场景，也各有代价——预防可能牺牲并发度，避免需要预先声明最大资源需求且有较高的状态空间开销，检测与恢复则需要付出回滚或终止进程的代价。

本节将从四个必要条件出发，逐一展开资源分配图（Resource Allocation Graph, RAG）模型、银行家算法（Banker's Algorithm）的数学原理与实现细节、死锁检测算法的内核实现、以及生产环境中常见的死锁陷阱与规避方法。作为 [[08-同步原语：互斥锁自旋锁信号量条件变量]] 中"死锁是锁的三大性质之一（进展性被破坏）"的深入展开，本节还将覆盖饥饿（Starvation）与活锁（Livelock）这两个与死锁密切相关的活性问题。

## 2. 核心原理

### 2.1 死锁的四个必要条件（Coffman Conditions）

Coffman 等人在 1971 年的形式化分析中证明，死锁发生当且仅当以下四个条件**同时成立**：

| 条件 | 英文 | 含义 |
|------|------|------|
| 互斥 | Mutual Exclusion | 资源一次只能被一个进程持有 |
| 持有并等待 | Hold and Wait | 进程持有至少一个资源，同时等待获取其他被占用的资源 |
| 不可抢占 | No Preemption | 资源只能由持有者自愿释放，不能被系统强制夺走 |
| 循环等待 | Circular Wait | 存在一个进程集合 {P₀, P₁, ..., Pₙ}，其中 P₀ 等待 P₁ 持有的资源，P₁ 等待 P₂ 持有的资源，...，Pₙ 等待 P₀ 持有的资源 |

**关键认知**：这四个条件是**必要条件**，不是充分条件。即死锁发生时这四个条件必然同时成立，但四个条件同时成立时死锁不一定已经发生（可能只是处于死锁潜在状态）。死锁预防的核心策略就是**在设计时保证至少一个条件永远不成立**。

### 2.2 资源分配图（Resource Allocation Graph）

**资源分配图（RAG）** 是分析死锁状态的经典图模型。它是一个有向二部图（bipartite digraph）：

- **节点集合**分为两类：进程节点（用圆圈 P 表示）和资源节点（用方框 R 表示，方框内用圆点表示该资源的实例数）
- **边集合**分为两类：请求边（Request Edge）从进程 P 指向资源 R（Pi → Rj，表示进程 Pi 请求资源 Rj）；分配边（Assignment Edge）从资源 R 指向进程 P（Rj → Pi，表示资源 Rj 已分配给进程 Pi）

**RAG 化简法（Reduction Algorithm）**：

1. 找到一个进程 Pi，其所有请求边对应的资源均有足够空闲实例（即 Rj 上的空闲实例数 > 0 或所有分配边都指向其他可释放的进程）
2. 假设 Pi 获得资源后能完成执行，释放其持有的所有资源（删除所有从 R 指向 Pi 的分配边）
3. 重复步骤 1 和 2，直到无法再找到满足条件的进程
4. 若最终所有边都被删除，则系统无死锁；若仍有剩余边，则这些边涉及的进程处于死锁状态

```text
    ┌───┐  request   ┌───┐  assign   ┌───┐
    │P1 │ ────────>  │R1 │ ────────> │P2 │
    └───┘            └───┘            └───┘
     ^                                  │
     │          ┌───┐  assign           │
     └──────────│R2 │ <─────────────────┘
                └───┘
                
    P1 持有 R2，请求 R1
    P2 持有 R1，请求 R2
    → 存在循环等待 → 死锁
```

### 2.3 死锁处理策略对比

| 策略 | 时机 | 代价 | 适用场景 |
|------|------|------|----------|
| 死锁预防 | 设计时 | 可能降低并发度、资源利用率低 | 硬实时系统、嵌入式系统 |
| 死锁避免 | 运行时（分配前） | 需要预知最大需求、O(m×n²) 计算开销 | 资源可预知的批处理系统 |
| 死锁检测与恢复 | 运行时（事后） | 回滚/终止开销、可能丢失计算 | 数据库系统、通用操作系统 |
| 鸵鸟策略 | 从不处理 | 死锁时重启 | 大多数桌面/移动操作系统 |

## 3. 详细知识点

### 3.1 死锁预防：破坏四个条件

#### 3.1.1 破坏互斥条件

**方法**：使用可共享读的资源（如 Read-Only File），或通过多副本（Copy-on-Write）让资源天然可共享。

**代价**：并非所有资源都可以共享——写入操作、独占锁、打印机等物理资源天然互斥。此策略适用范围极窄。

#### 3.1.2 破坏持有并等待条件

**方法**：要求进程在开始执行前一次性申请所有需要的资源（All-or-Nothing），如果某些资源不可用，则不分配任何资源。

**代价**：
- 资源利用率极低——进程可能在大部分时间内只使用少数资源，但必须独占所有资源
- 可能导致饥饿——高优先级进程可能因为资源被低优先级进程提前申请而无限等待

#### 3.1.3 破坏不可抢占条件

**方法**：当进程请求的资源不可用时，系统强制剥夺其已持有的资源，释放给其他进程使用。

**代价**：
- 只适用于资源状态可以保存和恢复的场景（如 CPU 寄存器、内存页）
- 对于打印机、磁带机等不可保存状态的资源，强制剥夺会丢失中间状态
- 频繁的抢占和回滚会严重影响性能

#### 3.1.4 破坏循环等待条件（最常用）

**方法**：对所有资源类型进行**全局排序（Total Ordering）**，要求每个进程只能按资源编号递增的顺序请求资源。

```c
/* 资源编号示例：mutex_a = 1, mutex_b = 2, mutex_c = 3 */

/* 正确：按编号递增顺序获取锁 */
pthread_mutex_lock(&mutex_a);  /* 编号 1 */
pthread_mutex_lock(&mutex_b);  /* 编号 2 */
/* ... 临界区 ... */
pthread_mutex_unlock(&mutex_b);
pthread_mutex_unlock(&mutex_a);

/* 错误：逆序获取 → 可能导致循环等待 */
pthread_mutex_lock(&mutex_b);  /* 编号 2 */
pthread_mutex_lock(&mutex_a);  /* 编号 1 → 逆序！ */
```

**实际工程中的实现**：Linux 内核使用 `lockdep` 子系统（`CONFIG_LOCKDEP`）在运行时检测锁顺序不一致。当内核开发者无意中引入了新的锁获取顺序，`lockdep` 会通过 `lock ordering` 报告潜在的循环等待。

### 3.2 银行家算法（Banker's Algorithm）

银行家算法由 Edsger Dijkstra 于 1965 年提出，是**死锁避免**的经典算法。其核心思想是：在每次资源分配前，模拟分配后系统是否仍处于**安全状态（Safe State）**——即是否存在一个进程执行序列，使得每个进程都能获得其最大资源需求并完成执行。

#### 3.2.1 数据结构

设系统有 n 个进程，m 种资源类型：

| 变量 | 维度 | 含义 |
|------|------|------|
| Available[m] | 1×m 向量 | 每种资源当前可用的数量 |
| Max[n][m] | n×m 矩阵 | 每个进程对每种资源的最大需求 |
| Allocation[n][m] | n×m 矩阵 | 每个进程当前已分配的资源数量 |
| Need[n][m] | n×m 矩阵 | 每个进程还需要的资源数量（Need = Max - Allocation） |

#### 3.2.2 安全性检查算法

```python
def is_safe_state(Available, Max, Allocation, Need, n, m):
    """
    银行家算法安全性检查
    Available: 当前可用资源向量 (m,)
    Max: 最大需求矩阵 (n, m)
    Allocation: 已分配矩阵 (n, m)
    Need: 需求矩阵 (n, m)
    n: 进程数, m: 资源类型数
    返回: (是否安全, 安全序列)
    """
    Work = Available.copy()           # 工作向量，模拟可用资源
    Finish = [False] * n              # 标记每个进程是否能完成
    SafeSequence = []                 # 安全序列

    while True:
        found = False
        for i in range(n):
            if not Finish[i]:
                # 检查进程 i 的所有需求是否都能被满足
                can_allocate = all(Need[i][j] <= Work[j] for j in range(m))
                if can_allocate:
                    # 假设进程 i 完成并释放资源
                    Work = [Work[j] + Allocation[i][j] for j in range(m)]
                    Finish[i] = True
                    SafeSequence.append(i)
                    found = True
                    break  # 重新从头扫描
        
        if not found:
            break

    all_finished = all(Finish)
    return all_finished, SafeSequence
```

#### 3.2.3 资源请求算法

当进程 Pi 请求资源 Request[i] 时：

1. 检查 Request[i] ≤ Need[i]，否则报错（进程超额请求）
2. 检查 Request[i] ≤ Available，否则等待（资源不足）
3. **试探性分配**：更新 Available、Allocation、Need
4. 调用安全性检查算法
5. 若安全，正式分配；若不安全，撤销试探性分配，Pi 等待

**复杂度分析**：安全性检查的最坏时间复杂度为 O(m × n²)，因为每轮扫描最多找到一个可完成的进程（最多 n 轮），每轮检查需要 O(m) 时间。对于大规模系统（如数据库有数百个事务、数十种资源），这个开销可能不可忽略。

### 3.3 死锁检测算法

与银行家算法不同，死锁检测**不需要预先声明最大需求**。它只根据当前的分配图和请求图进行检测。

**单实例资源的死锁检测**：直接在 RAG 中检测环路——如果存在有向环路，则存在死锁。

**多实例资源的死锁检测**：使用与安全性检查类似的算法，但 Work 初始值设为 Available，并额外考虑已分配但尚未释放的资源：

```python
def detect_deadlock(Available, Allocation, Request, n, m):
    """
    多资源死锁检测算法
    Request[i][j] = 当前进程 Pi 对资源 Rj 的请求数量
    """
    Work = Available.copy()
    Finish = [False] * n
    
    # 初始化：无分配的进程视为可完成
    for i in range(n):
        if sum(Allocation[i]) == 0:
            Finish[i] = True

    while True:
        found = False
        for i in range(n):
            if not Finish[i]:
                can_satisfy = all(Request[i][j] <= Work[j] for j in range(m))
                if can_satisfy:
                    Work = [Work[j] + Allocation[i][j] for j in range(m)]
                    Finish[i] = True
                    found = True
                    break
        if not found:
            break

    deadlocked = [i for i in range(n) if not Finish[i]]
    return deadlocked
```

**Linux 内核中的死锁检测**：Linux 内核的 `hung_task_detector`（`CONFIG_DETECT_HUNG_TASK`）通过检测进程在 `TASK_UNINTERRUPTIBLE` 状态停留超过 `hung_task_timeout_secs`（默认 120 秒）来发现可能的死锁。内核的 `lockdep` 则通过跟踪锁的获取顺序图来**预防性地**检测潜在死锁。

### 3.4 死锁恢复

当死锁检测算法发现死锁后，系统需要从死锁中恢复。主要策略有：

#### 3.4.1 进程终止（Process Termination）

- **终止所有死锁进程**：简单粗暴，代价最大——可能丢失大量计算结果
- **逐一终止**：每次终止一个进程，重新运行死锁检测，直到死锁解除。终止选择标准：
  - 进程优先级最低
  - 进程已运行时间最短
  - 进程已使用的资源最少
  - 进程剩余执行时间最长（损失最小）

#### 3.4.2 资源剥夺（Resource Preemption）

从某个进程中强制回收资源分配给其他进程：

- **选择牺牲者**：与进程终止类似的标准来选择被剥夺资源的进程
- **回滚（Rollback）**：将被剥夺资源的进程回滚到某个安全状态（检查点/checkpoint）
- **饥饿问题**：如果同一进程反复被选为牺牲者，可能永远无法完成——需要限制每个进程被选为牺牲者的次数

### 3.5 饥饿与活锁

#### 3.5.1 饥饿（Starvation）

饥饿是指进程无限期等待资源，虽然系统中没有死锁——其他进程不断获得资源并完成，但被等待的进程始终无法获得资源。

**与死锁的区别**：
- 死锁：所有相关进程都永远阻塞，没有任何进程能推进
- 饥饿：部分进程能正常推进，但特定进程永远无法获得资源

**典型场景**：在简单信号量实现中，如果多个进程竞争同一信号量，总有一些进程因调度策略（如短作业优先）而长期得不到执行。

**解决方案**：使用公平队列（FIFO）来管理等待进程；使用 `futex` 的 FUTEX_WAIT_QUEUE 保证先到先服务；实现有界等待（Bounded Waiting）机制。

#### 3.5.2 活锁（Livelock）

活锁是指进程不断改变状态以响应对方，但没有任何实际进展——就像两个人在走廊里相遇，同时让路到同一侧，然后又同时让到另一侧，如此反复。

**与死锁的区别**：
- 死锁：所有进程都阻塞在原地
- 活锁：进程不断运行（状态切换），但不产生有用工作

**典型场景**：两个线程同时检测到冲突后，同时释放锁并随机退避重试，结果又同时重试——如果退避策略完全相同，可能反复碰撞。

**解决方案**：随机退避（Random Backoff）；优先级机制（高优先级进程先尝试）；指数退避（Exponential Backoff）。

### 3.6 死锁检测的实际工程实现：Lockdep 与等待图

在内核工程实践中，死锁检测并不是抽象的理论算法，而是有具体实现工具。Linux 内核的 **lockdep（Lock Dependency Validator）** 是最著名的动态死锁预防工具。它通过记录内核代码中所有锁的获取顺序（lock ordering），建立一张"锁依赖图"（lock dependency graph），并在**每次加锁时动态验证**这张图是否会出现环路。

```text
lockdep 工作原理：

1. 记录阶段：
   内核代码中每次 pthread_mutex_lock(&A) 都会调用
   lock_acquire(&A, ...)，记录 A 的持有者线程
   
2. 建立依赖图：
   线程持有 A 又请求 B → 记录依赖 A → B
   线程持有 B 又请求 C → 记录依赖 B → C

3. 环路检测（运行时）：
   当出现 A → B → C → A 的依赖环路时，
   lockdep 立即报告 "possible circular locking dependency detected"

4. 报告示例：
   [ INFO: possible circular locking dependency detected ]
   chain_key: 0x123456
   Possible unsafe locking scenario:
     CPU0                    CPU1
     ----                    ----
     lock(A);
                              lock(B);
                              lock(A);
     lock(B);
   *** DEADLOCK ***
```

**用户态对应工具**：GCC 的 Thread Sanitizer（TSan）内置了死锁检测功能。它通过记录每一对锁的获取顺序来建立锁顺序图，并在检测到循环时输出"Cycle in lock order graph"。这比手工审查代码要可靠得多——因为它能捕捉到那些只在特定时序下才会触发的罕见死锁路径。

**多锁场景的分析**：当涉及两把以上的锁时，死锁的检测难度指数级上升。三把锁 (A, B, C) 的潜在死锁需要满足 A→B→C→A 的完整环路。lockdep 和 TSan 的优势就在于它们**自动**维护了锁依赖图，而不需要开发者手动追踪每一对锁的顺序。这也是为什么在现代工程实践中，"代码审查 + 动态检测工具（TSan/lockdep）"是防死锁的标准组合。

### 3.7 死锁避免的参数化资源模型

在实际系统中，一个进程可能需要多个不同类型的资源（内存、文件描述符、锁、网络连接），每种资源又有配额限制（如 `ulimit`）。这就形成了一个**多维资源分配问题**。银行家算法的基本模型可以扩展到多维场景，但需要引入参数化约束：

```text
多维资源模型示例：

n=2 个进程，m=3 类资源（内存页、文件描述符、socket）

进程 P0:  Max = (100 页,  64  fd, 16 sock)
          Alloc = (50 页,  20  fd,  8 sock)
          Need = (50 页,   44  fd,  8 sock)

进程 P1:  Max = (80 页,  32  fd, 12 sock)
          Alloc = (30 页,  10  fd,  4 sock)
          Need = (50 页,   22  fd,  8 sock)

Available = (20 页, 20 fd, 8 sock)

安全性检查：
  P0 是否可完成？Need=(50,44,8) Vs Work=(20,20,8) → 失败（页不足）
  P1 是否可完成？Need=(50,22,8) Vs Work=(20,20,8) → 失败（页不足）
  → 当前不是安全状态

若 Available = (60 页, 20 fd, 8 sock)：
  P1 可完成（Need=(50,22,8) ≤ Work），释放后 Work += (30,10,4)
  → Work = (90, 30, 12)
  P0 可完成（Need=(50,44,8) ≤ Work）
  → 安全状态，存在安全序列 [P1, P0]
```

**实际应用局限**：真实系统很少为每个进程声明"最大资源需求"（Max 矩阵），因为进程的行为是动态的、无法预知的。因此银行家算法主要用于**静态资源预估的系统**（如某些数据库连接池管理、嵌入式实时系统），而通用操作系统（Linux/Windows）采用"检测 + 恢复"或"鸵鸟策略"。

### 3.8 从并发视角看死锁分类

```text
┌─────────────────────────────────────────────────────────────────┐
│                        死锁分类体系                               │
├─────────────────┬───────────────────────────────────────────────┤
│ 资源类型         │ 排他性资源（锁、文件描述符、内存页）            │
│                 │ 通信资源（socket、管道、共享内存段）            │
├─────────────────┼───────────────────────────────────────────────┤
│ 涉及范围         │ 资源死锁：进程间争夺物理/逻辑资源              │
│                 │ 通信死锁：进程间消息传递中的循环等待            │
│                 │ 数据库死锁：事务间锁定行/表的循环等待           │
├─────────────────┼───────────────────────────────────────────────┤
│ 检测难度         │ 静态死锁：加载时即可发现（类型系统）           │
│                 │ 动态死锁：运行时偶发，取决于执行时序            │
└─────────────────┴───────────────────────────────────────────────┘
```

**数据库死锁的特殊性**：数据库管理系统（DBMS）是死锁处理的典型应用。MySQL InnoDB 使用等待图（Wait-for Graph）检测死锁，选择回滚代价最小的事务进行回滚。PostgreSQL 使用类似的超时机制（`deadlock_timeout`）。这些系统本质上是在应用层实现了死锁检测与恢复策略。

## 4. 实战与示例

### 4.1 C 语言银行家算法完整实现

```c
#include <stdio.h>
#include <stdbool.h>
#include <string.h>

#define N 5   /* 进程数 */
#define M 3   /* 资源类型数 */

/* 全局数据结构 */
int Available[M] = {3, 3, 2};

int Max[N][M] = {
    {7, 5, 3},
    {3, 2, 2},
    {9, 0, 2},
    {2, 2, 2},
    {4, 3, 3}
};

int Allocation[N][M] = {
    {0, 1, 0},
    {2, 0, 0},
    {3, 0, 2},
    {2, 1, 1},
    {0, 0, 2}
};

int Need[N][M];

/* 计算 Need 矩阵 */
void calculate_need(void) {
    for (int i = 0; i < N; i++)
        for (int j = 0; j < M; j++)
            Need[i][j] = Max[i][j] - Allocation[i][j];
}

/* 安全性检查 */
bool is_safe(int safe_seq[]) {
    int Work[M];
    bool Finish[N] = {false};
    memcpy(Work, Available, sizeof(int) * M);
    
    int count = 0;
    bool found;
    
    do {
        found = false;
        for (int i = 0; i < N; i++) {
            if (!Finish[i]) {
                bool can_run = true;
                for (int j = 0; j < M; j++) {
                    if (Need[i][j] > Work[j]) {
                        can_run = false;
                        break;
                    }
                }
                if (can_run) {
                    for (int j = 0; j < M; j++)
                        Work[j] += Allocation[i][j];
                    Finish[i] = true;
                    safe_seq[count++] = i;
                    found = true;
                }
            }
        }
    } while (found);
    
    /* 检查所有进程是否都能完成 */
    for (int i = 0; i < N; i++)
        if (!Finish[i]) return false;
    
    return true;
}

/* 资源请求处理 */
bool request_resources(int pid, int request[]) {
    /* 检查 Request <= Need */
    for (int j = 0; j < M; j++) {
        if (request[j] > Need[pid][j]) {
            printf("Error: 进程 %d 请求超过其声明的最大需求\n", pid);
            return false;
        }
    }
    
    /* 检查 Request <= Available */
    for (int j = 0; j < M; j++) {
        if (request[j] > Available[j]) {
            printf("进程 %d 必须等待：资源不足\n", pid);
            return false;
        }
    }
    
    /* 试探性分配 */
    for (int j = 0; j < M; j++) {
        Available[j] -= request[j];
        Allocation[pid][j] += request[j];
        Need[pid][j] -= request[j];
    }
    
    /* 安全性检查 */
    int safe_seq[N];
    if (is_safe(safe_seq)) {
        printf("试探性分配成功，系统安全。安全序列: ");
        for (int i = 0; i < N; i++)
            printf("P%d%s", safe_seq[i], i < N-1 ? " → " : "\n");
        return true;
    } else {
        /* 撤销分配 */
        for (int j = 0; j < M; j++) {
            Available[j] += request[j];
            Allocation[pid][j] -= request[j];
            Need[pid][j] += request[j];
        }
        printf("分配后系统不安全，已撤销\n");
        return false;
    }
}

int main(void) {
    calculate_need();
    
    int safe_seq[N];
    printf("=== 初始安全性检查 ===\n");
    if (is_safe(safe_seq)) {
        printf("系统处于安全状态。安全序列: ");
        for (int i = 0; i < N; i++)
            printf("P%d%s", safe_seq[i], i < N-1 ? " → " : "\n");
    } else {
        printf("系统处于不安全状态！\n");
    }
    
    printf("\n=== P1 请求资源 (1, 0, 2) ===\n");
    int req1[] = {1, 0, 2};
    request_resources(1, req1);
    
    printf("\n=== P4 请求资源 (3, 3, 0) ===\n");
    int req4[] = {3, 3, 0};
    request_resources(4, req4);
    
    printf("\n=== P0 请求资源 (0, 2, 0) ===\n");
    int req0[] = {0, 2, 0};
    request_resources(0, req0);
    
    return 0;
}
```

编译并运行：

```bash
gcc -o banker banker.c -Wall -Wextra
./banker
```

预期输出系统处于安全状态，安全序列为 P1 → P3 → P4 → P0 → P2（具体序列取决于算法扫描顺序）。

### 4.2 C 语言资源分配图检测

```c
#include <stdio.h>
#include <stdbool.h>
#include <string.h>

#define MAX_PROCESSES 100
#define MAX_RESOURCES 100

/* 简化的 RAG 检测：基于请求矩阵和分配矩阵检测死锁 */
bool detect_deadlock_rag(
    int available[],        /* 可用资源向量 */
    int allocation[][MAX_RESOURCES],  /* 已分配矩阵 */
    int request[][MAX_RESOURCES],     /* 请求矩阵 */
    int n, int m,           /* 进程数、资源数 */
    int deadlocked[])        /* 输出：死锁进程列表 */
{
    int work[MAX_RESOURCES];
    bool finish[MAX_PROCESSES] = {false};
    memcpy(work, available, sizeof(int) * m);
    
    /* 先标记无分配的进程 */
    for (int i = 0; i < n; i++) {
        bool has_alloc = false;
        for (int j = 0; j < m; j++) {
            if (allocation[i][j] > 0) {
                has_alloc = true;
                break;
            }
        }
        if (!has_alloc) finish[i] = true;
    }
    
    bool found;
    do {
        found = false;
        for (int i = 0; i < n; i++) {
            if (finish[i]) continue;
            bool can_satisfy = true;
            for (int j = 0; j < m; j++) {
                if (request[i][j] > work[j]) {
                    can_satisfy = false;
                    break;
                }
            }
            if (can_satisfy) {
                for (int j = 0; j < m; j++)
                    work[j] += allocation[i][j];
                finish[i] = true;
                found = true;
            }
        }
    } while (found);
    
    int count = 0;
    for (int i = 0; i < n; i++) {
        if (!finish[i])
            deadlocked[count++] = i;
    }
    deadlocked[count] = -1;  /* 哨兵 */
    return count > 0;
}
```

#include <pthread.h>
#include <time.h>
#include <errno.h>
#include <stdio.h>

int safe_lock(pthread_mutex_t *mutex, int timeout_ms) {
    struct timespec ts;
    clock_gettime(CLOCK_REALTIME, &ts);
    ts.tv_nsec += (timeout_ms % 1000) * 1000000;
    ts.tv_sec += timeout_ms / 1000 + ts.tv_nsec / 1000000000;
    ts.tv_nsec %= 1000000000;
    
    int ret = pthread_mutex_timedlock(mutex, &ts);
    if (ret == ETIMEDOUT) {
        fprintf(stderr, "锁获取超时，可能存在死锁\n");
        return -1;
    }
    return 0;
}

### 4.4 使用 Python 实现死锁检测器

```python
import threading
import time
import traceback
import sys

class DeadlockDetector:
    """基于锁等待图的死锁检测器"""
    
    def __init__(self):
        self.lock_map = {}       # lock_id → holding_thread
        self.wait_map = {}       # thread_id → waiting_lock_id
        self.locks = {}          # lock_id → threading.Lock
        self._lock = threading.Lock()
        self.detected = False
    
    def register_lock(self, lock_id, lock_obj):
        with self._lock:
            self.locks[lock_id] = lock_obj
    
    def acquire(self, thread_id, lock_id):
        """包装的锁获取，记录等待关系"""
        with self._lock:
            if lock_id in self.lock_map:
                if self.lock_map[lock_id] != thread_id:
                    self.wait_map[thread_id] = lock_id
                    # 检测死锁
                    if self._detect_cycle():
                        self.detected = True
                        self._report_deadlock()
                        return False
        
        self.locks[lock_id].acquire()
        
        with self._lock:
            self.lock_map[lock_id] = thread_id
            self.wait_map.pop(thread_id, None)
        return True
    
    def release(self, thread_id, lock_id):
        with self._lock:
            if lock_map := self.lock_map:
                if lock_id in self.lock_map and self.lock_map[lock_id] == thread_id:
                    del self.lock_map[lock_id]
        self.locks[lock_id].release()
    
    def _detect_cycle(self):
        """在等待图中检测环路"""
        wait_for = {}  # thread → thread (via lock)
        for tid, lid in self.wait_map.items():
            if lid in self.lock_map:
                holder = self.lock_map[lid]
                if holder != tid:
                    wait_for[tid] = holder
        
        # DFS 检测环路
        visited = set()
        stack = set()
        
        def dfs(node):
            if node in stack:
                return True
            if node in visited:
                return False
            visited.add(node)
            stack.add(node)
            if node in wait_for:
                if dfs(wait_for[node]):
                    return True
            stack.remove(node)
            return False
        
        for node in wait_for:
            if dfs(node):
                return True
        return False
    
    def _report_deadlock(self):
        print("=== 检测到死锁 ===", file=sys.stderr)
        for tid, lid in self.wait_map.items():
            holder = self.lock_map.get(lid, "unknown")
            print(f"  Thread {tid} 等待 Lock {lid}, "
                  f"被 Thread {holder} 持有", file=sys.stderr)
        traceback.print_stack(file=sys.stderr)
```

## 5. 常见坑与避坑指南

### 5.1 隐式资源申请

**问题**：开发者显式地管理了 A、B 两把锁的获取顺序，但忽略了某个库函数内部会获取第三把锁 C。当另一个模块以不同顺序获取 C 和 A 时，产生循环等待——而这个循环在代码审查中几乎不可能发现。

```c
/* 模块 A */
void module_a_func(void) {
    pthread_mutex_lock(&lock_a);      /* 显式获取 A */
    library_call();                    /* 库内部隐式获取 lock_c */
    pthread_mutex_lock(&lock_b);      /* 获取 B */
    /* ... */
    pthread_mutex_unlock(&lock_b);
    pthread_mutex_unlock(&lock_a);
}

/* 模块 B：先获取 C 再获取 A，而 C 与 A 的顺序与模块 A 相反 */
void module_b_func(void) {
    pthread_mutex_lock(&lock_c);
    pthread_mutex_lock(&lock_a);      /* 模块 A 中是先 A 后 C */
    /* ... */
    pthread_mutex_unlock(&lock_a);
    pthread_mutex_unlock(&lock_c);
}
```

**避坑**：
- 建立并维护**全局锁顺序文档**，所有模块必须遵守
- 使用 Linux `lockdep`（`CONFIG_LOCKDEP`）在内核中自动检测锁顺序不一致
- 用户态可使用 TSan 或自定义锁顺序跟踪器
- 调试时用 `ltrace`/`strace` 观察库函数的隐式加锁行为

### 5.2 锁顺序不一致导致的"概率性死锁"

**问题**：同一对锁 (A, B) 在大部分代码路径中以 A→B 的顺序获取，但某个罕见的异常路径以 B→A 获取。由于异常路径很少触发，死锁表现为"运行数小时后偶发挂起"。

```c
/* 正常路径 */
lock(A); lock(B); /* ... */ unlock(B); unlock(A);

/* 异常路径（错误） */
lock(B); lock(A); /* ... */ unlock(A); unlock(B);
```

**避坑**：
- 代码审查时，对所有加锁函数进行交叉比对
- 使用 `git log --all -p | grep -n "pthread_mutex_lock"` 全面搜索所有锁获取点
- 单元测试中引入随机化的执行顺序以增加偶发死锁的复现概率（如 Google 的 Thread Sanitizer + randomized scheduling）

### 5.3 库函数内部加锁

**问题**：标准库函数（如 `malloc`/`free`、`printf`、`gethostbyname`）通常使用内部锁保护全局状态（如堆管理器的 Arena、stdout 缓冲区）。如果用户在持有自定义锁的情况下调用这些函数，而另一个线程在持有另一个锁的情况下也调用这些函数，就可能在库函数内部产生死锁。

```c
/* 线程 1 */
pthread_mutex_lock(&lock_a);
malloc(1024);     /* 内部获取 arena_lock */
/* ... */
free(ptr);
pthread_mutex_unlock(&lock_a);

/* 线程 2 */
pthread_mutex_lock(&lock_b);
malloc(2048);     /* 内部获取同一个 arena_lock */
pthread_mutex_unlock(&lock_b);

/* 死锁条件：线程 1 持有 lock_a 等待 arena_lock，
   线程 2 持有 lock_b 等待 arena_lock（但这不会死锁，因为 arena_lock 是同一个） */

/* 真正的危险场景： */
/* 线程 1 */
pthread_mutex_lock(&lock_a);
printf("hello");     /* 获取 stdout_lock */
pthread_mutex_unlock(&lock_a);

/* 线程 2 */
pthread_mutex_lock(&lock_a);   /* 或先获取 stdout_lock 再 lock_a */
fprintf(stderr, "world");     /* 获取 stderr_lock → 如果 stderr 和 stdout 共享 buffer */
```

**避坑**：
- 避免在持有自定义锁时调用可能内部加锁的库函数
- 使用线程安全的库函数（如 `malloc` 的 per-thread Arena，glibc 的 `MALLOC_ARENA_TEST` 环境变量可测试）
- 对 I/O 操作使用 per-thread 缓冲区，避免共享全局 I/O 状态

### 5.4 Docker/容器环境死锁

**问题**：在容器环境中，cgroup 的 CPU 和内存限制可能导致隐蔽的死锁场景：

- **内存限制**：容器内存限制过低，触发 OOM Killer 终止进程，但如果进程持有锁并被终止，其他等待该锁的进程永远阻塞
- **CPU 限制**：cgroup `cpu.cfs_quota_us` 限制容器 CPU 时间，当所有 CPU 配额用完时，持有锁的线程无法被调度释放锁
- **Docker 守护进程死锁**：Docker Engine 自身的锁机制在高并发容器操作时可能死锁

```bash
# 检查容器资源限制
docker inspect <container> | grep -A5 "CpuQuota\|Memory"

# 检测容器内死锁（进程卡在 D 状态）
docker exec <container> ps aux | grep " D "
cat /proc/<pid>/status | grep -i "state\|wait"

# 检查 cgroup CPU 限制
cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us
cat /sys/fs/cgroup/cpu/cpu.cfs_period_us
```

**避坑**：
- 容器内合理设置内存和 CPU 限制，预留足够余量
- 使用 `pthread_mutex_timedlock` 而非 `pthread_mutex_lock`，在超时后触发告警
- 在容器健康检查中检测进程是否卡在不可中断状态（`D` 状态）
- Docker 引擎层面：避免在高并发场景下同时操作大量容器

### 5.6 常见陷阱汇总

| 陷阱 | 症状 | 根因 | 解决方案 |
|------|------|------|----------|
| AB-BA 顺序锁 | 程序偶发挂起 | 两个线程以相反顺序获取两把锁 | 统一锁获取全局顺序 |
| 锁嵌套过深 | 高并发下频繁挂起 | 多把锁嵌套导致锁链过长 | 减少锁粒度、使用细粒度锁 |
| 信号处理函数加锁 | 信号处理后程序挂起 | 信号处理函数获取了已被主程序持有的锁 | 信号处理函数中只设置标志位 |
| read-modify-write 无原子性 | 数据不一致 | 先读后写不原子 | 使用 CAS 或锁保护整个 RMW 操作 |
| 资源泄漏导致锁不释放 | 程序逐渐变慢直至挂起 | 异常路径未释放锁 | 使用 RAII/defer/`__attribute__((cleanup))` |

## 6. 知识关联

### 6.1 与同步原语的关系

死锁本质上是同步原语使用不当的后果。在 [[08-同步原语：互斥锁自旋锁信号量条件变量]] 中我们学习了互斥锁、自旋锁、信号量等同步原语的基本使用和正确性保证。死锁是互斥锁的"进展性"性质被破坏的结果——当多个互斥锁的获取形成环路时，所有相关线程都无法推进。理解死锁的四个条件是正确使用同步原语的前提。

### 6.2 与进程模型的关系

死锁发生在进程（或线程）之间。在 [[01-进程本质：PCB结构与进程创建流程]] 中我们了解了 PCB 中的状态字段——当进程因等待资源而阻塞时，其 PCB 状态从 `TASK_RUNNING` 变为 `TASK_UNINTERRUPTIBLE`（不可中断等待），这正是死锁进程的典型状态。内核的 `hung_task_detector` 就是通过检测长时间处于 `TASK_UNINTERRUPTIBLE` 状态的进程来发现潜在死锁。

### 6.3 与进程间通信的关系

进程间通信（IPC）也是死锁的常见来源。在 [[06-进程间通信：管道消息队列共享内存信号]] 中，管道和消息队列的阻塞读写可能导致通信死锁——例如进程 A 管道写入 100 字节但管道缓冲区只有 64 字节，而进程 B 在等待 A 先发送消息。共享内存虽然不涉及阻塞，但共享内存上的同步原语（如 POSIX semaphore）同样可能引发死锁。

### 6.4 与调度器的关系

调度策略直接影响死锁的检测与恢复。在 [[02-调度算法：从时间片轮转到CFS与EEVDF]] 中，CFS 调度器的虚拟运行时间（vruntime）决定了进程的调度顺序——高优先级的死锁进程可能获得更多 CPU 时间，但这并不能解决死锁（因为死锁进程不会主动释放资源）。饥饿问题与调度器的公平性策略密切相关。
