## 1. 概述

进程间通信（IPC, Inter-Process Communication）是操作系统提供的一组机制，用于让多个**地址空间相互隔离**的进程交换数据、发送事件通知、以及实现同步与互斥。因为现代操作系统强制进程隔离（各自的页表、各自的虚拟地址空间），进程之间不能像线程那样直接共享栈上的变量，必须借助内核托管的 IPC 通道。

IPC 的本质问题是**在隔离与共享之间架桥**：既要保证一个进程崩溃不拖垮另一个进程（隔离），又要能高效地把数据从一个进程传过去（共享）。

| IPC 机制 | 数据流方向 | 是否需要同步 | 传输单位 | 数据量级 | 典型速度 |
|----------|-----------|--------------|----------|----------|----------|
| 匿名管道 pipe | 单向 | 内核自动 | 字节流 | 小~中 | 中 |
| 命名管道 FIFO | 单向 | 内核自动 | 字节流 | 小~中 | 中 |
| 信号 signal | 单向 | 不需 | 事件号 | 极小小 | 快 |
| 信号量 semaphore | 无数据 | 是（自身即同步） | 计数值 | 无需 | 快 |
| 消息队列 message queue | 双向 | 部分 | 消息块 | 小~中 | 中 |
| 共享内存 shared memory | 双向 | **需自配锁** | 任意内存 | 最大 | **最快** |
| Unix 域套接字 AF_UNIX | 双向 | 内核自动 | 字节流/报文 | 中~大 | 快 |
| 网络 Socket | 双向 | 内核自动 | 字节流/报文 | 任意 | 慢（跨机） |

按数据复制次数划分，开销从小到大依次为：

```text
共享内存   ≈ 0 次内核复制（mmap 直接映射）
消息队列   ≈ 2 次（写者→内核、内核→读者）
管道        ≈ 2 次（写端→内核缓冲、内核缓冲→读端）
Socket     ≈ 2~多次（TCP 可能分段）
信号        ≈ 1 次（但只能传递事件号，不能带大数据）
```

共享内存之所以"最快"，本质是它通过 mmap 把同一物理页映射进多个进程的地址空间，**省去了用户态↔内核态的多次数据拷贝**。代价是：内核不帮你同步，读写竞争必须自己用互斥锁/信号量保护——这正是 [[08-同步原语：互斥锁自旋锁信号量条件变量]] 所讨论的主题。

本节把 IPC 分为三类讲述：**基于字节流/消息的**（管道、消息队列、Socket）、**基于事件通知的**（信号）、**基于内存共享的**（共享内存，配合同步原语）。理解每种 IPC 的"复制次数"与"是否需要手工同步"，就能在写代码时做出正确的性能与复杂度权衡。

## 2. 核心原理

### 2.1 管道（Pipe）的本质：内核中的环形缓冲区

匿名管道（anonymous pipe）由 `pipe()` 系统调用创建，返回一对文件描述符（fd）：`fd[0]` 是读端，`fd[1]` 是写端。

```text
进程 A                     内核                       进程 B
        fd[1] ──写──▶ ┌──────────────────┐ ──读──▶ fd[0]
                      │  环形缓冲区 buffer │
                      │  (默认 64KB)        │
                      └──────────────────┘
        write(fd[1], data)        read(fd[0], data)
```

- Linux 上管道缓冲区默认 64KB（`/proc/sys/fs/pipe-max-size` 可调，最大 1MB）。
- `PIPE_BUF`（POSIX 定义，Linux 为 4096 字节）：**对 pipe 的 `write` 小于等于 PIPE_BUF 时是原子的**——多进程写管道不会把一条消息截断交错。
- `write` 端在管道满时会阻塞（除非设置 O_NONBLOCK）；`read` 端在管道空时会阻塞。

**pipe 的典型陷阱**：父进程 fork 后若不在父写、子在读的模式下各自关闭多余端，管道将无法正常工作。经典范式是"父写子读"，父进程关闭 fd[0]，子进程关闭 fd[1]。

```c
#include <unistd.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>

int main(void) {
    int fd[2];
    if (pipe(fd) < 0) { perror("pipe"); return 1; }

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }

    if (pid == 0) {                    /* 子进程：读 */
        close(fd[1]);                  /* 关掉写端 */
        char buf[1024];
        ssize_t n = read(fd[0], buf, sizeof(buf));
        if (n > 0) {
            buf[n] = '\0';
            printf("子进程收到: %s\n", buf);
        }
        close(fd[0]);
        return 0;
    } else {                           /* 父进程：写 */
        close(fd[0]);                  /* 关掉读端 */
        const char *msg = "Hello via pipe!";
        write(fd[1], msg, strlen(msg));
        close(fd[1]);
        wait(NULL);                    /* 等子进程结束 */
    }
    return 0;
}
```

**为什么 fork 之后要 close 不必要的端？** 管道是否关闭以"所有副本"为准。父、子各有 fd[0]、fd[1] 两个副本。若不关闭，即使父只写、子只读，写端仍有两个副本存在，读端读到 EOF 的条件（所有读端关闭）也难满足，导致读端阻塞或 EOF 判断错误。

### 2.2 命名管道（FIFO）

`mkfifo` 在文件系统中创建一个 FIFO 特殊文件，允许**无亲缘关系**的进程通过路径名通信。

```bash
$ mkfifo /tmp/myfifo
```

- FIFO 是文件系统中的一个名字，但数据**不落盘**，只在内核缓冲区流动。
- 默认行为：**打开 FIFO 读会阻塞，直到有写者打开；打开写也会阻塞，直到有读者打开**。可以用 `O_RDWR` 或 `O_NONBLOCK` 调整。

```c
/* 读进程 read_fifo.c */
#include <unistd.h>
#include <fcntl.h>
#include <stdio.h>
int main(void) {
    int fd = open("/tmp/myfifo", O_RDONLY);   /* 阻塞到写者出现 */
    char buf[256]; ssize_t n;
    while ((n = read(fd, buf, sizeof(buf))) > 0)
        write(1, buf, n);
    close(fd);
    return 0;
}
```

```bash
$ ./read_fifo &           # 后台读
$ echo "来自 shell 的数据" > /tmp/myfifo   # 写者
```

### 2.3 信号（Signal）：只携带事件号的通知

信号是异步事件通知机制：内核或进程向目标进程/线程发送一个小整数（信号号），目标在到达安全点后执行默认动作或自定义处理函数。

常用信号：

| 信号 | 编号 | 默认动作 | 含义 |
|------|------|----------|------|
| SIGTERM | 15 | 终止 | 优雅终止，可捕获 |
| SIGKILL | 9 | 立即终止 | 不可捕获、不可阻塞 |
| SIGCHLD | 17 | 忽略 | 子进程状态改变 |
| SIGUSR1/2 | 10/12 | 终止 | 用户自定义 |
| SIGINT | 2 | 终止 | Ctrl+C |
| SIGSEGV | 11 | 终止+core | 段错误 |
| SIGALRM | 14 | 终止 | 定时器到期 |
| SIGSTOP/SIGCONT | 19/18 | 停止/继续 | 作业控制 |

关键 API 区别：

```c
/* 老的 signal()（行为可能随 glibc 变） */
signal(SIGINT, handler);

/* 推荐的 sigaction()：可指定要阻塞的信号、恢复语义 */
struct sigaction sa;
sa.sa_handler = handler;
sigemptyset(&sa.sa_mask);           /* handler 执行期间额外屏蔽的信号 */
sa.sa_flags = SA_RESTART;           /* 被中断的系统调用自动重启 */
sigaction(SIGINT, &sa, NULL);
```

**信号不可靠（unreliable signals）**：非实时信号（1~31）不排队，多次相同信号只投递一次，可能被合并/丢失。**实时信号**（SIGRTMIN=34 ~ SIGRTMAX=64）**排队且有额外数据载荷**（`sigqueue` + `siginfo_t`），是可靠的。

**经典坑**：信号处理函数在"不可重入的上下文"中被异步打断。处理函数应只做 `volatile sig_atomic_t` 赋值，真正的业务逻辑放到主循环（self-pipe / eventfd）里做，否则若 handler 中调用 printf/malloc 等非 async-signal-safe 函数，可能死锁或破坏堆。可重入安全函数列表见 `signal-safety(7)`。

### 2.4 System V IPC 三件套

System V IPC 以"标识符（id）+ key 键"管理，属于**有力的旧式**机制，提供消息队列、信号量、共享内存。

| 功能 | System V API | POSIX API |
|------|--------------|-----------|
| 共享内存 | `shmget`/`shmat`/`shmdt` | `shm_open` + `mmap` |
| 消息队列 | `msgget`/`msgsnd`/`msgrcv` | `mq_open`/`mq_send`/`mq_receive` |
| 信号量 | `semget`/`semop` | `sem_open`/`sem_wait`/`sem_post` |

System V 共享内存示例：

```c
#include <sys/ipc.h>
#include <sys/shm.h>
#include <stdio.h>
#include <string.h>

#define KEY 1234
#define SIZE 1024

int main(void) {
    /* 创建/获取一块共享内存 */
    int shmid = shmget(KEY, SIZE, IPC_CREAT | 0666);
    /* 附加到本进程地址空间 */
    char *p = shmat(shmid, NULL, 0);
    strcpy(p, "写入共享内存的数据");        /* 直接写入 */
    /* 分离 */
    shmdt(p);
    /* 用后最好清理（详见坑点） */
    shmctl(shmid, IPC_RMID, NULL);
    return 0;
}
```

**System V 的缺点**：资源不随进程退出自动释放，必须显式 `ipcrm` 或 `shmctl(IPC_RMID)` 清理；API 偏老、键（key）管理繁琐、对象是内核全局的唯一 id。POSIX IPC 用路径名 + 文件语义，更符合 Unix 习惯，且 `mmap` 共享内存更灵活（可设置大小、映射可读写）。

### 2.5 POSIX IPC 与 mmap 共享内存

**共享内存是速度最快的 IPC**，因为数据不经过内核复制：

```text
传统管道/消息队列： 写者 ──▶ 内核缓冲 ──▶ 读者      （2 次拷贝）
共享内存 mmap：     写者 ──────▶ 同一物理页 ◀───── 读者（0 次拷贝）
                         ↑ 各自通过页表映射到该物理页
```

POSIX 共享内存 `shm_open` 创建一个共享内存对象，配合 `mmap` 映射：

```c
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

#define SIZE 4096

int main(void) {
    /* 创建共享内存对象 */
    int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0666);
    ftruncate(fd, SIZE);                       /* 设定大小 */
    char *p = mmap(NULL, SIZE, PROT_READ | PROT_WRITE,
                   MAP_SHARED, fd, 0);         /* 映射 */
    strcpy(p, "POSIX 共享内存数据");

    /* 读者进程用同样的 "/myshm" 也能映射到同一物理页 */
    msync(p, SIZE, MS_SYNC);                   /* 可选，刷回 */
    munmap(p, SIZE);
    shm_unlink("/myshm");                      /* 用完解除 */
    close(fd);
    return 0;
}
```

> **重要**：共享内存本身**不做任何同步**。两个进程同时写会导致数据竞争。必须配合 [[08-同步原语：互斥锁自旋锁信号量条件变量]] 中的互斥锁/信号量来保护临界区。这也是"共享内存快但对程序员要求高"的根本原因。

### 2.6 Unix 域套接字（AF_UNIX）

Unix 域套接字（Unix domain socket）是进程间通信中功能最全、最易用的机制之一。它提供的语义与网络 TCP/UDP 几乎一致，但**无需 IP 协议栈、不跨网络、可靠性由内核保证**，因此性能远高于本地 TCP。

| 维度 | AF_UNIX | AF_INET（TCP loopback） |
|------|---------|-------------------------|
| 协议处理 | 无需 IP/TCP 栈 | 需要完整协议栈 |
| 可靠传输 | 内核直接交付 | TCP 重传/拥塞控制 |
| 地址形式 | 文件路径 `/tmp/sock` | IP:port |
| SOCK_STREAM（流） | 字节流，双向 | 字节流，双向 |
| SOCK_DGRAM（数据报） | 报文，双向，**可靠且有序** | 报文，双向，**可能丢包** |

示例——AF_UNIX SOCK_STREAM 服务端：

```c
#include <sys/socket.h>
#include <sys/un.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>

int main(void) {
    int sfd = socket(AF_UNIX, SOCK_STREAM, 0);
    struct sockaddr_un addr;
    memset(&addr, 0, sizeof(addr));
    addr.sun_family = AF_UNIX;
    strcpy(addr.sun_path, "/tmp/echo.sock");
    unlink("/tmp/echo.sock");
    bind(sfd, (struct sockaddr *)&addr, sizeof(addr));
    listen(sfd, 8);

    int cfd = accept(sfd, NULL, NULL);
    char buf[256];
    ssize_t n = read(cfd, buf, sizeof(buf));
    write(cfd, buf, n);              /* 原样回显 */
    close(cfd); close(sfd);
    unlink("/tmp/echo.sock");
    return 0;
}
```

**为什么选 AF_UNIX 而不是共享内存？** 共享内存最快但不自动同步；AF_UNIX 由内核保证字节流的正确性与同步，开发者无锁、无竞争，适合"消息模式"的请求/响应，兼顾性能与安全。现代高并发框架（如 nginx upstream、Redis Cluster、Docker socket）都大量用 AF_UNIX/pipe 做本地通信。

## 3. 详细知识点

### 3.1 IPC 的选型决策树

```text
需要传递数据吗？
├── 只需要事件/状态通知 → 信号（signal）或 eventfd
└── 需要传递数据
    ├── 数据量大、性能敏感、可接受自管同步 → 共享内存 + 互斥锁/信号量
    ├── 需要可靠的"消息/请求-响应"语义 → Unix 域套接字 / 网络 Socket
    ├── 简单单向字节流 → 匿名管道 / 命名管道
    └── 需要消息边界与优先级 → 消息队列（POSIX/System V）
需要同步互斥（无数据）？ → 信号量 / 互斥锁（POSIX sem / pthread_mutex）
```

### 3.2 信号量（Semaphore）：初值即资源数

信号量是一种计数同步原语，无需传递数据，只维护一个计数值（PV 操作）：

- **P（Proberen/等待）**：`sem_wait`——计数值减 1，若为负则阻塞等待资源。
- **V（Verhogen/释放）**：`sem_post`——计数值加 1，若可能唤醒等待者。

POSIX 命名信号量：

```c
#include <semaphore.h>
#include <fcntl.h>
#include <unistd.h>

sem_t *sem = sem_open("/mysem", O_CREAT, 0666, 1); /* 初值 1 */
sem_wait(sem);      /* P：占用 */
/* ... 临界区 ... */
sem_post(sem);      /* V：释放 */
sem_close(sem);
```

**二值信号量 vs 互斥锁**：初值为 1 的信号量行为类似互斥锁，但有区别——**互斥锁只能由持有者释放（ownership），信号量可由任意进程/线程释放**。所以互斥锁用于保护临界区（有 owner 约束），信号量更常用于"计数资源池"（如限制并发连接数），或生产者-消费者的定长缓冲。

### 3.3 消息队列：带边界的消息块

消息队列在管道"字节流"基础上增加了**消息边界**：每条消息是独立单元，有类型、长度。`msgrcv` 可按 `msgtyp` 选取消息。

```c
struct msgbuf {
    long mtype;      /* 消息类型 >0 */
    char mtext[100];
};
/* 发送 */
msgsnd(msgid, &msg, sizeof(msg.mtext), 0);
/* 按类型接收（mtype=2 取类型为 2 的消息） */
msgrcv(msgid, &msg, sizeof(msg.mtext), 2, 0);
```

**适用场景**：需要在消息级别做解耦、按类型/优先级分发、可持久恢复的场合。性能低于共享内存，但高于每次都要传递大块数据的管道。现代 Linux 用 POSIX 消息队列（`mq_open`）更推荐，支持优先级与超时（`mq_timedreceive`）。

### 3.4 各类 IPC 的内核实现要点

| 机制 | 内核实现 |
|------|----------|
| 管道 | `fs/pipe.c`：环形缓冲 + 两个 end，读写在两个 file 上 |
| 信号 | `kernel/signal.c`：每个任务有 pending 信号位图 + 处理函数表 |
| System V 共享内存 | `ipc/shm.c`：shm 段 + shmid；多个进程 attach 到同一物理页 |
| System V 消息队列 | `ipc/msg.c`：链表式消息 + msg_qbytes 上限 |
| System V 信号量 | `ipc/sem.c`：sem array with undo logs |
| POSIX 共享内存 | `mm/shmem.c`：tmpfs 上的文件，mmap 共享 |
| Unix 套接字 | `net/unix/af_unix.c`：内核内存中直接拷贝 |

### 3.5 与 Socket 网络通信的关系

IPC 与 Socket 的边界：Socket 面向"不一定同机的"进程通信（AF_INET 可跨机）；AF_UNIX/pipe/mmap 面向"同机"进程。跨机器只能走网络套接字（TCP/UDP），无法直接用共享内存。本组的 [[06-进程间通信]] 与 [[07-Socket通信模型与epoll实现机制]] 本属同族：网络服务进程之间的通信既用 TCP socket（跨机），也用 AF_UNIX/shmem（同机高性能）。

## 4. 实战与示例

### 4.1 mmap 共享内存 + 互斥锁（正确同步的姿势）

```c
#include <pthread.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

typedef struct {
    pthread_mutex_t lock;   /* 进程共享互斥锁 */
    int counter;
} Shared;

#define SIZE (sizeof(Shared))

int main(void) {
    int fd = shm_open("/shmctr", O_CREAT | O_RDWR, 0666);
    ftruncate(fd, SIZE);
    Shared *s = mmap(NULL, SIZE, PROT_READ | PROT_WRITE,
                     MAP_SHARED, fd, 0);

    /* 初始化进程共享锁；否则映射多次后锁未初始化会失败 */
    pthread_mutexattr_t mat;
    pthread_mutexattr_init(&mat);
    pthread_mutexattr_setpshared(&mat, PTHREAD_PROCESS_SHARED);
    pthread_mutex_init(&s->lock, &mat);

    /* 临界区：加锁 + 修改 + 解锁 */
    pthread_mutex_lock(&s->lock);
    s->counter++;
    pthread_mutex_unlock(&s->lock);

    printf("counter = %d\n", s->counter);
    munmap(s, SIZE);
    shm_unlink("/shmctr");
    return 0;
}
```

要点：**PTHREAD_PROCESS_SHARED** 属性让互斥锁可跨进程使用；多个进程 mmap 同一 block 时共享同一把锁，从而保护共享内存的临界区。

### 4.2 Unix 域套接字做"文件传输"

```c
/* writer：读文件 → AF_UNIX 发送 */
#include <sys/socket.h>
#include <sys/un.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>

int main(void) {
    int sock = socket(AF_UNIX, SOCK_STREAM, 0);
    struct sockaddr_un addr = {.sun_family = AF_UNIX};
    strcpy(addr.sun_path, "/tmp/transfer.sock");
    connect(sock, (struct sockaddr *)&addr, sizeof(addr));

    int fdin = open("source.bin", O_RDONLY);
    char buf[4096]; ssize_t n;
    while ((n = read(fdin, buf, sizeof(buf))) > 0)
        write(sock, buf, n);              /* 流式发送 */
    close(sock); close(fdin);
    return 0;
}
```

对端用相同 socket 路径 `accept` 后循环 `read` 写入目标文件即可。AF_UNIX SOCK_STREAM 保证"写入有序、不丢包"，非常适合本机的可靠大文件/大数据流。

### 4.3 信号 + eventfd（异步通知的现代实践）

传统 self-pipe 用 pipe 传递信号；现代 Linux 推荐 **eventfd**：信号 handler 只需写入一个 8 字节计数，主循环用 read/epoll 消费，避免 sigaction handler 中做危险操作。

```c
#include <sys/eventfd.h>
#include <signal.h>
#include <unistd.h>
#include <stdio.h>

static int efd;

static void handler(int sig) {
    uint64_t one = 1;
    write(efd, &one, 8);      /* 信号到达→仅通知计数器 */
}

int main(void) {
    efd = eventfd(0, 0);
    struct sigaction sa = {.sa_handler = handler};
    sigaction(SIGUSR1, &sa, NULL);

    while (1) {
        uint64_t cnt;
        ssize_t n = read(efd, &cnt, 8);   /* 阻塞等通知 */
        if (n == 8) {
            printf("收到 %llu 次信号\n", (unsigned long long)cnt);
            if (cnt >= 3) break;
        }
    }
    return 0;
}
```

## 5. 常见坑与避坑指南

### 坑 1：信号不可靠——被中断的系统调用（EINTR）

**症状**：进程收信号后，慢速系统调用（read/write/epoll_wait）莫名返回 -1，errno=EINTR。

**根因**：信号 delivery 打断阻塞的系统调用，且未设置 SA_RESTART。

**解决**：`sigaction` 置 `SA_RESTART` 标志自动重启大多数调用；或在代码里循环处理 EINTR：

```c
ssize_t r;
do {
    r = read(fd, buf, n);
} while (r < 0 && errno == EINTR);
```

### 坑 2：System V 残留资源未清理

**症状**：`ipcs -m` 显示大量残留共享内存段；新进程 `shmget` 报 `ENOMEM`/`EIDRM` 冲突。

**根因**：System V 资源是内核全局对象，进程崩溃/退出后**不会自动销毁**。

**解决**：用 `ipcrm` 或 `shmctl(IPC_RMID)` 显式清理；或用 POSIX `shm_unlink` 配合文件语义；必要时用 `IPC_CREAT|IPC_EXCL` 防止误用旧键。

```bash
$ ipcs -m          # 查看
$ ipcrm -m <shmid> # 删除指定共享内存段
```

### 坑 3：共享内存竞争条件（Race Condition）

**症状**：两个进程同时写共享缓冲，数据出现半个/乱序；读取越界崩溃。

**根因**：共享内存**无内建同步**，多个进程直接在物理页上竞争。

**解决**：必须用跨进程互斥锁（`PTHREAD_PROCESS_SHARED`）或信号量包裹整体临界区；读写都加锁；用 `volatile`/memory barrier 保证可见性。

### 坑 4：管道/套接字阻塞导致的死锁与半关闭

**症状**：写端一直 write 而读端不 read，写端永久阻塞（管道满）；或对端已关闭却继续写得到 SIGPIPE 进程被杀。

**根因**：管道缓冲有限；SIGPIPE 默认终止进程。

**解决**：读写方约定关闭时机；给端设置 `O_NONBLOCK` 或超时（socket `SO_RCVTIMEO`）；捕获 SIGPIPE（`signal(SIGPIPE, SIG_IGN)`）并检查 write 返回值。

### 坑 5：Docker/容器内共享内核的 IPC 泄漏

**症状**：容器退出但共享内存/消息队列仍占用宿主机 IPC 资源。

**根因**：容器共享宿主机内核，System V IPC 命名空间（`IPCNAMESPACE`）若未隔离或未清理，资源会在宿主机残留。

**解决**：合理设置容器的 IPC 命名空间隔离；应用退出时主动清理 IPC 资源；用 `ipcs`/`ipcrm` 在宿主机巡检。
