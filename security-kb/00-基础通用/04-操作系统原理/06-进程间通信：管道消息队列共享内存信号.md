## 1. 概述

进程间通信（IPC, Inter-Process Communication）是操作系统提供的一组机制，用于让多个**地址空间相互隔离**的进程交换数据、发送事件通知、以及实现同步与互斥。因为现代操作系统强制进程隔离（各自的页表、各自的虚拟地址空间），进程之间不能像线程那样直接共享栈上的变量，必须借助内核托管的 IPC 通道。

IPC 的本质问题，是**在隔离与共享之间架桥**：既要保证一个进程崩溃不拖垮另一个进程（隔离），又要能高效地把数据从一个进程传过去（共享）。把这个矛盾放平，就构成了"速度"与"安全"的权衡——越快的机制（共享内存）越需要程序员自己负责正确性，越安全的机制（Socket/管道）越慢。

| IPC 机制 | 数据流方向 | 是否需要同步 | 传输单位 | 数据量级 | 典型速度 |
|----------|-----------|--------------|----------|----------|----------|
| 匿名管道 pipe | 单向 | 内核自动 | 字节流 | 小~中 | 中 |
| 命名管道 FIFO | 单向 | 内核自动 | 字节流 | 小~中 | 中 |
| 信号 signal | 单向 | 不需 | 事件号 | 极小 | 快 |
| 信号量 semaphore | 无数据 | 是（自身即同步） | 计数值 | 无 | 快 |
| 消息队列 message queue | 双向 | 部分 | 消息块 | 小~中 | 中 |
| 共享内存 shared memory | 双向 | **需自配锁** | 任意内存 | 最大 | **最快** |
| Unix 域套接字 AF_UNIX | 双向 | 内核自动 | 字节流/报文 | 中~大 | 快 |
| 网络 Socket | 双向 | 内核自动 | 字节流/报文 | 任意 | 慢（跨机） |

按"数据被复制几次"划分，开销从小到大依次为：

```text
共享内存      ≈ 0 次内核复制（mmap 直接映射物理页）
消息队列      ≈ 2 次（写者→内核、内核→读者）
管道           ≈ 2 次（写端→内核缓冲→读端）
Socket        ≈ 2 次以上（TCP 可能分段重组）
信号           ≈ 0 次（只能传递事件号，不能带大数据）
```

共享内存之所以"最快"，本质是它通过 mmap 把同一物理页映射进多个进程的地址空间，**省去了用户态↔内核态的多轮数据拷贝**。代价是：内核不帮你同步，读写竞争必须自己用互斥锁/信号量保护——这正是 [[08-同步原语：互斥锁自旋锁信号量条件变量]] 所讨论的主题。换句话说：**共享内存把"正确性"的部分责任交给了程序员，把"性能"还给了程序员。**

从 Unix 哲学看，IPC 机制遵循两条主线：

1. **字节流线路**（管道 → 命名管道 → Socket）：数据是一条没有边界的流，内核保证读写有序，API 统一为 read/write。
2. **消息线路**（信号 → 消息队列 → 事件fd）：每次传输一个"事件"或"报文"，带边界、可排队。

任何真实系统（nginx、PostgreSQL、Docker、数据库连接池）的进程间协作，几乎都是这两种线路的组合。本节把 IPC 分三类讲述：**基于字节流/消息的**（管道、消息队列、Socket）、**基于事件通知的**（信号）、**基于内存共享的**（共享内存，配合同步原语）。理解每种 IPC 的"复制次数"与"是否需要手工同步"，就能在写代码时做出正确的性能与复杂度权衡。

## 2. 核心原理

### 2.1 匿名管道（pipe）的本质：内核中的环形缓冲区

匿名管道（anonymous pipe）由 `pipe()` 系统调用创建，返回一对文件描述符（fd）：`fd[0]` 是读端，`fd[1]` 是写端。

```text
进程 A                      内核                    进程 B
        fd[1] ──写──▶ ┌──────────────────┐ ──读──▶ fd[0]
                      │  环形缓冲区 buffer │
                      │  (默认 64KB)       │
                      └──────────────────┘
        write(fd[1], data)          read(fd[0], data)
```

- Linux 上管道缓冲区默认 64KB（`/proc/sys/fs/pipe-max-size` 可调，最大 1MB）。
- **PIPE_BUF**（POSIX 定义，Linux 为 4096 字节）：对 pipe 的 `write` 长度**小于等于 PIPE_BUF 时是原子的**——多个进程同时写管道，不会把一条消息截断交错。超过 PIPE_BUF 的写可能与其他写者交错分片。
- `write` 端在管道满时阻塞（除非 O_NONBLOCK 且 EAGAIN）；`read` 端在管道空时阻塞。

```c
#include <unistd.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>

int main(void) {
    int fd[2];
    if (pipe(fd) < 0) { perror("pipe"); return 1; }

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }

    if (pid == 0) {                    /* 子进程：读 */
        close(fd[1]);                  /* 关掉写端 */
        char buf[1024];
        ssize_t n = read(fd[0], buf, sizeof(buf));
        if (n > 0) {
            buf[n] = '\0';
            printf("子进程收到: %s\n", buf);
        }
        close(fd[0]);
        return 0;
    } else {                           /* 父进程：写 */
        close(fd[0]);                  /* 关掉读端 */
        const char *msg = "Hello via pipe!";
        write(fd[1], msg, strlen(msg));
        close(fd[1]);
        wait(NULL);                    /* 等子进程结束 */
    }
    return 0;
}
```

**为什么 fork 之后要 close 不必要的端？** 管道的读写端"到 EOF/满"以"所有副本都被关闭"为准。父、子各有 fd[0]、fd[1] 两个副本。若不关闭，即使父只写、子只读，写端仍存在两个副本。此时一旦写方全部退出（包括残留副本），读端才能读到 EOF；残留写端副本没关，读端将永远阻塞在"等数据"而非"等 EOF"上——这是 fork+pipe 最经典的死锁来源。

### 2.2 命名管道（FIFO）：无亲缘进程也通信

`mkfifo` 在文件系统中创建一个 FIFO 特殊文件，允许**无亲缘关系**的进程通过路径名通信。

```bash
$ mkfifo /tmp/myfifo
```

- FIFO 是文件系统中的一个名字，但数据**不落盘**，只在内核缓冲区流动。
- 默认行为：**打开 FIFO 读端会阻塞，直到有写者打开；打开写端也会阻塞，直到有读者打开**。可以用 `O_RDWR` 回避这个握手，或用 `O_NONBLOCK` 让 open 立即返回。

```c
/* 读进程 read_fifo.c */
#include <unistd.h>
#include <fcntl.h>
#include <stdio.h>
int main(void) {
    int fd = open("/tmp/myfifo", O_RDONLY);   /* 阻塞到写者出现 */
    char buf[256]; ssize_t n;
    while ((n = read(fd, buf, sizeof(buf))) > 0)
        write(1, buf, n);
    close(fd);
    return 0;
}
```

```bash
$ ./read_fifo &           # 后台读
$ echo "来自 shell 的数据" > /tmp/myfifo   # 写者
```

**FIFO 与匿名管道的区别**：匿名管道只能由"fork 产生的亲缘进程"使用；FIFO 通过路径名可为任意进程服务，常用于系统日志管道路径、守护进程间告警等。它们都是"单向字节流"，区别只在"如何命名/获取"。

### 2.3 信号（Signal）：只携带事件号的通知

信号是异步事件通知机制：内核或进程向目标进程/线程发送一个小整数（信号号），目标在到达安全点后执行默认动作或自定义处理函数。

常用信号：

| 信号 | 编号 | 默认动作 | 含义 |
|------|------|----------|------|
| SIGTERM | 15 | 终止 | 优雅终止，可捕获 |
| SIGKILL | 9 | 立即终止 | 不可捕获、不可阻塞 |
| SIGCHLD | 17 | 忽略 | 子进程状态改变 |
| SIGUSR1/2 | 10/12 | 终止 | 用户自定义 |
| SIGINT | 2 | 终止 | Ctrl+C |
| SIGSEGV | 11 | 终止+core | 段错误 |
| SIGALRM | 14 | 终止 | 定时器到期 |
| SIGSTOP/SIGCONT | 19/18 | 停止/继续 | 作业控制 |

关键 API 区别（**signal() 与 sigaction()**）：

```c
/* 老的 signal()（行为在 Linux/glibc 下依赖标志，语义不一） */
signal(SIGINT, handler);

/* 推荐的 sigaction()：可指定屏蔽集、恢复语义 */
struct sigaction sa;
sa.sa_handler = handler;
sigemptyset(&sa.sa_mask);           /* handler 执行期间额外屏蔽的信号 */
sa.sa_flags = SA_RESTART;           /* 被中断的系统调用自动重启 */
sigaction(SIGINT, &sa, NULL);
```

**信号不可靠**：非实时信号（1~31）**不排队**，多次相同信号只投递一次，可能被合并/丢失。**实时信号**（SIGRTMIN=34 起，到 SIGRTMAX=64）**排队**且可携带数据（通过 `sigqueue()` + `siginfo_t`），可靠。因此业务级"事件通知"应该用实时信号或 eventfd，而不是普通信号。

**经典坑**：信号处理函数在"不可重入的上下文"中被异步打断。处理函数应只做 `volatile sig_atomic_t` 赋值或写 eventfd，真正的业务逻辑放到主循环做；在 handler 中调用 printf/malloc/lock 等**非 async-signal-safe** 函数可能死锁或破坏堆。可重入安全函数清单见 `signal-safety(7)`。

### 2.4 System V IPC 三件套

System V IPC 以"标识符（id）+ key（键）"管理，属于**老而有力**的机制，提供消息队列、信号量、共享内存三类对象。

| 功能 | System V API | POSIX API |
|------|--------------|-----------|
| 共享内存 | `shmget`/`shmat`/`shmdt` | `shm_open` + `mmap` |
| 消息队列 | `msgget`/`msgsnd`/`msgrcv` | `mq_open`/`mq_send`/`mq_receive` |
| 信号量 | `semget`/`semop` | `sem_open`/`sem_wait`/`sem_post` |

System V 共享内存示例：

```c
#include <sys/ipc.h>
#include <sys/shm.h>
#include <stdio.h>
#include <string.h>

#define KEY 1234
#define SIZE 1024

int main(void) {
    int shmid = shmget(KEY, SIZE, IPC_CREAT | 0666);  /* 创建/获取 */
    char *p = shmat(shmid, NULL, 0);                  /* 附加到本进程地址空间 */
    strcpy(p, "写入共享内存的数据");                    /* 直接写入 */
    shmdt(p);                                          /* 分离 */
    shmctl(shmid, IPC_RMID, NULL);                     /* 删除资源 */
    return 0;
}
```

**System V 的缺点**：资源不随进程退出自动释放，必须显式 `ipcrm` 或 `shmctl(IPC_RMID)` 清理（进程崩溃后总会遗留）；键（key）管理繁琐；API 偏老。POSIX IPC 用路径名 + 文件语义，更符合 Unix 习惯，且 `mmap` 映射更灵活。

### 2.5 POSIX 共享内存与 mmap 原理

**共享内存是速度最快的 IPC**，因为数据不经过内核复制：

```text
传统管道/消息队列：写者 ──▶ 内核缓冲 ──▶ 读者    （2 次拷贝）
共享内存 mmap：    写者──────▶ 同一物理页 ◀───── 读者（0 次拷贝）
                        ↑ 各自通过页表映射到该物理页
```

POSIX 共享内存 `shm_open` 创建共享内存对象，配合 `mmap` 映射：

```c
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

#define SIZE 4096

int main(void) {
    int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0666);
    ftruncate(fd, SIZE);                      /* 设定大小 */
    char *p = mmap(NULL, SIZE, PROT_READ | PROT_WRITE,
                   MAP_SHARED, fd, 0);        /* 映射到本进程 */
    strcpy(p, "POSIX 共享内存数据");
    msync(p, SIZE, MS_SYNC);                  /* 主动刷回（可选） */
    munmap(p, SIZE);
    shm_unlink("/myshm");                     /* 解除（文件语义） */
    close(fd);
    return 0;
}
```

**mmap 实现要点**：`mmap(MAP_SHARED)` 在内核 `mm/shmem.c`（tmpfs 页缓存）上挂一个共享页缓存；多个进程把同一物理页映射进各自地址空间，对映射区读写直接命中同一物理页，因此**没有内核-用户态的逐次拷贝**。读者进程用同一路径名 `shm_open` + `mmap` 即映射到同一物理页。

> **重要**：共享内存本身**不做任何同步**。两个进程同时写会导致数据竞争。必须配合 [[08-同步原语：互斥锁自旋锁信号量条件变量]] 中的互斥锁/信号量来保护临界区。这也是"共享内存快但对程序员要求高"的根本原因。

### 2.6 Unix 域套接字（AF_UNIX）

Unix 域套接字是 IPC 中功能最全、最易用的机制之一。它提供的语义与网络 TCP/UDP 几乎一致，但**无需 IP 协议栈、不跨网络、可靠性由内核直接交付**，因此性能远高于本地 TCP。

| 维度 | AF_UNIX | AF_INET（TCP loopback） |
|------|---------|-------------------------|
| 协议处理 | 无需 IP/TCP 栈 | 完整协议栈 |
| 可靠传输 | 内核直接交付 | TCP 重传/拥塞控制 |
| 地址形式 | 文件路径 `/tmp/sock` | IP:port |
| SOCK_STREAM | 字节流，双向 | 字节流，双向 |
| SOCK_DGRAM | 报文，双向，**可靠且有序** | 报文，双向，**可能丢包** |

示例——AF_UNIX SOCK_STREAM 服务端：

```c
#include <sys/socket.h>
#include <sys/un.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>

int main(void) {
    int sfd = socket(AF_UNIX, SOCK_STREAM, 0);
    struct sockaddr_un addr;
    memset(&addr, 0, sizeof(addr));
    addr.sun_family = AF_UNIX;
    strcpy(addr.sun_path, "/tmp/echo.sock");
    unlink("/tmp/echo.sock");
    bind(sfd, (struct sockaddr *)&addr, sizeof(addr));
    listen(sfd, 8);

    int cfd = accept(sfd, NULL, NULL);
    char buf[256];
    ssize_t n = read(cfd, buf, sizeof(buf));
    write(cfd, buf, n);              /* 原样回显 */
    close(cfd); close(sfd);
    unlink("/tmp/echo.sock");
    return 0;
}
```

**为什么选 AF_UNIX 而不是共享内存？** 共享内存最快但不自动同步；AF_UNIX 由内核保证字节流的正确性与同步，开发者无锁、无竞争，适合"消息模式"的请求/响应，兼顾性能与安全。现代高并发框架（nginx upstream、Redis Cluster、Docker socket、systemd journal）都大量用 AF_UNIX 与 pipe 做本地通信。

## 3. 详细知识点

### 3.1 IPC 的选型决策树

```text
需要传递数据吗？
├── 只需要事件/状态通知 → 信号（signal）或 eventfd
└── 需要传递数据
    ├── 数据量大、性能敏感、可接受自管同步 → 共享内存 + 互斥锁/信号量
    ├── 需要可靠的"消息/请求-响应"语义     → Unix 域套接字 / 网络 Socket
    ├── 简单单向字节流                     → 匿名管道 / 命名管道
    └── 需要消息边界与优先级               → 消息队列（POSIX/System V）
需要同步互斥（无数据）？ → 信号量 / 互斥锁（POSIX sem / pthread_mutex）
```

### 3.2 信号量：初值即资源数

信号量是计数同步原语，不传递数据，只维护一个计数值（PV 操作）：

- **P（等待）**：`sem_wait`——计数值减 1，若为负则阻塞等待资源。

```c
#include <semaphore.h>
#include <fcntl.h>
sem_t *sem = sem_open("/mysem", O_CREAT, 0666, 1); /* 初值 1 */
sem_wait(sem);      /* P：占用资源 */
/* ... 临界区 ... */
sem_post(sem);      /* V：释放资源 */
sem_close(sem);
```

**二值信号量 vs 互斥锁**：初值 1 的信号量行为类似互斥锁，但区别在于——**互斥锁只能由持有者释放（ownership），信号量可由任意进程/线程释放**。所以互斥锁用于保护临界区（有 owner 约束），信号量更适合"计数资源池"（限制并发连接数）与生产者-消费者的定长缓冲。

### 3.3 消息队列：带边界的消息块

消息队列在管道"字节流"基础上增加了**消息边界**：每条消息是独立单元，有类型与长度。`msgrcv` 可按 `msgtyp` 选取消息。

```c
struct msgbuf {
    long mtype;      /* 消息类型 >0 */
    char mtext[100];
};
msgsnd(msgid, &msg, sizeof(msg.mtext), 0);
msgrcv(msgid, &msg, sizeof(msg.mtext), 2, 0);  /* 取类型为 2 的消息 */
```

**适用场景**：需要在消息级别解耦、按类型/优先级分发、可持久恢复的场合。性能低于共享内存，但高于"每次都要传大块数据"的管道。现代 Linux 更推荐 POSIX 消息队列（`mq_open`），支持优先级与超时（`mq_timedreceive`）。

### 3.4 各类 IPC 的内核实现要点

| 机制 | 内核实现 |
|------|----------|
| 管道 | `fs/pipe.c`：环形缓冲 + 两个 end，读写在两个 file 对象上 |
| 信号 | `kernel/signal.c`：每任务 pending 信号位图 + 处理函数表 |
| System V 共享内存 | `ipc/shm.c`：shm 段 + shmid，多个进程 attach 同一物理页 |
| System V 消息队列 | `ipc/msg.c`：链表消息 + msg_qbytes 上限（默认 16KB/队列） |
| System V 信号量 | `ipc/sem.c`：信号量数组 + undo 日志（进程退出自动回滚） |
| POSIX 共享内存 | `mm/shmem.c`：tmpfs 文件 + mmap 共享页缓存 |
| Unix 套接字 | `net/unix/af_unix.c`：内核内存直接拷贝交付 |

### 3.5 IPC 与网络 Socket 的边界

IPC 与 Socket 的边界：Socket 面向"不一定同机"的进程通信（AF_INET 可跨机）；AF_UNIX/pipe/mmap 面向"同机"进程。跨机器只能走网络套接字（TCP/UDP），无法直接用共享内存。分布式系统的进程间通信（RPC/gRPC 内部）最终都落在 TCP/UDP 之上——它们是"跨机版 IPC"。本组篇目 [[06-进程间通信]] 与 [[07-Socket通信模型与epoll实现机制]] 本属同族：网络服务进程之间既用 TCP socket（跨机），也用 AF_UNIX/shmem（同机高性能）。

### 3.6 SCM_RIGHTS：通过 Unix Socket 传递文件描述符

AF_UNIX 的一个杀手级特性是 **fd 传递（passing file descriptors）**：通过控制消息（ancillary data）把某个进程的文件描述符"引荐"给另一个进程——接收方得到的是同一内核文件的引用，而非复制。这让"特权进程打开 fd、普通进程接过来用"成为可能，常用于数据库连接对象、日志 fd 的按需派发。发送方调用 `sendmsg` 携带 `SCM_RIGHTS` 控制消息，接收方用 `recvmsg` 提取。这本质上是"在进程之间移动授权"——安全场景下要注意：被传递的 fd 所代表的权限会随之转移，必须做接收方身份校验。

### 3.7 消息边界：字节流 vs 报文——再谈选型

管道与 AF_UNIX SOCK_STREAM 传输的是**字节流（stream）**，本身没有"一条消息"的概念——read 一次可能读到"半条消息 + 下一条消息的开头"。而消息队列、AF_UNIX SOCK_DGRAM 与信号量提供**边界**。这一个差别看似微小，却直接决定应用层的复杂程度：

```text
字节流模式（pipe/SOCK_STREAM）：
  发送方 write [HEAD][BODY][TAIL]
  接收方 read  ── 可能一次拿到 [HEAD][BODY] 的一部分/组合
  → 应用层必须自定帧格式（长度前缀/分隔符），自己封装"组帧-拆帧"

报文模式（消息队列/SOCK_DGRAM）：
  发送方 write 一条消息
  接收方 read  恰好一条完整消息
  → 无需组帧，天然有边界
```

工程判断：**既想数据量大、性能高，又不想手写拆帧协议**，很多项目退而选择"大报文"（如 Unix SOCK_DGRAM 的大 payload 或消息队列）。但报文的边界也意味着每跳都要完整拷贝，payload 越大越接近字节流成本。因此成熟方案（如 gRPC/HTTP/2）在字节流上定义自己的帧格式；而需要"事件"级别的通信（告警、命令字）时，报文线（队列/DGRAM）往往更省事。

### 3.8 观察 IPC 的故障排查工具

- `strace -e trace=ipc -p <pid>`：跟踪 System V IPC 与管道调用，看进程到底卡在哪个 msgrcv/semop 上。
- `ipcs -m -s -q`：查看 System V 三件套的残留与占用。
- `lsof -U`：列出 AF_UNIX 套接字与 FIFO 的连接双方 pid。
- `/proc/<pid>/fd/`：查看进程持有的管道、FIFO、socket 描述符，配合 `lsof -p` 可还原 IPC 拓扑。

```bash
$ lsof -U       # 显示 AF_UNIX 连接
COMMAND PID FD TYPE DEVICE OFFSET NODE NAME
mydemo  100 3u  unix 0x...  ...  12345 /tmp/echo.sock
```

在攻防与取证视角下，`lsof -U` / `strace` 也是还原"恶意进程与哪个管道/套接字通信"的常用手段——理解 IPC 机制，才能读懂这些证据。

### 3.9 IPC 与零拷贝：sendfile/splice 的关系

字节流转发场景（代理、网关）常遇到"从 fd A 读、写到 fd B"的搬运，命中内核的 `splice`/`sendfile` 零拷贝路径可以避免落用户态：

```c
#include <fcntl.h>
int in = open("big.bin", O_RDONLY);
int out = open("out.bin", O_WRONLY | O_CREAT, 0644);
/* sendfile: 内核里直接把数据从 in 拷到 out，不经过用户缓冲 */
off_t off = 0;
sendfile(out, in, &off, 100000);
```

在 grep 语义上，`splice(pipe, sock)` 的"管道 + 零拷贝"组合，正是 nginx 发送大文件时 CPU 占用极低的秘密。理解"数据在 IPC 路径上有几次拷贝"，是性能优化的核心抓手——这条线索与 [[13-IO模型演进：select-poll-epoll-io_uring]] 中 io_uring 的零拷贝思想同源。

## 4. 实战与示例

### 4.1 mmap 共享内存 + 互斥锁（正确同步的姿势）

```c
#include <pthread.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

typedef struct {
    pthread_mutex_t lock;   /* 进程共享互斥锁 */
    int counter;
} Shared;

#define SIZE (sizeof(Shared))

int main(void) {
    int fd = shm_open("/shmctr", O_CREAT | O_RDWR, 0666);
    ftruncate(fd, SIZE);
    Shared *s = mmap(NULL, SIZE, PROT_READ | PROT_WRITE,
                     MAP_SHARED, fd, 0);

    pthread_mutexattr_t mat;
    pthread_mutexattr_init(&mat);
    pthread_mutexattr_setpshared(&mat, PTHREAD_PROCESS_SHARED); /* 跨进程锁 */
    pthread_mutex_init(&s->lock, &mat);

    pthread_mutex_lock(&s->lock);
    s->counter++;                        /* 临界区 */
    pthread_mutex_unlock(&s->lock);

    printf("counter = %d\n", s->counter);
    munmap(s, SIZE);
    shm_unlink("/shmctr");
    return 0;
}
```

要点：**PTHREAD_PROCESS_SHARED** 属性让互斥锁可跨进程使用；多个进程 mmap 同一 block 时共享同一把锁，从而保护共享内存的临界区。

### 4.2 Unix 域套接字做"文件传输"

```c
/* writer：读文件 → AF_UNIX 发送 */
#include <sys/socket.h>
#include <sys/un.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>

int main(void) {
    int sock = socket(AF_UNIX, SOCK_STREAM, 0);
    struct sockaddr_un addr = {.sun_family = AF_UNIX};
    strcpy(addr.sun_path, "/tmp/transfer.sock");
    connect(sock, (struct sockaddr *)&addr, sizeof(addr));

    int fdin = open("source.bin", O_RDONLY);
    char buf[4096]; ssize_t n;
    while ((n = read(fdin, buf, sizeof(buf))) > 0)
        write(sock, buf, n);              /* 流式发送 */
    close(sock); close(fdin);
    return 0;
}
```

对端用同一 socket 路径 `accept` 后循环 `read` 写入目标文件即可。AF_UNIX SOCK_STREAM 保证"写入有序、不丢包"，非常适合本机的可靠大文件/大数据流传输——简单程度远超 TCP，性能优于 loopback。

### 4.3 信号 + eventfd（异步通知的现代实践）

传统 self-pipe 用 pipe 传递信号；现代 Linux 推荐 **eventfd**：信号 handler 只需写入一个 8 字节计数，主循环用 read 或 epoll 消费，避免在 handler 里做危险操作。

```c
#include <sys/eventfd.h>
#include <signal.h>
#include <unistd.h>
#include <stdio.h>

static int efd;

static void handler(int sig) {
    uint64_t one = 1;
    write(efd, &one, 8);      /* 信号到达→仅通知计数器 */
}

int main(void) {
    efd = eventfd(0, 0);
    struct sigaction sa = {.sa_handler = handler};
    sigaction(SIGUSR1, &sa, NULL);

    while (1) {
        uint64_t cnt;
        ssize_t n = read(efd, &cnt, 8);   /* 阻塞等通知 */
        if (n == 8) {
            printf("收到 %llu 次信号\n", (unsigned long long)cnt);
            if (cnt >= 3) break;
        }
    }
    return 0;
}
```

**安全提示**：handler 只写 eventfd，绝不碰共享的可变数据——这是"handler 最小化 + 异步存档"的标准实践，能避免在信号上下文里踩到不可重入锁。

### 4.4 信号量限流（资源池）

```c
#include <semaphore.h>
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>

#define MAX_WORKERS 4
sem_t limit;                     /* 并发上限 */

void *do_work(void *arg) {
    sem_wait(&limit);            /* P：拿到名额 */
    printf("worker %ld 开始\n", (long)arg);
    usleep(100000);              /* 模拟耗时 */
    printf("worker %ld 结束\n", (long)arg);
    sem_post(&limit);            /* V：归还名额 */
    return NULL;
}

int main(void) {
    sem_init(&limit, 0, MAX_WORKERS);
    pthread_t t[16];
    for (long i = 0; i < 16; i++)
        pthread_create(&t[i], NULL, do_work, (void *)i);
    for (int i = 0; i < 16; i++) pthread_join(t[i], NULL);
    return 0;
}
```

并发上限恒为 MAX_WORKERS=4，与线程池的效果等价，但实现更轻——信号量的 P/V 比"队列 + worker 线程"省去一层调度复杂度。

### 4.5 SysV vs POSIX：一张表结束纠结

| 维度 | System V | POSIX |
|------|----------|-------|
| 授权 | key（整型）+ 权限位 | 路径名 + open 语义，天然支持 ACL |
| 生命周期 | 内核对象，需显式 ipcrm | 映射/文件语义，进程退出自动回收更容易 |
| 唯一性检查 | `IPC_PRIVATE`/预定义 key | `O_CREAT|O_EXCL` 类似文件 |
| 消息优先级 | msgtyp 整数 | 正整数优先级，`mq_timedreceive` |
| 信号量操作 | `semop` 一次可改多个 | `sem_wait/post` 单值，更简单 |
| 同步共享内存 | `shmat` 无同步 | `mmap + PTHREAD_PROCESS_SHARED` 现代组合 |

**结论**：新代码优先 POSIX；维护老系统时看懂 SysV 的 `ipcs`/`ipcrm` 运维手法。两者都遇到"共享内存 + 锁"时，正确性关键都在"同一块内存上同一把锁"这一件事上。

### 4.6 生产者-消费者：条件变量 vs 信号量两个版本对比

条件变量版见 [[08-同步原语：互斥锁自旋锁信号量条件变量]] 的完整 C 代码；信号量版只需要两个信号量：`empty=容量`、`full=0`，生产者 `P(empty)` 入队再 `V(full)`，消费者 `P(full)` 出队再 `V(empty)`——无需 MVP 地址的判断，代码更短但边界语义（如多条消息原子入队）需要额外设计。选型时遵循规律：**多消费者共享缓冲用条件变量+锁**（不易漏通知，语义清晰），**纯计数/限流用信号量**（P/V 更轻）。

### 4.7 Bash 中快速体验 IPC

```bash

$ seq 1 5 | wc -l

# 命名管道（FIFO）跨进程通信
$ mkfifo /tmp/q

$ echo hello > /tmp/q              # 写端 → 输出 hello

```

## 5. 常见坑与避坑指南

### 坑 1：信号不可靠——被中断的系统调用（EINTR）

**症状**：进程收信号后，慢速系统调用（read/write/epoll_wait）莫名返回 -1，errno=EINTR，业务误判为失败。

**根因**：信号 delivery 打断阻塞的系统调用，且未设置 `SA_RESTART`。

**解决**：`sigaction` 置 `SA_RESTART` 标志自动重启绝大多数调用；或在代码里显式循环处理：

```c
ssize_t r;
do {
    r = read(fd, buf, n);
} while (r < 0 && errno == EINTR);
```

### 坑 2：System V 残留资源未清理

**症状**：`ipcs -m` 显示大量残留共享内存段；新进程 `shmget` 报 `ENOMEM`/`EIDRM`；重启应用前必须手清。

**根因**：System V 资源是内核全局对象，进程崩溃/退出后**不会自动销毁**。

**解决**：用 `ipcrm` 或 `shmctl(IPC_RMID)` 显式清理；或改用 POSIX `shm_unlink`（文件语义更符合生命周期管理）；必要时用 `IPC_CREAT|IPC_EXCL` 防止复用旧键导致串数据。

```bash
$ ipcs -m          # 查看共享内存段
$ ipcrm -m <shmid> # 删除指定段
```

### 坑 3：共享内存竞争条件（Race Condition）

**症状**：两个进程同时写共享缓冲，数据出现半个/乱序；读取越界崩溃。

**根因**：共享内存**无内建同步**，多个进程直接在物理页上竞争。

**解决**：必须用跨进程互斥锁（`PTHREAD_PROCESS_SHARED`）或信号量包裹整个临界区；读写都要加锁；共享内存里的标志用原子操作（`atomic_*`）而非普通 `volatile`。

### 坑 4：管道阻塞导致死锁或 SIGPIPE 杀进程

**症状**：写端一直 write 而读端不 read，写端永久阻塞（管道满）；或对端已关闭继续 write，收到 SIGPIPE 进程被默认终止。

**根因**：管道缓冲有限；SIGPIPE 默认动作是杀掉进程。

**解决**：约定好"谁关闭、何时关闭"的协议；给端设置 `O_NONBLOCK` 或超时；需要时用 `signal(SIGPIPE, SIG_IGN)` 并检查 write 返回值（返回 -1 + EPIPE 即对端关闭）。生产代码里，能区分 EPIPE 与 EAGAIN 是基本功。

### 坑 5：信号处理函数调用非 async-signal-safe 函数

**症状**：信号触发后程序偶发段错误或卡死，尤其在高频信号下。

**根因**：handler 里调用了 malloc/printf/锁等不可重入函数，打断主线程正在执行的相同操作，破坏内部状态。

**解决**：handler 只写 `volatile sig_atomic_t` 或 eventfd/pipe；数据落地放到主循环；确实需要复杂处理时用实时信号 + `sigwait` 在专用线程同步消费。

### 坑 6：Docker/容器共享内核导致 IPC 资源泄漏

**症状**：容器退出，但宿主机上共享内存/消息队列仍占用资源，`ipcs` 越积越多。

**根因**：容器共享宿主机内核，System V IPC 若不通过 namespace 隔离或清理，资源残留在宿主机。

**解决**：生产中尽量避免容器的 System V IPC，改用 POSIX IPC 与套接字；应用退出前显式 `shm_unlink`/`mq_close`；在宿主机巡检 `ipcs` 并定期清理孤儿资源。
