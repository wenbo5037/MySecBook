## 1. 概述

**中断（Interrupt）** 和 **异常（Exception）** 是操作系统与硬件交互的核心机制。如果说系统调用是用户态程序"主动请求"内核服务，那么中断就是硬件设备"被动通知"内核有事件需要处理。时钟中断驱动着操作系统的调度器，I/O 中断驱动着磁盘和网卡的数据传输，缺页异常实现了虚拟内存的按需分配——没有中断机制，现代操作系统根本无法运作。

从历史视角看，中断的概念可以追溯到 1950 年代的大型机时代。1964 年 IBM System/360 引入了标准化的中断机制。1981 年 IBM PC 使用 8259A 可编程中断控制器（PIC）管理 15 个硬件中断。到了多核时代，PIC 被 APIC（Advanced Programmable Interrupt Controller）取代——每个 CPU 核心有自己的 Local APIC，系统有一个 I/O APIC 负责将外设中断路由到合适的 CPU 核心。MSI/MSI-X（Message Signaled Interrupts）进一步允许 PCIe 设备直接向特定 CPU 发送中断，绕过了 I/O APIC。

中断处理是操作系统中最关键的代码路径之一——它在**不可预测的时间**执行（随时可能打断任何代码），必须**尽可能快**地完成（否则影响系统响应），并且**不能睡眠**（因为中断上下文没有关联的进程）。这种约束催生了 Linux 内核独特的"上半部/下半部（Top Half / Bottom Half）"中断处理架构——硬中断处理最紧急的工作，延迟处理耗时较长的工作。

本节将从中断/异常/陷入的分类开始，逐步深入中断向量表（IDT）结构、中断控制器演进（PIC→APIC→MSI）、中断处理流程、软中断与工作队列机制、典型异常类型、以及从安全视角分析中断机制的攻击面与防御措施。

外部硬件中断与 CPU 内部异常还有一个关键区别：**时机（Timing）**。中断是**异步（Asynchronous）**的——它可以在任何时刻打断当前正在执行的任何指令序列，与当前指令的执行内容无关。异常是**同步（Synchronous）**的——它总是由当前正在执行的某条特定指令触发的，例如执行 `div` 指令时除数为零。这个区别决定了调试和故障定位的方式：中断处理程序无法轻易确定"是谁在什么时刻打断了什么"，而异常处理程序则明确知道触发异常的指令地址。

## 2. 核心原理

### 2.1 中断 vs 异常 vs 陷入

三个术语在日常使用中经常混用，但在操作系统理论中有严格区分：

| 类型 | 英文 | 触发源 | 时序特征 | 典型示例 |
|------|------|--------|----------|----------|
| **中断** | Interrupt | 外部硬件设备 | 异步（与当前指令无关） | 时钟中断、网卡数据到达、键盘输入 |
| **异常** | Exception | CPU 执行指令时检测到的错误/条件 | 同步（与当前指令直接相关） | 除零错误、缺页异常、非法指令 |
| **陷入** | Trap | 程序主动触发的指令 | 同步（有意触发） | 系统调用（`int 0x80`/`syscall`）、调试断点（`int 3`） |

硬件中断又分为**可屏蔽中断（Maskable Interrupt）** 和**不可屏蔽中断（Non-Maskable Interrupt, NMI）**。可屏蔽中断可以通过 `cli`/`sti` 指令或中断控制器的屏蔽位来屏蔽；NMI 则不可屏蔽，用于处理严重错误（如硬件 watchdog 超时、内存校验错误），通过 NMI 专用引脚触发。

异常则根据 CPU 的返回行为分为三类：

| 异常类别 | 中文 | 返回行为 | 典型示例 |
|----------|------|----------|----------|
| **Fault** | 故障 | 修复后**重新执行**触发指令 | 缺页异常（Page Fault）、除零错误（Divide Error） |
| **Trap** | 陷阱 | 返回**下一条**指令 | 调试断点（`int 3`）、系统调用（`int 0x80`） |
| **Abort** | 中止 | **无法恢复**，通常终止进程或系统 | 双重故障（Double Fault）、机器检查异常（Machine Check） |

故障（Fault）的关键特征是：CPU 在执行指令**之前**检测到问题（如页表项的 Present 位为 0），触发异常后，内核修复问题（如分配物理页），然后**重新执行**该指令。陷阱（Trap）的关键特征是：CPU 在执行指令**之后**触发（如 `int 3` 调试断点），返回时执行**下一条**指令。中止（Abort）则用于 CPU 本身状态已经严重损坏（如双重故障）的场景，无法安全恢复。

### 2.2 中断向量表（IVT/IDT）

x86 架构使用**中断描述符表（IDT, Interrupt Descriptor Table）** 来管理所有中断和异常的处理入口。IDT 是一个包含 256 个条目的数组，每个条目称为一个**门描述符（Gate Descriptor）**，对应一个中断向量号（0-255）。

```text
IDT 结构（x86-64）

256 个门描述符：
┌─────────────────────────┐
│ Vector 0:  Divide Error │  #DE 除零错误（异常）
│ Vector 1:  Debug         │  #DB 调试异常
│ Vector 2:  NMI           │  不可屏蔽中断
│ Vector 3:  Breakpoint    │  #BP int 3 断点
│ Vector 4:  Overflow      │  #OF 溢出错误
│ Vector 5:  Bounds        │  #BR 越界
│ Vector 6:  Invalid Opcode│  #UD 非法指令
│ Vector 7:  Device Not... │  #NM 设备不可用
│ Vector 8:  Double Fault  │  #DF 双重故障
│ Vector 9:  (保留)        │
│ Vector 10: Invalid TSS   │  #TS
│ Vector 11: Segment Not.. │  #NP
│ Vector 12: Stack Fault   │  #SS
│ Vector 13: General Prot. │  #GP 通用保护
│ Vector 14: Page Fault    │  #PF 缺页异常
│ ...                      │  ...（保留向量 15-31）
│ Vector 32-255: 可编程    │  硬件中断（IRQ）、软中断、系统调用等
└─────────────────────────┘

每 16 字节的门描述符包含（x86-64 中断门）：
  Offset[31:16] + Segment Selector + Type + DPL + Offset[63:32]
                （目标代码段前缀）     （门类型） （目标偏移地址）
```

**门描述符类型**：

| 类型 | 说明 | 是否改变特权级 |
|------|------|----------------|
| 中断门（Interrupt Gate） | 进入后自动禁用中断（IF 标志清零） | 是（DPL=0） |
| 陷阱门（Trap Gate） | 进入后保留中断状态（IF 不清） | 是（DPL=0） |
| 任务门（Task Gate） | 通过 TSS 进行任务切换 | 是 |

Linux 内核使用中断门和陷阱门两种类型：硬件中断和大部分异常使用中断门（进入时自动关闭中断，防止嵌套中断破坏数据）；部分调试和系统调用（`int 0x80`）使用陷阱门。

### 2.3 中断控制器演进

#### 2.3.1 8259A PIC（Programmable Interrupt Controller）

1980 年代的 PC 使用两片级联的 8259A 控制器，总共支持 15 个硬件中断（IRQ 0-15）：

```text
传统 PIC 布局（8259A，两个级联）：

  主 8259A (IRQ 0-7)          从 8259A (IRQ 8-15)
  0  Timer                   8  RTC
  1  Keyboard                 9  Reserved
  2  Cascade（给从片）        10  Free
  3  COM2                     11  Free
  4  COM1                     12  PS/2 Mouse
  5  LPT1                     13  FPU/Coprocessor
  6  Floppy                   14  Primary IDE
  7  Free                     15  Secondary IDE
```

**局限**：8259A 是单一定时器、固定优先级的中断方案，且没有 SMP（Symmetric Multi-Processing）支持——多个 CPU 无法分散处理不同的中断。这正是现代 x86 系统中构建 8259A 之前使用 APIC 的原因。

#### 2.3.2 APIC（Advanced Programmable Interrupt Controller）

自 Pentium Pro 以后，x86 处理器引入了 APIC 架构，包含：

- **Local APIC**：集成在每个 CPU 核心内部，处理该核心的中断接收、优先级判断和调度
- **I/O APIC**：系统级芯片，负责将外部硬件中断路由到指定 CPU 的 Local APIC

```text
APIC 架构：

┌─────────────┐      IPI（处理器间中断）      ┌─────────────┐
│ CPU Core 0  │ ◄───────────────────────►  │ CPU Core 1  │
│ Local APIC  │                            │ Local APIC  │
└─────▲───────┘                            └─────▲───────┘
      │ 中断信号（通过 APIC 总线/系统总线）         │
      └──────────────┬──────────────────────────┘
                     │
              ┌──────┴──────┐
              │  I/O APIC    │
              └──────▲──────┘
                     │
              ┌──────┴──────┐
              │  PCIe / 设备 │
              └─────────────┘
```

**关键特性**：

1. **多核中断路由**：I/O APIC 可将不同的外设中断路由到不同 CPU 核心，实现负载均衡（`irqbalance` 服务）
2. **IPI（Inter-Processor Interrupt）**：CPU 之间通过 IPI 通信，用于 TLB 刷新、调度抢占等
3. **优先级控制**：根据源中断的优先权动态分配
4. **NMI 支持**：可向指定 CPU 发送 NMI

#### 2.3.3 MSI/MSI-X

现代 PCIe 设备通过 **MSI（Message Signaled Interrupt）** 直接向 CPU 发送中断消息，不再需要 I/O APIC 的中介。MSI-X 是 MSI 的扩展版本，支持更多中断向量和更灵活的路由配置。

| 特性 | PIC | APIC | MSI/MSI-X |
|------|-----|------|-----------|
| 中断路由 | 固定 | 可配置到任意 CPU | 设备直接指定 CPU |
| SMP 支持 | 无 | 是 | 是 |
| 中断数量 | 固定（15） | 可达 224 | 每设备 2-2048 |
| 处理延迟 | 较高 | 较低 | 最低 |
| 应用场景 | 老式硬件/兼容 | 现代 APIC 系统 | 高性能 PCIe（NVMe、网卡） |

### 2.4 中断处理完整流程

一次硬件中断从发生到处理完成的完整流程：

```text
┌────────────────────────────────────────────────────────────┐
│ 定时器中断发生（tick）                                        │
│                                                            │
│ ① 硬件层：                                                   │
│   Timer 芯片 → I/O APIC → CPU 的 Local APIC                 │
│   → CPU 收到中断请求                                        │
│                                                            │
│ ② CPU 层（硬件自动执行）：                                    │
│   ├─ 保存当前指令的 RIP、CS、RFLAGS 到内核栈                  │
│   ├─ 若发生模式切换（用户态→内核态），切换到内核栈段           │
│   ├─ 查 IDT 找到对应向量（Vector 32）的门描述符               │
│   └─ 跳转到中断处理入口（asm_common_interrupt）               │
│                                                            │
│ ③ 内核层（entry 阶段）：                                     │
│   ├─ 保存所有通用寄存器到内核栈（pt_regs）                    │
│   ├─ 切换 GS 基地址（swapgs）                                │
│   ├─ 记录当前 CPU 的中断上下文                               │
│   └─ 调用中断处理程序（handle_irq → do_IRQ）                 │
│                                                            │
│ ④ 上半部（Top Half / hardirq handler）：                     │
│   ├─ 执行硬中断处理函数（irqaction 的 handler）               │
│   ├─ 标记 IRQ_PENDING（如果处理不及时）                       │
│   └─ 调度软中断（raise_softirq）                             │
│                                                            │
│ ⑤ 下半部（Bottom Half / softirq）：                         │
│   ├─ 在返回用户态前或调用 schedule 时检查 pending softirq    │
│   ├─ 执行 tasklet/workqueue/softirq 函数                     │
│   └─ 处理耗时的后续工作（如网络包处理）                       │
│                                                            │
│ ⑥ 返回：                                                    │
│   └─ iretq / sysretq：恢复寄存器、恢复 RFLAGS、返回           │
│      被中断的指令继续执行                                     │
└────────────────────────────────────────────────────────────┘
```

## 3. 详细知识点

### 3.1 中断上半部 / 下半部（Top Half / Bottom Half）

中断处理分两个阶段是**中断处理效率**的基石——硬中断处理程序必须短且快（不能睡眠、不能长时间占用 CPU），而耗时工作延期处理。

```text
中断延迟处理机制对比（Linux）：

硬中断（上半部）：
  ├─ 高优先级，立即执行
  ├─ 不能睡眠（没有进程上下文）
  ├─ 必须快速返回（建议 <100 us）
  └─ 处理：确认设备、读取状态、标记事件

softirq（软中断）：
  ├─ 由硬中断唤醒（raise_softirq）
  ├─ 在中断返回路径 / ksoftirqd 中执行
  ├─ 允许部分重入（多核并行）
  └─ 典型：网络收发（NET_RX_SOFTIRQ）、块设备（BLOCK_SOFTIRQ）

tasklet（小任务）：
  ├─ 基于 softirq 实现，但同一 tasklet 串行执行
  ├─ 由内核调度，不能睡眠
  └─ 典型：设备驱动延迟队列

workqueue（工作队列）：
  ├─ 内核线程上下文（可以睡眠！）
  ├─ 由 kworker 线程执行
  ├─ 可以阻塞、可以睡眠（适合长任务）
  └─ 典型：磁盘写回延迟处理、文件系统延迟工作

优先级（同一 CPU 上）：
  hardirq > softirq > tasklet > ksoftirqd > workqueue > 普通进程
```

**选择原则**：

| 任务特征 | 推荐机制 |
|----------|----------|
| 极短（<100us），不能睡眠 | 硬中断处理程序 |
| 短，不能睡眠，可串行 | tasklet |
| 短，不能睡眠，需多核并行 | softirq |
| 中等，可以睡眠 | workqueue |
| 长任务，可阻塞 | 专用内核线程（kthread） |

### 3.2 典型异常详解

#### 3.2.1 Page Fault（#PF, 异常编号 14）

缺页异常是最常见的异常类型，也是虚拟内存机制的核心。当 CPU 访问一个虚拟地址，而对应的页表项有效位（Present）为 0，或权限不足时，触发 #PF。

```text
Page Fault 触发条件：
  1. 页面未映射（Present=0）
  2. 写访问只读页面（写保护）
  3. 访问权限不足（CPL 高于页面允许的 DPL，如 RING 3 访问 RING 0 页面）

Page Fault 错误码（在栈上）：
  Bit 0: P    = 保护违规（0=页面不存在, 1=保护违反）
  Bit 1: W/R  = 写/读（0=读, 1=写）
  Bit 2: U/S  = 用户/超级（0=超级, 1=用户）
  Bit 3: RSVD = 保留位违例
  Bit 4: I/D  = 取指/数据（0=数据, 1=取指）

内核处理：
  ├─ fault 在用户态 → 进程处理（如 mmap 延迟映射）
  ├─ fault 在内核态 → 内核修复（如 copy_from_user 的 fault）
  └─ 不可修复 → 发送 SIGSEGV / oops
```

**内核从用户态访问数据的安全机制**：内核中的 `copy_from_user()` / `copy_to_user()` 之所以必须用专用函数，就是因为它们封装了 Page Fault 处理——如果用户传入的指针指向的页面未映射（如已释放的内存），内核会捕获这个 Page Fault 并返回 `-EFAULT`，而不是让内核直接崩溃。如果内核直接解引用用户态指针，遇到 Page Fault 会导致整机崩溃（oops）甚至系统重启。

#### 3.2.2 Double Fault（#DF, 异常编号 8）

当 CPU 在处理一个异常时，又发生了另一个异常（如处理 Page Fault 时又发生 General Protection），且两个异常产生的问题无法被异常处理程序处理时，触发 Double Fault。如果 Double Fault 也无法恢复，CPU 进入**三重故障（Triple Fault）**状态，此时 CPU 复位重启。

```text
Double Fault 触发：
  1. 异常 A 发生 → CPU 尝试压入异常 A 的栈帧
  2. 压栈时栈空间不足 → 触发异常 B（Stack Segment Fault #SS）
  3. 此时 CPU 无法正常保存状态 → 触发 Double Fault
  4. Double Fault 也无法处理 → Triple Fault → CPU 硬复位

常见的 Double Fault 触发场景：
  - 内核栈溢出（没有剩余空间保存异常上下文）
  - 恶意构造的异常触发序列
```

#### 3.2.3 Machine Check Exception（#MC, 异常编号 18）

由 CPU 的机器检查架构（MCA）触发，用于报告硬件错误（ECC 内存错误、总线错误、缓存错误等）。MCE 会记录错误并通常触发 MCE Handler 决定继续运行（可纠正错误）或停机（不可纠正错误）。

### 3.3 NMI Watchdog 与系统安全

**NMI Watchdog** 是内核的软锁/硬锁检测机制，通过 NMI（不可屏蔽中断）定期"戳"每个 CPU 核心，检查是否存在死锁或长时间阻塞：

```bash
# 内核配置
CONFIG_HARDLOCKUP_DETECTOR=y
CONFIG_SOFTLOCKUP_DETECTOR=y

# 运行状态
cat /proc/sys/kernel/nmi_watchdog
# 1 = 启用, 0 = 禁用

# 查看 watchdog 触发的消息
dmesg | grep -i "watchdog\|soft lockup\|hard lockup"
# 示例输出：
# BUG: soft lockup - CPU#2 stuck for 22s! [kworker/2:1:54]
# BUG: hard LOCKUP on CPU#1

# 触发条件
# 软锁（softlockup）：CPU 在 20s 内未调度（soft lockup threshold）
# 硬锁（hardlockup）：CPU 在 10s 内未响应 NMI（hard lockup threshold）
```

### 3.4 `/proc/interrupts` 中断统计

Linux 通过 `/proc/interrupts` 展示每个 CPU 核心上各种中断的累计次数：

```bash
cat /proc/interrupts
# 输出示例：
#            CPU0       CPU1       CPU2       CPU3
```

**关键中断类型解读**：

| 中断 | 含义 | 关注点 |
|------|------|--------|
| timer | 当地时钟中断（每秒 100-1000 Hz） | 过多可能表示 CPU 过载 |
| LOC | 本地 APIC 时钟 | 各核心应大致均衡 |
| RES | 重新调度中断（IPI） | 过高表示调度风暴 |
| CAL | 函数调用中断（IPI） | 用于 TLB shootdown 等 |
| TLB | TLB 刷新 shootdown | 过多表示频繁切换页表 |

### 3.5 中断处理在设备驱动中的实践

理解中断的抽象机制不够，还需要理解它如何在真实设备驱动的场景下被使用。以网卡（NIC）为例，一次数据包接收的完整路径展示了硬中断、软中断和唤醒等待进程的协作：

```text
网卡收包路径（NAPI 机制简化版）：

① 网卡硬件收到数据包，写入 DMA 环（Rx Ring），触发硬件中断
     │
     ▼
② CPU 响应 IRQ，执行硬中断处理器（napi_schedule）
     ├─ 关闭该设备的硬中断（避免频繁打断）
     ├─ 将设备加入 softnet_data 的 backlog 队列
     └─ 调度 NET_RX_SOFTIRQ 软中断
     │
     ▼
③ softirq 在合适时机执行 net_rx_action
     ├─ 遍历 backlog 中的 napi_struct
     ├─ 批量从 DMA 环取包（napi poll）
     ├─ 分配 sk_buff，交给协议栈（ip_rcv → tcp_v4_rcv）
     ├─ 若有进程在 accept()/recv() 上阻塞 → 唤醒
     └─ 处理完一批后重新开启硬中断
     │
     ▼
④ 用户态进程从 recv() 返回，读取数据
```

这个 NAPI（New API）机制的设计动机，正是第 1 节提到的"中断处理必须快 + 不能睡眠"约束：**在高流量下，与其让每个数据包都触发一次硬中断打断了 CPU，不如先批量拉取一批包一次性处理，再重新开中断**。这是中断降频（interrupt coalescing）思想的典型实践。理解这条路径，对分析网络性能瓶颈（高 PPS 下 CPU 中断软中断占用过高）至关重要，也直接关系到 [[13-IO模型演进：select-poll-epoll-io_uring]] 中 I/O 事件通知的实现原理。

普通字符设备驱动（如 GPIO、键盘）的中断处理要简单得多：

```c
/* 一个典型的 GPIO 中断驱动片段（上半部只置标志） */
struct btn_data {
    struct work_struct work;
    int count;
};

static irqreturn_t btn_isr(int irq, void *dev_id) {
    struct btn_data *d = (struct btn_data *)dev_id;
    /* 上半部：只是把耗时工作放入 workqueue */
    schedule_work(&d->work);
    return IRQ_HANDLED;
}

static void btn_work(struct work_struct *work) {
    struct btn_data *d = container_of(work, struct btn_data, work);
    d->count++;
    printk(KERN_INFO "Button pressed %d times\n", d->count);
    /* 这里可以安全地睡眠/做耗时操作 */
}
```

**关键要点**：硬中断处理程序（ISR）只应做"确认设备、清除中断标志、标记事件"这类最小工作；任何可能阻塞或耗时的处理都要延后（softirq/tasklet/workqueue 或专有内核线程）。ISR 中绝不能调用 `sleep`、`kmalloc(GFP_KERNEL)`、`mutex_lock` 等可能睡眠的函数，否则会造成内核死锁或崩溃。

### 3.6 时钟中断与高精度时钟（hrtimer）

时钟中断是中断系统中最关键、最频繁的一类。Linux 在标准 tick（tick-based）之外还引入了**高精度时钟（hrtimer）** 机制，用于支持纳秒级定时精度，满足实时应用（RT）、网络超时、音视频等场景的精确时序需求。

```text
时钟子系统：
  ┌─────────────────────────────────────────────┐
  │ 时钟源（clocksource）                        │
  │   TSC（x86 TSC）/ ACPI PM Timer / HPET      │
  │   提供单调递增的高分辨率时钟计数              │
  ├─────────────────────────────────────────────┤
  │ 时钟事件设备（clockevent device）            │
  │   用于设置下一次定时中断的触发时刻            │
  ├─────────────────────────────────────────────┤
  │ 定时器层次：                                 │
  │   ├─ tick（周期性，传统 jiffies 心跳）        │
  │   ├─ hrtimer（高精度，纳秒级，红黑树组织）     │
  │   └─ watchdog / scheduler（依赖于时钟）      │
  └─────────────────────────────────────────────┘
```

```bash
# 查看当前定时器频率（Hz）
cat /proc/sys/kernel/hz  # 或 /proc/uptime 推算 tick
# 常见值：100 / 250 / 1000

# 查看 hrtimer 相关
cat /proc/timer_list | head -30
cat /proc/timer_stats

# 动态时钟（tickless/dynticks）：空闲时暂停周期 tick 节省功耗
# 内核配置 CONFIG_NO_HZ_IDLE
```

**动态时钟（tickless idle）** 允许 CPU 在空闲时完全暂停周期性的时钟中断，只在有事件需要处理时才醒来，显著降低空转功耗。这在高密度云服务器和手机 SoC 上尤为重要。同时，它也让"中断频率"变成动态的——这也是为什么在高并发网络服务器上，`/proc/interrupts` 的 timer 数值往往不代表实际性能瓶颈的原因之一。

### 3.7 中断负载均衡：irqbalance 与 NUMA 亲和性

多核时代，如何把大量硬件中断均衡地分布到各个 CPU，直接决定系统的吞吐与服务延迟。这个任务由 **irqbalance** 守护进程完成。

```text
irqbalance 的工作：
  1. 周期性读取 /proc/interrupts 统计每种中断的频率
  2. 根据设备的 IRQ 类型、CPU 负载、NUMA 拓扑打指标
  3. 将高负载中断分配到不同的 CPU 核心（写 smp_affinity）
  4. 平衡目标：避免某个 CPU 独占大量中断导致其软中断过载

示例：8 核机器上，网卡 IRQ 例如 16-19 应分布到 4 个不同 CPU，
而不是全部集中到 CPU0。
```

**NUMA（Non-Uniform Memory Access）亲和性**：在多路服务器上，中断应该绑定到"设备所在 NUMA 节点"的 CPU——否则中断处理程序和其访问的设备内存需要跨节点访问，带来额外的内存延迟（称为 remote zone memory access）。

```bash
# 检查 NUMA 拓扑
numactl --hardware
# 输出每个 node 的 CPU 和内存范围

# 查看设备所在 NUMA 节点
cat /sys/class/net/eth0/device/numa_node

# 根据设备所在 node 绑定中断亲和性
# 例如设备在 node0（CPU 0-3），则：
echo "0f" > /proc/irq/16/smp_affinity   # CPU 0-3

# 或在 RPS（Receive Packet Steering）中绑定对应 CPU 集合
echo "0f" > /sys/class/net/eth0/queues/rx-0/rps_cpus

# 用 mpstat 观察各 CPU 的硬/软中断占用，验证是否均衡
mpstat -P ALL 1
# %irq  = 硬中断占用比例
# %soft = 软中断占用比例
```

```text
NUMA 拓扑示例（2 socket 服务器）：
  Socket 0 (node0)          Socket 1 (node1)
  ┌───────────────┐         ┌───────────────┐
  │ CPU 0-3       │  QPI    │ CPU 4-7       │
  │ 内存区 0      │◄──────►│ 内存区 1       │
  │ PCIe slot 0   │         │ PCIe slot 1   │
  └───────────────┘         └───────────────┘
      ↑ 网卡插在 slot0          ↑ 网卡插在 slot1 → 绑定 CPU 4-7
      网卡在 node0 → 绑定 CPU 0-3
      否则跨 socket 访问有明显延迟
```

**实际生产建议**：对高吞吐网卡（如 10G/100G），优先用硬件中断+irqbalance 自动化管理；对超高 PPS 场景，可手动绑定中断并配合 RPS/XPS（Transmit Packet Steering）做软中断分发，将收包软中断分散到多个 CPU，避免单个 CPU 成为瓶颈。这也与 [[13-IO模型演进：select-poll-epoll-io_uring]] 中高并发服务器的优化手段一脉相承。

### 4.3 内核模块：注册中断处理

```c
/* 内核模块：注册并处理自定义 IRQ */
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/interrupt.h>
#include <linux/slab.h>
#include <linux/version.h>

#define MY_IRQ 24      /* 示例：使用 IRQ 24（实际设备不同） */
#define MY_NAME "my_irq_handler"

/* 中断处理函数（上半部）——必须快速返回 */
static irqreturn_t my_irq_handler(int irq, void *dev_id) {
    struct my_irq_data *data = (struct my_irq_data *)dev_id;
    
    /* 上半部只做紧急工作：ack 设备、读状态寄存器 */
    data->count++;
    printk(KERN_INFO "IRQ %d received, count=%lu\n", irq, data->count);
    
    /* 返回 IRQ_HANDLED 表示已正确处理 */
    return IRQ_HANDLED;
}

/* 数据结构（通过 dev_id 传递，避免全局变量） */
struct my_irq_data {
    unsigned long count;
    char name[32];
};

static struct my_irq_data irq_data;

static int __init irq_demo_init(void) {
    int ret;
    snprintf(irq_data.name, sizeof(irq_data.name), "my_driver");
    
    /* 注册中断处理程序 */
    ret = request_irq(MY_IRQ, my_irq_handler, IRQF_SHARED,
                      irq_data.name, &irq_data);
    if (ret) {
        printk(KERN_ERR "Failed to request IRQ %d: %d\n", MY_IRQ, ret);
        return ret;
    }
    
    printk(KERN_INFO "IRQ handler registered on %d\n", MY_IRQ);
    return 0;
}

static void __exit irq_demo_exit(void) {
    free_irq(MY_IRQ, &irq_data);
    printk(KERN_INFO "IRQ %d handler released, total count=%lu\n",
           MY_IRQ, irq_data.count);
}

module_init(irq_demo_init);
module_exit(irq_demo_exit);
MODULE_LICENSE("GPL");
```

**注意事项**：
1. 使用 `request_irq` 时需要传递 `dev_id` 参数（避免全局变量，同时作为 free_irq 的标识）
2. 注册共享 IRQ 时使用 `IRQF_SHARED`，处理函数必须兼容并发调用
3. 中断处理函数不能调用 `printk` 过多（可能死锁），应使用轻量的 `trace_printk` 或计数

## 5. 常见坑与避坑指南

### 5.1 中断上下文不能睡眠

**问题**：在硬中断处理程序中使用可能会睡眠的函数（`kmalloc(GFP_KERNEL)`、`mutex_lock`、`printk` 的某些路径），会导致内核崩溃或死锁。

```c
/* 错误：在硬中断处理函数中使用可能睡眠的操作 */
irqreturn_t bad_handler(int irq, void *dev) {
    /* kmalloc(GFP_KERNEL) 可能睡眠（阻塞等待内存） */
    void *buf = kmalloc(1024, GFP_KERNEL);   /* 错误！中断上下文不能睡眠 */
    return IRQ_HANDLED;
}

/* 正确：使用不睡眠的变体 */
irqreturn_t good_handler(int irq, void *dev) {
    /* GFP_ATOMIC 不会睡眠，上下文中分配 */
    void *buf = kmalloc(1024, GFP_ATOMIC);   /* 正确 */
    if (!buf)
        return IRQ_NONE;  /* 无法分配，让内核处理 */
    /* ... 使用 buf ... */
    return IRQ_HANDLED;
}

/* 正确：把睡眠操作延迟到 workqueue */
irqreturn_t defer_handler(int irq, void *dev) {
    /* 只做超级快的处理，把耗时操作放入 workqueue */
    schedule_work(&my_work);   /* workqueue 在进程上下文执行 */
    return IRQ_HANDLED;
}
```

**避坑原则**：
- 硬中断/softirq/tasklet 中只使用 `GFP_ATOMIC` 分配
- 需要睡眠的操作（如 `mutex`、`kmalloc(GFP_KERNEL)`）必须移到 workqueue 或内核线程
- 使用 `in_interrupt()` 检查是否在中断上下文

### 5.2 软中断与硬中断亲和性设置不当

**问题**：软中断（softirq）在"返回用户态之前的那个 CPU"上执行，如果某个 CPU 上既有大量硬中断又有大量 softirq，会形成 CPU 过载和延迟上升的双重问题。

```bash
# 症状：某个 CPU 的 softirq 时间过高（LOAD 上升但 CPU 利用率分散）
mpstat -I SCPU 1

# 造成延迟：网络包处理在主网卡中断所在的 CPU 上排队
# 如果该 CPU 同时运行 irqbalance 无法平衡的进程，延迟会急剧上升

# 解决：限制硬中断和 softirq 在专用 CPU 上处理
# 方法一：将网卡中断绑定到专用 CPU（2 核机器，绑定 1 号核）
echo "2" > /proc/irq/16/smp_affinity_list  # 网卡 IRQ 16 绑定 CPU1

# 方法二：使用 RPS（Receive Packet Steering）分散软中断
echo "ff" > /sys/class/net/eth0/queues/rx-0/rps_cpus
```

### 5.3 IRQ affinity 设置不当导致延迟

**问题**：将中断绑定到错误的 CPU（如绑定到 CPU0，而 CPU0 又负责所有系统管理任务）可能导致中断处理延迟升高。

```bash
# 检查当前各中断的 CPU 亲和性
for irq in /proc/irq/*/smp_affinity; do
  printf "%s: " "$(basename $(dirname "$irq"))"
  cat "$irq"
done

# 重绑中断（例如将 IRQ 24 的网络中断绑定到 CPU2 和 CPU3）
echo "06" > /proc/irq/24/smp_affinity

# 使用 irqbalance 自动管理（推荐）
systemctl restart irqbalance

# 注意：在 NUMA 机器上，应该将中断绑定到设备的 NUMA 节点对应的 CPU
# 否则会造成跨节点内存访问延迟
```

### 5.4 中断风暴与系统挂起

**问题**：某些硬件故障（如设备持续发送中断请求，但驱动无法正确 ack）会导致中断风暴——CPU 几乎不能在中断之间执行任何用户态代码，系统表现为"假死"。

```text
中断风暴特征：
  - CPU0 利用率飙升至 100%（中断处理占满）
  - 用户态进程几乎得不到 CPU 时间
  - /proc/interrupts 中特定中断计数疯狂增长
  - 系统响应极慢或完全无响应

诊断方法：
  - 检查 /proc/interrupts 中是否某个中断在短时间内大量增长
  - 查看 dmesg 中是否有 "irq 17: nobody cared" 的警告
  - 使用 perf top 观察内核中断处理热点

应急处理：
  1. 禁用有问题的设备：echo "1" > /sys/bus/pci/devices/0000:00:1f.2/remove
  2. 屏蔽特定中断：echo "mask" > /proc/irq/17/action
  3. 重启设备驱动：rmmod/insmod 对应驱动模块
  4. 硬件故障修复或更换设备
```

### 5.5 IDT Hook 检测与防御

**问题**：恶意 Rootkit 或内核模块可能通过修改 IDT 表中的门描述符，将某个中断向量劫持到自己的恶意处理程序，实现隐藏自身或拦截系统调用。

```c
/* 检测 IDT 是否被篡改（内核模块） */
#include <linux/module.h>
#include <linux/kernel.h>
#include <asm/desc.h>

static void check_idt_integrity(void) {
    struct desc_ptr idtr;
    unsigned long idt_base;
    
    /* 读取 IDTR 寄存器 */
    store_idt(&idtr);
    idt_base = idtr.address;
    
    /* 检查关键向量（如系统调用 int 0x80 对应的向量） */
    /* 正常情况：所有向量都应指向内核代码段（kernel text） */
    
    for (int i = 0; i < 256; i++) {
        struct desc_struct *gate = (struct desc_struct *)(idt_base + i * 16);
        unsigned long handler_addr = gate->offset_low |
                    ((unsigned long)gate->offset_middle << 16) |
                    ((unsigned long)gate->offset_high << 32);
        unsigned long seg = gate->segment;
        
        /* 检查段选择子（应指向 __KERNEL_CS） */
        if (seg != 0x10) {
            printk(KERN_WARNING "IRQ/Vector %d: suspicious segment 0x%lx\n",
                   i, seg);
        }
        
        /* 检查处理程序地址是否落在内核代码段 */
        if (handler_addr < 0xffffffff81000000UL ||
            handler_addr > 0xffffffff81ffffffUL) {
            printk(KERN_WARNING "IRQ/Vector %d: handler at %#lx (可能的 hook)\n",
                   i, handler_addr);
        }
    }
}
```

**备注**：现代内核（4.x+）的 IDT 由 `irq_entries_start` / `irq_entries_end` 定义，且通过 `CONFIG_X86_INTEL_MPX` 等特性做完整性校验。由于 KASLR（Kernel Address Space Layout Randomization）和 IDT 内容的动态性，简单比较地址范围的方法可能产生误报，需要结合其他证据。

### 5.6 SMI 固件攻击面

**问题**：系统管理模式（System Management Mode, SMM）是一个比 Ring 0 更高权限的执行环境，运行在 SMM 中的代码（SMM handler）可以完全访问物理内存和所有 I/O。攻击者若能在 SMM 中植入代码（如通过 `SMI` 触发），就获得了固件级持久化能力——OS 层面的防御（如 KASLR、SMEP）全部失效。

```text
SMM 攻击向量：
  - 固件漏洞（如 SWSM 溢出）
  - SMI invocation（通过 SMI 引脚或软件生成 SMI）
  - 固件更新流程中的篡改
  - 共享 SMRAM（System Management RAM）的越权访问

防御措施：
  - 硬件层面的 SMRAM 锁定（D_LOCK 位）
  - 固件签名验证
  - TPM（Trusted Platform Module）信任根
  - SPI flash 写保护
```

### 5.7 常见陷阱汇总

| 陷阱 | 症状 | 根因 | 解决方案 |
|------|------|------|----------|
| 中断上下文睡眠 | 内核 oops 或死锁 | 使用 GFP_KERNEL/mutex | 用 GFP_ATOMIC、延迟到 workqueue |
| 单 CPU 中断过载 | 延迟升高、丢包 | 中断集中在 CPU0 | irqbalance、RPS、按 NUMA 绑定 |
| IRQ affinity 设置不当 | 性能不稳定 | 跨 NUMA 节点路由 | 绑定到设备所在 NUMA 的 CPU |
| IDT hook 未检测 | 隐藏后门 | Rootkit 篡改 IDT | hash 校验、完整性检测器 |
| interrupt storm | 系统假死 | 硬件故障/驱动 bug | 禁用设备、屏蔽中断、更新驱动 |
| 软中断饥饿 | 网络延迟增大 | softirq 被硬中断挤占 | 设置 softirq 优先级、绑定 CPU |

## 6. 知识关联

### 6.1 与内核态/用户态的关系

中断和异常是用户态→内核态切换的两大触发方式之一，与系统调用并列。在 [[10-内核态用户态：特权级与模式切换]] 中，我们学习了 Ring 0/Ring 3 特权级体系——中断机制正是建立在特权级之上的：硬件通过中断将 CPU 从 Ring 3（用户态）拉入 Ring 0（内核态）执行中断处理程序，处理完毕后通过 `iretq` 返回用户态。中断向量表（IDT）的门描述符中包含了目标代码段的 RPL（Requested Privilege Level）设定，这正是模式切换的关键。

### 6.2 与系统调用机制的关系

`int 0x80` 系统调用本质上就是利用中断机制——通过 IDT 第 0x80 号门描述符的陷阱门进入内核。在 [[11-系统调用机制：syscall指令与vDSO优化]] 中，我们对比了 `int 0x80`、`sysenter` 和 `syscall` 三种系统调用指令的性能差异——这也是理解为什么现代 Linux 从 `int 0x80` 迁移到更快 `syscall` 指令的原因（`syscall` 绕过 IDT 查找，直接从 MSR 加载入口，省去了大部分中断处理开销）。vDSO 优化（见 [[11-系统调用机制：syscall指令与vDSO优化]]）也是为了避免不必要的陷入。

### 6.3 与 IO 模型的关系

中断是 I/O 事件的硬件通知机制。在 [[13-IO模型演进：select-poll-epoll-io_uring]] 中，select/poll/epoll 的用户态接口最终都依赖内核通过中断获知设备就绪状态。`epoll` 的用户态事件就绪通知，正是内核在网卡中断（IRQ）和软中断（NET_RX_SOFTIRQ）中检测到数据包到达后，唤醒等待的进程实现的。`io_uring` 的完成通知（CQ ring）也在中断处理路径中更新。

### 6.4 与进程/调度器的关系

时钟中断（timer interrupt, IRQ 0）是操作系统调度器的心跳。在 [[01-进程本质：PCB结构与进程创建流程]] 和 [[02-调度算法：从时间片轮转到CFS与EEVDF]] 中，进程的 CPU 时间片耗尽、上下文切换的触发，都来自周期性时钟中断。每次时钟中断发生时，内核的中断处理程序会更新 jiffies 计数、检查当前进程的时间片余量，并在必要时调用调度器进行进程切换。
