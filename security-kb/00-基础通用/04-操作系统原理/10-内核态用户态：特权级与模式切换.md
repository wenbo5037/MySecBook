## 1. 概述

**用户态（User Mode）** 和**内核态（Kernel Mode）** 是现代操作系统安全模型的基石。将 CPU 的执行权限划分为不同级别，是保护操作系统内核不受用户程序干扰、同时保护用户进程互不侵犯的核心手段。

从历史视角看，1960 年代的大型机（如 IBM System/360）就已引入"监控态（Monitor Mode）"与"问题态（Problem Mode）"的概念。到了 1978 年 Intel 8086 处理器诞生时，x86 架构并未引入特权级——所有代码运行在同一权限层级。真正的特权级保护始于 1985 年的 Intel 80386 处理器，它引入了 4 个特权级（Ring 0 至 Ring 3），至今仍是 x86/x86-64 架构的基础。ARM 架构在 ARMv7 引入了 7 种处理器模式（Processor Mode），ARMv8/A 则定义了 4 个异常级别（Exception Level, EL0-EL3），与 x86 的 Ring 0-3 概念上一一对应但实现机制不同。

操作系统内核运行在最高特权级（x86 Ring 0 / ARM EL1），拥有对所有 CPU 指令、物理内存、I/O 端口的完全访问权限。用户程序运行在最低特权级（x86 Ring 3 / ARM EL0），只能执行非特权指令，无法直接访问硬件或修改关键系统数据结构。当用户程序需要操作系统服务（如读写文件、创建进程、分配内存）时，必须通过受控的入口点（syscall）切换到内核态执行，完成后返回用户态——这个切换过程涉及 CPU 特权级变更、栈切换、寄存器保存与恢复等底层操作，是系统调用（System Call）的基础，也是理解 [[11-系统调用机制：syscall指令与vDSO优化]] 的前提。

从安全视角看，用户态/内核态的边界是**操作系统最重要的安全边界**。攻击者（如恶意软件、漏洞利用代码）的核心目标之一就是突破这个边界——从用户态获得内核态的代码执行权限（即"内核提权"）。历史上众多著名的漏洞利用技术（ret2usr、ROP 内核利用、Spectre/Meltdown）都围绕这个边界展开。防御技术（SMEP、SMAP、KPTI）也都是在加固这个边界。

## 2. 核心原理

### 2.1 CPU 特权级架构

#### 2.1.1 x86 Ring 模型

x86 架构定义了 4 个特权级（Protection Ring），编号 0-3，数字越小特权越高：

```text
┌─────────────────────────────────────────────────┐
│                  Ring 0（内核态）                  │
│         完全访问：所有 CPU 指令、所有内存、I/O       │
│                                                   │
│   ┌─────────────────────────────────────────┐    │
│   │            Ring 1（驱动程序）             │    │
│   │        大多数 OS 不使用此级               │    │
│   │                                         │    │
│   │   ┌─────────────────────────────────┐   │    │
│   │   │        Ring 2（驱动程序）         │   │    │
│   │   │    大多数 OS 不使用此级           │   │    │
│   │   │                                 │   │    │
│   │   │   ┌─────────────────────────┐   │   │    │
│   │   │   │    Ring 3（用户态）       │   │   │    │
│   │   │   │  受限：非特权指令、虚拟内存 │   │   │    │
│   │   │   └─────────────────────────┘   │   │    │
│   │   └─────────────────────────────────┘   │    │
│   └─────────────────────────────────────────┘    │
└─────────────────────────────────────────────────┘
```

**实际使用情况**：Linux 和 Windows 只使用 Ring 0 和 Ring 3 两个级别。Ring 1 和 Ring 2 在现代通用操作系统中被"忽略"——所有内核代码运行在 Ring 0，所有用户代码运行在 Ring 3。一些嵌入式操作系统（如 QNX）会使用 Ring 1 来运行设备驱动程序，实现驱动与内核的进一步隔离。

**特权级检查**：CPU 在每次内存访问和指令执行时都会检查当前特权级（CPL, Current Privilege Level）。CPL 保存在 CS 段寄存器的低 2 位中。当 CPL=0 时为内核态，CPL=3 时为用户态。某些敏感指令（如 `cli`/`sti`、`lgdt`、`mov cr3`、`in`/`out`）在 CPL > 0 时执行会触发 **General Protection Fault（#GP, 异常编号 13）**。

#### 2.1.2 ARM EL 模型

ARMv8-A 架构定义了 4 个异常级别（Exception Level）：

| 异常级别 | 对应角色 | 等效 x86 |
|----------|----------|-----------|
| EL0 | 用户态应用程序 | Ring 3 |
| EL1 | OS 内核 | Ring 0 |
| EL2 | 虚拟机管理器（Hypervisor） | 无直接对应 |
| EL3 | 安全监控器（Secure Monitor / TrustZone） | 无直接对应 |

ARM 的额外层级（EL2/EL3）为虚拟化和安全隔离提供了硬件支持，这是 x86 Ring 模型所不具备的。在 ARM Linux 上，EL0→EL1 的切换通过 `SVC`（Supervisor Call）指令完成，与 x86 的 `syscall` 类似但寄存器约定不同。

### 2.2 模式切换触发机制

用户态→内核态的切换（即"模式切换"或"特权级切换"）有三种主要触发方式：

| 触发方式 | 英文 | 典型场景 | 切换方式 |
|----------|------|----------|----------|
| 系统调用 | System Call | read()、write()、fork() 等 | 主动触发 |
| 中断 | Interrupt | 时钟中断、网卡数据到达、键盘输入 | 外部硬件触发 |
| 异常 | Exception | 除零错误、缺页中断、非法指令 | CPU 内部事件触发 |

**系统调用**是用户态程序**主动**请求内核服务的入口点。在 x86-64 Linux 上，系统调用通过 `syscall` 指令触发（历史上使用 `int 0x80`，`sysenter` 是中间过渡方案）。CPU 执行 `syscall` 时自动完成：保存 RIP 到 RCX、保存 RFLAGS 到 R11、加载 MSRs（STAR/LSTAR）中预设的内核入口地址到 RIP，同时将 CPL 从 3 切换到 0。

**中断**是由外部硬件设备通过中断控制器（如 APIC）向 CPU 发送的信号。当网卡收到数据包、键盘产生按键事件、或时钟中断触发调度器时，CPU 会暂停当前用户态代码的执行，保存上下文，跳转到内核的中断处理程序。

**异常**是 CPU 在执行指令时检测到的错误或特殊情况。例如执行 `div` 指令除数为零（#DE 异常）、访问虚拟地址但对应的物理页尚未映射（#PF 缺页异常）等。异常与中断的区别在于：异常与当前执行的指令直接相关，而中断与当前指令无关。

### 2.3 虚拟地址空间隔离

用户态和内核态的内存隔离依赖于**虚拟地址空间**和**页表（Page Table）**机制。在 x86-64 Linux 上，每个进程有独立的虚拟地址空间，高地址部分（通常 `0xffff800000000000` 以上）映射到内核空间，低地址部分映射到用户空间。

```text
x86-64 Linux 进程虚拟地址空间布局（简化）：

  高地址
  ┌──────────────────────────────────┐ 0xFFFF_FFFF_FFFF_FFFF
  │  内核空间（Kernel Space）          │
  │  所有进程共享同一份内核映射          │
  │  仅 Ring 0 可访问（通过 CR3 的     │
  │  高地址位标记或 KPTI 隔离）          │
  ├──────────────────────────────────┤ 0xFFFF_8000_0000_0000
  │          （未映射/保护区域）          │
  ├──────────────────────────────────┤
  │  栈（Stack）↓                      │
  │  ...                              │
  │  mmap 区域（共享库、匿名映射）       │
  │  ...                              │
  │  堆（Heap）↑                       │
  ├──────────────────────────────────┤ 0x0000_0000_0040_0000
  │  BSS（未初始化数据段）               │
  │  Data（已初始化数据段）              │
  │  Text（代码段，只读+可执行）          │
  └──────────────────────────────────┘ 0x0000_0000_0000_0000
  低地址
```

**关键寄存器**：
- **CR3（x86）/ TTBR0_EL1（ARM）**：页表基地址寄存器，进程切换时更新，指向当前进程的页全局目录（PGD）
- **CR0.PE**：保护模式启用位
- **CR4.SMEP**：Supervisor Mode Execution Prevention，阻止内核执行用户态页面中的代码
- **CR4.SMAP**：Supervisor Mode Access Prevention，阻止内核直接访问用户态内存

## 3. 详细知识点

### 3.1 x86-64 Linux syscall 约定

Linux x86-64 的系统调用使用 `syscall` 指令（AMD 引入的 `SYSCALL`/`SYSRET` 指令对），取代了传统的 `int 0x80` 中断方式。

#### 3.1.1 寄存器约定

| 寄存器 | 用途 | 备注 |
|--------|------|------|
| RAX | 系统调用号（输入）/ 返回值（输出） | 返回值 < 0 表示错误（-errno） |
| RDI | 第 1 个参数 | |
| RSI | 第 2 个参数 | |
| RDX | 第 3 个参数 | |
| R10 | 第 4 个参数 | 注意：不是 RCX（syscall 指令会覆盖 RCX） |
| R8 | 第 5 个参数 | |
| R9 | 第 6 个参数 | |
| RCX | syscall 返回地址（输出） | 被 syscall 指令覆盖 |
| R11 | syscall 返回 RFLAGS（输出） | 被 syscall 指令覆盖 |

```text
syscall 执行流程：

用户态                              内核态
┌──────────────┐                ┌──────────────────┐
│ RAX = 调用号  │                │                   │
│ RDI = arg1   │                │  entry_SYSCALL_64 │
│ RSI = arg2   │ ──syscall───>  │  ├─ 保存寄存器     │
│ RDX = arg3   │   CPL: 3→0     │  ├─ 查 syscall 表  │
│ ...          │   RIP → LSTAR  │  ├─ 执行 handler   │
│              │                │  ├─ 恢复寄存器     │
│              │ <──sysret───   │  └─ sysret 返回    │
│ RAX = 返回值  │   CPL: 0→3     │                   │
└──────────────┘                └──────────────────┘
```

#### 3.1.2 syscall 指令 vs int 0x80 vs sysenter

| 指令 | 引入时间 | 性能 | 备注 |
|------|----------|------|------|
| `int 0x80` | 80386 (1985) | 最慢（~100+ cycles） | 走中断描述符表（IDT），通用但慢 |
| `sysenter` | Pentium II (1997) | 快（~30 cycles） | Intel 专用，不保存返回地址 |
| `syscall` | AMD K6 (1998) / x86-64 | 最快（~20 cycles） | AMD 首创，x86-64 标准 |

在现代 x86-64 Linux 上，libc（如 glibc）总是使用 `syscall` 指令。`int 0x80` 仍可用于 32 位兼容模式（通过 IA32 兼容层），但性能最差。

### 3.2 ARM64 Linux syscall 约定

ARM64 (AArch64) Linux 使用 `SVC #0`（Supervisor Call）指令触发系统调用：

| 寄存器 | 用途 |
|--------|------|
| X8 | 系统调用号 |
| X0 | 第 1 个参数 / 返回值 |
| X1 | 第 2 个参数 |
| X2 | 第 3 个参数 |
| X3 | 第 4 个参数 |
| X4 | 第 5 个参数 |
| X5 | 第 6 个参数 |

ARM64 与 x86-64 的关键差异：ARM64 使用 X0 既作为第一个参数输入又作为返回值输出（函数调用约定），而 x86-64 用 RAX 专门作为返回值。ARM64 的系统调用号分配与 x86-64 不同，且部分系统调用的行为存在差异（如 `mmap` 的参数位置不同）。

### 3.3 模式切换的完整流程

以 `read()` 系统调用为例，完整的用户态→内核态→用户态流程：

```text
1. 用户态：调用 read(fd, buf, count)
   └─ glibc 的 read() 包装函数
      └─ 将 sys_read 的调用号放入 RAX
         将 fd, buf, count 放入 RDI, RSI, RDX

2. 触发切换：syscall 指令
   ├─ CPU 自动执行：
   │   ├─ 保存 RIP → RCX
   │   ├─ 保存 RFLAGS → R11
   │   ├─ 加载 LSTAR MSR → RIP（内核入口）
   │   └─ CPL 从 3 切换到 0

3. 内核态：entry_SYSCALL_64
   ├─ 保存所有用户态寄存器到 pt_regs 结构
   ├─ 切换到内核栈（通过 per-CPU 的 TSS）
   ├─ 调用 __x64_sys_read()
   │   └─ syscalls table[nr] → sys_read()
   │       └─ vfs_read() → 文件系统 → 驱动
   ├─ 从内核栈恢复寄存器到 pt_regs
   └─ 执行 sysret 指令

4. 返回用户态：sysret
   ├─ CPL 从 0 切换到 3
   ├─ RCX → RIP（返回地址）
   ├─ R11 → RFLAGS
   └─ RAX = 返回值（成功返回读取字节数，失败返回 -errno）
```

### 3.4 vDSO（virtual Dynamic Shared Object）

vDSO 是内核映射到每个用户进程地址空间的一小段共享库代码，用于加速不需要真正进入内核态的"伪系统调用"。最经典的例子是 `gettimeofday()`——如果每次获取时间都要触发一次 `syscall`，频繁调用会严重影响性能（每个 syscall 有 ~20 个周期的切换开销）。

```text
vDSO 工作原理：

┌─────────────────────────────┐
│         用户进程              │
│                             │
│  gettimeofday() ──调用──>   │
│     ↓                       │
│  vDSO 中的 __vdso_          │
│  gettimeofday():            │
│     ├─ 读取共享内存页         │ ← 内核在时钟中断时更新此页
│     │  中的当前时间           │
│     └─ 直接返回              │ ← 无需 syscall！
│                             │
└─────────────────────────────┘
         ↑
    内核定期更新（通过时钟中断）

vs.

┌─────────────────────────────┐
│  无 vDSO 的旧方案：           │
│  gettimeofday() → syscall   │ → 每次都要切换到内核态
│  （开销 ~100-200 cycles）    │
└─────────────────────────────┘
```

**vDSO 中的函数**（Linux 5.x+ 典型包含）：

| 函数 | 用途 | 避免的 syscall |
|------|------|----------------|
| `__vdso_gettimeofday` | 获取当前时间 | `gettimeofday()` |
| `__vdso_clock_gettime` | 获取时钟值 | `clock_gettime()` |
| `__vdso_clock_getres` | 获取时钟精度 | `clock_getres()` |
| `__vdso_time` | 获取时间戳 | `time()` |

### 3.5 vsyscall vs vDSO

**vsyscall**（Virtual System Call）是 Linux 的早期方案（内核 2.6 之前），将固定地址的"系统调用模拟代码"映射到每个进程的固定虚拟地址（`0xffffffffff600000`）。

```text
vsyscall 页面布局（已废弃）：

  0xffffffffff600000: vsyscall 页面（只读）
  ├─ gettimeofday 模拟代码
  ├─ time 模拟代码
  └─ getcpu 模拟代码

问题：
- 固定虚拟地址 → 可被 ret2usr/ROP 攻击利用
- 代码只读但地址固定 → 安全隐患
- 已在内核 5.x 中被标记为"可选禁用"，最终废弃
```

**vDSO 取代 vsyscall 的原因**：
- vsyscall 页面映射在固定地址，成为内核攻击的稳定跳板（ROP gadget）
- vsyscall 是静态的——内核无法更新其中的代码
- vDSO 使用 ASLR 随机化地址，且由内核控制内容

### 3.6 用户态内存访问与缺页中断

当用户态程序访问其虚拟地址空间中的内存时，如果对应的物理页尚未映射或权限不匹配，CPU 会产生**缺页异常（Page Fault, #PF, 异常编号 14）**。内核的缺页处理程序负责：

1. 查找进程的 VMA（Virtual Memory Area）链表，确定该地址属于哪个 VMA
2. 如果是合法的延迟分配（anonymous page），分配物理页并填充零
3. 如果是文件映射（file-backed page），从磁盘读取数据到物理页
4. 如果是非法访问（段错误），向进程发送 SIGSEGV 信号

**内核态访问用户态内存**：内核代码不能直接解引用用户态指针——因为用户态指针可能指向未映射的地址，或被用户态恶意修改（TOCTOU 攻击）。内核必须使用 `copy_from_user()` 和 `copy_to_user()` 函数，这些函数内部会：

1. 验证用户态指针是否在合法的用户地址范围内
2. 使用临时页表映射来安全地访问用户态内存
3. 处理缺页异常（如果页面不在内存中）
4. 如果任何步骤失败，返回 `-EFAULT`

```c
/* 内核代码中安全的用户态内存访问示例 */
ssize_t my_read(struct file *filp, char __user *buf, size_t count, loff_t *pos) {
    char kernel_buf[256];
    
    /* 从设备读取数据到内核缓冲区 */
    int len = device_read(kernel_buf, sizeof(kernel_buf), pos);
    
    /* 安全地复制到用户态 */
    if (copy_to_user(buf, kernel_buf, len))
        return -EFAULT;
    
    return len;
}
```

**TOCTOU（Time-of-Check-Time-of-Use）攻击**：攻击者在内核检查用户态指针和实际使用指针之间修改指针值，使内核访问到非法地址。`copy_to_user()` / `copy_from_user()` 的原子性验证是防御 TOCTOU 的关键。

### 3.7 安全视角：Ring 0 攻击面分析

用户态→内核态的安全边界是操作系统最重要的攻击面：

| 攻击向量 | 描述 | 缓解措施 |
|----------|------|----------|
| **ret2usr** | 将用户态代码注入到用户地址空间，然后通过内核漏洞跳转到该代码执行（此时 CPU 已在 Ring 0） | SMEP（阻止内核执行用户页面代码） |
| **内核栈溢出** | 覆写内核栈上的返回地址/函数指针，控制内核执行流 | KASLR、Stack Canaries、Shadow Call Stack |
| **内核地址泄露** | 泄露内核地址以绕过 KASLR | 限制 `/proc/kallsyms` 访问、清理 dmesg 输出 |
| **vsyscall 信息泄露** | 通过 vsyscall 页面泄露内核基地址 | 禁用 vsyscall、迁移到 vDSO |
| **Spectre/Meltdown** | 利用推测执行绕过内存保护读取内核数据 | KPTI（Kernel Page Table Isolation）、IBRS/STIBP |
| **SMEP/SMAP 绕过** | 利用 ROP 链修改 CR4 寄存器的 SMEP/SMAP 位 | 内核 CR4 保护（cr4_pinned_bits） |

**SMEP（Supervisor Mode Execution Prevention）**：CR4 的第 20 位，启用后内核不能执行用户态地址空间中的代码。如果内核漏洞将 RIP 跳转到用户态地址，CPU 会触发 #PF。

**SMAP（Supervisor Mode Access Prevention）**：CR4 的第 21 位，启用后内核不能读写用户态地址空间中的数据。内核必须显式地通过 `copy_from_user()` / `copy_to_user()` 来访问用户态数据。

**KPTI（Kernel Page Table Islection）**：Meltdown 漏洞的缓解措施。KPTI 为每个进程维护两套页表：一套包含完整的用户+内核映射（用户态使用），另一套只包含内核映射（内核态使用）。当 CPU 处于用户态时，内核地址空间的映射被完全移除，即使通过推测执行也无法访问。

## 4. 实战与示例

### 4.1 strace 跟踪系统调用

`strace` 是最常用的系统调用追踪工具，通过 `ptrace()` 机制拦截和记录进程的所有系统调用：

```bash
# 跟踪简单命令的系统调用
strace ls /tmp

# 跟踪网络相关系统调用
strace -e trace=network curl https://example.com

# 跟踪文件操作
strace -e trace=open,read,write cat /etc/passwd

# 统计系统调用耗时
strace -c ls /tmp

# 输出格式化时间戳
strace -T ls /tmp
# 输出示例：
# execve("/bin/ls", ["ls"], 0x7ffd...) = 0    <0.000123>
# brk(NULL)                               = 0x55a... <0.000015>
# openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3 <0.000034>
```

### 4.2 perf trace 分析系统调用

`perf trace` 是比 `strace` 更高效的系统调用追踪工具，使用内核的 `perf_events` 子系统而非 `ptrace`，对被跟踪进程的干扰更小：

```bash
# 跟踪系统调用（轻量级）
perf trace ls /tmp

# 按耗时排序
perf trace --summary ls -R /tmp

# 跟踪特定系统调用
perf trace -e openat,read,write --duration 10

# 统计模式
perf stat -e syscalls:sys_enter_read -- ls /tmp
```

### 4.3 手写汇编触发 syscall

```c
/* 直接通过内联汇编发起 syscall，不依赖 libc */
#include <stdio.h>

long my_syscall1(long syscall_no, long arg1) {
    long ret;
    __asm__ volatile (
        "mov %1, %%rax\n\t"     /* 调用号 → RAX */
        "mov %2, %%rdi\n\t"     /* arg1 → RDI */
        "syscall\n\t"
        "mov %%rax, %0\n\t"     /* 返回值 → ret */
        : "=r"(ret)
        : "r"(syscall_no), "r"(arg1)
        : "rax", "rdi", "rcx", "r11", "memory"
    );
    return ret;
}

long my_syscall3(long syscall_no, long arg1, long arg2, long arg3) {
    long ret;
    __asm__ volatile (
        "mov %1, %%rax\n\t"
        "mov %2, %%rdi\n\t"
        "mov %3, %%rsi\n\t"
        "mov %4, %%rdx\n\t"
        "syscall\n\t"
        "mov %%rax, %0\n\t"
        : "=r"(ret)
        : "r"(syscall_no), "r"(arg1), "r"(arg2), "r"(arg3)
        : "rax", "rdi", "rsi", "rdx", "rcx", "r11", "memory"
    );
    return ret;
}

int main(void) {
    /* SYS_write = 1 (x86-64) */
    const char msg[] = "Hello from raw syscall!\n";
    long ret = my_syscall3(1, 1 /*stdout*/, (long)msg, sizeof(msg) - 1);
    printf("syscall returned: %ld\n", ret);
    
    /* SYS_getpid = 39 (x86-64) */
    long pid = my_syscall1(39, 0);
    printf("pid from syscall: %ld\n", pid);
    
    return 0;
}
```

```bash
# 编译运行
gcc -o raw_syscall raw_syscall.c -Wall
./raw_syscall
```

### 4.5 内核模块：读取当前特权级

```c
/* 内核模块示例：显示当前 CPU 的特权级 */
#include <linux/module.h>
#include <linux/kernel.h>
#include <asm/ptrace.h>

static int __init check_cpl_init(void) {
    unsigned long cr4;
    
    /* 读取 CR4 寄存器检查 SMEP/SMAP */
    asm volatile("mov %%cr4, %0" : "=r"(cr4));
    
    printk(KERN_INFO "Current CR4 = 0x%lx\n", cr4);
    printk(KERN_INFO "SMEP: %s\n", (cr4 & (1 << 20)) ? "enabled" : "disabled");
    printk(KERN_INFO "SMAP: %s\n", (cr4 & (1 << 21)) ? "enabled" : "disabled");
    
    /* 在内核态执行，CPL 应为 0 */
    unsigned long cs;
    asm volatile("mov %%cs, %0" : "=r"(cs));
    printk(KERN_INFO "CS register = 0x%lx, CPL = %lu\n", cs, cs & 3);
    
    return 0;
}

static void __exit check_cpl_exit(void) {
    printk(KERN_INFO "Module unloaded\n");
}

module_init(check_cpl_init);
module_exit(check_cpl_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Check CPU privilege level");
```

## 5. 常见坑与避坑指南

### 5.1 errno 是线程局部的

**问题**：`errno` 是一个宏，展开为 `(*__errno_location())`，指向线程局部存储（TLS）中的错误码变量。如果在检查 `errno` 之前有其他系统调用或库函数修改了 `errno`，会得到错误的错误码。

```c
/* 错误示范 */
FILE *fp = fopen("nonexistent.txt", "r");
if (fp == NULL) {
    /* 此处 errno 可能已被后续操作修改 */
    printf("Error: %d\n", errno);  // 可能不是 ENOENT
}

/* 正确做法 */
FILE *fp = fopen("nonexistent.txt", "r");
if (fp == NULL) {
    int saved_errno = errno;       // 立即保存
    printf("Error: %d\n", saved_errno);
    /* 后续操作不会影响 saved_errno */
}
```

### 5.2 syscall 返回值检查

**问题**：直接使用汇编 `syscall` 指令时，返回值在 RAX 中。x86-64 Linux 的 syscall 返回约定：RAX >= 0 表示成功，RAX < 0 表示错误（`-errno`）。但很多人误以为 0 是唯一的成功标志。

```c
/* 正确的 syscall 返回值检查 */
long ret = my_syscall3(SYS_write, fd, buf, len);

/* 错误：ret == 0 只表示写了 0 字节，不一定是错误 */
if (ret == 0) { /* ... */ }

/* 正确：检查负值 */
if (ret < 0) {
    errno = -ret;  /* 转换回正的 errno 值 */
    perror("syscall failed");
}

/* 对于 write，0 表示写入 0 字节（在某些情况下是合法的） */
if (ret >= 0) {
    printf("写入了 %ld 字节\n", ret);
}
```

### 5.3 vsyscall 页面信息泄露

**问题**：即使在现代 Linux 上禁用了 vsyscall 执行，vsyscall 页面仍然存在于进程的虚拟地址空间中。如果内核没有正确清理该页面的内容，可能泄露内核信息（如时间戳精度等）。

```bash
# 检查 vsyscall 页面
cat /proc/<pid>/maps | grep "ffffffffff600000"

# 内核参数禁用 vsyscall
# 在 /etc/default/grub 中添加：
GRUB_CMDLINE_LINUX="vsyscall=none"
# 或
GRUB_CMDLINE_LINUX="vsyscall=xonly"  # 仅允许执行，不可读取
```

**当前内核默认行为**：Linux 4.4+ 默认 `vsyscall=xonly`（只可执行），Linux 5.x+ 可完全禁用。检查方法：

```bash
cat /proc/sys/kernel/vsyscall
# 返回：0=none, 1=xonly, 2=emulate
```

### 5.4 32/64 位兼容层问题

**问题**：在 64 位 Linux 上运行 32 位程序时，系统调用通过 IA32 兼容层处理。32 位程序使用 `int 0x80` 触发系统调用，调用号与 64 位不同（如 `__NR_write` 在 32 位是 4，在 64 位是 1）。如果混用会导致调用到错误的系统调用。

```c
/* 32 位兼容问题示例 */
#include <stdio.h>

/* 如果用 int 0x80 调用，32 位和 64 位的调用号不同 */
/* 32 位: __NR_write = 4 */
/* 64 位: __NR_write = 1 */
/* 在 64 位程序中使用 32 位调用号会调用到错误的 syscall */

/* glibc 的解决办法：vsyscall/vDSO 自动适配 */
```

### 5.5 KPTI 的性能开销

**问题**：KPTI（Kernel Page Table Isolation）在每次用户态→内核态切换时都需要切换页表（加载新的 CR3），这会增加 TLB（Translation Lookaside Buffer）刷新开销，导致系统调用密集型应用性能下降 5%-30%。

```bash
# 查看 KPTI 是否启用
cat /proc/cpuinfo | grep pti
# 或
dmesg | grep "Page Table Isolation"

# 关闭 KPTI（仅用于不受 Meltdown 影响的 CPU）
# 在 /etc/default/grub 中添加：
GRUB_CMDLINE_LINUX="pti=off"
```

**缓解策略**：对于系统调用密集的应用，考虑使用 vDSO 中的函数（如 `clock_gettime()`）来减少 syscall 次数；或使用 `io_uring`（见 [[13-IO模型演进：select-poll-epoll-io_uring]]）将多个 I/O 操作批量提交。

### 5.6 常见陷阱汇总

| 陷阱 | 症状 | 根因 | 解决方案 |
|------|------|------|----------|
| 忘记检查 errno | 错误信息不准确 | errno 被后续操作覆盖 | 立即保存 errno 到局部变量 |
| 混用 int 0x80 和 syscall | 段错误或数据错误 | 32/64 位调用号不同 | 始终使用与架构匹配的调用方式 |
| 直接读取 vsyscall 页 | 信息泄露 | vsyscall 页内容未清理 | 禁用 vsyscall（`vsyscall=none`） |
| 忘记 copy_to_user | 内核崩溃（oops） | 内核直接解引用用户态指针 | 必须使用 `copy_to_user()` / `copy_from_user()` |
| KPTI 性能回归 | 系统调用密集应用变慢 | 额外的页表切换开销 | 使用 vDSO、io_uring、batch syscall |

## 6. 知识关联

### 6.1 与系统调用机制的关系

本文详细讲解了用户态/内核态切换的硬件机制和模式切换流程，是理解 [[11-系统调用机制：syscall指令与vDSO优化]] 的硬件基础。系统调用是用户态程序进入内核态的最常见入口，而 vDSO 是避免不必要模式切换的关键优化。理解本文中的寄存器约定（RAX/RDI/RSI 等）和 `syscall` 指令的执行流程，是掌握系统调用机制的前提。

### 6.2 与中断和异常的关系

中断和异常是除系统调用外触发模式切换的另外两种机制。在 [[12-中断与异常：中断向量与处理流程]] 中，我们深入学习了中断控制器（PIC→APIC）、中断向量表（IDT）、以及中断处理的上半部/下半部机制。中断处理是操作系统的核心——时钟中断驱动调度器、I/O 中断驱动设备驱动——它们都涉及从用户态（或内核态）到中断处理程序的切换。

### 6.3 与推测执行漏洞的关系

用户态/内核态边界的安全性直接关系到 Spectre/Meltdown 等推测执行漏洞。在 [[10-推测执行漏洞：Spectre与Meltdown原理]] 中，Meltdown 的核心攻击就是利用 CPU 的推测执行，在 KPTI 引入之前，通过用户态程序读取内核内存——因为内核内存映射在每个进程的地址空间中（只是被页表权限位保护），而推测执行可以绕过这个权限检查。KPTI 的引入彻底改变了这个攻击面：内核地址空间在用户态时完全不可见（从页表中移除），即使推测执行也无法访问。

### 6.4 与进程模型的关系

用户态/内核态切换是 [[01-进程本质：PCB结构与进程创建流程]] 中进程执行的核心环节。每个进程都有自己独立的虚拟地址空间（通过 CR3/TTBR0 切换），但在内核态中所有进程共享同一份内核映射。进程调度器（[[02-调度算法：从时间片轮转到CFS与EEVDF]]）在时钟中断处理程序中运行，此时 CPU 处于内核态——调度器通过修改下一个进程的 CR3 来切换虚拟地址空间，实现进程间隔离。
