## 1. 概述

进程为程序提供了资源隔离与地址空间，但进程创建、切换成本高，且进程间通信复杂。为满足"共享数据 + 多路执行"的需求，操作系统引入**线程(Thread)**：线程是进程内部的执行单元，同进程的多个线程**共享**代码段、数据段、堆和打开的文件，但各自拥有独立的栈、寄存器上下文和线程局部存储(TLS)。

**线程 vs 进程**：

| 维度 | 进程(Process) | 线程(Thread) |
|------|--------------|--------------|
| 调度单位 | 进程（现代内核调度线程） | 线程（调度粒度更细） |
| 地址空间 | 各自独立 | 同进程线程共享 |
| 资源隔离 | 强（崩溃不波及其他进程） | 弱（一个线程崩溃可拖垮整个进程） |
| 创建/切换开销 | 大（需复制/重建地址空间、页表、fd 表） | 小（共享大部分结构） |
| 通信方式 | IPC（管道/共享内存/信号等） | 直接读写共享变量（需同步） |
| 系统调用 | fork/exec | pthread_create / clone |

从第一性原理看：**进程是资源分配单位，线程是 CPU 调度/执行单位**。把资源与执行分离是线程模型的核心思想——这也是现代高性能服务器的设计基石（连接→线程/goroutine 而非进程）。

从安全视角看，线程共享地址空间带来便利的同时放大了风险：一个线程的缓冲区溢出可直接破坏同进程其他线程的数据；数据竞争（data race)导致的不确定行为也常被利用。理解线程模型对编写可靠并发系统与审计并发安全至关重要。

## 2. 核心原理

### 2.1 线程模型：ULT / KLT / 混合

依据"谁来管理线程的创建、调度、切换"，分为三类模型：

```ascii
N:1 用户级线程(ULT)         1:1 内核级线程(KLT)          M:N 混合模型
库调度器                     内核调度                    用户级+内核级
+---------+                 +---------+                 +---------+
| ULT ULT |  用户态          | KThread |                  | ULT ULT |
| (库调度) |                 |         |                  | (库调度)|
+----|----+                 +----|----+                 +----|----+
     | 映射到1个OS线程             | 每线程=1内核线程          | 多对多
+----+----+                 +----+----+                 +----+----+
|  OS线程  |   内核           | CPU CPU |                  | K K    |
+---------+                 +---------+                 |(多线程)|
                                                       +----|----+
                                                            |
                                                       +----+----+
                                                       | CPU CPU  |
                                                       +---------+
```

| 模型 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| 用户级线程 ULT (N:1) | 线程由用户态线程库管理，与内核无关 | 切换无需陷入内核，开销极小；可在非线程操作系统上实现 | 一个阻塞系统调用会阻塞整个进程（所有线程）；无法利用多核并行 |
| 内核级线程 KLT (1:1) | 每个用户线程对应一个内核线程 | 可被多核调度、真正并行；阻塞不阻塞其他线程 | 创建/切换需进内核，开销大；线程数量受内核资源限制 |
| 混合模型 (M:N) | 用户态库管理 M 个用户线程，映射到 N 个内核线程 | 兼顾低切换开销与多核并行 | 实现复杂，调度/映射逻辑难调好；用户态与内核态嵌套调度易出偏差 |

**现代容器化 OS 的真实选择**：
- **Linux/Windows 主流是 1:1**（pthread/Windows Thread → 内核线程）。实现简单可靠。
- **Go runtime 是 M:N（GMP）**：M 个 goroutine 映射到 N 个 OS 线程。
- **Erlang BEAM、Java(传统)、NPTL**：各有取舍。Java 早期是 N:1（绿色线程 green thread），后改为 1:1；现代 JVM 支持虚拟线程(Virtual Threads, Java 21+)本质是 M:N 用户态协程。

### 2.2 线程的调度粒度与上下文

内核调度器调度的最小单位是线程（内核线程/KSE, Kernel Scheduling Entity）。Linux 中每个线程是一个独立 task_struct，共享 mm 等资源。

```ascii
线程切换示意（同进程内）
      线程A运行            保存A的上下文         恢复B的上下文         线程B运行
CPU  |=====A=====|----save(A)---->|====load(B)====|=====B=====|
                        ↑ 主要保存/恢复 SP、PC、寄存器
        由于共享 mm，不需要换页表 → TLB 不需刷新
        → 线程切换比进程切换快（省去 mm 切换与页表切换开销）
```

这是线程在性能上优于进程的关键：**同进程线程切换不切换地址空间**，避免了 TLB(Translation Lookaside Buffer) 刷新和页表切换的巨大代价。见 [[05-上下文切换：开销来源与实测分析]]。

|------|:-------:|:-------:|:----------------|
| 地址空间(mm) | ✔ | | ✔ |
| 代码段 | ✔ | | ✔ |
| 数据段/全局变量 | ✔ | | ✔ |

## 3. 详细知识点

### 3.1 Linux 线程实现：NPTL

历史上 Linux 线程实现经历了：
- **LinuxThreads**（早期）：用 `clone()` 的早期实现，线程模型有缺陷（信号处理、getpid 不一致）。
- **NPTL(Native POSIX Thread Library)**：glibc ≥ 2.3.2 默认。由 Ulrich Drepper 等设计，基于 `clone()` 与内核的 tgid/CLONE_THREAD 支持，完全符合 POSIX 线程规格。

验证：
```bash
getconf GNU_LIBPTHREAD_VERSION
# 输出如: NPTL 2.31
```

**NPTL 核心**：
- 线程由 `clone()` + 一组标志创建（本质是"共享资源的轻量进程"）。
- 引入 **tgid**(thread group id)概念：`getpid()` 返回 tgid，同一线程组所有线程 tgid 相同、tid 不同。
- 内核调度器直接调度每个线程（1:1）。
- 信号、exit、wait 按线程组语义处理（一个线程 exit 触发整个进程 exit 取决于语义）。

```c
// glibc pthread_create 内部等价调用（示意）
clone(
    start_thread,        // 线程入口包装函数
    child_stack,         // 新线程独立栈
    CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | ...,
    arg);
```

### 3.2 pthread 关键 API

```c
#include <pthread.h>

int pthread_create(pthread_t *thread, const pthread_attr_t *attr,
                   void *(*start_routine)(void *), void *arg);
int pthread_join(pthread_t thread, void **retval);
int pthread_detach(pthread_t thread);
int pthread_exit(void *retval);
pthread_t pthread_self(void);
int pthread_equal(pthread_t t1, pthread_t t2);
```

- `pthread_create`：创建线程，起始函数为 `start_routine`，参数仅一个指针 `arg`。
- `pthread_join`：阻塞等待线程结束并回收其资源，可通过 `retval` 取返回值。
- `pthread_detach`：分离线程，使其中止后自动回收资源（不再需要 join）。
- **每一个 join 线程都需 join**，否则线程结束不回收资源（线程泄漏）。

**线程属性 pthread_attr_t**：
```c
pthread_attr_t attr;
pthread_attr_init(&attr);
pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
pthread_attr_getstacksize(&attr, &stacksize);      // 默认栈大小
pthread_attr_setstacksize(&attr, 1 << 20);         // 设置栈 1MB
pthread_attr_setguardsize(&attr, 4096);            // 溢出保护页
```

**互斥锁(Mutex)**：
```c
pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_lock(&mtx);
pthread_mutex_unlock(&mtx);

// 递归锁：允许同一线程重复加锁
pthread_mutexattr_t ma;
pthread_mutexattr_init(&ma);
pthread_mutexattr_settype(&ma, PTHREAD_MUTEX_RECURSIVE);
pthread_mutex_t rmtx;
pthread_mutex_init(&rmtx, &ma);

// 带超时/尝试的锁（避免死锁）
pthread_mutex_trylock(&mtx);
pthread_mutex_timedlock(&mtx, &abs_timeout);
```

**条件变量(Condition Variable)**：
```c
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

// 生产者/消费者中的等待
pthread_mutex_lock(&m);
while (queue.empty())               // 必须 while，防"虚假唤醒"
    pthread_cond_wait(&cond, &m);   // 原子地释放 m 并睡眠
// 取出数据...
pthread_mutex_unlock(&m);

// 通知
pthread_mutex_lock(&m);
pthread_cond_signal(&cond);   // 唤醒一个等待者
pthread_cond_broadcast(&cond);// 唤醒所有
pthread_mutex_unlock(&m);
```

条件变量等待典型用法见第 4 节生产者-消费者示例。

### 3.3 线程私有资源详解

1. **栈(Stack)**：每个线程独立栈。大小默认 `ulimit -s`（常见 8MB）。栈在创建线程时分配，溢出→栈溢出错误/段错误。
2. **寄存器上下文**：SP、PC、通用寄存器、FPU/浮点状态在切换时保存。
3. **TLS(Thread-Local Storage)**：每个线程独有的存储区。编译器支持 `__thread` 关键字；POSIX 提供 `pthread_key_t`：

```c
// C11 _Thread_local 与 GCC __thread
_Thread_local int tls_counter = 0;
__thread int tls_counter2 = 0;

// POSIX 线程特定数据 pthread_key_t
pthread_key_t key;
pthread_key_create(&key, destructor);       // 第二个参数为销毁回调
pthread_setspecific(key, value);            // 设置
pthread_getspecific(key);                    // 读取
```

4. **errno**：每个线程独立 errno（glibc 通过 TLS 实现），避免线程间污染。

### 3.4 线程共享资源详解

1. **代码段**：所有线程执行同一段代码。
2. **数据段/全局与静态变量**：线程共享，可被任意线程读写——这是并发同步问题的根源。
3. **堆**：`malloc/free` 操作同一堆，必须线程安全（glibc ptmalloc 带锁/竞技场 arena）。
4. **文件描述符表**：线程共享 fd 表格，打开/关闭影响整个进程。
5. **信号处理函数表**：共享（CLONE_SIGHAND），但信号发送到特定线程还是进程取决于目标。
6. **当前工作目录、umask、资源限制(getrlimit)**：进程级共享。

### 3.5 线程安全：可重入函数、原子操作、内存屏障

#### 3.5.1 可重入函数 vs 线程安全

- **可重入(reentrant)**：函数可被同一线程中断后再次安全调用（无静态状态、无全局修改）。
- **线程安全(thread-safe)**：多线程并发调用结果正确（可能通过锁实现，但可重入不需锁）。
- 二者不完全等价：可重入函数一定线程安全（在合适条件下），但线程安全函数不一定是可重入的。

```c
// 不可重入：使用静态缓冲区，多线程并发调用会互相覆盖
char *strtok(char *str, const char *delim);   // 有静态内部状态

// 可重入版本：状态由调用者显式传递
char *strtok_r(char *str, const char *delim, char **saveptr);

// 线程安全但不可重入：加锁但要小心信号场景死锁
```

`man 7 pthreads` 中列出哪些函数是 MT-Safe(线程安全)、MT-Unsafe。

#### 3.5.2 原子操作

现代硬件提供原子指令（x86 的 `lock` 前缀、`cmpxchg`，ARM 的 `ldxr/stxr`）：

```c
#include <stdatomic.h>

atomic_int counter = ATOMIC_VAR_INIT(0);
atomic_fetch_add(&counter, 1);      // 原子自增
int v = atomic_load(&counter);
atomic_store(&counter, 10);

// C11 GCC __atomic 内置
__atomic_add_fetch(&x, 1, __ATOMIC_SEQ_CST);
__atomic_compare_exchange_n(&x, &expected, desired, 0, __ATOMIC_SEQ_CST, __ATOMIC_SEQ_CST);
```

原子操作保证不被打断，但**互斥锁基于原子操作 + 内存屏障**实现，更广阔。

#### 3.5.3 内存屏障与内存序

由于编译器重排 + CPU 乱序执行，指令可能被重排。内存屏障(memory barrier)阻止重排，保证可见性/顺序。

```c
// GCC 原子内存序
__ATOMIC_RELAXED   // 只保证原子性，不保证顺序
__ATOMIC_ACQUIRE   // 本线程后续读不能被重排到此之前
__ATOMIC_RELEASE   // 本线程此前写不能被重排到此之后
__ATOMIC_SEQ_CST   // 全顺序一致（默认，最重）
```

经典无锁队列的实现正是依赖 acquire/release 等内存序配合。理解内存序对排查诡异并发 bug 至关重要。

### 3.6 Go 的 goroutine：M:N 调度模型

Go 的并发原语是 **goroutine**，由 Go runtime 用户态调度器管理，采用 M:N 模型。

**GMP 模型**：
- **G(goroutine)**：轻量协程，栈可动态增长（初始 2KB~64KB 起，按需扩容）。
- **M(machine)**：OS 线程（真正的内核线程），runtime 调度器把 G 放到 M 上执行。
- **P(processor)**：逻辑处理器，是 M 与 G 之间的调度中间层，维护本地 G 队列；`GOMAXPROCS` 决定 P 的数量（默认 = CPU 核数）。

```ascii
Go GMP 模型
       全局 G 队列
       +---------+
       |  G G G  |
       +----|----+
   +--------+--------+
   |        |        |
 本地队列 本地队列  本地队列
 +------+ +------+ +------+
 | P0:  | | P1:  | | P2:  |
 | GGG  | | G G  | |   G  |
 +--|---+ +--|---+ +--|---+
    |        |        |
   M0       M1       M2   <- OS 线程
    |        |        |
   CPU0    CPU1     CPU2
```

**关键机制**：
- **工作窃取(work stealing)**：某 P 本地队列为空时，从全局队列或其他 P 偷取 G，保持各核负载均衡。
- **栈增长**：goroutine 栈从 2KB 开始，通过编译器的栈分裂(stack splitting) 或 栈复制(stack copying, Go 1.3+) 动态扩缩。
- **阻塞处理**：goroutine 做阻塞系统调用时，runtime 会把它从 P 摘出，让出该 P 给其他 G；系统调用完成后该 G 再被重新排队——这就是"m:n"的意义。
- **对比 OS 线程**：goroutine 切换在用户态完成，开销约几十 ns，远低于 OS 线程切换（微秒级）；内存占用小，可轻松创建数十万 goroutine，而 OS 线程受栈大小与内核资源限制。

**GOMAXPROCS 影响**：
```bash
export GOMAXPROCS=8      # 限制并发 OS 线程数
go run -gcflags '...'    # 程序代码侧
```

`runtime.GOMAXPROCS(0)` 返回当前值。P 的数量决定了同时运行的 goroutine 数（非并发数，只是并行度）。

## 4. 实战与示例

### 4.1 C pthread 生产者-消费者（条件变量 + 互斥锁）

```c
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
#include <unistd.h>

#define BUFSIZE 5

int buf[BUFSIZE];
int head = 0, tail = 0, count = 0;
pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t not_full  = PTHREAD_COND_INITIALIZER;  // 缓冲区有空位
pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;  // 缓冲区有数据

void *producer(void *arg) {
    int id = *(int *)arg;
    for (int i = 0; i < 20; i++) {
        pthread_mutex_lock(&mtx);
        while (count == BUFSIZE)                 // while，非 if
            pthread_cond_wait(&not_full, &mtx);  // 等空位
        buf[tail] = i;
        tail = (tail + 1) % BUFSIZE;
        count++;
        printf("[P%d] produce %d (count=%d)\n", id, i, count);
        pthread_cond_signal(&not_empty);         // 通知消费者
        pthread_mutex_unlock(&mtx);
        usleep(rand() % 3000);
    }
    return NULL;
}

void *consumer(void *arg) {
    int id = *(int *)arg;
    for (int i = 0; i < 20; i++) {
        pthread_mutex_lock(&mtx);
        while (count == 0)                       // while，非 if
            pthread_cond_wait(&not_empty, &mtx); // 等数据
        int v = buf[head];
        head = (head + 1) % BUFSIZE;
        count--;
        printf("[C%d] consume %d (count=%d)\n", id, v, count);
        pthread_cond_signal(&not_full);          // 通知生产者
        pthread_mutex_unlock(&mtx);
        usleep(rand() % 5000);
    }
    return NULL;
}

int main(void) {
    pthread_t tp, tc;
    int a = 1, b = 1;
    pthread_create(&tp, NULL, producer, &a);
    pthread_create(&tc, NULL, consumer, &b);
    pthread_join(tp, NULL);
    pthread_join(tc, NULL);
    return 0;
}
```

编译链接：
```bash
gcc -O2 -pthread -o pc pc.c
./pc
```

**重点**：条件变量 `wait` 必须用 `while` 循环检查条件（防虚假唤醒 spurious wakeup）；`wait` 会原子地释放锁，唤醒后重新获取锁。

### 4.2 线程私有数据(TLS)演示

```c
#include <stdio.h>
#include <pthread.h>

__thread int tls_val = 0;   // 每线程独立

void *worker(void *arg) {
    int id = *(int *)arg;
    tls_val = id * 100;      // 只影响本线程的 tls_val
    printf("thread %d: tls_val=%d\n", id, tls_val);
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    int a = 1, b = 2;
    pthread_create(&t1, NULL, worker, &a);
    pthread_create(&t2, NULL, worker, &b);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("main: tls_val=%d\n", tls_val);  // 主线程独立
    return 0;
}
```

### 4.3 Go goroutine 调度观察

```go
package main

import (
    "fmt"
    "runtime"
    "time"
)

func spin(name string) {
    for i := 0; i < 5; i++ {
        fmt.Printf("[%s] %d\n", name, i)
        time.Sleep(10 * time.Millisecond)
    }
}

func main() {
    fmt.Println("GOMAXPROCS =", runtime.GOMAXPROCS(0))
    runtime.GOMAXPROCS(2)   // 限制并行度
    for i := 0; i < 8; i++ {
        go spin(fmt.Sprintf("g%d", i))
    }
    time.Sleep(200 * time.Millisecond)
}
```

运行并观察：
```bash
GOMAXPROCS=1 go run gmp.go   # 单 P：goroutine 完全由用户态调度，观察串行交叠
GOMAXPROCS=2 go run gmp.go   # 双 P
```

对比"创建 10 万个 goroutine" vs "创建 10 万 OS 线程"：
```go
func main() {
    start := time.Now()
    for i := 0; i < 100000; i++ {
        go func(){ runtime.Gosched() }()   // 让出
    }
    fmt.Println("10万 goroutine 启动耗时:", time.Since(start))
}
```
一般毫秒级完成，而 10 万 OS 线程将耗尽系统资源或触发 `pthread_create` 失败——这直观展示了用户态轻量并发与内核线程的差异。

## 5. 常见坑与避坑指南

### 5.1 全局变量数据竞争（data race）

**现象**：计数器计数结果小于预期，或程序行为不确定、偶发崩溃。
**原因**：多个线程并发读写同一全局变量，未同步，导致丢失更新/撕裂。
**避坑**：
- 对共享变量用互斥锁/原子操作。
- 用 ThreadSanitizer 检测：`gcc -fsanitize=thread`。
- 若非必须共享，改为线程局部存储(TLS)；用 `restrict`/不可变数据结构减少共享。
- C++20 `std::atomic`、Go 的 channel/mutex。

### 5.2 线程栈溢出

**现象**：深递归或大栈局部变量导致 `Segmentation fault`。
**原因**：线程栈大小有限（默认 8MB），深递归/大数组越界。
**避坑**：
- 合理减少递归深度（改迭代）或把大数组放堆上。
- `ulimit -s` 查看/设置，`pthread_attr_setstacksize` 单独设大栈。
- 设 guard page（`pthread_attr_setguardsize`）让溢出触发可检测的 SIGSEGV 而非静默破坏。
- 调试时用 `pthread_getattr_np` 查询实际栈大小。

### 5.3 pthread_cancel 的取消点问题

**现象**：调用 `pthread_cancel` 线程不一定立即终止，可能继续运行或崩溃。
**原因**：线程默认**异步取消关、延迟取消开**，只有在**取消点(cancellation point)**（如 `read`、`write`、`sleep`、`cond_wait` 等阻塞系统调用）才检查取消。在取消点之间不生效。
**避坑**：
- 理解取消语义，勿假设 `pthread_cancel` 立即生效。
- 若需立即终止，用错误码/标志协同退出更可控（避免资源泄漏）。
- 用 `pthread_setcancelstate(PTHREAD_CANCEL_DISABLE)` 保护关键资源区域，`pthread_cleanup_push/pop` 做清理。

### 5.4 pthread key / TLS 泄漏

**现象**：线程反复创建销毁后内存缓慢增长，最终 OOM。
**原因**：`pthread_key_create` 创建的 key 未用 `pthread_key_delete`，或线程末调 `pthread_setspecific` 存了未释放的堆内存且未注册析构函数，导致泄漏。
**避坑**：
- 用动态 TLS 时注册 destructor 释放内存。
- 线程退出前清理 `pthread_getspecific` 得到的内存。
- 尽量用编译期 `__thread`/`_Thread_local`（自动回收），仅在需要析构时用 pthread_key。

### 5.5 忘记 join 导致的资源泄漏

**现象**：`pthread_create` 后不 join 也不 detach，线程结束资源不回收。
**原因**：join 型线程结束后 PCB/TLS 仍在等待回收。
**避坑**：创建线程前决定 join 或 detach；detach 后不可 join；用线程池复用而非频繁创建销毁。

### 5.6 递归锁与不可重入锁误用导致死锁

**现象**：同一线程对普通锁重入时死锁。
**原因**：普通互斥锁非递归，同一线程重复 lock 自己阻塞。
**避坑**：明确锁的递归性；必要时用递归锁；重构避免嵌套/重复加同一锁；用 `pthread_mutex_trylock`/超时做防御。

### 5.7 条件变量 wait 用 if 而非 while

**现象**：偶尔多消费一次或漏通知。
**原因**：`pthread_cond_wait` 存在虚假唤醒、或因多生产者/消费者 while 条件被破坏。
**避坑**：**一律用 while 循环**包住条件检查（规范做法）。这是教科书反复强调且最易踩的坑。

### 5.8 GOMAXPROCS 设置不当

**现象**：Go 程序并行度异常（多核利用率低或 CPU 核数误判）。
**原因**：容器/虚机中 `runtime.NumCPU` 可能读到宿主核数而非 cgroup 配额，导致 GOMAXPROCS 过大（超配额）。
**避坑**：生产环境用 `automaxprocs`(Uber) 自动按 cgroup 限额设置；显式 `runtime.GOMAXPROCS(n)`；监控实际并行度。

### 5.9 线程数量失控

**现象**：服务在连接增长时创建海量线程，内存/上下文切换爆炸。
**原因**：线程栈 8MB 虚拟地址 + 调度开销，-22 创建失败/内存耗尽。
**避坑**：固定线程池/事件循环；或用 goroutine/协程承载轻量并发；控制并发上限，超限排队/降级。
