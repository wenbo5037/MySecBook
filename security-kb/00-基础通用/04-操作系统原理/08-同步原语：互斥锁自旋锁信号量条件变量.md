## 1. 概述

**同步原语（Synchronization Primitive）** 是并发编程的基石。当多个线程或进程并发访问共享数据时，如果没有同步，会出现**竞态条件（Race Condition）**——执行的最终结果取决于各执行流的交织时序（interleaving），可能得到错误、甚至崩溃的结果。

同步要解决的两类核心问题：

1. **互斥（Mutual Exclusion）**：同一时刻只允许一个执行流进入临界区（critical section）访问共享资源，防止同时读写。
2. **协作/同步（Coordination）**：让执行流按预定顺序等待与唤醒，如"生产者产出数据后通知消费者来取"。

操作系统与编程语言提供了一系列原语，从底层到高层可排成一条"能力递增、开销递增"的线：

```text
原子操作(atomic) → 内存屏障(barrier) → 自旋锁(spinlock) → 互斥锁(mutex)
   → 读写锁(rwlock) → 信号量(semaphore) → 条件变量(condvar)
        低开销 / 高复杂度       ────▶      高开销 / 低复杂度
```

| 原语 | 等待方式 | 适用场景 | 典型开销 |
|------|----------|----------|----------|
| 原子操作 | 无等待（CAS/read-modify-write） | 单变量计数、无锁数据结构 | 最低 |
| 自旋锁 | 忙等待（spin） | 极短临界区（μs 内） | 低但空转 CPU |
| 互斥锁 | 睡眠等待（sleep） | 常规临界区、持锁较久 | 中（有 syscall 时） |
| 读写锁 | 读共享写互斥 | 读多写少 | 中 |
| 信号量 | 睡眠/唤醒 | 资源计数、限流 | 中 |
| 条件变量 | 睡眠+通知 | 等待条件成立 | 中高 |

选择原则：**临界区越短，越倾向于自旋锁/原子；临界区越久（可能阻塞、sleep），用互斥锁/信号量**。自旋锁在短临界区上比互斥锁快（免去 sleep/wakeup 的 syscall），但长临界区会白白烧 CPU。

本节与 [[01-进程本质：PCB结构与进程创建流程]]、[[03-线程模型：内核线程用户线程与混合模型]] 紧密相关：同步的对象本质上是"共享的可变状态"，而共享状态的存在依赖于线程共享地址空间。深入理解同步原语的底层实现（futex、缓存一致性）能帮助写出既正确又高效的高并发代码，也是 [[09-死锁：四条件检测算法与预防策略]] 的预防基础。

## 2. 核心原理

### 2.1 竞态条件与临界区

一段必须整体不可分割执行的共享资源访问代码称为**临界区（critical section）**。竞态条件的本质是两个执行流在临界区的执行链路交叉，破坏了"读-改-写"的原子性。

以经典的"计数器自增"为例：

```text
线程 A:           线程 B:
LOAD  counter        LOAD  counter        ← 两者读到同一个旧值
ADD   1              ADD   1
STOR  counter        STOR  counter
```

若无同步，counter 可能只 +1 而非 +2（lost update）。要修复，必须保证"LOAD-ADD-STOR"要么整体原子（原子操作），要么用锁包裹（互斥）。

### 2.2 锁的本质与三要素

无论哪种锁，其正确性都必须满足三个性质：

| 性质 | 含义 |
|------|------|
| **互斥（Mutual Exclusion）** | 一时刻仅一个线程持锁进临界区 |
| **进展（Progress）** | 总有进程能进入临界区，不会死锁/活锁 |
| **有界等待（Bounded Waiting）** | 每个等待者最终能进入，不会无限饥饿 |

### 2.3 硬件原语：原子性与内存序的来源

所有锁最终都依赖 CPU 提供的**原子指令**。x86 上常见的原子 RMW（Read-Modify-Write）指令：

```text
xchg    reg, mem      # 原子交换
lock add / lock inc   # 带 lock 前缀的读-改-写
lock cmpxchg          # 比较并交换（CAS）
lock xadd / xaddq     # 原子加并返回旧值
```

- **Lock 前缀**：x86 上 `lock` 前缀对缓存行（cache line）执行原子操作，并通过缓存一致性协议（MESI）保证多核可见性。详见 [[09-缓存一致性：MESI协议与伪共享性能问题]]。
- **CAS（Compare-And-Swap）**：`cmp` `cmpxchg` 是实现无锁算法与自旋锁的基础——只有内存值等于期望值才交换，否则失败并返回旧值。

### 2.4 单核 vs 多核：禁用中断的局限

**禁用中断（disable interrupts）** 是最古老的同步手段：单核 CPU 上，只要在临界区期间禁止时钟中断，就不会被抢占，天然互斥。

```c
/* 单核时代的典型（如早期 Linux UP） */
cli();            /* 关中断 */
/* 临界区 */
sti();            /* 开中断 */
```

**局限**：禁用中断只对**单核**有效。多核上两个核同时跑不同线程，各自"不被打断"并不能阻止另一个核同时访问同一变量。此外，长期关中断会延迟时钟、丢失中断。因此现代内核只在内核临界区短用它，用户态与多核环境必须依赖锁与原子操作。

## 3. 详细知识点

### 3.1 自旋锁（Spinlock）——忙等待

自旋锁的等待线程**不睡眠**，而是不断循环测试锁是否可获取（spin），一旦可用立即抢入。No scheduling，无 sleep/wakeup overhead。

**朴素实现"锁变量 + CAS"**：

```c
/* x86 上典型的自旋锁实现（用户态示意） */
static inline void spin_lock(volatile int *lock) {
    while (__atomic_exchange_n(lock, 1, __ATOMIC_ACQUIRE))
        /* spin: 忙等待，空转 CPU */;
}
static inline void spin_unlock(volatile int *lock) {
    __atomic_store_n(lock, 0, __ATOMIC_RELEASE);
}
```

问题：**所有竞争者都抢同一个缓存行**；在 MESI 中，每次有进程获得锁都会 invalidate 其他核的缓存行，导致缓存行在各核间"乒乓"（cache line bouncing），锁竞争越激烈，性能越差。

**Ticket Lock（排队自旋锁）**：用"发号"机制保证 FIFO 公平，避免一个锁被某个核反复抢到（饥饿）：

```c
/* Ticket lock：next_ticket 发放，now_serving 表示当前服务到 */
lock_acquire:
    my_ticket = atomic_fetch_add(&next_ticket, 1);   /* 取号 */
    while (atomic_load(&now_serving) != my_ticket)
        ;   /* 自旋等号到 */
lock_release:
    atomic_fetch_add(&now_serving, 1);               /* 叫下一个号 */
```

**MCS Lock（Mellor-Crummey & Scott）**：每个线程在自己的节点上自旋组装成队列，避免共享缓存行乒乓，是 Linux qspinlock 的前身。

**qspinlock（Linux 内核的排队自旋锁）**：`arch/x86/include/asm/qspinlock.h`，用 32 位原子操作编码锁 + 队列尾，实现公平排队自旋，且用 MCS 风格避免缓存乒乓。

**适用场景**：只在**极短临界区**（几分之一微秒）使用；长临界区应使用互斥锁，否则浪费 CPU 并可能饥饿其他线程。内核中的 `spin_lock` 常用于保护链表/计数等轻量操作。**自旋锁**不可在持锁时 sleep/调度（会死锁或破坏内核状态）。

### 3.2 互斥锁（Mutex）——睡眠等待与 futex

互斥锁的等待线程**睡眠**（让出 CPU），由内核在锁释放时唤醒。持锁时间可长可短都不会烧 CPU，但 sleep/wakeup 有 syscall 开销。

**futex（Fast Userspace Mutex，快速用户态互斥）** 是 Linux 互斥锁的基础，设计目标是"锁竞争不激烈时零 syscall"：

```code
            用户态                           内核态
  ┌─────────────────────────┐
  │ 快速路径（无竞争）:       │
  │  lock: CAS(0→1)          │  成功 → 直接进临界区，零 syscall
  │                          │
  │  竞争路径:               │
  │  lock: CAS(0→1) 失败     │
  │  ↓ 调用 futex(WAIT) ────▶│  挂起线程，加入等待队列
  │  unlock: 1→0            │
  │  ↓ futex(WAKE) ────────▶│  唤醒一个等待者
  └─────────────────────────┘
```

futex 的核心思想：**锁状态其实是个普通原子变量**。无竞争时用原子 CAS 拿锁根本不进内核；只有真正竞争才通过 `futex(FUTEX_WAIT/FUTEX_WAKE)` 让内核帮忙睡眠与唤醒。这使互斥锁在低竞争时开销接近原子操作。

**优先级继承（Priority Inheritance, PI）**：解决"低优先级任务持锁阻塞高优先级任务"的优先级反转（priority inversion）问题。Linux 用 `PTHREAD_PRIO_INHERIT` 属性让持锁者临时继承等待者中最高优先级，避免高优先级任务被饿死。对应 futex 的 `FUTEX_LOCK_PI` / `FUTEX_UNLOCK_PI` 操作。

pthread 互斥锁 API：

```c
#include <pthread.h>
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

pthread_mutex_lock(&mutex);      /* 进入临界区 */
/* ... 操作共享资源 ... */
pthread_mutex_unlock(&mutex);    /* 退出临界区 */
```

### 3.3 读写锁（RWLock）与 RCU

读写锁区分读锁与写锁：

- **读锁（shared lock）**：可被多个读者同时持有（读共享）。
- **写锁（exclusive lock）**：仅一个写者可持有，且读者不能同时持（写互斥）。

```c
pthread_rwlock_t rwlock = PTHREAD_RWLOCK_INITIALIZER;

pthread_rwlock_rdlock(&rwlock);   /* 多个读者可同时进入 */
/* 只读共享 */
pthread_rwlock_unlock(&rwlock);

pthread_rwlock_wrlock(&rwlock);   /* 独占写 */
/* 修改 */
pthread_rwlock_unlock(&rwlock);
```

**写者优先 vs 读者优先**：读者优先可能让写者饿死（读者源源不断进来）；写者优先避免写者饥饿但读者吞吐略降。Linux 内核 rwlock 与用户态 rwlock 的策略不同，需按读多写少的场景选择。

**RCU（Read-Copy-Update）**：Linux 内核内核用的高性能读多写少同步机制。读者读旧版本（无需加锁），写者先复制一份修改后原子切换指针，等所有读者离开（grace period，宽限期）后再释放旧版本。读者侧近乎零开销，是很多高性能内核数据结构的基石。

```text
RCU 思想:
 写者:  旧数据复制 → 修改副本 → 原子切换指针(读者看到新) → 等旧读者退出 → 释放旧
 读者:  读当前指针指向的数据（无锁、极快）
```

### 3.4 信号量（Semaphore）——计数值与 PV 操作

信号量维护一个**计数值** counter，不传递数据，只表达"可用资源数量"：

- **P/V 操作**（Proberen/Verhogen，源自 Dijkstra）：
  - `P`（wait/pend）：counter>0 则减 1 并继续；否则阻塞等待。
  - `V`（signal/post）：counter 加 1，可能唤醒一个等待者。

```c
#include <semaphore.h>
sem_t sem;
sem_init(&sem, 0, 3);      /* 初值 3：允许 3 个并发访问 */

sem_wait(&sem);            /* P */
/* 使用有限资源（如连接池） */
sem_post(&sem);            /* V */
```

**二值信号量 vs 互斥锁**：初值 1 的"二值信号量"行为看似互斥锁，但关键区别是**所有权（ownership）**：

| 维度 | 互斥锁 Mutex | 二值信号量 |
|------|--------------|------------|
| 所有权 | 只能持锁者释放 | 任意线程可 release |
| 用途 | 保护临界区 | 资源可用性/计数 |
| 嵌套锁 | 支持（可重入类） | 不支持 |

因此：**互斥锁用于保护临界区**（有 owner 语义），**信号量用于"计数资源池"或定长缓冲的生产者-消费者**。

### 3.5 条件变量（Condition Variable）——等待条件成立

条件变量与互斥锁**配对使用**，解决"等待某个条件成立"的问题（互斥锁只能解决互斥，不能表达等待/通知）。

```c
pthread_mutex_t mu = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cv = PTHREAD_COND_INITIALIZER;
int ready = 0;                     /* 受 mu 保护的条件 */

/* 生产者：修改条件后通知 */
pthread_mutex_lock(&mu);
ready = 1;
pthread_cond_signal(&cv);          /* 唤醒一个等待者 */
pthread_mutex_unlock(&mu);

/* 消费者：等待条件 */
pthread_mutex_lock(&mu);
while (!ready)                     /* 必须 while 循环，防 spurious wakeup */
    pthread_cond_wait(&cv, &mu);   /* 先释放 mu 并睡眠，被唤醒后重新获得 mu */
pthread_mutex_unlock(&mu);
```

**为什么必须 while 而不是 if？** 因为存在 **spurious wakeup（虚假唤醒）**：即使没人 signal，wait 也可能被唤醒一次。用 while 重新检查条件，保证正确性。

**signal vs broadcast**：
- `pthread_cond_signal`：只唤醒**一个**等待者（适合单个资源的消费者）。
- `pthread_cond_broadcast`：唤醒**所有**等待者（适合"多个消费者都要检查变了的条件"，例如 `all=1` 之类）。

**wait 会释放互斥锁**：`pthread_cond_wait` 原子地"释放 mu + 睡眠"，被唤醒后"重新获取 mu 再返回"。这是条件变量的关键语义——避免睡眠时还锁着。

### 3.6 内存序与原子操作（C11）

C11 `<stdatomic.h>` 提供跨平台原子操作与内存序控制：

```c
#include <stdatomic.h>

atomic_int counter = ATOMIC_VAR_INIT(0);
atomic_fetch_add(&counter, 1);            /* 原子加 */

atomic_bool flag = ATOMIC_VAR_INIT(false);
atomic_store(&flag, true, memory_order_release);   /* 发布-获取 */
bool v = atomic_load(&flag, memory_order_acquire);
```

**内存序（memory_order）** 决定原子操作之间如何排序：

| 内存序 | 含义 | 适用 |
|--------|------|------|
| `memory_order_relaxed` | 只保证单个原子操作不撕裂，不做排序约束 | 计数（fetch_add） |
| `memory_order_acquire` / `release` | 获取/释放语义，用于发布数据 | 锁、单生产者-消费者 |
| `memory_order_seq_cst` | 顺序一致，最严格 | 默认，通用但慢 |

### 3.7 内存屏障与 volatile 的真相

**内存屏障（memory barrier）** 防止编译器/CPU 对内存操作乱序：

- **编译器屏障（compiler barrier）**：防止 gcc 重排生成机器指令。用 `asm volatile("" ::: "memory")`。
- **CPU 屏障（hardware barrier / fences）**：防止 CPU 乱序执行（StoreLoad 重排）。x86 用 `mfence` / `lock` 指令，ARM 用 `dmb`/`dsb`。

```text
编译/CPU 乱序示意：
  线程1:                   观察到的顺序可能是：
    data = 1;                 data=1 还没写
    flag = 1;  ──► CPU 可把   flag=1 先执行
      （x86 上 StoreLoad 重排）
```

**关键误区**：`volatile` 只保证"每次都从内存读、不优化掉"，**绝不是同步原语**——它既不提供原子性，也不提供内存序。`volatile int x` 在多线程下依然可能竞态。正确做法是使用 `_Atomic`/`stdatomic` 或锁，不要用 volatile 做线程同步。

## 4. 实战与示例

### 4.1 pthread 互斥锁 + 条件变量：生产者-消费者

```c
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>

#define CAP 5
int buffer[CAP], head = 0, count = 0;
pthread_mutex_t mu = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cv_full  = PTHREAD_COND_INITIALIZER;  /* 缓冲满? */
pthread_cond_t cv_empty = PTHREAD_COND_INITIALIZER;  /* 缓冲空? */

void *producer(void *arg) {
    for (int i = 0; i < 20; i++) {
        pthread_mutex_lock(&mu);
        while (count == CAP)                 /* 满则等 */
            pthread_cond_wait(&cv_full, &mu);
        buffer[(head + count) % CAP] = i;    /* 入队 */
        count++;
        pthread_cond_signal(&cv_empty);      /* 通知消费者 */
        pthread_mutex_unlock(&mu);
        usleep(100000);
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < 20; i++) {
        pthread_mutex_lock(&mu);
        while (count == 0)                   /* 空则等 */
            pthread_cond_wait(&cv_empty, &mu);
        int v = buffer[head];
        head = (head + 1) % CAP;
        count--;
        pthread_cond_signal(&cv_full);       /* 通知生产者 */
        pthread_mutex_unlock(&mu);
        printf("消费 %d\n", v);
    }
    return NULL;
}

int main(void) {
    pthread_t pt, ct;
    pthread_create(&pt, NULL, producer, NULL);
    pthread_create(&ct, NULL, consumer, NULL);
    pthread_join(pt, NULL);
    pthread_join(ct, NULL);
    return 0;
}
```

```bash
$ gcc -O2 -pthread -o pc pc.c
$ ./pc
```

要点：两个条件变量分别表达"有空位"和"有数据"，`while` 循环防虚假唤醒，signal 精确通知相应方。这是最经典、最需要写对的生产者-消费者模板。

### 4.2 C11 atomic 无锁 SPSC（单生产者单消费者）队列

```c
#include <stdatomic.h>
#include <stdio.h>

#define N 1024
typedef struct { atomic_int head, tail; int buf[N]; } SPSC;

/* 单生产者单消费者：无锁环形队列 */
int spsc_push(SPSC *q, int v) {
    int tail = atomic_load(&q->tail, memory_order_relaxed);
    int head = atomic_load(&q->head, memory_order_acquire);
    if ((tail + 1) % N == head) return -1;      /* 满 */
    q->buf[tail] = v;
    atomic_store(&q->tail, (tail + 1) % N, memory_order_release);
    return 0;
}
int spsc_pop(SPSC *q, int *out) {
    int head = atomic_load(&q->head, memory_order_relaxed);
    int tail = atomic_load(&q->tail, memory_order_acquire);
    if (head == tail) return -1;                /* 空 */
    *out = q->buf[head];
    atomic_store(&q->head, (head + 1) % N, memory_order_release);
    return 0;
}

int main(void) {
    SPSC q = {.head = 0, .tail = 0};
    spsc_push(&q, 42);
    int v;
    if (spsc_pop(&q, &v) == 0) printf("pop=%d\n", v);
    return 0;
}
```

要点：生产者只改 `tail`（release），消费者只改 `head`（release），对方用 acquire 读取，形成正确的 happens-before。SPSC 是少数可以真正无锁的队列结构；多生产多消费者需要 CAS 且要处理 ABA（见坑点）。

### 4.3 Go 的 sync.Mutex / RWMutex

```go
package main

import (
    "fmt"
    "sync"
)

var mu sync.Mutex
var m = map[string]int{}

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func(k int) {
            mu.Lock()              // sync.Mutex
            m["k"] = k
            mu.Unlock()
            wg.Done()
        }(i)
    }
    wg.Wait()
    fmt.Println(m)
}
```

Go 中 `sync.RWMutex` 的 `RLock`/`RUnlock` 支持读共享；`sync.Map` 是内建的无锁并发 map。Go runtime 的 goroutine 调度由 G（goroutine）+ M（machine）+ P（processor）组成，锁竞争会触发 goroutine 让出，降低上下文切换压力——这正呼应 [[04-协程原理：用户态调度与栈管理]]。

### 4.4 内核态 vs 用户态开销的简单测试

```c
/* 粗略比较：无锁计数 vs 持锁计数 vs 原子计数 */
#include <pthread.h>
#include <stdatomic.h>
#include <time.h>
#include <stdio.h>
#include <stdint.h>

static long long now(void) {
    struct timespec ts; clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1000000000LL + ts.tv_nsec;
}
static uint64_t loop_atomic(uint64_t n) {
    atomic_uint_fast64_t c = 0;
    for (uint64_t i = 0; i < n; i++) atomic_fetch_add(&c, 1);
    return c;
}
int main(void) {
    uint64_t n = 200000000;
    long long t0 = now(); loop_atomic(n);
    printf("atomic fetch_add: %.2f ns/op\n", (double)(now()-t0)/n);
    return 0;
}
```

## 5. 常见坑与避坑指南

### 坑 1：递归锁死锁 / 重复加锁

**症状**：同一线程对非可重入 mutex 连续两次 `lock`，第二次永久阻塞（死锁）。

**根因**：默认 pthread mutex 不可重入；持锁期间再次 lock 自己把自己卡死。

**解决**：区分锁用途；确需重入时用 `PTHREAD_MUTEX_RECURSIVE`（记录 owner 与计数）；或重构避免嵌套加锁；遵守"加锁顺序一致 + 最小临界区"原则。详见 [[09-死锁：四条件检测算法与预防策略]]。

### 坑 2：条件变量忘记 broadcast / signal 丢唤醒导致永久等待

**症状**：消费者永久阻塞在 `pthread_cond_wait`，即使条件早已为真。

**根因**：a) 生产者改了条件但忘了 `signal`/`broadcast`；b) 使用了 `signal` 但有两个以上消费者在等而只需要一个名额（后续另一个消费者等不到通知）；c) 条件改变发生在 wait 之前，通知未被"排队"（条件变量不记录历史通知）。

**解决**：a) 每次改条件都记得 notify；b) 多个消费者时用 `broadcast`（尤其当"一个事件让多个等待者都该醒"时）；c) 标准模板是"先检查条件再 wait"，while 循环。

### 坑 3：无锁队列的 ABA 问题

**症状**：无锁数据结构在并发删插下产生不可见错误（如误判节点已释放、环已形成）。

**根因**：CAS 是"等于旧值则交换"。若 A→B→A（值从 A 变 B 再变回 A），CAS 误以为没变过，导致指针指向已回收/复用的节点。典型出现在带后进栈（lock-free stack）等结构。

**解决**：用**版本号/计数**附加到指针（double-word CAS，`__int128` 打包指针+版本），每操作递增版本；或用 hazard pointers / epoch reclamation 管理内存回收，避免 ABA 触发对已释放内存的访问。

### 坑 4：用 volatile 当同步原语

**症状**：`volatile` 标识共享标志位，但仍出现读不到最新值或竞态。

**根因**：`volatile` 只阻止编译器优化，不提供内存序（不保证跨越 CPU 的可见性排序），也非原子。

**解决**：改用 C11 `_Atomic`/`stdatomic` 与正确内存序；或加锁；不要用 volatile 做跨线程共享标志。内核代码里 volatile 用于映射 IO（MMIO），用户态线程同步用它≈错误。

### 坑 5：futex 慢速路径与优先级反转（PI 相关）

**症状**：锁竞争激烈时性能骤降，每条 lock/unlock 都触发 syscall；或高优先级任务被低优先级任务持有锁卡住。

**根因**：竞争激烈时 futex 走内核慢速路径（FUTEX_WAIT/WAKE 每次 syscall）；不启用 PI 时低优先级持锁会阻止高优先级。

**解决**：减少锁竞争面（细粒度锁/无锁）；需要实时性时启用优先级继承 `FUTEX_LOCK_PI` / `PTHREAD_PRIO_INHERIT`；分布式场景避免大关键路径锁竞争。

### 坑 6：伪共享（False Sharing）导致的"锁不忙但慢"

**症状**：互不相关的变量被多个核各自独立读写，却意外地相互拖慢。

**根因**：两个变量落在同一条缓存行。核 A 改变量甲 invalidate 该行，核 B 改变量乙也 invalidate 同一行，二者互相撤缓存，即使毫无共享关系。若变量本身是锁/计数，伪共享会让"本应无竞争"的操作也冲突。

**解决**：把高竞争变量**缓存行对齐/填充**（cache line padding，通常 64 字节）独立开；使用 `__attribute__((aligned(64)))` / `alignas(64)` 或结构体填充。详见 [[09-缓存一致性：MESI协议与伪共享性能问题]]。

```c
struct alignas(64) hot_counters {
    atomic_long counter_a;   /* 核A单独用它 */
    char pad[48];            /* 填充，避免与 counter_b 同行 */
    atomic_long counter_b;   /* 核B单独用它 */
};
```
