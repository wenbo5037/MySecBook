## 1. 概述

上下文切换（Context Switch）是操作系统多任务并发的基础机制。所谓"上下文"（context），指的是某个执行流（execution stream）在当前时刻的全部运行状态——包括通用寄存器（general-purpose registers）、程序计数器（PC）、栈指针、状态寄存器、页表基址（CR3/PTBR）、浮点与 SIMD 寄存器、以及内核中该任务对应的 PCB（Process Control Block）/TCB（Thread Control Block）数据结构。

当 CPU 从一个执行流切换到另一个执行流时，必须完成三件事：

1. **保存**当前执行流的全部状态（save state）；
2. **加载**目标执行流的全部状态（load state）；
3. **执行**调度器决定"下一个跑谁"的逻辑（scheduler decision）。

这一过程看似简单，却是现代操作系统性能分析中最容易被低估的隐藏开销。不少性能工程师在分析高并发服务时，只关注 CPU 使用率、内存占用、网络带宽，却忽略了"大量线程在互相抢占 CPU"这件事本身带来的成本。一次上下文切换本身只需要微秒级时间，但当线程数远超 CPU 核数时，切换频率可能高达每秒数十万次，累计开销足以把吞吐量打掉 30%~50%。

上下文切换可以按维度划分为以下几种类型：

| 类型 | 说明 | 相对开销 |
|------|------|----------|
| 进程切换（Process Switch） | 不同进程间切换，需切换地址空间，TLB 必须刷新 | 最高 |
| 线程切换（Thread Switch） | 同进程不同线程间切换，共享地址空间（内核线程仍需内核态介入） | 中 |
| 用户态协程切换 | 协程/纤程在用户态调度，无需进入内核态 | 最低 |
| 中断切换（Interrupt） | 内核态中断处理，只涉及部分现场 | 视情况而定 |

理解上下文切换，首先要区分"内核态进程/线程切换"与"用户态协程切换"。前者需要特权级切换（privilege level switching，ring 3 → ring 0）加 TLB 刷新，开销大；后者仅仅在用户态保存/恢复少量寄存器，开销小一个数量级以上。这也是协程（coroutine）、goroutine 之所以高性能的根本原因。

在现代数据中心与云原生场景中，上下文切换的代价被进一步放大：容器（Container）共享宿主机内核，一个节点上成百上千个容器、数万个线程在同一批核上争抢；虚拟化环境中嵌套页表（EPT/NPT）让每次切换多付出虚拟化开销；再加上近年的安全补丁（KPTI 内核页表隔离、Spectre BTB 刷新）给每次切换增加了额外指令。不夸张地说，**上下文切换是云上"看不见的性能税"**——它在 CPU 采样里几乎不显示为热点，却实实在在地侵蚀着每一条路径的延迟。这也是为什么编写高性能服务时，"减少切换次数"本身就是一种优化手段（绑核、协程化、事件驱动）。

本节为 [[03-线程模型：内核线程用户线程与混合模型]] 的姊妹篇，重点从**性能开销的量化来源**与**实测方法**角度深入。理解开销的精确来源，是后续做性能调优、高并发设计以及安全加固的前提。

在容量规划中还有一个常见误区：很多人把 CPU 核数直接当作"并发能力的上限"，认为跑满几个核就是极限。真实情况是，每条 CPU 时间里还含有一部分"切换税"——超卖的线程会把这部分税翻倍甚至翻几倍。因此，做容量评估时应当先通过 `perf stat` 测出真实的 context-switch 率，再把"切换税"从可用的 CPU 时间里扣除后再算吞吐余量。同一套逻辑也适用于云上按核计费的成本评估：线程越收敛，实际"买到"的有效算力越多。

## 2. 核心原理

### 2.1 上下文切换的完整流程

以 Linux x86-64 为例，一次典型的进程上下文切换（由抢占触发）完整流程如下：

```text
           时钟中断 / 主动让出（schedule() 路径）
                        │
                        ▼
   ┌────── 进入内核态（syscall/中断入口，保存用户态寄存器到 pt_regs）
   │
   ▼
   ┌────────────────────────────────────┐
   │ 1. 时钟中断处理（irq_enter）          │
   │    更新调度节拍（tick）、检查抢占      │
   └───────────────┬────────────────────┘
                   │  若需要调度
                   ▼
   ┌────────────────────────────────────┐
   │ 2. schedule() 调度器决策             │
   │    选择下一个任务（pick_next_task）   │
   │    CFS/EEVDF 运行队列操作            │
   └───────────────┬────────────────────┘
                   ▼
   ┌────────────────────────────────────┐
   │ 3. switch_to() 上下文切换            │
   │    __switch_to():                  │
   │     保存旧任务寄存器到内核栈          │
   │     加载新任务寄存器                 │
   │     切换内核栈 (rsp)                │
   │     切换 CR3（页表，进程间）          │
   │     切换 TSS / FSBASE（线程局部存储） │
   └───────────────┬────────────────────┘
                   ▼
   ┌────────────────────────────────────┐
   │ 4. ret_from_fork 返回新任务用户态     │
   │    sysretq / iretq                  │
   └────────────────────────────────────┘
```

关键实现位于 `arch/x86/kernel/process_64.c` 的 `__switch_to()`，以及调度核心 `kernel/sched/core.c` 的 `schedule()`。`switch_to()` 宏本质上是保存/恢复一组寄存器的汇编代码，调用 `__switch_to_asm` 完成寄存器交换。

**中断上下文切换与进程上下文切换的区别**：中断处理虽然也"切换"了执行流（用户态→内核中断处理），但它**不涉及调度器决策**——中断处理完会原样返回被中断的进程，现场保存在该进程的内核栈上。而真正的上下文切换意味着调度器选择了**另一个任务**，被切换任务的现场必须完整保存到内核栈/PCB 中，等待下次被调度时恢复。这也是为什么"每秒中断次数很高"不等于"上下文切换很多"。

### 2.2 进程切换 vs 线程切换 vs 协程切换

| 维度 | 进程切换 | 同进程线程切换 | 协程（用户态）切换 |
|------|----------|---------------|-------------------|
| 地址空间切换 | 需要（换页表/CR3） | 不需要 | 不需要 |
| TLB 影响 | 必须刷新 | 一般不需要 | 不需要 |
| 内核态介入 | 需要 | 需要（内核线程） | 用户态即可 |
| 寄存器开销 | 全量 | 全量 | 少量 |
| 典型开销 | 3~10µs | 1~3µs | 数十~数百 ns |
| 调度器 | CFS/EEVDF | CFS/EEVDF | 用户态调度器 |

**为什么同进程线程切换免掉 TLB/Cache 开销**：线程共享进程的地址空间与页表，切换线程时 CR3 不变，TLB 条目依然有效（同一进程所有线程的虚拟地址空间映射相同）；L1/L2 中驻留的是同一进程的代码与数据，热缓存天然保留。因此高并发场景中"多线程"对缓存的友好度远高于"多进程"——进程切换付出的 cache 冷启动代价是线程切换的近一个数量级。

### 2.3 voluntary vs involuntary

- **Voluntary context switch（自愿切换）**：执行流主动让出 CPU。典型场景：`sleep()`、等待 I/O（阻塞 `read`）、`sched_yield()`、获取互斥锁失败而阻塞。次数可从 `/proc/<pid>/status` 的 `voluntary_ctxt_switches` 字段查看。
- **Involuntary context switch（非自愿/被动切换）**：执行流被强制剥夺 CPU。典型场景：时间片耗尽（time slice expired）、更高优先级任务抢占、CPU 负载过高。对应 `nonvoluntary_ctxt_switches` 字段。

```bash
$ cat /proc/8701/status | grep -i ctxt
voluntary_ctxt_switches:        812
nonvoluntary_ctxt_switches:     43
```

**voluntary 与 involuntary 的比值有明确的诊断意义**：

- **voluntary 高、involuntary 低**：进程大量等待 I/O 或锁，属于"阻塞型"负载。这是大多服务进程的正常形态，切换是"不得不等"的结果；但若 voluntary 高到离谱（每秒数千次），说明锁竞争面过宽或等待链过长，值得优化。
- **involuntary 高**：说明**超过 CPU 能力的线程在争抢核**，时间片耗尽被迫让出。这是"线程数过多"的典型信号，往往伴随吞吐下降与延迟抖动——每个线程每秒都被割成若干片，请求被频繁打断。
- **两者都高**：既要等资源又要被抢占，系统整体排队严重（CPU 饱和 + 竞争叠加），需要扩容或降低并发度。

### 2.4 内核抢占模型：CONFIG_PREEMPT 的影响

Linux 内核本身也有"可抢占性"配置，直接影响上下文切换的频率与实时性：

| 配置 | 说明 | 适用 |
|------|------|------|
| `CONFIG_PREEMPT_NONE` | 内核只在意难以抢占点退出时调度，切换最少、吞吐最大 | 服务器 |
| `CONFIG_PREEMPT_VOLUNTARY` | 内核在部分自愿让出点可抢占 | 桌面 |
| `CONFIG_PREEMPT_FULL` | 内核几乎所有地方可抢占，响应快但切换多 | 桌面/交互 |
| `CONFIG_PREEMPT_RT` | 完全抢占 + 实时补丁，调度延迟可到百微秒级 | 实时系统 |

理解这一点有助于解释"为什么同一台机器跑服务器应用与桌面应用，调度表现截然不同"——抢占配置从内核层面决定了"切换的触发密度"。

## 3. 详细知识点

### 3.1 开销来源 1：寄存器保存与恢复（CPU 时间）

这是最直观的开销。一次切换需要保存/恢复：通用寄存器（RAX~R15 共 16 个 64 位寄存器）、RIP、RSP、RBP、RFLAGS、段寄存器、XMM/YMM（AVX 向量寄存器）、FPU 状态（MXCSR）以及浮点寄存器的全部值。

现代处理器使用 **FPU 延迟保存（lazy FPU saving）** 优化：只有当新任务真正使用浮点/SIMD 指令时才强制保存恢复，避免每次切换都付出全量 FPU 拷贝成本。AVX-512 的 ZMM 寄存器多达 64×512 位（约 4KB 数据），若每次切换都保存恢复，纯寄存器开销就会翻几倍——这正是"懒加载"存在的意义。在 Linux 上，这体现为内核线程切换时的 `fpu` 状态按需换入换出，遇到 SIMD 密集任务时会明显变慢。

### 3.2 开销来源 2：TLB 刷新与 PCID（内存访问延迟）

**TLB（Translation Lookaside Buffer，转换后备缓冲器）** 缓存虚拟地址→物理地址的映射。进程切换时若换了页表，旧进程的 TLB 条目全部失效。

- 若不使用 PCID，切换进程后整个 TLB 需要刷新（CR3 写入触发全量 invalidate），TLB miss 率在切换后一段时间内飙升，页表遍历（page walk）次数大增，每个内存访问都可能慢几十到几百个周期。
- **PCID（Process Context IDentifier，进程上下文标识符，x86 的 CR4.PCIDE 使能）** 允许每个进程拥有独立的 TLB 条目标记。切换进程时只需切换 PCID，无需刷新全部 TLB，从而保留大多数 TLB 命中。Linux 3.11+ 默认启用。
- ARM64 对应 **ASID（Address Space IDentifier）**，原理相同：每个进程有独立 ASID，TLB 条目带 ASID 标记，切换时避免全量刷新。

```text
              无 PCID 的 TLB 行为
  进程 A       切换        进程 B       切换
  ──────────    │        ──────────      │
  TLB:[A]       │清除      TLB:(空)       │
  命中率↑       │       全部miss/pagewalk │
                ▼                        ▼

              启用 PCID/ASID 后
  进程 A       切换        进程 B       切换
  ──────────    │        ──────────      │
  TLB[ASID=1]  PCID      TLB[ASID=2]    PCID
  命中率↑       切换       命中率↑         切换
```

**Meltdown/Spectre 之后的防护换了一批代价**：内核页表隔离（KPTI/KAISER）本质是"切换进程时也交换内核页表"，又引入了新的 TLB 刷新开销——所以后来发展出 KPTI 的 PCID 变体来缓解。这印证了一个规律：**安全与性能在此处互相拉扯**，每个补丁都在切换路径上加了成本。

### 3.3 开销来源 3：缓存污染（Cache Pollution）

上下文切换最隐蔽的开销在于：即使寄存器保存恢复了，新任务运行的代码路径与数据也完全不同于旧任务，导致 **L1/L2/L3 Cache 被"冷启动"**。

- 旧任务在缓存中的指令、数据全部变成冷的（cold），新任务第一次访问全部 cache miss。
- 调度器若在 CPU 间迁移任务，还会损失该任务原先驻留在原核私有 L1/L2 中的工作集（working set），因此**绑定 CPU（CPU affinity，`sched_setaffinity`）** 是减少 cache 抖动的关键手段。
- Linux 的 `perf` 通过 `cache-misses` 事件可以量化切换前后的 miss 率变化：一个热热点函数原本 L1 miss 率可能 <1%，切走再切回来后，头几千次访问的 miss 率可能升到 30% 以上——"回暖期"乘以切换频率，就是缓存污染的量化代价。

### 3.4 开销来源 4：内核态切换（syscall/中断）

用户态→内核态本身就有成本：特权级切换（ring 3→ring 0）、切换内核栈、保存 pt_regs。`syscall` 指令比老的 `int 0x80` 快得多（约 20~50ns），但仍比用户态函数调用贵一个量级。上下文切换往往意味着**至少两次**内核态过渡（进入调度 + 返回用户态），若再叠加中断，开销更大。

**vDSO（Virtual Dynamically-linked Shared Object）** 将 `gettimeofday`、`clock_gettime` 等只读系统调用下沉到用户态，避免多次内核态切换——详见 [[11-系统调用机制：syscall指令与vDSO优化]]。**io_uring** 则把大批量的 read/write 异步化、非阻塞化，进一步削减逐次 syscall 的内核态往返——见 [[13-IO模型演进：select-poll-epoll-io_uring]]。

### 3.5 开销来源 5：调度器决策开销

`schedule()` 需要从可运行队列（runqueue）中选择下一个任务。CFS 用红黑树维护运行队列，选最左（最小 vruntime）节点是 O(log n) 操作；现代 **EEVDF** 沿用类似结构并引入虚拟截止时间。多核场景下还要做负载均衡（load balance），跨 CPU 迁移任务同样引入 TLB/cache 损失。调度器本身持有内核锁（rq lock），高并发下锁竞争本身会成为热点——Linux 6.6 起为 EEVDF 引入的无锁（lockless）调度优化，正是为了解决"调度比切换还贵"的极端场景。

### 3.6 上下文切换的量化数据

| 场景 | 典型开销 |
|------|----------|
| 同进程线程切换（Linux x86-64） | ~1~3µs |
| 进程切换（含 TLB flush） | ~3~10µs |
| 用户态协程切换 | ~20~200ns |
| `syscall`（`getpid`） | ~20~50ns |
| L1 cache miss | ~1ns 量级 |
| TLB miss + page walk | ~100ns 量级 |

一次进程切换的"总成本"，往往是"寄存器时间 + TLB miss 连锁 + cache 冷启动 + 调度决策"的**组合放大**，远大于单纯的寄存器保存。这也解释了为什么**"减少切换次数"比"让单次切换更快"更重要**——绑核、协程化、事件驱动能成倍省掉连带成本。

### 3.7 迁移代价与 NUMA

现代多路服务器是 NUMA（Non-Uniform Memory Access）架构：内存附着在不同节点（node）上，跨节点访问延迟显著更高。调度器把任务从一个 NUMA 节点迁到另一个，除了 TLB/cache 损失，还引入远端内存访问延迟（本地访问约 80ns，跨节点 200ns+）。因此：

- 大数据/内存密集的高负载服务应绑定 NUMA 节点（`numactl --cpunodebind`）。
- 内核的 NUMA-aware 调度尽量把任务留在原节点，代价是"负载均衡被削弱"——这是调度器在均衡与局部性之间的折中。

```bash
$ numactl --cpunodebind=0 ./myservice   # 绑定节点 0
```

### 3.8 involuntary 高企时的诊断顺序

经验法则：**运行态线程数 ≤ CPU 核数 ×（1 + 少量余量）**。一旦运行态线程数持续超过核数，involuntary 切换就不可避免。诊断顺序：

1. `top` 看 `R` 态线程数与核数；注意区分 `S`（睡眠）与 `R`（运行）态。
2. `vmstat 1` 看 `cs`（context switches/s）与 `r`（运行队列长度）。
3. `perf stat -e context-switches` 量化应用级切换。
4. 回到代码：线程池大小、锁粒度、阻塞点是否合理。

### 3.9 用 perf sched 与 eBPF 观察"切换事件"本身

`perf stat` 只能给出计数，要看清"是谁切给谁、为什么切"，需要事件级观测：

```bash
# 以调度器模式采样，记录每次 switch 的前后任务与时长
$ perf sched record ./myworkload
$ perf sched latency          # 汇总各任务的调度等待/运行时间
$ perf sched map              # 时序图，直观看到 CPU 上任务交替

# 或用 perf record 记录 sched:sched_switch 跟踪点
$ perf record -e sched:sched_switch -a ./myworkload
```

```bash
$ perf sched latency
  Task                  | Runtime ms | Switches | Average delay ms
  ----------------------+------------+----------+-----------------
  myworkload            |   812.30   |    5220  |    3.21
  worker-0              |   410.22   |    4801  |    2.88
  kworker/u8:0          |    12.40   |   10320  |    0.11   ← 内核线程疯狂切换！
```

如果某类内核工作线程（kworker）的切换次数异常高，往往是事件驱动框架在短时间触发大量软中断——这本身就是"切换噪声"的来源。`sched:sched_switch` 跟踪点在安全取证中也可以还原"某个攻击进程最后被调度在哪颗核上"的时序证据，是事故复盘的有力工具。

### 3.10 实时性视角：切换频率与调度延迟的关系

对于 RT（实时）与低延迟场景，关注的不只是切换开销大小，更是**切换的抖动（jitter）**：

- 高优先级任务等待低优先级任务让出 CPU 的时间不可控，是实时系统最怕的切。启用**优先级继承（PI）**与**RT 节流（RT throttling，`/proc/sys/kernel/sched_rt_runtime_us`）** 可约束切的行为。
- `perf sched` 与内核的 `sched_tick` 统计可以给出最坏调度延迟（worst-case wakeup latency），实时系统常以此为验收指标。这部分与实时抢占配置（CONFIG_PREEMPT_RT）强相关。

### 3.11 切换频率的"经济效益"计算

工程上常需要把"切换次数"换算成"可预算的损失"，用来评估减线程/绑核改造的收益：

```text
每秒切换 10 万次 × 每次综合代价 5µs = 每秒消耗 0.5s 的 CPU
                                      = 白白损失 20% 单核能力
若改用 1:1 线程 + 绑核，切换降到 2 万次/s，节省 0.4s CPU/秒
```

把这个估算结合 `perf stat` 的真实计数，就能在改造前算清 ROI，避免"凭感觉优化"。这也是本篇文章反复强调"先测量、再优化"的原因：上下文切换是隐藏成本，不测就不知道多大。

## 4. 实战与示例

### 4.1 lmbench 测量切换开销

`lmbench` 的 `lat_ctx` 直接测量上下文切换延迟：

```bash
$ lat_ctx -s 32 2 4 8 16 24 32 64
Context switching - time in microseconds
                 (32 bytes of data)
      2 processes:     3.91
      4 processes:     4.22
      8 processes:     5.10
     16 processes:     7.43
     32 processes:    10.21
```

结果解读：进程数越多，缓存污染越严重，切换时间随进程数增长——这正是"缓存污染 + TLB"成本的直接体现。2 个进程时切换约 3.9µs，32 个进程时涨到约 10.2µs，多出的是互相挤占缓存与频繁 TLB 刷新的代价。

### 4.2 用 `perf stat` 统计 context switch

```bash
$ perf stat -e context-switches,cpu-migrations,cache-misses,cycles ./workload
 Performance counter stats for './workload':
           1,023,431      context-switches              #   K/sec
               2,198      cpu-migrations
       1,420,558,910      cache-misses
     82,401,993,201      cycles

       0.482925160 seconds time elapsed
```

- `context-switches`：本次运行的上下文切换总次数。
- `cpu-migrations`：任务在不同 CPU 间迁移次数（多核负载均衡导致）。

配合 `/proc/stat` 的 `ctxt` 总计数器可看系统级切换速率：

```bash
$ awk '{print $3}' /proc/stat; sleep 1; awk '{print $3}' /proc/stat
123456789
123457211   # 1 秒内 +422，即每秒约 422 次系统级切换
```

**`vmstat` 的 cs 列**是运维中最常用的观测点：

```bash
$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 3  0      0 812000  10000 700000    0    0     0     0 1200 4000 30 15 55  0  0
```

- `cs`（context switches/s）：系统级每秒切换次数。
- `r`（runnable）：运行态任务数。r 持续大于核数且 cs 高企，即为"切换风暴"信号。
- 正常服务器 cs 在每秒几千到几万；若几十万且 `us+sy` 又不大，多半是大量睡眠线程互相唤醒、抢锁。

### 4.3 用 `perf bench sched` 测量管道切换开销

Linux 自带 `perf bench` 子命令，用 pipe 测量调度/切换开销：

```bash
$ perf bench sched pipe
# Running 'sched/pipe' benchmark:
# Executed 1000000 pipe operations between two tasks
     Total time: 4.353 [sec]
       1.85892 [msec] ops/sec
   993325.00000 [sec] rate
```

数值越小，说明一次 pipe 写入 + 唤醒 + 切换越快。这个基准测的是"写 → 唤醒读者 → 切换过去"的完整路径，比理论值更贴近真实。

### 4.4 C 代码：用 `getrusage` 统计 voluntary/involuntary 切换

`getrusage` 的 `ru_nvcsw` / `ru_nivcsw` 字段可统计进程级切换次数，是定位"线程过多"问题的利器：

```c
#include <stdio.h>
#include <sys/resource.h>
#include <unistd.h>
#include <pthread.h>

static void *worker(void *arg) {
    volatile unsigned long x = 0;
    for (int i = 0; i < 10000000; i++) x += i;  /* CPU 密集 */
    return NULL;
}

int main(int argc, char **argv) {
    int nthr = argv[1] ? atoi(argv[1]) : 1;
    pthread_t tid[256];
    for (int i = 0; i < nthr; i++)
        pthread_create(&tid[i], NULL, worker, NULL);
    for (int i = 0; i < nthr; i++)
        pthread_join(tid[i], NULL);

    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    printf("voluntary   ctxt switches: %ld\n", ru.ru_nvcsw);
    printf("involuntary ctxt switches: %ld\n", ru.ru_nivcsw);
    return 0;
}
```

```bash
$ gcc -O2 -pthread -o cstest cstest.c
$ ./cstest 1
voluntary   ctxt switches: 0
involuntary ctxt switches: 4
$ ./cstest 64          # 线程数远超 CPU 核数时
voluntary   ctxt switches: 12
involuntary ctxt switches: 1320   # 显著上升！
```

对比可见：线程数暴增 → involuntary 切换激增 → CPU 时间被切换吞噬。这正是高并发服务"线程越多反而越慢"的根源。注意：此时 `top` 里的 CPU 使用率仍然 100%，但吞吐却在下降——因为 CPU 在"切换"上忙而不在"干活"上忙。

### 4.5 Python：threading 与多进程的性能对比

```python
import time
import threading

def busy(n):
    x = 0
    for _ in range(n):
        x = (x + 1) % 1000003
    return x

def run_threads(n, per):
    ths = [threading.Thread(target=busy, args=(per,)) for _ in range(n)]
    t0 = time.perf_counter()
    for t in ths: t.start()
    for t in ths: t.join()
    return time.perf_counter() - t0

if __name__ == "__main__":
    for n in (1, 4, 16, 64):
        print(f"threads={n:2d}  time={run_threads(n, 2000_000):.3f}s")
```

```bash
$ python3 csw.py
threads= 1  time=0.402s
threads= 4  time=1.607s
threads=16  time=6.510s   # 切换 + GIL 争抢，线性变慢
threads=64  time=27.4s
```

注意：此处变慢主因是 CPython 的 GIL；但即便在无 GIL 的原生多线程（如 C）中，线程数远超核数时 involuntary 切换同样会让吞吐下降。这个例子说明两点：**"线程数"不是免费的抽象**，且**测量才有结论**——不要凭直觉判断该用多少线程。

## 5. 常见坑与避坑指南

### 坑 1：Context Switch Storm（切换风暴）

**症状**：CPU 使用率看起来不高（或 user+sys 已经很大），但吞吐极差；`vmstat` 显示 `cs` 列高达数十万每秒，`wa` 不大但请求卡顿明显。

**根因**：创建了远超 CPU 核数的线程/进程，每个都依赖锁或定时唤醒，彼此争抢，调度器忙于切换而不是干活。常见触发：线程池大小默认过大、短周期定时任务大量唤醒、连接池滥用。

**解决**：用 `perf stat -e context-switches` 确认；把线程数压到与核数匹配（线程池 1:1 或稍多）；减少轮询，改用事件驱动（epoll 单线程）；把短周期定时器合并为长周期批量处理。

### 坑 2：CPU affinity 未设置导致 cache 抖动

**症状**：常驻热点线程的 `cpu-migrations` 很高，cache-misses 异常偏大。

**根因**：任务在各核间迁移，丢掉了热 cache 与 TLB。

**解决**：`sched_setaffinity` 或 `taskset` 绑核；对实时/高吞吐线程固定核。大数据类任务配合 `numactl` 绑定 NUMA 节点效果更佳。

```bash
$ taskset -c 0-1 ./myapp        # 绑定到核 0-1
```

### 坑 3：VM / 容器中 TLB flush 开销被放大

**症状**：同样的负载，虚拟化或容器环境下切换开销比物理机高出数倍。

**根因**：Guest 进程切换触发嵌套分页刷新（EPT/NPT）、影子页表同步；KVM 的 TLB flush 交互开销大。容器虽共享宿主机内核，但 namespace 隔离与 cgroup 限制仍带来额外切换成本。

**解决**：同进程内偏好线程而非进程（共享 mm，免 TLB 刷新）；启用内核 PCID；虚拟化开启 EPT/VPID 等硬件加速；容器里避免大量短生命周期进程互相切换。

### 坑 4：误把"进程切换"当"线程切换"，以为免费

**症状**：用 fork 创建大量进程做"并发"，性能反而不如单线程。

**根因**：进程切换的 TLB 刷新与地址空间切换成本远高于线程；fork 本身还涉及页表与 fd 表复制（COW）。

**解决**：同进程内并发优先线程/协程；只有需要故障隔离或跨越较长排障周期时才用进程。

### 坑 5：Spectre v2 侧信道利用上下文切换间隙

**安全视角**：Meltdown/Spectre 系列攻击利用的是 CPU 在权限检查与预测执行之间的"间隙"。上下文切换是**分支目标缓冲（BTB）** 状态残留的高发点：进程 A 切走后，其分支预测信息可能留在 BTB 中，被进程 B 探测，从而推断 A 执行过的代码分支（BTB 中毒/Spectre v2 变体）。

```text
进程 A（受害者）分支预测残留
        │  上下文切换
        ▼
进程 B（攻击者）探测 BTB：
  判断进程 A 曾走过哪个分支 → 侧信道泄露

缓解：IBRS / IBPB / STIBP（Intel），
     切换进程时刷新 BTB（IBPB）
```

**防御意义**：内核安全团队启用 KPTI 与 BTB 刷新指令（`ibpb`），就是在用"切换开销"换"隔离安全"——安全与性能存在明确权衡。理解上下文切换机制，才能评估此类补丁的性能成本。

### 坑 6：定时器与轻量线程组合召唤"唤醒风暴"

**症状**：每 GOMAXPROCS 设得很大、或者是协程库 + 大量 `time.Sleep`/定时器回调的高并发程序，`cs` 每秒几十万次，`us` 却不到 30%。

**根因**：定时器到期会唤醒内核线程/协程；若定时器粒度极细（毫秒级）且数量巨大，每次到期都触发一次"唤醒→调度→睡眠"的切换，形成唤醒风暴。COROUTINE 越多、定时器越密，切换不亚于线程。

**解决**：合并定时器（时间轮/层级时间轮）、只让少量内核线程持有真实定时器并批量回调用户态协程、提高超时粒度。这也是 epoll 超时用「一次 wait + 批量处理」而非逐任务定时器的原因。

### 坑 7：把 CFS 的 nice 当"允许超卖"的借口

**症状**：运维给每个容器 `cpu.shares` 都配置很大，宿主机核数少、容器多，每核运行态线程长期超过几十，involuntary 切换疯狂。

**根因**：CFS/EEVDF 的权重（nice/shares）只决定**分配比例**，不决定"并行的线程数"。超卖过多时，权重只是把切换切得"有优先级"，切换总量不会减少。

**解决**：控制容器的 `cpu.max`（quota/period）与运行态线程数；大并发服务在容器内同样遵循"线程数 ≈ 核数"的约束；用 `cpuset` 绑核收窄运行范围。
