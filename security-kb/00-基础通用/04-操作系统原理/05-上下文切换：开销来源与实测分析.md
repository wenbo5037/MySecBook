## 1. 概述

上下文切换（Context Switch）是操作系统多任务并发的基础机制。所谓"上下文"（context），指的是某个执行流（execution stream）在当前时刻的全部运行状态——包括通用寄存器（general-purpose registers）、程序计数器（PC）、栈指针、状态寄存器、页表基址（CR3/PTBR）、浮点与 SIMD 寄存器、以及内核中该任务对应的 PCB（Process Control Block）/TCB（Thread Control Block）数据结构。

当 CPU 从一个执行流切换到另一个执行流时，必须完成三件事：

1. **保存**当前执行流的全部状态（save state）；
2. **加载**目标执行流的全部状态（load state）；
3. **执行**调度器决定"下一个跑谁"的逻辑（scheduler decision）。

这一过程看似简单，却是现代操作系统性能分析中最容易被低估的隐藏开销。不少性能工程师在分析高并发服务时，只关注 CPU 使用率、内存占用、网络带宽，却忽略了"大量线程在互相抢占 CPU"这件事本身带来的成本。一次上下文切换本身只需要微秒级时间，但当线程数远超 CPU 核数时，切换频率可能高达每秒数十万次，累计开销足以把吞吐量打掉 30%~50%。

上下文切换可以按维度划分为以下几种类型：

| 类型 | 说明 | 相对开销 |
|------|------|----------|
| 进程切换（Process Switch） | 不同进程间切换，需切换地址空间，TLB 必须刷新 | 最高 |
| 线程切换（Thread Switch） | 同进程不同线程间切换，共享地址空间（内核线程仍需内核态介入） | 中 |
| 用户态协程切换 | 协程/纤程在用户态调度，无需进入内核态 | 最低 |
| 中断切换（Interrupt） | 内核态中断处理，只涉及部分现场 | 视情况而定 |

理解上下文切换，首先要区分"内核态进程/线程切换"与"用户态协程切换"。前者需要特权级切换（privilege level switching，ring 3 → ring 0）加 TLB 刷新，开销大；后者仅仅在用户态保存/恢复少量寄存器，开销小一个数量级以上。这也是协程（coroutine）、goroutine 之所以高性能的根本原因。

在现代数据中心与云原生场景中，上下文切换的代价被进一步放大：容器（Container）共享宿主机内核，一个节点上成百上千个容器、数万个线程在同一批核上争抢；虚拟化环境中嵌套页表（EPT/NPT）让每次切换多付出虚拟化开销；再加上近年的安全补丁（KPTI 内核页表隔离、Spectre BTB 刷新）给每次切换增加了额外指令。不夸张地说，**上下文切换是云上"看不见的性能税"**——它在 CPU 采样里几乎不显示为热点，却实实在在地侵蚀着每一条路径的延迟。这也是为什么编写高性能服务时，"减少切换次数"本身就是一种优化手段（绑核、协程化、事件驱动）。

本节为 [[03-线程模型：内核线程用户线程与混合模型]] 的姊妹篇，重点从**性能开销的量化来源**与**实测方法**角度深入。理解开销的精确来源，是后续做性能调优、高并发设计以及安全加固的前提。

## 2. 核心原理

### 2.1 上下文切换的完整流程

以 Linux x86-64 为例，一次典型的进程上下文切换（由抢占触发）完整流程如下：

```text
           时钟中断 / 主动让出（schedule() 路径）
                        │
                        ▼
   ┌────── 进入内核态（syscall/中断入口，保存用户态寄存器到 pt_regs）
   │
   ▼
   ┌────────────────────────────────────┐
   │ 1. 时钟中断处理（irq_enter）          │
   │    更新调度节拍（tick）、检查抢占      │
   └───────────────┬────────────────────┘
                   │  若需要调度
                   ▼
   ┌────────────────────────────────────┐
   │ 2. schedule() 调度器决策             │
   │    选择下一个任务（pick_next_task）   │
   │    CFS/EEVDF 运行队列操作            │
   └───────────────┬────────────────────┘
                   ▼
   ┌────────────────────────────────────┐
   │ 3. switch_to() 上下文切换            │
   │    __switch_to():                  │
   │     保存旧任务寄存器到内核栈          │
   │     加载新任务寄存器                 │
   │     切换内核栈 (rsp)                │
   │     切换 CR3（页表，进程间）          │
   │     切换 TSS / FSBASE（线程局部存储） │
   └───────────────┬────────────────────┘
                   ▼
   ┌────────────────────────────────────┐
   │ 4. ret_from_fork 返回新任务用户态     │
   │    sysretq / iretq                  │
   └────────────────────────────────────┘
```

关键实现位于 `arch/x86/kernel/process_64.c` 的 `__switch_to()`，以及调度核心 `kernel/sched/core.c` 的 `schedule()`。`switch_to()` 宏本质上是保存/恢复一组寄存器的汇编代码，调用 `__switch_to_asm` 完成寄存器交换。

**中断上下文切换与进程上下文切换的区别**：中断处理虽然也"切换"了执行流（用户态→内核中断处理），但它**不涉及调度器决策**——中断处理完会原样返回被中断的进程，现场保存在该进程的内核栈上。而真正的上下文切换意味着调度器选择了**另一个任务**，被切换任务的现场必须完整保存到内核栈/PCB 中，等待下次被调度时恢复。这也是为什么"每秒中断次数很高"不等于"上下文切换很多"。

### 2.2 进程切换 vs 线程切换 vs 协程切换

| 维度 | 进程切换 | 同进程线程切换 | 协程（用户态）切换 |
|------|----------|---------------|-------------------|
| 地址空间切换 | 需要（换页表/CR3） | 不需要 | 不需要 |
| TLB 影响 | 必须刷新 | 一般不需要 | 不需要 |
| 内核态介入 | 需要 | 需要（内核线程） | 用户态即可 |
| 寄存器开销 | 全量 | 全量 | 少量 |
| 典型开销 | 3~10µs | 1~3µs | 数十~数百 ns |
| 调度器 | CFS/EEVDF | CFS/EEVDF | 用户态调度器 |

**为什么同进程线程切换免掉 TLB/Cache 开销**：线程共享进程的地址空间与页表，切换线程时 CR3 不变，TLB 条目依然有效（同一进程所有线程的虚拟地址空间映射相同）；L1/L2 中驻留的是同一进程的代码与数据，热缓存天然保留。因此高并发场景中"多线程"对缓存的友好度远高于"多进程"——进程切换付出的 cache 冷启动代价是线程切换的近一个数量级。

### 2.3 voluntary vs involuntary

- **Voluntary context switch（自愿切换）**：执行流主动让出 CPU。典型场景：`sleep()`、等待 I/O（阻塞 `read`）、`sched_yield()`、获取互斥锁失败而阻塞。次数可从 `/proc/<pid>/status` 的 `voluntary_ctxt_switches` 字段查看。
- **Involuntary context switch（非自愿/被动切换）**：执行流被强制剥夺 CPU。典型场景：时间片耗尽（time slice expired）、更高优先级任务抢占、CPU 负载过高。对应 `nonvoluntary_ctxt_switches` 字段。

```bash
$ cat /proc/8701/status | grep -i ctxt
voluntary_ctxt_switches:        812
nonvoluntary_ctxt_switches:     43
```

**voluntary 与 involuntary 的比值有明确的诊断意义**：

- **voluntary 高、involuntary 低**：进程大量等待 I/O 或锁，属于"阻塞型"负载。这是大多服务进程的正常形态，切换是"不得不等"的结果；但若 voluntary 高到离谱（每秒数千次），说明锁竞争面过宽或等待链过长，值得优化。
- **involuntary 高**：说明**超过 CPU 能力的线程在争抢核**，时间片耗尽被迫让出。这是"线程数过多"的典型信号，往往伴随吞吐下降与延迟抖动——每个线程每秒都被割成若干片，请求被频繁打断。
- **两者都高**：既要等资源又要被抢占，系统整体排队严重（CPU 饱和 + 竞争叠加），需要扩容或降低并发度。

### 2.4 内核抢占模型：CONFIG_PREEMPT 的影响

Linux 内核本身也有"可抢占性"配置，直接影响上下文切换的频率与实时性：

| 配置 | 说明 | 适用 |
|------|------|------|
| `CONFIG_PREEMPT_NONE` | 内核只在意难以抢占点退出时调度，切换最少、吞吐最大 | 服务器 |
| `CONFIG_PREEMPT_VOLUNTARY` | 内核在部分自愿让出点可抢占 | 桌面 |
| `CONFIG_PREEMPT_FULL` | 内核几乎所有地方可抢占，响应快但切换多 | 桌面/交互 |
| `CONFIG_PREEMPT_RT` | 完全抢占 + 实时补丁，调度延迟可到百微秒级 | 实时系统 |

理解这一点有助于解释"为什么同一台机器跑服务器应用与桌面应用，调度表现截然不同"——抢占配置从内核层面决定了"切换的触发密度"。
