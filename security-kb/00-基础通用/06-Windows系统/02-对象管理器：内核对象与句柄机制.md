## 1. 概述

Windows 操作系统的稳定与安全，很大程度上建立在一个核心抽象之上：**对象管理器（Object Manager）**。它是 Windows 内核执行体（Executive）六大核心组件之一，由 `ntoskrnl.exe` 实现，负责对内核中几乎全部可命名资源进行统一管理。无论是一个文件（File）、一个进程（Process）、一个线程（Thread）、一个注册表键（Key），还是一个事件（Event）、互斥体（Mutex）、信号量（Semaphore）或符号链接（SymbolicLink），在内核中都被建模为一个**对象（Object）**，并由对象管理器统一提供如下服务：

1. 对象的创建、命名与命名空间管理；
2. 对象类型的注册与类型元数据维护；
3. 基于句柄的引用与引用计数（Reference Count）管理；
4. 对象安全描述符的附加与访问检查；
5. 句柄表（Handle Table）的分配、复制、继承与清理；
6. 对象撤销（Object Teardown）与关闭时的清理回调。

从安全角度来看，对象管理器是**权限边界（Security Boundary）** 的第一道闸门。用户态进程无法直接触碰内核对象，必须先通过系统服务（System Service）如 `NtOpenProcess`、`NtCreateFile`、`NtQuerySystemInformation` 拿到一个**句柄（Handle）**，此后对该对象的一切操作都依赖这个句柄。攻击者的提权（Privilege Escalation）、进程注入（Process Injection）、句柄劫持（Handle Hijacking）、Rootkit 隐藏（Hide Process）、DPC/Shellcode 落地等攻击技术，绝大部分都绕不开对象管理器与句柄机制。同时，EDR（端点检测与响应）与内核防护产品也正是通过 `ObRegisterCallbacks`、句柄枚举、对象类型过滤等手段驻扎在对象管理器这条必经之路上。

本文属于《Windows 系统》方向的**主攻级（Primary）** 知识点，要求读者掌握：对象管理器整体架构、`OBJECT_HEADER`/`OBJECT_BODY` 内部结构、句柄表布局与标志位、对象安全（安全描述符与访问权限）、以及从攻防两端理解句柄泄漏、句柄提权、对象目录操纵等实战技巧。

需要特别强调的一点是：对象管理器并不是“可选的抽象层”，而是**所有系统资源的必经之路**。无论是杀毒软件读取文件、浏览器创建互斥体，还是攻击者注入一段 Shellcode，最终都要在对象管理器里注册一个对象、在某个句柄表里留下一条表项。正因为如此，对象管理器成为了攻防交锋的主战场：防御方在这里挂上 `ObRegisterCallbacks` 过滤危险请求，攻击方则在这里寻找可滥用的句柄、可操纵的名称空间、可欺骗的安全检查。理解了这一点，就会明白为什么“对象”和“句柄”这两个看似底层的话题，会反复出现在提权漏洞（如沙箱逃逸、内核提权）、进程注入、签章绕过与 Rootkit 对抗等所有高级课题里。可以说，**对象管理器的掌握程度，直接决定了你对 Windows 安全机制的理解深度**。

## 2. 核心原理

### 2.1 一次对象访问的完整旅程

以一个用户进程调用 `CreateFile` 为例，其对象管理器路径为：

```
user-mode:  CreateFile()  →  kernel32/ntdll:  NtCreateFile()
                                                    │
                                            (SYSCALL 进入内核)
                                                    ▼
kernel:   NtCreateFile()  →  ObpCreateHandle() / ObReferenceObjectByName()
                                                    │
                        （先沿对象目录解析名称路径，中途触发安全检查）
                                                    ▼
                   ObpLookupObjectName()  →  IopParseDevice (文件解析器)
                                                    │
                                                    ▼
                   object body 创建成功 → ObpInsertHandle() 
                                                    │
                                                    ▼
              在进程句柄表中分配一个句柄表项（HANDLE_TABLE_ENTRY）,
              设置对象引用计数 +1，安全检查通过后返回句柄值（低2位为标志）
```

整个过程体现了三个关键设计：

- **间接性（Indirection）**：内核对象从不直接暴露给用户态，用户态只持有**句柄（一个 4/8 字节的索引值）**。句柄值本身并不指向对象，而是指向**进程句柄表（Process Handle Table）**中的某一行；
- **统一的命名空间（Unified Namespace）**：文件、设备、符号链接等被拼接到同一个 `\` 根目录下的对象目录（Object Directory）树中，形成 `\Device`、`\BaseNamedObjects`、`\GLOBAL??`、`\ObjectTypes`、`\Security`、`\KnownDlls` 等著名目录；
- **引用计数的双计数模型（Two Counters）**：每个对象同时维护“句柄引用（Handle Count）”与“对象指针引用（Pointer/Reference Count）”。句柄增删影响前者；当两个计数都为 0 时对象被销毁。

### 2.2 对象 = 头部（Header） + 体（Body）

在内核中，一个对象的布局是：

```
                对象管理器管理的数据                     对象类型（如进程）管理的数据
        ┌───────────────────────────────┐  ┌──────────────────────┐
        │      OBJECT_HEADER            │  │      OBJECT_BODY      │
        │  ┌-------------------------┐  │  │  ┌------------------┐  │
        │  │ (Padding, InfoMask)     │  │  │  │  EPROCESS 等     │  │
        │  │  Collapsed Headers      │  │  │  │  (类型私有数据)   │  │
        │  │  CreatorInfo / Name /   │  │  │  │                  │  │
        │  │  HandleInfo / Quota /   │  │  │  │                  │  │
        │  │  AuditInfo /          │  │  │  │                  │  │
        │  │  ExtendedInfo (可选)    │  │  │  │                  │  │
        │  ├-------------------------┤  │  │  │                  │  │
        │  │  Body (主区块)          │  │  │  │                  │  │
        │  │  始终存在               │  │  ├──────────────────┤  │
        │  └-------------------------┘  │  └──────────────────┘  │
        └───────────────────────────────┘  └────────────────────┘
          地址向上增长                  地址向下增长（x64 上两者相邻）
```

- 分配对象时，`ObpAllocateObject` 一次性分配“头部 + 体”的连续内存，返回给组件（如进程管理器、I/O 管理器）的指针指向 **OBJECT_BODY**；
- 头部紧挨体，位于对象指针的下方（负偏移）。WinDbg 中一个句柄反解到对象时常规先取 `OBJECT_BODY`，再向上/向下（按架构）找 `OBJECT_HEADER`；
- 头部内部根据 `InfoMask` 标志按固定偏移放置可选的**“折叠头（Collapsed Header）”**：`OBJECT_HEADER_CREATOR_INFO()`、`OBJECT_HEADER_NAME_INFO()`、`OBJECT_HEADER_HANDLE_INFO()`、`OBJECT_HEADER_QUOTA_INFO()`、`OBJECT_HEADER_PROCESS_INFO()`、`OBJECT_HEADER_AUDIT_INFO()`、`OBJECT_HEADER_EXTENDED_INFO()` 等，只有需要时才驻留；
- **体（Body）** 的数据结构由对象类型决定：进程对象体即 `EPROCESS`，线程对象体即 `ETHREAD`，文件对象体即 `FILE_OBJECT`，互斥体对象体即 `KMUTANT`。这就是为什么 `dt _EPROCESS` 与 `dt _OBJECT_BODY` 不同——后者只是一个“体指针”，通常是前缀（Body）结构。

也就是说，**对象管理器负责的是“壳”，对象类型负责的是“芯”**。对象管理器不关心一个进程里面有什么字段，它只管这个对象有多少引用、有谁在持有句柄、安全描述符是否有效、名称叫什么；而 `EPROCESS` 里面的 `ImageFileName`、`Token`、`ThreadListHead` 这些字段则完全由进程管理器（Ps）来维护。两者通过对象类型结构里的方法表（Method Table）相互配合——例如当对象管理器需要“询问对象的名字”时，就调用类型对象里注册的 `ObQueryNameInfo` 回调，由进程管理器的实现回答。这种“接口与实现分离”的设计，让十六种以上截然不同的内核资源能够共用同一套生命周期、安全与命名框架。

折叠头还有一个重要的安全含义：`OBJECT_HEADER_AUDIT_INFO` 只在对象启用审计时才驻留，而 `OBJECT_HEADER_QUOTA_INFO` 则记录了该对象消耗的配额字节数——如果恶意驱动伪造 `InfoMask`，会导致内核凭错误的偏移读取头部,从而出现内存越界读写。**InfoMask 由此成为内核漏洞（尤其是对象头溢出类）研究的热点字段**。

核心结构示意（x64，Windows 10/11）：

```c
typedef struct _OBJECT_HEADER {
    LONG64  PointerCount;         // 指针引用计数（Pointer Count）
    union {
        LONG64 HandleCount;       // 句柄引用计数（Handle Count）
        PVOID  NextToFree;        // 空闲句柄链表指针（指向下一个空闲表项）
    };
    POBJECT_TYPE ObjectType;      // 指向对象类型（_OBJECT_TYPE）
    UCHAR  InfoMask;              // 指示存在哪些“折叠头”
    UCHAR  Flags;                 // 对象标志（如 Permament、KeepAlive）
    union {
        UCHAR Reserved;
        ULONG ObjectCreateInfo;
        PVOID QuotaBlockCharged;
    };
    POBJECT_HEADER_CREATOR_INFO CreatorBackTraceIndex; // 创建栈回溯信息
    PUCHAR SecurityDescriptor;    // 指向对象安全描述符（自相关结构）
    // 可选折叠头从本结构之后按 InfoMask 排列
} OBJECT_HEADER;

typedef struct _OBJECT_BODY {      // 体是“容器”标记，类型私有数据就贴在后面
    UCHAR  Data[1];
} OBJECT_BODY;
```

### 2.3 句柄：从“值”到“表项”

句柄值不是指针。Windows 使用 **句柄表（Handle Table）** 将句柄值映射到对象。每个进程有一个专属句柄表（进程的 `EPROCESS.ObjectTable` 指向它），系统进程还有若干内核专用句柄表（如 `PspCidTable`、`ExCallbackObject` 使用的表）。句柄值在 x64 上是 8 字节对齐索引 + 低 2 位属性标志，**句柄粒度（Handle Granularity）为 4**：

```
十六进制句柄值 0x0000_0000_00F0_0004 的二进制解读:
    0xF00004 = 1111 0000 0000 0000 0000 0100b
                └──────────┬──────────┘  └──┬──┘
                        表项索引(bits 2+)
                                            │
                                    低2位属性标志:
                                    bit0 = HANDLE_FLAG_INHERIT          (0x1, 可继承)
                                    bit1 = HANDLE_FLAG_PROTECT_FROM_CLOSE(0x2, 防关闭)
```

即：句柄表项索引 = 句柄值 >> 2；对象管理器根据索引、表级数与一级表索引即可定位到对应的 `_HANDLE_TABLE_ENTRY`。

## 3. 详细知识点

### 3.1 对象类型（Object Types）与类型体系

对象管理器维护一张全局对象类型列表，每个类型由一个 `POBJECT_TYPE` 描述，大致等价于内核 C++ 语义中的“类”，包含：

- 类型名称（如 `Process`、`Thread`、`File`、`Key`、`Event`、`Mutex`、`Semaphore`、`Mutant` 等）；
- 类型 GUID（Windows 10 之后引入，`_OBJECT_TYPE.TypeGuid`）；
- 对象类型的默认属性：`CaseInsensitive`（名称不区分大小写）、`PoolType`（NonPagedPool/NPaged）、`InvalidAttributes`、`DefaultNonPagedPoolCharge`、`DefaultPagedPoolCharge`、`DefaultQuota`、`SecurityRequired`（必须带安全描述符）、`MaintainHandleCount`、`MaintainTypeList`、`SupportsObjectCallbacks`、`CacheAligned` 等；
- 一组**方法表（Object Methods）** 回调：`Create`、`Delete`、`Parse`、`Security`、`QueryName`、`Close`、`Dump`、`Open`、`Reserved`。这些回调让不同类型把通用生命周期 hook 到自己的语义上（例如 `File` 类型的 Parse 由 I/O 管理器提供，负责把“文件名”解析为真正的文件体）；
- 带有 `ProcessClassIndex`/`ProcessClass` 等扩展字段的类型（进程、线程、MP2 表等）。

```c
typedef struct _OBJECT_TYPE_INITIALIZER {
    USHORT Length;
    BOOLEAN UseDefaultObject;
    BOOLEAN CaseInsensitive;
    ULONG InvalidAttributes;             // 创建对象时禁止的句柄属性
    ULONG DefaultNonPagedPoolCharge;
    ULONG DefaultPagedPoolCharge;
    POBJECT_TYPE_INITIALIZER_EXTENSION DefaultQuota;
    OBJECT_TYPE_INITIALIZER_OBJECTIVE_INFORMATION Objectives;
    SECURITY_INFORMATION SecurityInformation;
    POBJECT_TYPE_INITIALIZER Extension;
    ...方法表...
    OBJECT_TYPE_INITIALIZER_SIGNATURE Signatures;   // WIN10+: 签名校验
    OBJECT_TYPE_INITIALIZER_ONE_SIGNATURE OneSignatures;
    ...
} OBJECT_TYPE_INITIALIZER;
```

### 3.2 对象目录与命名空间（Object Directory & Namespace）

对象命名空间是一棵以 `\` 为根的对象目录树，普通用户可通过**对象管理器 API**（如 `NtCreateDirectoryObject`）、内核工具（WinDbg `!object`）或开源工具（如 Sysinternals `WinObj`）查看。常见目录：

- `\GLOBAL??`（全局 Dos 设备符链接，指向 `\Device` 下各设备对象；`\DosDevices` 是它向用户态 Win32 的映射端点，因此盘符 `C:` 实际解析为 `\Device\HarddiskVolume3`）；
- `\Device`（设备对象，如 `\Device\NamedPipe`、`\Device\Tcp`）；
- `\BaseNamedObjects`（会话相关的命名内核对象：`Event`、`Mutex`、`Semaphore`、`Section` 等，用户态 `CreateMutex/F/i` 落在这里；非交互会话则落在 `\Sessions\<n>\BaseNamedObjects`）；
- `\??\` / `\GLOBAL??` 交替存在（Windows 8+ 中 `\??` 指向上边际、`\GLOBAL??` 指向全局）；
- `\ObjectTypes`（类型目录，punk 不为用户可直接遍历）；
- `\Security`、`\KnownDlls`（已知 DLL 映射的 Section 对象，LDR 机制依赖）、`\ArcName`（早期 NTLDR）、`\KernelObjects`（`\KernelObjects\MemoryPartition` 等）。

**对象目录也是可授予安全权限的对象**。它能被额外 DACL 限制，从而拦截未授权进程对命名空间的访问。Win32API `CreateMutexW` 等在 `\BaseNamedObjects` 创建对象时，若与另一会话/进程名称冲突，会因“不同命名空间”而互相不可见——这类“命名空间欺骗”是某些本地提权/对象利用（OpObject 利用链）的历史根源。

### 3.3 句柄表结构：_HANDLE_TABLE 与 _HANDLE_TABLE_ENTRY

每个进程句柄表对应：

```c
typedef struct _HANDLE_TABLE {
    ULONG_PTR TableCode;              // 顶位路径：低2位表示表级数(1/2/3级)
                                      // bit0,bit1: 0=一级表，1=二级表，2=三级表
    PEPROCESS QuotaProcess;           // 所属进程（配额记账）
    // 下面还有 HandleCount、NextHandleToFree、FirstFree、
    // LastFree、MaxCount/Limit（_HANDLE_TABLE_*）
    ...
} HANDLE_TABLE;

typedef union _HANDLE_TABLE_ENTRY {   // 大小为 16 字节 (x64)
    struct {
        PVOID Object;                 // 指向 OBJECT_HEADER（低4位含信息）
        struct {
            ULONG32 GrantedAccess;    // 授予的访问权限（Granted Access）
            UCHAR GrantedAccessIndex;
            union {
                UCHAR Flags;         // 标志位
                UCHAR Attributes;    // 继承等属性（HANDLE_FLAG_*）
            };
        } Info;
        union {
            struct {
                UCHAR  WriteProtect;
                UCHAR  ReadProtect;
                union {
                    ULONG  Value;
                    struct { UCHAR Modified; UCHAR ListIndex; UCHAR Visible; ... } Bits;
                };
            };
            struct {
                ULONG64 Value;
                struct { ULONG Volatile; ULONG ExplicitlyFreed; } Bits;
            };
        } ValueBits;
    };
    struct {
        KIRQL  WaitListLock;
        LIST_ENTRY WaitList;          // 可等待回调列表
    } Object;
} HANDLE_TABLE_ENTRY;
```

要点：

1. **TableCode 的低 2 位编码表级数**：一级表直接指向 `HANDLE_TABLE_ENTRY[]`；二级表指向 `HANDLE_TABLE_LEVEL1[]`（页级指针）；三级表再做一层索引。这种设计让句柄表可以按需增长，同时保证查询 O(1)；
2. **每个表项 16 字节**（x64），`Object` 域是内核对象指针的关键——它指向对象 `OBJECT_HEADER`（因此**表项中的 Object 地址 = 对象体地址 - 头部偏移**）。低 4 位被对象管理器用作空闲链表标记与 `HANDLE_ENTRY_NFO`，故内核会用 `OBJ_KERNEL_OBJECT` 等宏按 16 对齐还原；
3. **GrantedAccess 字段**记录该句柄拥有哪些权限，这是后续所有 `ObpAccessCheck` 的依据——**句柄权限是“借来的权限”，本身不扩大令牌，但若拥有 SeDebugPrivilege 则可提升对象权限**；
4. 表项复用通过“空闲句柄链表”完成，`NextFree` 指针存放在空闲表项的 `Object` 字段中。

### 3.4 句柄表级数与增长算法

- 一级表：`TABLE_SIZE_ONE = 16 * 1024 / 16 = 1024` 项（低 2 位为 `LEVEL_ONE`）；
- 二级表：每级 512 项，支持约 524288 项（`0x1000`/`0x800`）；
- 三级表：最高支持 `0x10000 * 0x1000 * 0x1000` 项，接近 68 亿，令牌未到上限几乎不会用到；
- 扩容时 `ExInitializeHandleTable`/`ExExpandHandleTable` 分配新页并把旧表页指针拷入新级表。

用户态常用 `SetProcessHandleCount`（SYSTEMI）调节句柄配额，`PROCESS_QUERY_LIMITED_INFORMATION`+`NtQueryInformationProcess(HandleCount)` 可读取当前句柄数。Windows 每个进程默认句柄上限为 1,048,576（`MaxHandles`），超过会触发 `STATUS_INVALID_HANDLE` / `STATUS_NO_MORE_HANDLES`。

句柄表的**二级/三级结构**是许多内核研究与 Rootkit 隐藏技术的切入点。由于一级表只有约一千个表项，绝大多数进程实际都使用二级表；二级表首层是一个页表式的“编号页”数组，每页指向独立的表项页。这让句柄表的遍历变成了“双层循环”：先遍历第一层指针数组，再遍历每页内的表项。攻击者如果想把某个对象从进程中“藏起来”，就必须同时清掉该对象在二级表页里的表项——但清理时若有其他线程正在通过这个句柄操作对象，就会造成 Use-After-Free。这也是为什么句柄表遍历工具（如 Handle.exe、`!handle`）在扫描的同时,系统里任何一个线程都可能新建或关闭句柄，导致扫描结果出现“瞬间不一致”，需要结合对象引用计数来交叉验证。

### 3.5 内核句柄（Kernel Handles）与用户句柄（User Handles）

句柄按作用域可分三类：

| 类型 | 存放位置 | 特点 | 常见例子 |
|------|----------|------|----------|
| 用户句柄 | 进程句柄表（EPROCESS.ObjectTable） | 用户态可访问，受对象安全描述符约束 | `OpenProcess` 返回句柄 |
| 内核句柄 | 内核专用/当前进程表，通过 `ObOpenObjectByType` 等在内核态创建 | 标志 `OBJ_KERNEL_HANDLE`（0x10）；内核句柄不参与用户态可见，**不允许继承**，关闭时直接由内核完成 | `CmpRegistrySd`、`ExEventObject`、设备对象内核引用 |
| 进程/线程 ID 表（PspCidTable） | 专用句柄表，用进程/线程 ID 作为句柄索引 | `NtOpenProcess(PID)` 本质上是在该表上做句柄转换 | `OpenProcess`、`NtOpenProcessToken` 内部 |

关键区别：**内核句柄带有 `HANDLE_FLAG_KERNEL`（0x10）**，在关闭时即使该句柄被用户态进程持有也只能由内核间接关闭（`ObCloseHandle` 检查 `/OBJ_KERNEL_HANDLE` 分支）。传统 Rootkit 隐藏进程时勾兑 PspCidTable 中的表项，就是利用“Cid 表项即句柄”的机制。

### 3.6 对象安全：安全描述符与访问检查（Security Descriptor / Access Check）

每个对象可以携带一个**安全描述符（Security Descriptor）**，内含：

- DACL（Discretionary ACL，自主访问控制列表）：决定谁能访问；
- SACL（System ACL）：审计；
- Owner（所有者）、PrimaryGroup；
- 控制位（SE_DACL_PRESENT 等）。

内核在 `ObInsertObject`/`ObpCreateHandle` 时若检查到 `SecurityRequired` 类型（如 File、Process、Thread、Key），会调用 `SeCaptureSecurityDescriptor` + `SeAccessCheck`，以调用者令牌冒充的 SID 对照对象的 DACL 逐条匹配。这就是**对象级安全边界**：

```
NtOpenProcess(PID)
   → ObpLookupObjectName 找到 PspCidTable 中的 EPROCESS
   → 带 PROCESS_ALL_ACCESS 请求权限
   → ObpCreateHandle → SeAccessCheck(token, SE_PS_PROCESSCONTEXT, GrantedAccess)
        ├─ DACL 拒绝 → STATUS_ACCESS_DENIED
        └─ DACL 允许 → 表项写入 GrantedAccess
             若调用者有 SeDebugPrivilege：
                 SePrivilegeCheck 通过 → 以高权限重新做安全检查(实际授予 PROCESS_ALL_ACCESS)
```

因此：**能否打开一个进程/线程句柄，是 DACL + Token（含特权）共同决定**。系统进程（system）的 DACL 默认只允许 SYSTEM 自身以 `PROCESS_ALL_ACCESS` 打开；Administrators 即使有管理员，无 SeDebugPrivilege，同样打不开 services.exe。这也解释了会话隔离：跨会话不共享 `\BaseNamedObjects`，配合低特权令牌构成纵深防御。

从攻击者的视角看，`SeAccessCheck` 是一条可以“协商”而不是“一次定死”的路径：一方面，令牌中的所有者 SID、组成员关系、特权列表会影响判定结果，因此把令牌“打回”到完整的管理员令牌（如 `RestoreServerParams`、删除受限 SID）就能把被拒的请求变成被允许；另一方面，**权限检查发生在“打开句柄”的那一刻**，而不是对象建立之后。也就是说，如果攻击者在对象创建前以低权限打开了一个后续会写入敏感内容的命名对象（例如交互式会话的输入事件、日志文件），那么即使高权限进程后来才用该对象，它持有的句柄权限依然受限于当初创建/打开时的判定——这正是“命名对象抢占”类攻击（对象目录和时间窗口组合）的典型逻辑。

### 3.7 句柄的创建、复制、继承与关闭

- **创建/打开**：`NtCreateFile/NtOpenKey/...` 内部走 `ObpCreateHandle` 或 `ObReferenceObjectByName`；
- **复制（Duplicate）**：`NtDuplicateObject` 可在同一/不同进程的句柄表复制句柄，攻击者可借此在“无法直接打开”时通过已授权句柄的复制实现横向迁移（句柄窃取/句柄投递）；
- **继承（Inherit）**：创建句柄时置 `OBJECT_ATTRIBUTES.InheritHandle = TRUE`，子进程通过 `CreateProcess(bInheritHandles)` 继承；注意 `HANDLE_FLAG_INHERIT` 位于句柄值低 2 位，是纯粹的用户态标志,并可被 `SetHandleInformation` 翻转；
- **关闭**：`CloseHandle/NtClose → ObpCloseHandle`，递减句柄引用；若表项置了 `PROTECT_FROM_CLOSE`，`NtClose` 会返回 `STATUS_HANDLE_NOT_CLOSABLE`——这既是防御（对象被保护）也是攻击面（恶意驱动可把关键进程的句柄置为不可关闭以规避回收）。

### 3.8 对象回调：ObRegisterCallbacks（EDR 挂点）

Windows 8+ 提供 `ObRegisterCallbacks`（`ObRegisterCallbacks`/`ObUnRegisterCallbacks`/`ObGetFilterVersion`），允许内核驱动在以下事件插入回调：

- **ProcCreate**：进程对象句柄**即将打开或复制**（`OB_OPERATION_*`），可拒绝 `PROCESS_VM_WRITE`、`PROCESS_TERMINATE` 等危险权限；
- **ProcDuplicate**、**ThrCreate**、**ThrDuplicate**：线程句柄相应操作；
- 回调运行时 `ObPostOperationCallback`/`ObPreOperationCallback` 可修改操作上下文（`OB_PREOP_*`）——规则上是**无论如何都执行后置回调**，除非放进禁止列表。

安全视角：这是当前主流 EDR 在“句柄层”拦截提权/注入的主要挂点（如 CrowdStrike、Defender 驱动的进程保护）。Rootkit 对抗手段则是先清理回调例程表（inline HOOK `ObRegisterCallbacks` 或 patch 回调链表）。

需要指出的是，`ObRegisterCallbacks` 的设计本身也引入了新的对抗面：系统的回调列表是以链表组织、由 `ObFilterList` 头对象管理的，驱动之间可以互相注销对方的过滤器（Windows 10 1809 之前甚至不校验任意驱动注销他人回调的合法性），于是又出现了“EDR 卸载回调 → 恶意驱动顶上 → 重新注册回调”的攻防接力游戏。而回调例程执行时运行在受扰动的异步上下文里（可能在任意线程、任意 IRQL），任何越界访问都会引发系统崩溃——**回调代码本质上是内核里另一块攻击者希望 echo 的入口**。因此在分析内核样本时，应当沿 `ObRegisterCallbacks` 的下游（`ObpCreateHandleEx` 路径）用 `!drvobj`、`bp ObRegisterCallbacks` 反向定位那些“只注册了进程回调却没有任何文件操作”的驱动，这往往是隐藏注入器的指纹。

### 4.4 攻击脚本级实例：句柄提权 vs 句柄窃取

场景 A——**句柄提权（Handle PE）**：目标无法直接打开目标进程（DACL 拒绝），但攻击者拥有 `SeDebugPrivilege`。此时用 `NtOpenProcess` 请求 `PROCESS_ALL_ACCESS`，对象管理器在内部因特权打开访问检查的红字通过，最终拿到全权限句柄，进而 `WriteProcessMemory` 注入 Shellcode。经典路：`whoami /priv` 确认 → `OpenProcess(0x1FFFFF)` → `VirtualAllocEx + WriteProcessMemory + CreateRemoteThread`。

场景 B——**句柄继承/复制（Handle Hijacking）**：作用于“句柄已在目标进程、但无权限克隆”的场景。通过 `NtDuplicateObject`（跨进程复制句柄）拿到目标进程持有的诸如 `\Device\NamedPipe`、令牌句柄等，实现“借道”访问。防御：EDR 用 `ObRegisterCallbacks` 拦截两进程间的 duplicate。

场景 C——**对象目录操纵**：在 `\BaseNamedObjects` 前置目录对象并替换符号链接，即可把线程/进程地址海的 `LoadLibrary` 引导到攻击者 DLL，绕过“文件是否真实存在”的检查（DOS 名劫持）。这也是老牌提权/CVE（如 CVE-2010-0elf 系列、IPC 目录劫持）的根源。

### 4.5 检测侧：EDR/Rootkit 如何用对象管理器

- EDR：`ObRegisterCallbacks` 过滤上述操作；Hook `NtOpenProcess`/`NtDuplicateObject` 拉黑危险权限组合；监控句柄表中突然出现的高权限 `PROCESS_ALL_ACCESS` 打开事件；结合 `\GLOBAL??` 链接变化监控文件隐藏；
- Rootkit：把 `PspCidTable` 中目标进程项标记为 `HANDLE_ENTRY_OBJ` 空闲、在 `OBJECT_HEADER.Flags` 上置 `KeepAlive`，进程就无法被枚举；或直接摘除/异地化 `\ObjectTypes` 中的类型索引，从 `!object` 视野中消失；对 EDR 的 `ObRegisterCallbacks` 则用 inline patch/清回调表反制。

## 5. 常见坑与避坑指南

1. **误把句柄当指针**：`HANDLE` 不是指向对象的内存地址，句柄值 = 表项索引 << 2 | flags。写内核代码用 `ObReferenceObjectByHandle`，不要拿句柄强制转 `POBJECT`。
2. **忽略句柄粒度（粒度=4）**：句柄低 2 位是属性位，直接 `+1` 操作句柄会错位。枚举时务必 `>> 2` 得到行号；检查继承/防关闭用位运算 `(handle & 0x3)`。
3. **句柄泄漏是致命的**:每次 `NtOpenProcess`/`CreateFile` 都要配对 `CloseHandle`/`NtClose`，否则句柄计数指向峰值后 `STATUS_NO_MORE_HANDLES`，进程崩溃/DoS。用 `process explorer` 或 `Get-Process.Handles` 做基线监控。
4. **Token 权限≠打开权限**：即便以管理员运行，有无 SeDebugPrivilege 决定能否打开 SYSTEM 进程；先 `whoami /priv`/`PrivilegeCheck` 确认，而不是直接失败。
5. **跨会话对象不可见**：`\BaseNamedObjects` 与 `\Sessions\<n>\BaseNamedObjects` 隔离；`CreateMutex(GLOBAL_)` 时若没有 SeCreateGlobalObjectPrivilege 会失败——这就是很多服务写成非全局锁、导致会话名冲突的 bug 根源。
6. **句柄复制/继承的坑**：`DuplicateHandle` 时 `DuplicateOptions` 不能带 `DUPLICATE_CLOSE_SOURCE` 又想保留源；继承句柄必须 `InheritHandle=TRUE` 且 `bInheritHandles=TRUE` 同时成立。
7. **句柄值复用与竞态**：`CloseHandle` 后句柄可能立刻被复用；并发使用同一句柄（尤其跨线程 close 与 op 交错）会操作到别的对象——这就是传说中的“句柄重复使用（Handle Reuse）漏洞”，必须用 `NtDuplicateObject`+生命周期锁或引用计数隔离。
8. **WinDbg 32/64 位差异**：`OBJECT_HEADER` 字段布局在 x86/x64 不同（`CreatorBackTraceIndex`、`InfoMask` 前插项），用 `dt nt!_OBJECT_HEADER` 现查，不要背死狗。
9. **PEPROCESS/对象体地址混淆**：`!process` 输出的 `ObjectTable` 是句柄表；`!object` 给的是 `OBJECT_BODY`。两者之间没有偏移关系，须分别处理。
10. **别在 `\GLOBAL??` 手改链接**：用户态改名盘符/符号链接会带来隐蔽性，但破坏 DACL 后会导致整个 Win32 子系统功能异常，是典型的“自断双手”坑。
