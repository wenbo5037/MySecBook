## 1. 概述

**字节序**（Endianness）是指多字节数据类型（如 `uint32_t`、`uint64_t`、`float` 等）在内存中各个字节的排列顺序。由于现代计算机普遍以**字节**为最小可寻址单元，一个 4 字节整数 `0x01020304` 在内存中至少存在两种排列方式。这个看似简单的存储选择，在跨平台通信、二进制协议解析、文件格式读取、安全逆向等场景中频繁制造隐蔽 Bug，甚至是可被利用的安全漏洞。

字节序问题的根源在于：**没有任何国际标准强制规定多字节整数必须按何种顺序存储**。不同 CPU 厂商在设计架构时做出了不同的选择，而 TCP/IP 协议栈则在 1980 年代通过 RFC 规范确立了统一的网络字节序（大端），从而催生了 `htons`/`htonl`/`ntohs`/`ntohl` 等一系列转换函数。

对于安全研究者而言，字节序是逆向工程、漏洞利用和协议分析的基本功——一个字节的顺序错误可能导致 shellcode 执行失败、PE 文件解析异常、DNS 响应被错误解读。

## 2. 核心原理

### 2.1 大端与小端的定义

**大端序（Big-Endian）**：数据的**高位字节**存放在内存的**低地址**端，**低位字节**存放在**高地址**端。这与人类从左到右阅读数字的习惯一致。

**小端序（Little-Endian）**：数据的**低位字节**存放在内存的**低地址**端，**高位字节**存放在**高地址**端。这在数值运算上更为高效，因为 CPU 加法器从最低位开始计算。

以 `uint32_t val = 0x01020304` 为例，假设变量存储在起始地址 `0x1000`：

```
地址:       0x1000  0x1001  0x1002  0x1003
大端序:      01      02      03      04     (符合人类直觉)
小端序:      04      03      02      01     (低位优先)
```

"Little-Endian" 一词源自乔纳森·斯威夫特的《格列佛游记》，书中小人国居民因"从大端还是小端打鸡蛋"而引发战争，Dan Cohen 在 1980 年的 RFC 中借用了这个典故。

### 2.2 为什么 x86 选择小端

Intel 8008/8080/8086 系列处理器从诞生起就采用小端序，主要历史原因包括：

1. **运算效率**：小端序使得多精度整数加法、乘法可以从最低位（最低地址）开始逐字节计算，无需预先知道数据的总字节数。CPU 的 ALU 在做加法时天然从低位开始进位，小端存储与这一硬件行为天然对齐。
2. **类型提升的便利**：在 C 语言中将 `uint8_t` 提升为 `uint16_t` 再提升为 `uint32_t` 时，小端序下所有类型共享相同的起始地址，强制类型转换可以直接进行，无需偏移调整。
3. **历史惯性**：x86 的巨大生态锁定使得这一选择延续至今，即使 AMD64 也保持了小端序。

值得注意的是，大端阵营的代表包括 Motorola 68000、SPARC、IBM PowerPC（可配置）、部分 MIPS 实例，以及所有主流网络协议。

### 2.3 双端序（Bi-Endian）

部分 CPU 架构支持在运行时切换字节序，称为**双端序**：

- **ARM**（ARMv7 及之前）：通过 CP15 协处理器的 `SCTLR` 寄存器 `E` 位切换；ARMv8 (AArch64) 同样支持 BE-8 和 LE-8 模式
- **MIPS**：在处理器复位时通过引脚或寄存器配置，内核编译时可选大端或小端
- **PowerPC**：通过 MSR 寄存器的 `ILE` 位切换
- **RISC-V**：rv32/rv64 原生支持大端和小端模式

双端序在嵌入式场景中尤为重要——同一个固件可能需要在不同字节序的设备间移植。

## 3. 详细知识点

### 3.1 大端与小端的内存布局详解

为了更直观地理解，我们用一个 64 位双精度浮点数 `double d = 3.14` 来展示。其 IEEE 754 表示为 `0x400921FB54442D18`：

```
地址递增 →
┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│ 0x2000 │ 0x2001 │ 0x2002 │ 0x2003 │ 0x2004 │ 0x2005 │ 0x2006 │ 0x2007 │
├────────┼────────┼────────┼────────┼────────┼────────┼────────┼────────┤
│ 大端: 40│ 09 21 │ FB 54 │ 44 2D │ 18                     │
│ 小端: 18│ 2D 44 │ 54 FB │ 21 09 │ 40                     │
└────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘
         ↑低地址                                       高地址↑
```

**大端序**下，`0x40`（最高有效字节）位于最低地址 `0x2000`，阅读顺序与十六进制书写顺序一致。**小端序**下，`0x18`（最低有效字节）位于最低地址，阅读时需要从高地址往低地址读才能还原数值。

### 3.2 字节序判定方法

#### 方法一：指针强制转换法（最常用）

利用 C 语言将 `uint32_t*` 强转为 `uint8_t*` 的行为——两种类型共享起始地址：

```c
#include <stdio.h>
#include <stdint.h>

const char* detect_endian(void) {
    uint32_t val = 0x01020304;
    uint8_t *p = (uint8_t*)&val;
    if (p[0] == 0x01) return "Big-Endian";
    if (p[0] == 0x04) return "Little-Endian";
    return "Unknown (PDP/Middle-Endian)";
}

int main(void) {
    printf("Machine endianness: %s\n", detect_endian());
    return 0;
}
```

> **原理**：地址 `&val` 同时也是 `&val` 的第一个字节。在大端下，第一个字节存储最高位 `0x01`；在小端下存储最低位 `0x04`。

#### 方法二：union 技巧

利用 union 的所有成员共享同一内存的特性：

```c
#include <stdio.h>
#include <stdint.h>

union endian_test {
    uint32_t i;
    uint8_t  c[4];
};

int main(void) {
    union endian_test ut;
    ut.i = 0x01020304;

    if (ut.c[0] == 0x01)
        printf("Big-Endian\n");
    else if (ut.c[0] == 0x04)
        printf("Little-Endian\n");
    else
        printf("PDP/Middle-Endian\n");

    return 0;
}
```

#### 方法三：联合体单字节读取（宏版本）

```c
#define IS_LITTLE_ENDIAN (*(unsigned short *)"\0\1" == 1)
// 或者更严格的写法
#define CHECK_ENDIAN() \
    (((union { unsigned int i; unsigned char c; }){ .i = 1 }).c == 1)
```

#### 方法四：编译器内建宏

现代主流编译器提供了检测字节序的预定义宏：

| 编译器 | 大端宏 | 小端宏 |
|--------|--------|--------|
| GCC/Clang | `__BYTE_ORDER__ == __ORDER_BIG_ENDIAN__` | `__BYTE_ORDER__ == __ORDER_LITTLE_ENDIAN__` |
| MSVC | 无直接宏 | `_M_IX86` / `_M_X64` 隐含小端 |
| `<endian.h>` (glibc) | `BYTE_ORDER == BIG_ENDIAN` | `BYTE_ORDER == LITTLE_ENDIAN` |

### 3.3 网络字节序（Network Byte Order）

**网络字节序（NBO）** 在 RFC 1700 中明确定义为**大端序（Big-Endian）**。这意味着所有 TCP/IP 协议头部的多字节字段（IP 地址、端口号、序列号等）都必须以大端序传输。

> **关键理解**：发送方主机的 CPU 字节序与网络字节序可能不同，因此发送前需要转换，接收后也需要转换。

**端口转换函数族**（`<arpa/inet.h>` 或 `<winsock2.h>`）：

```c
// htons = Host TO Network Short (16-bit)
uint16_t htons(uint16_t hostshort);

// htonl = Host TO Network Long (32-bit)
uint32_t htonl(uint32_t hostlong);

// ntohs = Network TO Host Short (16-bit)
uint16_t ntohs(uint16_t netshort);

// ntohl = Network TO Host Long (32-bit)
uint32_t ntohl(uint32_t netlong);
```

在**大端主机**上，这些函数通常为空宏（无需转换）。在**小端主机**上，编译器生成字节交换指令（x86 上通常是 `BSWAP` 或 `XCHG`）。

**64 位扩展**（POSIX 2008）：

```c
uint64_t htobe64(uint64_t host_64);  // host to big-endian 64
uint64_t htole64(uint64_t host_64);  // host to little-endian 64
uint64_t be64toh(uint64_t big_64);   // big-endian to host 64
uint64_t le64toh(uint64_t little_64); // little-endian to host 64
```

### 3.4 文件格式中的字节序

不同文件格式对字节序的约定差异巨大，这是安全解析二进制文件时必须关注的关键点：

| 文件格式 | 字节序约定 | 说明 |
|----------|-----------|------|
| **PE/COFF (Windows)** | **小端序** | DOS Header、PE Header 所有多字节字段均为小端 |
| **ELF (Linux)** | **小端为主** | `e_ident[EI_DATA] = 0x01` 表示小端，`0x02` 表示大端 |
| **PNG** | **大端序** | IHDR、IDAT 等 chunk 的多字节字段均为大端 |
| **BMP** | **小端序** | BITMAPINFOHEADER 等所有字段为小端 |
| **GIF** | **小端序** | Logical Screen Descriptor 等字段为小端 |
| **TIFF** | **可变** | 通过魔数 `II`（小端）或 `MM`（大端）标记，文件自身包含字节序信息 |
| **Java .class** | **大端序** | JVM 规范规定 class 文件采用大端存储 |
| **WAV** | **小端序** | RIFF 格式采用小端 |

**验证 ELF 魔数的字节序标记**：

```
偏移  内容        含义
0x00  7F 45 4C 46  \x7F + "ELF" (ELF魔数)
0x04  01           EI_CLASS: ELFCLASS32 (32位)
0x05  01           EI_DATA:  ELFDATA2LSB (小端) ← 关键字段
                   0x01=小端, 0x02=大端
0x06  01           EI_VERSION: 当前版本
```

**PE 文件的 DOS 魔数**：

```
偏移  内容        含义
0x00  4D 5A       "MZ" (DOS签名)
0x3C  文件偏移    指向PE签名"PE\0\0"的32位偏移 (小端序存储)
```

在 `0x3C` 处读取 4 字节作为小端序 `uint32_t`，得到的值即为 PE Header 的文件偏移量。

### 3.5 各平台默认字节序对照

| 平台/架构 | 默认字节序 | 典型设备 |
|-----------|-----------|----------|
| x86 | **小端** | 桌面 PC、笔记本 |
| x86-64 (AMD64) | **小端** | 64 位 PC 服务器 |
| ARM (AArch32) | **可配置** | 路由器、IoT 设备 |
| AArch64 (ARMv8) | **小端** (默认) | iPhone、Android 手机 |
| MIPS | **可配置** | 路由器固件、嵌入式 |
| PowerPC | **可配置** | 游戏主机、旧 Mac |
| SPARC | **大端** | Oracle 服务器 |
| RISC-V | **可配置** | 新兴嵌入式 |
| IBM z/Architecture | **大端** | 大型机 |
| WebAssembly | **小端** | 浏览器 |
| Java (JVM) | **大端** | 跨平台字节码 |

> **安全提示**：嵌入式设备（ARM/MIPS/PowerPC）的固件逆向中，字节序必须根据目标架构正确识别，否则反汇编结果将完全错误。

### 3.6 bitfield 与字节序的交互

C 语言的 **bitfield** 布局由编译器和平台共同决定，这是字节序问题中最容易被忽视的角落：

```c
struct Flags {
    uint8_t a : 3;  // 3 bits
    uint8_t b : 5;  // 5 bits
};
```

在**小端序**（x86）上，`a` 占据字节的低 3 位（bit 0-2），`b` 占据高 5 位（bit 3-7）：

```
字节内容: [b7 b6 b5 b4 b3 | a2 a1 a0]
             ←── b (5 bits) ──→  ←a(3)→
```

在**大端序**（SPARC）上，bitfield 的布局方向取决于编译器实现，可能 `a` 占据高 3 位、`b` 占据低 5 位，也可能相反。

**关键风险**：跨平台传输包含 bitfield 的结构体时，即使两个平台字节序相同，bitfield 的排列也可能不同（因为 C 标准不保证 bitfield 的布局）。安全做法是使用位移操作替代 bitfield，或使用固定的位域序列化格式。

```c
// 不安全的跨平台方式
struct PackedFlags { uint8_t a : 3; uint8_t b : 5; };

// 安全的跨平台方式
uint8_t pack_flags(uint8_t a, uint8_t b) {
    return (a & 0x07) | ((b & 0x1F) << 3);
}
uint8_t unpack_a(uint8_t packed) { return packed & 0x07; }
uint8_t unpack_b(uint8_t packed) { return (packed >> 3) & 0x1F; }
```

```c
/* endian_demo.c
 * 编译: gcc -o endian_demo endian_demo.c -Wall -Wextra
 * 或:   cl endian_demo.c /W4   (MSVC)
 */
#include <stdio.h>
#include <stdint.h>
#include <string.h>

/* 方法1: 指针法 */
int check_endian_ptr(void) {
    uint32_t val = 0x01020304;
    uint8_t *p = (uint8_t *)&val;
    return p[0]; /* 大端返回1, 小端返回4 */
}

/* 方法2: union法 */
int check_endian_union(void) {
    union { uint32_t u; uint8_t c[4]; } u;
    u.u = 0x01020304;
    return u.c[0];
}

/* 打印多字节整数在内存中的字节布局 */
void dump_memory(const char *label, const void *ptr, size_t n) {
    const uint8_t *p = (const uint8_t *)ptr;
    printf("%s: ", label);
    for (size_t i = 0; i < n; i++) {
        printf("%02X ", p[i]);
    }
    printf("\n");
}

/* 手动实现 htons（不依赖系统函数） */
uint16_t my_htons(uint16_t x) {
    return (uint16_t)((x << 8) | (x >> 8));
}

uint32_t my_htonl(uint32_t x) {
    return ((x & 0xFF000000) >> 24) |
           ((x & 0x00FF0000) >>  8) |
           ((x & 0x0000FF00) <<  8) |
           ((x & 0x000000FF) << 24);
}

int main(void) {
    uint32_t val = 0x01020304;
    uint64_t big_val = 0x0102030405060708ULL;

    printf("=== Endianness Detection ===\n");
    printf("Ptr method:  %s (byte[0]=0x%02X)\n",
           check_endian_ptr() == 1 ? "Big" : "Little",
           check_endian_ptr());
    printf("Union method: %s (byte[0]=0x%02X)\n",
           check_endian_union() == 1 ? "Big" : "Little",
           check_endian_union());

    printf("\n=== Memory Layout of 0x01020304 ===\n");
    dump_memory("uint32_t", &val, sizeof(val));

    printf("\n=== Memory Layout of 0x0102030405060708 ===\n");
    dump_memory("uint64_t", &big_val, sizeof(big_val));

    printf("\n=== htons/htonl Demo ===\n");
    uint16_t port = 8080;
    printf("Host port 8080 -> NBO: 0x%04X\n", my_htons(port));
    printf("Host 0x01020304 -> NBO: 0x%08X\n", my_htonl(0x01020304));

    return 0;
}
```

### 4.4 常见编译/运行报错表

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| `implicit declaration of function 'htons'` | 未包含头文件 | 添加 `#include <arpa/inet.h>`（Linux）或 `#include <winsock2.h>`（Windows） |
| `htons` 返回值与预期相反 | 在大端系统上本身就是恒等函数 | 理解：大端系统上 `htons` 不改变值，因为网络序本身就是大端 |
| `warning: dereferencing 'void *' pointer` | 对 `void*` 做指针运算 | 显式转为 `uint8_t*` 后再索引 |
| 跨平台文件解析乱码 | 发送端/接收端未统一字节序转换 | 使用 `htonl`/`ntohl` 系列函数做双向转换 |
| ARM 固件反汇编结果异常 | 未识别目标固件为大端序 | 用 `file` 命令或 ELF 头 `EI_DATA` 字段确认 |
| bitfield 布局在不同编译器下不同 | C 标准未定义 bitfield 布局 | 避免 bitfield 传输，使用位移 + 掩码操作 |

### 4.5 用 Python 辅助验证字节序

```python
import struct, sys

val = 0x01020304

# 查看本机字节序
print(f"本机字节序: {'大端' if sys.byteorder == 'big' else '小端'}")

# 小端打包 (主机序在 x86 上)
le_bytes = struct.pack('<I', val)
print(f"小端打包: {le_bytes.hex()}")  # 04030201

# 大端打包 (网络序)
be_bytes = struct.pack('>I', val)
print(f"大端打包: {be_bytes.hex()}")  # 01020304

# 模拟网络序解包
ntoh_val = struct.unpack('>I', be_bytes)[0]
print(f"大端解包还原: 0x{ntoh_val:08X}")  # 0x01020304
```

## 5. 常见坑与避坑指南

### 坑1：memcpy 逐字节比较时字节序陷阱

```c
/* 危险：依赖特定字节序的比较 */
uint32_t expected = 0xdeadbeef;
uint8_t buf[4];
memcpy(buf, &expected, 4);

/* 错误假设 buf[0] == 0xde —— 小端系统上 buf[0] == 0xef! */
if (buf[0] != 0xDE) {
    printf("Signature mismatch!\n");  // 小端系统上必定触发
}
```

**避坑**：按具体字节位置比较时，先明确目标字节序，或者使用 `memcmp` 比较整体值后再做字节序转换。

### 坑2：跨端二进制文件解析错误

```c
/* 错误：直接将缓冲区指针强转为多字节类型 */
uint8_t packet[1024];
uint32_t *field = (uint32_t *)(packet + offset);
uint32_t value = *field;  /* 在非原生字节序下值完全错误 */
```

**避坑**：

```c
/* 正确：显式按字节序解析 */
uint32_t value;
memcpy(&value, packet + offset, sizeof(value));
value = ntohl(value);  /* 从网络大端序转为主机序 */
```

### 坑3：Shellcode 字节序问题

Shellcode 中构造立即数时，`mov eax, 0x01020304` 在内存中的编码为 `B8 04 03 02 01`（x86 小端）。如果在大端架构上执行或用于跨架构 payload，字节顺序必须调整：

```nasm
; x86 (小端) - 正确
mov eax, 0x01020304    ; 编码: B8 04 03 02 01

; 如果手动构造 shellcode 字节数组:
char shellcode[] = "\xb8\x04\x03\x02\x01";  /* 小端序! */
```

在 MIPS（大端模式）上，同样的立即数编码为 `3C 01 01 02` + `34 21 03 04`，字节序完全不同。

### 坑4：DNS/协议字段解析错误

DNS 响应中的 A 记录 IP 地址以**网络字节序（大端）**传输。以下代码常见于错误实现：

```c
/* 错误实现：未做字节序转换 */
struct dns_a_record {
    uint32_t ip;   /* 网络序，大端 */
};
uint32_t ip = record->ip;  /* 直接使用 → 在小端系统上 IP 被倒序 */
/* 例如 192.168.1.1 = 0xC0A80101
   网络序内存: C0 A8 01 01
   小端系统直接读为: 0x0101A8C0 → 显示为 1.1.168.192 → 完全错误! */
```

**避坑**：

```c
uint32_t ip = ntohl(record->ip);  /* 正确：先转为主机序 */
printf("%d.%d.%d.%d\n",
       (ip >> 24) & 0xFF,
       (ip >> 16) & 0xFF,
       (ip >>  8) & 0xFF,
        ip        & 0xFF);
```

### 坑5：使用位移替代指针强转

```c
/* 危险：依赖对齐和字节序 */
uint8_t buf[4] = {0xDE, 0xAD, 0xBE, 0xEF};
uint32_t val = *(uint32_t *)buf;  /* 可能违反对齐要求! UB! */

/* 安全：显式按字节组装 */
uint32_t val = ((uint32_t)buf[0] << 24) |
               ((uint32_t)buf[1] << 16) |
               ((uint32_t)buf[2] <<  8) |
               ((uint32_t)buf[3]);
/* 这段代码假设 buf 是大端序网络数据，组装为主机序整数 */
```
