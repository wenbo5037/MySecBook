## 1. 概述

### 1.1 技术定义

**TLS（Transport Layer Security，传输层安全）**为TCP之上的应用（HTTP、SMTP等）提供三重保障：
1. **机密性（Confidentiality）**：数据对称加密
2. **完整性（Integrity）**：MAC/HMAC认证
3. **身份认证（Authentication）**：证书链验证服务器/客户端身份

TLS协议分为**握手层**（协商密钥与参数）与**记录层**（用协商的密钥加密/认证应用数据）。

### 1.2 知识体系定位

TLS是安全传输的基础设施，位于应用层与传输层之间：

```
HTTP / SMTP / FTP |  (应用层)
------------------
TLS (握手+记录层)
------------------
TCP               |  (传输层)
```

几乎所有Web安全（HTTPS）、API安全、证书管理（PKI、CSR、根证书）、以及QUIC中内嵌TLS1.3（见 [[14-HTTP2多路复用与HTTP3核心变化]] 与 [[11-UDP特性与QUIC协议设计动机]]）都依赖TLS。

### 1.3 核心应用场景

- HTTPS（443）——绝大多数Web流量
- 邮件SMTPS/IMAPS/POPS、TLS-DH SIP、LDAPS
- VPN（OpenVPN/WireGuard第三方自己在UDP上实现）
- 内部API网关mTLS（双向认证）
- 证书验证、CT日志、OCSP、私钥管理

### 1.4 技术演进简史

| 时间 | 里程碑 | 说明 |
|------|--------|------|
| 1994 | SSL 2.0 | 早期Netscape（有严重缺陷） |
| 1996 | SSL 3.0 | 吸收POODLE教训前的原型 |
| 1999 | TLS 1.0 (RFC 2246) | HMAC与PRF改进 |
| 2006 | TLS 1.1 (RFC 4346) | IV与填充防护（BEAST后修补） |
| 2008 | TLS 1.2 (RFC 5246) | 明确分块完整性方式、移除有缺陷套件 |
| 2012 | BEAST/POODLE等攻击系统化 | 老版本被不断批评 |
| 2018 | TLS 1.3 (RFC 8446) | 大幅简化握手、移除RSA密钥传输与弱算法 |
| 2020+ | TLS证书透明度(CT)、OCSP Stapling普及 | 生态成熟 |

## 2. 核心原理

### 2.1 TLS 1.2 完整握手（1-RTT 建立密钥，实际2-RTT应用数据）

TLS 1.2 完整握手（没有会话恢复）流程：

```
客户端                                          服务器
  |--- 1. ClientHello (支持的套件/扩展) ---------->|
  |<-- 2. ServerHello (选套件/随机数) -------------|
  |<-- 3. Certificate (服务器证书链) --------------|
  |<-- 4. ServerKeyExchange (ECDHE参数/密钥交换) ---|
  |<-- 5. CertificateRequest (可选,双向认证) -------|
  |<-- 6. ServerHelloDone ------------------------>|
  |--- 7. ClientKeyExchange (ECDHE客户端参数) ----->|
  |--- 8. CertificateVerify (可选mTLS签名) -------->|
  |--- 9. ChangeCipherSpec (切加密) -------------->|
  |--- 10. Finished (握手MAC) -------------------->|
  |<-- 11. ChangeCipherSpec ----------------------|
  |<-- 12. Finished -------------------------------|
  |=== 握手完成, 应用数据可用 ===|
```

- 1,2 协商参数
- 3-6 服务器身份认证 + 密钥交换参数
- 7-9 客户端密钥贡献 + 完成
- Finished 用握手密钥对全部握手消息计算MAC，保证握手消息完整性

### 2.2 TLS 1.3 握手（1-RTT）

TLS 1.3 显著简化（RFC 8446）：

```
客户端                                 服务器
  |-- 1. ClientHello (键共享在扩展中) ------>|
  |<-- 2. ServerHello (选套件) -------------|
  |<-- 3. {EncryptedExtensions}             |   ← 服务端应用数据(证书等)加密
  |<-- 4. {Certificate, CertificateVerify}  |
  |<-- 5. {Finished}                        |
  |--- 6. {Finished} ----------------------->|
  |=== 1-RTT 后应用数据可在双方发送 ===|
```

关键改进：
- **精简到1-RTT**：证书、证书验证、Finished合并到服务端1个飞行（flight）中，简化往返
- **删除RSA密钥传输**：只用ECDHE（或PSK），前向保密成为默认
- **删除弱套件**：移除RC4、CBC/<1.2、静态RSA/DH
- **无RA/无静态DH**：减少可被攻击的面
- **0-RTT（Early Data）**：见下文

### 2.3 0-RTT 与重放风险

0-RTT只适用于PSK（会话恢复/预先共享密钥）场景。客户端在首个ClientHello中直接发送Early Data（加密应用数据），服务器用PSK密钥解密：

```
Client                                  Server
  |-- 0-RTT 请求(Early Data, 用PSK) ----->|
  |<-- ServerHello + 结果 -----------------|
  |=== 0-RTT: 应用数据在首个飞行即发送 ===|
```

**重放风险**：由于服务器没有在Early Data中注入服务器随机数，0-RTT数据可被恶意重放（攻击者截获后重放给服务器）。RFC 8446 明确要求：
- 开发者必须确保0-RTT请求**幂等**（如实GET，不可用于敏感写操作）
- 服务器应限制Early Data的重放范围（如Anti-Replay窗口、限制0-RTT数据量）

### 2.4 密码套件命名对比

**TLS 1.2 套件命名**（详细）：
```
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
│      │      │        │         │
│      │      │        │         └── PRF哈希 (SHA384)
│      │      │        └── 对称加密(密钥交换时用的会话加密)
│      │      └── 密钥交换用证书类型 (RSA签名认证)
│      └── 密钥交换算法 (Elliptic Curve Diffie-Hellman Ephemeral)
└── 协议前缀
```

**TLS 1.3 套件命名**（简化）：
```
TLS_AES_256_GCM_SHA384
│      │         │
│      │         └── 哈希 (HKDF/PRF)
│      └── 对称加密 (AEAD)
└── TLS 1.3 专用, 不再区分密钥交换(都是(EC)DHE或PSK)
```

TLS 1.3 的套件由IETF指定，只保留 AEAD 密码 + 哈希，密钥交换算法不再出现在套件名中（由握手keyshare扩展决定）。

### 2.5 证书链验证

服务器证书由CA签名，验证需自下而上构建信任链：

```
客户端信任根CA (预置公钥) 
        │ 验证子CA证书的签名
        ▼
中间CA证书 (由根CA签发)
        │ 验证叶证书签名
        ▼
服务器证书 (叶, 含公钥/域名SAN)
        │ 验证域名匹配 + 有效期 + 证书用途
        ▼
TLS可用(服务器身份已验证)
```

验证步骤：
1. 证书链：叶→中间→根，逐级签名验证（从信任锚自上而下）
2. 域名匹配：SAN（subjectAltName）中的 dNSName 必须匹配访问的hostname
3. 有效期：notBefore/notAfter
4. 吊销：OCSP（Online Certificate Status Protocol）/ CRL 检查
5. （可选扩展）CT（Certificate Transparency）：服务器证书应有SCT（Signed Certificate Timestamp）日志凭证

**证书链验证失败的常见利用**：自签名证书被当有效、中间证书缺失、域名不匹配（如泛域名/内部IP）、吊销检查被绕过。中间人可借机伪造。

### 2.6 OCSP Stapling 与 CT 日志

- **OCSP Stapling（RFC 6066/6961）**：服务器自己向OCSP响应服务器获取"证书未吊销"的签名证明，然后随TLS握手一并发给客户端（staple），避免客户端每次额外请求OCSP响应服务器（减少延迟、防隐私泄露）。客户端验证staple签名。
- **Certificate Transparency（CT）**：所有公网CA颁发的证书必须提交给独立透明日志服务器，返回SCT（签名时间戳）。浏览器在TLS握手时检查证书是否携带SCT（Chrome强制），这是对CA违规/伪造证书的遏制措施。

## 3. 详细知识点

### 3.1 ClientHello 与 ServerHello 详细字段

**ClientHello**（明文发送）核心字段：

```
ClientHello:
  - version (最高支持的, 如 0x0303 = TLS1.2)
  - random (32字节随机数, 客户端随机)
  - session_id (会话恢复用)
  - cipher_suites: [TLS_AES_256_GCM_SHA384, TLS_AES_128_GCM_SHA256, ...]
  - compression_methods: [null]
  - extensions:
      - supported_groups (椭圆曲线, e.g. x25519, secp256r1)
      - key_share (客户端ECDHE公钥)
      - signature_algorithms (RSA-PSS, ECDSA)
      - SNI (server_name)
      - ALPN (应用协议: ["h2","http/1.1"])
      - supported_versions (TLS1.3/1.2)
      - ec_point_formats, padding, ... 
```

**ServerHello**：
```
  - version
  - random（服务器随机）
  - selected_cipher_suite
  - 无压缩 (1.3)
  - extensions: key_share(服务器公钥), supported_versions=TLS1.3, ALPN选中值
```

**安全观察**：ClientHello 明文携带 SNI（域名）与ALPN，监控/中间件可看到目标域名（SNI泄露）。ECDHE密钥交换在key_share中携带，保证前向保密。

### 3.2 密钥派生与HKDF（以TLS1.3为例）

TLS 1.3 密钥导出采用 **HKDF（HMAC-based Key Derivation Function, RFC 5869）**，经过 `Extract`（用ECSMS输出与ISKDF（IKM）派生主秘密）与 `Expand` 多级派生：

```
ECDHE共享秘密 (pre_shared_key_out = 服务器/客户端ECDH)
      │
      ▼
Early Secret (通过HKDF-Extract S=0*32, IKM=PSK/ECDHE)
      │
      ▼ (经过若干个HKDF-LabeledExpand)
Handshake Secret
      │
      ▼
Master Secret
      │
      ├─ 应用读取密钥 (client/server application traffic secret)
      ├─ 会话导出密钥
      └─ resumption secret (会话恢复PSK)
```

分级派生确保前向保密：早期/握手级秘密与后续应用秘密隔离，泄露早期不会危及已交付数据。

### 3.3 ECDHE 与 前向保密（Forward Secrecy）

**前向保密**：即使服务器/客户端长期私钥（如证书私钥）日后泄露，过去的会话（用ECDHE临时密钥）依然不可解。因为每次会话都用**临时（ephemeral）ECDH密钥对**，不落盘。

```
每次完整握手:
  生成临时 ECDH 密钥对 (客户端+服务器各一)
  用长期私钥(证书)签名临时公钥(CertificateVerify/ServerKeyExchange签名)
  推出会话主秘密
  断开后临时私钥销毁
→ 长期密钥泄露不影响旧会话
```

对比RSA密钥传输（TLS1.2静态RSA套件，无前向保密）：用证书公钥加密预主密钥，若长期私钥泄露则可解密所有历史会话——这正是DROWN/ROBOT的背景，因此TLS1.3默认强制(EC)DHE/PSK。

### 3.4 BEAST、POODLE、DROWN、ROBOT 攻击回顾

| 攻击 | 针对协议 | 原理 | 影响/修复 |
|------|----------|------|-----------|
| BEAST (2011) | TLS1.0 CBC | 对CBC模式IV可预测性预测明文 | 修复：RC4替代(被否)、1.1+随机IV、1.0禁用 |
| POODLE (2014) | SSL 3.0 CBC填充 | 利用填充字节校验缺陷逐字节泄露后块 | 禁用SSL3.0、强制TLS1.2+ |
| DROWN (2016) | SSL 2.0 | 降级到SSL2并用RSA密钥传输导出历史会话 | 禁用SSL2、禁用RSA密钥传输(ECDHE) |
| ROBOT (2017) | TLS1.2 RSA密钥传输 | Bleichenbacher padding oracle (Bald)反弹侧信道 | 禁用RSA密钥传输、ECDHE优先 |

共同主题：**降级到弱协议+旧算法是主要风险**；TLS1.3通过移除RSA密钥传输、弱对称算法，系统性消除这些。

### 3.5 证书Pinning与绕过

**证书固定（Certificate Pinning）**：客户端预先固定某证书/公钥/PIN哈希，验证时不再动态信任CA链，降低CA被攻破风险。

**价值与问题**：
- 防止中间人（CA被攻破/伪造证书时依然有效）
- 但移动App若硬编码过期/轮换证书会"锁死"服务；运营麻烦
- 攻击者破解App（静态逆向）可取出pin并绕过（dump certpin → 伪造中间人）
- 因此现在推荐"多后端pinning"（pin CA而非叶证书、poly-pinning）与动态更新

**绕过方式**（安全审计视角）：
- Frida/objection hook验证函数返回true（`SSL_CTX_set_verify`/`ok_override`）
- 替换系统CA，导入自签中间CA，覆盖信任链（Android emulator `adb`安装用户CA + 关闭pinning）
- Android 7+ 默认不信任用户CA，需在`res/xml/network_security_config.xml` 开放

```xml
<!-- Android network_security_config.xml -->
<network-security-config>
  <base-config cleartextTrafficPermitted="false">
    <trust-anchors>
      <certificates src="user"/>     <!-- 信任用户安装CA→用于测试代理 -->
      <certificates src="system"/>
    </trust-anchors>
  </base-config>
</network-security-config>
```

## 4. 实战与示例

### 4.1 环境准备

```bash
sudo apt install -y openssl python3-pip curl
pip install pyOpenSSL
# 或下载靶场（自签CA/本地Nginx + mTLS）
```

本地用openssl生成CA与服务器证书，搭建https服务器：

```bash
# 生成自签CA
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout ca.key -out ca.crt -subj "/CN=MyTestCA"
# 生成服务器私钥+CSR
openssl req -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj "/CN=localhost"
# 用CA签服务器证书(带SAN)
cat > ext.cnf <<'EOF'
subjectAltName=DNS:localhost,IP:127.0.0.1
basicConstraints=CA:FALSE
keyUsage=digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
EOF
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out server.crt -days 365 -extfile ext.cnf
```

## 5. 常见坑与避坑指南

1. **证书链不完整**：只给服务器端证书而缺中间CA，导致客户端无法构建到根CA的链。部署时必须把**叶子+中间**合入server.crt。

2. **SAN不匹配**：只配CN不配SAN，现代浏览器仅看SAN。生成证书务必填 `subjectAltName`；内部IP要加 `IP:192.168.x.x`。

3. **保留旧TLS/旧套件**：为兼容遗留设备保留TLS1.0/1.1或RC4、CBC静态RSA，等于敞开BEAST/POODLE/DROWN入口。强制TLS1.2+、仅ECDHE/ECDSA、AEAD套件。

4. **安全坑：0-RTT未做幂等**：Early Data允许非幂等写操作会引入重放攻击。确保0-RTT只用于幂等GET/查询，或在服务器端做Anti-Replay。

5. **忽略OCSP Stapling与CT**：不启staple让客户端每次额外查OCSP泄漏隐私+增加延迟；不嵌SCT会使Chrome/浏览器拒绝证书。部署时确认两者可用。

6. **证书Pinning硬编码一刀切**：pin叶证书到浏览器/App内，轮换/备份密钥时全平台锁死；应pin到中间CA或双层对齐（backup PIN），并做模板化更新。

7. **抓包解TLS失败**：只有导出keylog并确保握手使用导出套件才能解密；TLS1.3需在ServerHello后密钥已参与。确认`SSLKEYLOGFILE`版本与tshark/Wireshark兼容。
