# 08-001 云计算基础与共享责任模型

## 基础信息
- 难度：入门
- 前置知识：无
- 对应语言等级：入门级

## 核心原理

云计算把 IT 资源（计算、存储、网络、数据库、AI 能力）以服务形态按需提供，三大服务模型是 **IaaS（基础设施即服务，如虚拟机/存储）**、**PaaS（平台即服务，如数据库托管/容器平台）**、**SaaS（软件即服务，如邮箱/办公套件）**。安全上最重要的认知是**共享责任模型（Shared Responsibility Model）**：云厂商负责「云的安全」（物理设施、虚拟化层、托管服务的基础组件），用户负责「云中的安全」（配置、数据、访问控制、应用层），且责任边界随服务模型变化——IaaS 用户责任最大，SaaS 用户责任最小。

主要云厂商对共享责任模型各有官方文档：AWS Shared Responsibility Model、Azure Security 责任矩阵、Google Cloud 共享责任，三者核心一致：无论哪个模型，**数据的主权与最终责任都在用户**，这一点无法委托给厂商。

## 技术要点

- **基础概念**：虚拟化（Hypervisor 隔离）、计算（虚拟机 VM / 容器 / Serverless）、存储（对象存储 Object Storage / 块存储）、网络（VPC 虚拟私有云、安全组 Security Group、防火墙规则）。
- **责任边界示例**（以 IaaS 虚拟机为例）：云厂商负责物理机、Hypervisor、网络基础设施；用户负责实例 OS 补丁、SSH 密钥、应用、数据加密、VPC 内网划分与安全组规则。
- **身份与访问管理（IAM）**：用户/角色/策略、最小权限原则、多因素认证（MFA）、临时凭据（STS）、服务账号与密钥轮换——IAMA 错误配置（过宽策略、暴露密钥）是云上事件第一成因。
- **云上常见风险**：存储桶/对象存储权限公开读写、密钥/环境变量泄露进代码仓库、配置漂移（未被 IaC 管理的资源）、日志与审计缺失、第三方 API 权限过宽。
- **基础合规**：加密（静态与传输）、日志留存（审计）、基线（CIS Benchmark for 各云平台/实例）。

## 实践示例

环境：AWS CLI 2.x（开源免费账号即可）、本地 Linux/WSL。

只读自查账户下对象存储的公开读写配置（安全审核场景，仅读不修改）：

```bash
# 检查所有 S3 桶的授权策略是否允许公开读/写
aws s3api list-buckets --query 'Buckets[*].Name' --output text | \
while read bucket; do
  echo "== $bucket ==";
  aws s3api get-bucket-acl --bucket "$bucket" \
      --query 'Grants[?Grantee.Type==`Group` && Grantee.URI!=null].Grantee.URI' --output text;
done
```

输出中出现 `AllUsers` 即代表存在公开访问风险，应立即在本账户完善策略（仅演示命令用法，勿对他人账户执行）。

IAM 最小权限自查（查看用户是否有 `AdministratorAccess` 管理策略）：

```bash
aws iam list-attached-user-policies --user-name demo-user \
  --query 'AttachedPolicies[*].PolicyName' --output text
```

## 常见问题与误区

- 误区一：以为云厂商「包办安全」。共享责任模型里用户侧配置错误占重大事件八成以上，安全组开 0.0.0.0/0、桶公开可写等仍是高频事故。
- 误区二：把权限给「服务账号」却不可控。长期密钥、全局管理权限、未轮换凭据是云上爆炸半径扩大的主因；优先用临时凭据与 IAM Role。
- 误区三：忽略配置审计。资源由控制台手工创建、缺少 Infrastructure as Code（IaC）与基线扫描（如 `aws config`、CIS 检查），配置漂移会无限放大责任面。
